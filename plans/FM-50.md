# FM-50: Create Order: Order Table

https://openlmis.atlassian.net/browse/FM-50 · Parent: [FM-39] Requisitions · Subtasks [FM-59]
(tabs), [FM-60] (picker, table, Delete Batch), [FM-61] (Save Draft, Create Order, summary)

Shipped in one PR with [FM-49] (pick facility, [plan](FM-49.md)), branch
`feat/fm-49-50-create-order`.

## Scope

- New order table at `/requisitions/create-orders/$orderIds` (comma-separated ids, as legacy's
  `orderCreate/<id>,<id>`), opened by [FM-49] or by link with existing draft order ids.
- One tab per draft order (requesting facility), each with its header, Delete Order, product picker,
  Packs/Doses toggle and lines; Delete Batch, Save Draft and Create Order with the summary dialog.
- Not in scope: offline save and create (legacy queues them locally; orders are not in the offline
  pass); the read-only view and its Angola print report; a drafts list (legacy reopens drafts from
  View Orders, not yet migrated, whose Edit link will point here).

## Summary

After choosing facilities on the first screen, the planner fills one order per facility: they
search for products, add them, type quantities and either save the drafts to come back later or
create the orders, after checking a summary. In legacy each draft is already a real order on the
server, with status Creating; Save Draft updates it and Create Order sends it to the warehouse.
Legacy takes up to 40 seconds to open a tab because it downloads every product and stock record
of the facility before showing anything.

The new screen keeps the same drafts on the server and the same steps, but opens at once: product
search asks the server for matching products as the planner types, and stock on hand is read only
for the products in the order. It also warns before leaving with unsaved edits, marks tabs with
unsaved edits as well as invalid ones, shows the server's reason when something fails, and works
on phones.

## Legacy Today

Walked on test.openlmis.org as administrator with every write stubbed; findings, logs and
screenshots in `.screenshots/FM-50/` (`legacy-order-table-*`, `legacy-order-summary-modal-1440.png`,
`legacy-order-batch-delete-confirm-1440.png`). Source:
`openlmis-requisition-ui/src/requisition-order-create/` (`order-create-table.jsx`,
`order-create-tab.jsx`, `order-create-summary-modal.jsx`, helpers), shared
`openlmis-ui-components` tab navigation and quantity unit input.

- Route `#!/requisitions/orderCreate/<id>,<id>` (breadcrumb "Edit"), `ORDER_CREATE`. Loads each
  order (`GET orders/{id}`), then for the active tab every v2 stock card summary of the requesting
  facility and program, unpaged, plus every orderable and lot by id, behind a "Loading..." modal:
  32 s and about 12 MB for Essential Meds at Comfort Health Clinic, 3 s for Family Planning. A user
  without stock rights at the facility gets an empty product list.
- Tabs: facility name, a red dot when the order is invalid (no lines, or an empty or zero
  quantity), and a × for Creating orders: "Are you sure you want to delete this order?" (Delete /
  Cancel), deletes it, toasts "Order(s) deleted successfully." and returns to the first tab.
- Header: Status (raw "CREATING"), Date Created, Program, Requesting Facility, Supplying Facility.
- Picker "Select an option" listing every product on open, filtered by name; Add disabled for a
  product already added ("This product was already added to the table"); Packs/Doses toggle;
  table Product Code, Product, Pack Size, Stock On Hand (requesting facility, in packs `N ( +R )` in
  Packs mode), Quantity (Packs mode `[packs] + [doses]`, the doses input disabled when the pack
  holds one dose; hint "Will be ordered as N pack(s) (M doses)" in both modes, hidden for one-dose
  packs or no quantity), trash; 6 rows a page.
- Save Draft (always enabled): validates (quantity required, not negative; one toast per error),
  `PUT` every order, toast "Orders saved successfully"; no error handling.
- Create Order: disabled until every tab has lines with quantities above 0; "Orders Summary"
  dialog with a tab per facility and a read-only table (Product Code, Product, Pack Size, Stock On
  Hand, Quantity with the hint, in the chosen unit), Cancel / "Create Orders"; sends each order,
  toast "Orders created successfully", back to the first screen; no error handling.
- Delete Batch: "Are you sure you want to delete available orders?" (Delete Batch / Cancel),
  deletes all, toast "Order(s) deleted successfully.", back to the first screen. Delete failures
  toast "Error occurred while deleting order(s)."
- No leave warning; reload refetches and drops unsaved edits. A user with only `ORDER_CREATE`
  gets 403 on the order reads and legacy spins forever.

## Agent Brief

### API Map

| Step | Method And Path | Params / Body | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Load each order | `GET orders/{id}` | | `id, status, createdDate, program, requestingFacility, supplyingFacility, receivingFacility, orderLineItems[].{id, orderedQuantity, orderable}` (orderables expanded) | ORDERS_VIEW/EDIT or SHIPMENTS_VIEW/EDIT at the supplier, or PODS_VIEW/MANAGE at the requesting facility and program | `order-create-table.jsx#L57-L68` |
| Product search | `GET facilities/{requestingId}/approvedProducts` (`approvedProductsOptions`) | `programId`, `orderableName`, `page`, `size` | `orderable.{id, productCode, fullProductName, dispensable, netContent, packRoundingThreshold, roundToZero, meta.versionNumber}` | none | legacy reads v2 summaries, built from the same approved products (Decisions) |
| Stock On Hand of lines | `GET v2/stockCardSummaries` | `programId, facilityId=<requesting>, orderableId` (repeated, `fetchIdBatches`) | `orderable.id, stockOnHand` | STOCK_CARDS_VIEW (refused: blank cells) | `table-helper#L1-L41`, which legacy also calls for saved lines |
| Save Draft | `PUT orders/{id}` per changed order | the loaded order with `orderLineItems: [{id?, orderable: {id, meta: {versionNumber}}, orderedQuantity}]` (doses) | 200 order (line ids, expanded orderables) | `ORDER_CREATE` at the receiving facility | `order-create-table.jsx#L104-L119` |
| Create | `PUT orders/{id}/requisitionLess/send` per order | same body | 200, no body | `ORDER_CREATE` | `#L86-L102` |
| Delete tab / batch | `DELETE orders` (axios `data: {ids}`) | body `{ids}` | 204; 404 `notFoundOrWrongStatus` names the ids and deletes nothing | `ORDER_CREATE` or ORDERS_DELETE | `order-create.service.js#L77-L88` |

The server updates only line items on both PUTs (it also needs `receivingFacility.id` and each
line's `orderable.meta.versionNumber`; the loaded order carries both), rejects duplicates, missing
and negative quantities, and refuses orders no longer Creating (400). Send converts doses to packs
and moves the order to Ordered in one transaction.

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.create-orders_.$orderIds.tsx`; the ids are
  in the path (deduped), so a different batch is a different pathname and `useDiscardGuard`
  protects unsaved edits; the active tab is search `tab?: orderId` (replace), which the guard rightly
  ignores. `crumbKey` (Edit) under Create Orders, `preload: false`. Loader awaits `requirePermissions`
  (`ORDER_CREATE`), starts `deploymentTimeZoneOptions`, then settles each order fresh
  (`fetchQuery`, `staleTime: 0` on `cause: 'enter'`, `Promise.allSettled`): every refused read gives
  an in-place message naming the rights that open orders; a missing or no-longer-Creating order
  gives that tab a message and a Remove From Batch action (drops the id from the URL); other
  failures go to the route error with retry. Batch reductions read cached orders synchronously.
- One TanStack form above the tabs holds every order's lines keyed by order id, so tab switches keep
  edits. Each order keeps its own baseline. Values are initialised once per order id: when our own
  writes drop ids from the path (sent or deleted orders), surviving orders keep their values and
  baselines. Each client line has a local key. Unsaved and invalid
  markers, Save and Create gating come from pure `order-draft.ts` checks over the live values,
  validating from the first change as the requisition editors do.
- Products: per active tab, the Receive editor's approved-products search copied: a server-paged
  combobox by name with `productSearchStatus`, first page on opening.
- Stock On Hand: `orderStockOnHandOptions({programId, facilityId, orderableIds})` under
  `queryKeys.stockCardSummaries`, for the tab's lines. Cache individual product balances for
  30 seconds and share in-flight product reads; adding lines requests only newly needed products,
  batched in groups of 100. It never blocks the editor: cells show a placeholder until it answers.
  A refused stock read leaves cells blank; other failures show a retryable error in both the editor
  and summary. The summary reuses these balances. The server still computes every
  stock card of the facility for this call (the product filter applies after the balances), so its
  cost on the large Essential Meds facility is measured in the browser check rather than assumed.
- Writes through `useSessionMutation` and `settleFew`, **one write action at a time**: while Save,
  Create, Delete Order or Delete Batch runs, the other write buttons are disabled (typing stays
  allowed during Save). Each action captures its payload once from the values at the start and
  works only from that snapshot.
  - Save Draft: changed orders only. Each success makes the submitted snapshot (not the live values)
    that order's baseline, so typing during the save stays unsaved. The response's line ids merge
    only into the same surviving client line (local key) whose product and version still match;
    a line removed or re-added meanwhile stays new. Failures keep their edits and markers, named in
    one AlertDialog with deduplicated server reasons.
  - Create: validate, open the summary, freeze the payload on confirm, then send every order. Each
    success leaves the batch (it is Ordered now). A failure rereads the order: Creating means not
    sent, with the server message; any other status or not found means it is no longer a draft
    here (sent or deleted elsewhere, or our lost response), shown as such without claiming our
    quantities were sent, and never sent again; a refused or failed reread leaves the tab blocked
    as "may have been sent, check View Orders". All sent: toast, back to [FM-49].
  - Recovery rereads rethrow `SessionEndedError` and check the captured session scope after every
    await, catches included, before touching the form or cache.
  - Delete Order (tab): confirm, delete, drop the id, back to the first tab, toast; last order gone:
    back to [FM-49].
  - Delete Batch: confirm and delete only readable Creating entries without a known problem.
    Keep problem tabs in the batch; when all remaining orders are deleted, return to [FM-49].
  - A delete 404 names orders no longer Creating and deletes nothing: reread them, mark those tabs,
    and show legacy's delete error in an AlertDialog with the reason.
- Navigations after deletes and Create replace history, so Back never reaches deleted ids.
  A one-use in-memory navigation token permits cached reads only during the immediate batch
  reduction, preserving surviving edits. Every entry still checks permission; a later re-entry
  reads fresh data even when history retains the token.
  `useDiscardGuard(dirty, { pending, allowLeave })`, with a leaving ref set just before those
  navigations, as the facility editor.

### Rules

- A product appears once per order: products already in the tab are disabled in the list with
  legacy's message.
- Save: every line in the changed orders has a whole quantity of 0 or more (server rules). Create:
  every tab has at least one line and every quantity is above 0 (legacy). Save Draft is disabled
  with nothing changed. Invalid Save or Create opens `InvalidSubmitDialog`, switches to the first
  invalid tab and focuses the field (`revealField` in cards), or the product picker for an empty order.
  Create stays enabled while idle so zero quantities and empty/problem tabs receive an explanation.
- Quantities are stored and sent in doses. Packs mode shows `[Packs] + [Doses]` (doses disabled
  when `netContent` is 1) and Stock On Hand in packs plus remainder (`cardQuantity`). The hint
  "Will be ordered as N pack(s) (M doses)" shows in both modes, hidden when `netContent` is 1 or the
  quantity is 0, with legacy's rounding: move `packsToShip` from requisitions to `src/lib/quantity.ts`
  with its tests, and use it in batch approval's `batchCost` too. Batch's null threshold differs
  (no round-up): keep each caller's legacy behaviour, pinned by the moved tests.
- Removing a line is instant; Delete Order and Delete Batch confirm (server deletes).

### Risks And Edge Cases

- Another user may send or delete a draft meanwhile: saves then fail with the server's status
  message and the tab shows the not-Creating message.
- Two people editing the same Creating draft overwrite each other's lines on save: the server keeps
  no revision to compare. Legacy behaves the same; a safe check needs a backend conditional write,
  so this stays a known limitation.
- A user with `ORDER_CREATE` at the supplier's side but not at a tab's facility sees the server's
  refusal on write; no pre-check (rare, and the server is authoritative).
- Very large orders: lines are not paged in legacy's 6-row way; the table shows every line, as the
  stock event editors, with cards on phones.

## UI/UX

**Port**: tabs per facility, the header box, picker and Add, the unit toggle, Stock On Hand in packs
and the packs hint, the line table, Save Draft, the summary, Delete Order and Delete Batch with
legacy's confirmations, buttons and toasts.

**Improve**: opens at once (server product search, stock read only for lines); products listed even
without stock rights (Stock On Hand blank); already-added products disabled in the list; a leave
warning for unsaved edits; an unsaved marker beside legacy's invalid marker; error messages on every
failed write and partial-failure handling; one invalid dialog that opens the right tab instead of a
toast per error; Status shown as "Creating"; a message for drafts no longer Creating or gone; no
endless spinner when order reads are refused; phone cards.

**Drop**: offline save and create; the read-only view and Angola print; legacy's 6-row pager
inside each tab; the × inside each tab (Delete Order moves into the tab, see Decisions).

Layout: `Workspace` (default width); header with title Create Orders and a description; `TabsList
size="lg" wrap="column"`, each trigger with the facility name, an alert icon when invalid and a dot
when unsaved (both with screen-reader text); in each tab the header box as label/value pairs with a
destructive Delete Order button beside it; the picker row with Add; toolbar with the unit toggle;
the line table (cards below 672px). Summary: `DialogContent size="2xl"` with one `DialogTable`,
a heading row per facility. Sticky `WorkspaceFooter`: Cancel (back to Create Orders, guarded) and
Delete Batch (`variant="destructive"`) at the start, Save Draft and Create Order at the end, all
`size="lg"`.

## Decisions

- **Drafts are saved on the server**, as legacy: each draft is a Creating order; Save Draft updates
  it; reopening uses the order ids in the address.
- **Products are searched on the server** (approved products of the requesting facility, by name)
  instead of downloading every stock summary: the same products, and what makes the screen fast.
  The list opens on its first page; typing finds the rest. Stock on hand still comes from the
  summaries, for the added lines only.
- **Batch changes keep surviving edits** through cached reads; adding new ids starts a new editor.
- **Tabs show both markers**: legacy's red marker means invalid; the ticket asks for unsaved. Save
  Draft clears the unsaved one.
- **Delete Order sits inside each tab**, not as a × on the tab: a button inside a tab list breaks
  keyboard navigation and screen readers.
- **Summary as one table with a heading per facility**, not tabs inside the dialog: everything that
  will be ordered is visible at once.
- **Save Draft writes only changed drafts** and is disabled with no changes; legacy rewrites all.
- **Create Order explains invalid tabs** with an AlertDialog and focuses the first correction,
  following the app's editor conventions. It remains disabled during writes.
- **Browser checks use real drafts on test.openlmis.org**: the user allowed creating items there;
  checks create drafts through the new screen and delete them afterwards.
- **A Cancel button** returns to Create Orders, the app's draft editor footer; legacy has none.
