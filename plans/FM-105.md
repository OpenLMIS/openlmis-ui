## Summary

After a forecast is prepared, the facility checks the yearly consumption the system calculated
for each product, enters the demand it expects, explains any difference with a remark, records
how the purchase will be funded, and sends the forecast on. An authorizer then checks it and
authorizes it for the district.

Legacy does this on one long grid. It downloads every product in the system before showing the
page (about 10 MB, several seconds), shows no message when a number is missing, keeps funding
entries in the browser in a way that can carry them to another forecast or another user, lets
Cancel discard work without asking, and on a phone the bottom bar covers the Submit button.

The new page keeps the same columns, values and totals, loads only the products in the forecast,
shows what is wrong on the field and on the page in the pager, keeps the funding entries with the
forecast's own draft, asks before discarding changes, and works on a phone. Actions appear only to
the people who may take them, and only in the statuses where they make sense.

## Legacy Today

- `#!/buq/create/{id}` from Forecast on the list; rights CREATE or AUTHORIZE (route), the grid
  itself checks status only (`FacilityDemandingForecasting.jsx:386-415,501-523`).
- Header "Facility Demanding Forecasting Form" and a details block: Region, Council, Facility Type,
  Facility Code, Facility Name, Quantification Period.
- Columns: MSD Item Code, Product, Unit of Measure, Annual adjusted consumption (read-only),
  Verified annual adjusted consumption, Forecasted demand (editable), MSD Sales Price, Total Cost
  (read-only), Remarks ("Select Remark"). Category rows sorted by name, products by name, 10
  products a page ("Showing 10 item(s) out of 12 total").
- Initial Verified = AAC, Forecasted = Verified; editing Verified copies it to Forecasted; Total Cost
  = Forecasted x price, `toFixed(2)`; the bar shows "Total Cost: 7 388.46 $" (sum of all lines).
- Remark picker enabled only when Verified differs from Forecasted (then red "!"), cleared when they
  match again. Inputs filter keys (no negatives, no decimals, no upper bound) and show no message.
- Paging keeps edits; reload loses them; Cancel leaves without asking.
- Bar: Draft and Rejected: Save, Submit, Cancel, Add Source of Fund (Rejected adds View reasons for
  rejection); Submitted: Save, Authorize, Cancel, Add Source of Fund, still fully editable. With
  `skipAuthorization`, one Submit & Authorize for every status. No button is ever disabled.
- Submit and Authorize confirm ("Are you sure you want to submit this forecasting?"), then check
  touched lines and that funding exists; failure: "The forecasting form has invalid line items.".
  Success toasts ("The form has been submitted successfully") and return to the list. Save
  ("The form has been saved successfully") stays and does not validate.
- Source of funds dialog "Funding Source For Health Commodities Procurement": every source (saved
  ones, or all from the API), Amount Used in Last Financial Year and Projected Fund in $, decimals
  up to 2, both required per row; footer Total Projected Fund, Total Forecasted Cost, Gap
  (projected minus total cost). Save only writes `localStorage` keys shared by every forecast and
  user (`openlmis.sourceOfFundForm`, `openlmis.sourceOfFundFinance`).
- Rejection Comments dialog: only the reasons chosen in the most recent rejection (category name
  `BUQ`) and General comments, read-only (`RejectionCommentsForm.jsx:64-99`).
- Calls on open: `GET /processingPeriods` (unused), `GET /bottomUpQuantifications/{id}`,
  `GET /processingPeriods/{id}`, `GET /remark`, `GET /orderables` (all 10233, 10.2 MB, 3.5-8 s).
- Phone: the total overlaps Submit and Cancel (not clickable); two buttons run off-screen.
- Price and category come from `orderable.programs[0]`; the BUQ program has no product entries on
  this instance, so every price is another program's.

### Data Flow

- Loader: `loadBuqAccess(queryClient, [create, authorize])`; non-ready access shows `BuqUnavailable`,
  as the list. Then the forecast read fresh (`fetchQuery` with `staleTime: 0` on `cause: 'enter'`,
  cached on `stay`, `preload: false`, AGENTS.md whole-record saves); a forecast of another facility
  or a missing one shows not found. Products, facility, program, remarks and periods are prefetched
  without awaiting.
- Breadcrumb: `staticData.crumbKey` (Home / BUQ / Create / Authorize Forecasting / Forecast).
- Return to the list: the Forecast link puts the list's search in history state
  (`buqListSearch`, declared in `lib/search.ts` with the repo's `biome-ignore` for interface
  merging, user decision); Cancel and a send go back to it.
- Rights per row and page: `buqAccess` also returns the granted rights (`granted`), so the list and
  the editor know CREATE and AUTHORIZE separately (`useForecastRights`), and `skipAuthorization`
  from the user's programs, with no extra request.
- Facility: `facilityOptions(forecast.facilityId)`, not the cached home record, whose offline fallback
  may lack the zone chain the details need. Period: from the BUQ schedule's periods, else
  `processingPeriodOptions(id)`.
- Keys: `buq.detail(id)`; lookups reuse `reference-data` (`orderablesByIdsOptions`,
  `facilityOptions`, `rejectionReasonsOptions`); remarks and sources of funds
  get `buq` keys and readers (Decisions). Writes invalidate `[...buq.all]`, so both lists refresh.
- Draft: one `useAppForm` with values keyed by line id (`verified`, `forecasted`, `remarkId`) and the
  funding rows keyed by source id; the grid renders the page slice. Dirty against the loaded values;
  `useDiscardGuard(dirty, { pending, allowLeave })`, as the order editor, so leaving after a send does
  not ask.
- Funding dialog: a `DialogTable` in a `2xl` dialog (cards below its width), its own small form
  opened from the page values; Save copies them into the page
  draft (not to the server) and closes; Cancel discards the dialog edits. The page's Save, Submit or
  Authorize sends them, as legacy.
- URL: `page`, `size` (local paging) and the open dialog (`?dialog=funding` / `rejection`) through
  `useSearchNavigation`.
- After Submit, Authorize or Submit & Authorize: toast and return to the list with its search from
  history state. After Save: stay, reload the fresh forecast, reset the draft to it.
- Writes through `useSessionMutation`; errors in an `InvalidSubmitDialog` with the server message.

### Server-Side Work

- Products: only the forecast's orderables by id (the shared 100-id batched reader) instead of all
  10233; the backend checks the same ids on save.
- Program by id instead of every program matched by name; the unused full period fetch dropped.
- Lines, totals and paging stay client-side: the forecast read returns every line and no endpoint
  computes the totals.

### Rules

- Initial: AAC = server ?? 0; Verified = server ?? AAC; Forecasted = server ?? Verified.
- Editing Verified sets Forecasted to the same value; Forecasted can then change on its own.
- Total Cost = Forecasted x price, two decimals; the total sums every line, not the page. Values are
  computed and sent with two decimals; only the display follows the currency settings.
- Remark required when Verified differs from Forecasted; cleared when they match.
- Verified and Forecasted required, whole numbers 0..2147483647 (Java `int`). Errors show live from
  the first change, as the requisition editors (Decisions). Save is refused while a number is blank
  or invalid (the server's save validates nothing and would store null); a missing remark does not
  block Save, as legacy.
- Funding rows: the forecast's saved entries if any, else every source; sources added after a save
  are not shown, as legacy (`BuqSourceOfFundAddForm.jsx:44-84`).
- Funding: before Submit or Authorize every source needs both amounts, zero for unused ones, as
  legacy (Decisions); Save keeps partial entries; decimals, two places, >= 0;
  Total Projected Fund = sum of Projected Fund; Gap = Total Projected Fund - Total Cost.
- Price and category: the BUQ program's entry in `orderable.programs`, else the first entry
  (Decisions; on the demo data the BUQ program has no product entries, so the result is legacy's).
  Categories by name, products by name, 10 products a page.
- Actions (`forecastActions`), rights exact at home for BUQ:
  - Without skip: CREATE on Draft and Rejected offers Save and Submit; AUTHORIZE on Submitted offers
    Save and Authorize.
  - With skip: CREATE on Draft, Rejected and Submitted offers Save and Submit & Authorize (one
    `POST /authorize`); AUTHORIZE alone is read-only (the server checks CREATE then).
  - Any other status or right: read-only, no actions. Rejection Reasons only with CREATE.
  - The Forecast row action shows exactly when `forecastActions` returns actions, as FM-104 recorded.
- Submit, Authorize and Submit & Authorize confirm first: they move the forecast on to others, as
  the requisition editors (AGENTS.md: confirm when a save affects other records); Save does not.
- Writes send the stored `facilityId` and `programId`, every line with its id, AAC unchanged, money
  rounded to two decimals; Submit and Authorize validate every line, not only touched ones.

### Risks And Edge Cases

- Backend bugs this page meets (vault): authorize accepted from any status (only offered from
  Submitted); home facility checked from the body (stored values always sent); a deleted remark or
  source makes the read 500 (shown as the page load error); multi-version products doubled by
  Prepare (shown as the server returns them).
- A line list missing lines deletes them on the server; money with more than two decimals is a 400.
- Funding values come from the forecast only, never from browser storage.
- `supervisoryNodeCannotBeNull` on authorize when the facility has no node: shown as the server
  message.
- Region is the first zone up the parent chain whose level code is `Region` (legacy
  `helpers.jsx:16-19`); when absent the field stays empty, never crash (legacy throws).

## UI/UX

**Port**: the details block, nine columns in order, categories, 10 products a page, Verified copied
to Forecasted, Remark only when they differ, the total, the funding dialog with its totals and Gap,
Rejection Reasons for a Rejected forecast (not an AC of its own, kept for legacy parity),
confirmations before Submit and Authorize.

**Improve**:
- Products by id: the page opens without downloading every product.
- A clear message on each invalid field (hover or focus, AGENTS.md editor tables), invalid rows
  tinted, pages with errors marked in the pager, and Submit checks every line, focusing the first
  invalid one.
- Funding entries kept with the forecast's draft; nothing in browser storage.
- Leaving with unsaved changes asks first; Cancel returns to the list with its filters.
- Actions only for the right and status; Submitted is editable only for an authorizer.
- Sticky footer (Cancel at the start; Save and Submit or Authorize at the end), the total beside
  them; cards below 672px, as requisition editing.
- Money in the deployment's currency format (`currencySettingsOptions`) instead of the build symbol,
  through a small BUQ formatter (Decisions).

**Drop**: the full product download; the unused period fetch; the shared funding storage; buttons
that act on statuses the server should refuse.

States: loading (real header, skeleton grid), not found, load error with retry, ready, saving,
sending, server refusal, read-only. RTL with logical classes; product names in `<bdi>`.

## Decisions

- **Branch from FM-104**, which is not merged.
- **Products by id** instead of every product.
- **Plain Authorize only from Submitted**, guarding the backend bug; Submit & Authorize from Draft,
  Rejected or Submitted, only when the program skips authorization.
- **Remarks and sources of funds lookups in `buq`**, not `reference-data` (user, FM-103: shared
  code stays unchanged); Manage BUQ (FM-161) can move them.
- **Money through a small BUQ formatter** (user, 2026-11-09) from the deployment currency settings;
  `formatCurrency` stays in `requisitions`, which is team code.
- **Validation live from the first change** (user, 2026-11-09), as the requisition editors and
  legacy; the pager marks pages with errors as they appear.
- **Funding as legacy** (user, 2026-11-09): both amounts for every source before Submit or
  Authorize, zero for unused ones; the backend does not check it.
- **Price and category from the BUQ program's entry, else the first** (user, 2026-11-09), so a
  deployment that prices products for BUQ gets its own prices.
