## Scope

- New batch approval page at `/requisitions/approve/batch?ids=<id>,<id>`, opened by the approval
  list's View Selected (replacing the hand-off to legacy from [FM-45]).
- Grid of products by requisitions with Approved Quantity and Cost per requisition, Total For All
  Facilities, a Total row, sticky headers and Code/Name, device autosave with a status indicator,
  Sync With Server, Revert and Approve, phone cards.
- FM-191 adds offline opening from complete saved batch copies with owner-scoped access.
  Server Sync and Approve still require a connection. Selection rules remain those of the list.

## Summary

When many facilities send requisitions for the same program, an approver can review them side by
side instead of one by one. In legacy, the approver ticks requisitions on the Approve list and
presses View Selected: a grid lists every product once, with each requisition's approved quantity
and cost next to each other, a total per product across facilities and a total cost per
requisition. Edits are kept on the device; Sync saves them, Revert drops them, and Approve approves
them all at once.

The new page keeps all of that and its totals match legacy exactly. It fixes legacy's problems:
columns and rows no longer reshuffle on every load, reloading never loses product names or costs,
Revert really discards the device copy, a cleared field no longer turns a total into "NaN",
approval failures name the requisition and the server's reason, and a lost answer from the server
can never approve a requisition twice. Phones get one card per product.

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.approve_.batch.tsx` (URL
  `/requisitions/approve/batch`, `staticData.crumbKey` for "Batch Approval" under Approve), search
  `ids` (comma-joined, de-duplicated, order kept), loader awaits
  `requireRight(queryClient, RIGHTS.requisitionApprove)` and the batch query, with a
  `pendingComponent`; return to the approval list through history state from View Selected, else
  the plain approval list (its own fallback, not `/requisitions/view`); replacing the URL after a
  partial approval keeps that history state.
- Approval list: View Selected navigates here with the ticked ids in the list's row order: each
  tick stores a global row index (page x size + row), and ids sort by it, as legacy builds its URL.
  The legacy hand-off and its `useBackToLegacy` go.
- `batchRequisitionsOptions(ids)` under `queryKeys.requisitions`; records reordered to the `ids`
  order; refused records (a 400 carrying the rest) listed by name above the grid; ids that came
  back missing named too.
- Rows: every product once, in order of first appearance across the records in `ids` order (stable
  across loads); a product a record lacks shows blank cells there.
- Drafts: a new owned Dexie table `requisitionBatchDrafts` (one new schema version), one owner-scoped
  row per requisition id through `local-records.ts`: `{revision, baselineModifiedDate,
  approvedQuantities: {lineId: text}, unresolvedApproval?: {attemptedAt}}`, holding only changed
  cells, written through the shared revisioned draft store and serial writer
  (`src/lib/draft-store.ts`) after each change and on leave (`useDiscardGuard` with
  `flushBeforeLeave`). Writes and clears compare the revision, so another tab's newer edits are
  never overwritten or cleared; a revision conflict reloads that record's draft. Session scope is
  checked after every await. On insecure origins (`isSecureOrigin` false) there are no device
  drafts, as the requisition page: edits stay in memory and the indicator says they are not saved
  on this device. It is separate from the requisition page's drafts, as
  legacy keeps a separate batch copy, so Sync, Revert and Approve can only ever drop batch
  quantities, never comments or other edits made on the requisition page. A batch draft whose
  baseline differs from the server's `modifiedDate` is outdated: that record shows an outdated
  notice with Update (discard its batch draft), reusing the requisition page's banner extracted
  into a component. Batch drafts count as unsynced work through a counter registered in route
  composition. One combined indicator (`DraftStatus` from `components/display/draft-status.tsx`)
  shows Saving, then Saved On This Device, or the failure.
- Grid state: values read per cell through a stable context so a keystroke re-renders one cell,
  its product's totals and the Total row.

### Rules

- Cost per line: packs x the line's `pricePerPack` (0 when missing) from the batch DTO. Packs follow
  legacy exactly, in a batch helper (or `packsToShip` without its default threshold): floor of
  quantity / net content, plus one when the remainder is strictly greater than the threshold and a
  threshold is present (a missing threshold adds no pack, as legacy's `remainder > undefined`), at
  least one pack for a non-zero quantity unless `roundToZero`; 0 gives 0. Tested with a missing
  threshold (15 / 10 is one pack). Quantity shown and summed as 0 when null or empty (user,
  2026-11-02: as legacy). Rows keep each record's server line order (first appearance across
  records in `ids` order). Products skipped in every record never arrive (the server drops them).
- Totals: per product, sum quantities and costs across records; Total row, cost per record and
  overall; skipped lines included (unlike the requisition page's totals); raw sums, rounded only
  for display with the deployment currency.
- Skipped lines show "Skipped" and their cost, no input. Missing products show blank table
  cells and `EMPTY_VALUE` in phone cards.
- Validation (live from the first change, as requisition editors), a small batch validator reusing
  the whole-number rules (`validateLine` needs a full requisition): whole numbers 0 to 2147483647; a
  cleared cell is required for Approve. Errors as other requisition table fields: tinted cell,
  message on hover or focus, group header and phone record label marked invalid with an icon
  and label; Approve with errors
  opens the invalid dialog and focuses the first invalid cell.
- Sync: confirm-free (as legacy); sends every record on screen, cleared cells as 0 (as legacy);
  records holding a number above 2147483647 are held back and named (legacy saves them silently).
  On success: refetch the whole batch (the save response drops products skipped in the saved
  records only), rebuild baselines from it, clear the saved records' batch drafts by revision, toast
  "N Requisitions Were Synchronized". On a 400 with per-record errors: refetch likewise; successes
  rebased and cleared, failures keep their drafts and are named with their reason. An exception-style 400 or a
  lost answer saved nothing for certain: keep every draft, apply the immediate refresh, then
  refresh and ask for review of only the attempted records before the next Sync. Retain server
  refusal reasons from refreshed responses. Removed ids never appear as missing while the URL
  replacement is loading.
- Revert: confirm "Are you sure you want to revert all changes?"; discard the device drafts of every
  record on screen (persisted, unlike legacy) and show server values.
- Approve: block while invalid; confirm "Are you sure you want to approve these Requisitions?";
  saveAll first (records that fail to save are not approved and are named); then approveAll for
  the saved ones. When every save succeeds, use the returned modifiedDate/status as the marker
  baseline without retrieveAll; partial saves refetch. Keep remaining columns and dialog reasons
  in the opening approval list order. Local marker cleanup after POST cannot change its known outcome.
  - The outcome is the union of save failures, approval failures and unresolved records. Approved
    records' drafts are cleared, requisitions and Home invalidated, and a toast gives the approved
    count. Only when that union is empty does the page return to the approval list with its search.
  - Otherwise stay with only the records in the union (the URL's `ids` updated, replacing history,
    keeping its state), each named with its reason (save or approval error from the server) in one
    dialog, on its column header and beside its phone card record label.
  - 400 without `requisitionErrors`: nothing approved; show the message; stay.
  - Before sending approveAll, each record's batch draft row records `unresolvedApproval` on
    HTTPS. HTTP instead stores only `{userId, requisitionId, attemptedAt, baselineModifiedDate,
    baselineStatus}` in owner-scoped sessionStorage, surviving reloads within the tab. Both
    writes complete before POST; quantity drafts remain unavailable on HTTP. On success or a
    definite failure it is cleared. On no response or 5xx it stays: approveAll checks no supervisory node, has no
    idempotency and may still commit after the client's 60 s timeout, so a second approve could
    approve a record again at the next level. Without backend idempotency nothing can prove the
    first request is over; the page never resends on its own.
  - Records marked unresolved: on every load and on Check Again, records whose status or
    `modifiedDate` changed since the save, or that are now refused, missing or not returned, are
    removed, named "may have been approved; check the approval list" and their mark cleared.
    Records still unchanged stay listed with a warning and Approve disabled for them; the user can
    clear the mark only with an explicit "Approve Anyway" confirmation that states the risk of
    approving at the next level, or remove them from the batch.
  - An id missing from both `requisitionDtos` and `requisitionErrors` is treated as not approved
    and named. A record already APPROVED rejected as "must be authorized" is named as possibly
    approved rather than failed.
  - Double clicks blocked while pending; `useSessionMutation` with session checks after awaits.

### Risks And Edge Cases

- Approve-all has no idempotency or lock: the uncertain-outcome rule above is the only protection.
- approveAll needs the permission string at the facility and program; a user approving through a
  node role only can open and sync but the server refuses approval per record, shown with reasons.
- A record changed elsewhere since load: saveAll's `dateModifiedMismatch` names it; Update reloads.
- Large batches: if typing or scrolling misses the budget, add row virtualization
  (`@tanstack/react-virtual`) keeping sticky columns; record the measurement in the plan.

## Decisions

- **Columns follow the approval list's row order**, as legacy (user, 2026-11-02), not tick order.
- **Empty or null approved quantities count as 0** in costs and totals and save as 0, as legacy
  (user, 2026-11-02); a cell the user clears must be filled before Approve, as legacy.
- **Invalid feedback follows the requisition table rule** (tint, tooltip, dialog on Approve) rather
  than text under each input; FM-57's "inline message" is met by the tooltip and header marker.
- **Batch keeps its own device drafts**, as legacy, holding only approved quantities, so batch
  actions never touch edits made on the requisition page. A record edited in both places shows the
  outdated notice in the other once one side saves.
- **Not gated by `BATCH_APPROVE_SCREEN`**, as legacy; the flag still controls the list's selection.

- Steps 3 to 5 add the guarded route, in-app list hand-off in global row order, return history,

  and actions, clear resolved markers, and require explicit confirmation to approve anyway.

## Epic Review Corrections

Partially advanced batches retain eligible copies and show other columns as no longer awaiting
approval, excluding them from totals. Sync and Approve display the saved response before device
copy persistence completes. Tab skips read-only columns in both directions. Dirty drafts preserve
their baseline without freezing the saved list status. Double-click coverage protects the single
approval request while pending.

## Screen Review Follow-Up (2026-11-05)

## Approval Performance Follow-Up (2026-11-05)

Picked approval-list rows verify online batch openings immediately. The independent membership
read still controls complete offline copies. Direct openings verify membership, and approveAll
remains authoritative for picked rows that changed status. Route cache is discarded on exit;
unchanged membership preserves record identity and active input focus on warm reopen.
