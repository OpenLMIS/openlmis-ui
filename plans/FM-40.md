# FM-40: Create/Authorize: Pick Facility And Period

https://openlmis.atlassian.net/browse/FM-40 · Parent: [FM-39] Requisitions

## Scope

The Requisitions > Create/Authorize screen at `/requisitions/initiate`: the shared facility and
program picker with a Regular/Emergency choice, the periods table, and Proceed, which starts a
requisition or opens the existing one. It also lets the requisition page return to this screen
after Submit, Authorize, Delete or Skip, as legacy does.

Out of scope: editing (shipped in [FM-41]), approval ([FM-43]), Patients templates ([FM-42],
which still open read-only with a link to legacy), offline use ([FM-164]/[FM-167]; this route stays
online-only).

## Summary

Facility staff use Create/Authorize to start the requisition for a reporting period, or to reopen
the one already in progress. In legacy they pick My Facility or Supervised Facility, a facility, a
program and Regular or Emergency, then press Search. A table lists the periods. Only the first
open regular period can be started; later ones read "Previous R&R pending". Every current
emergency period can be started. Proceed starts a new requisition or opens the existing one.

The new screen keeps all of that, with the same picker as Stock On Hand and Transaction History,
and the search kept in the address so reload and Back work. It improves three things:

- It never sends the option that makes the server quietly delete old unfinished drafts.
- When starting a requisition fails, the message says why ("Please finish the previous
  requisition", "Program not supported"), instead of a generic error.
- Phones get one card per period instead of a sideways-scrolling strip.

After starting or opening a requisition, the user lands on the requisition page shipped in FM-41.
Finishing it (Submit, Authorize, Delete, Skip) returns to the same Create/Authorize search.

  Create/Authorize. Opens with any of CREATE, DELETE or AUTHORIZE (any scope). wclerk1 has none:
  no menu entry; a direct link shows "You are not authorized to perform this action."
- The form sits in a sidebar left of the table: Facility Type (My Facility / Supervised
  Facility), Facility, Program, Type (Regular / Emergency, default Regular), Search. The picker
  uses only CREATE and AUTHORIZE grants, so a DELETE-only user sees an empty picker. Supervised
  is disabled without grants away from home; with no home facility it starts in Supervised.
- Search is always enabled; missing fields get "This field is required" and an invalid-form

- Periods table: Period(s), Start date, End date, R&R Status, Actions; DD/MM/YYYY; unpaged (33 to
  108 rows on test). Regular: Proceed on the first row only, status is the requisition's or "Not
  yet started"; later rows "Previous R&R pending", no button. Emergency: every row active.
  Periods with finished requisitions are absent.
- Before a search, and after an empty or failed search, the table caption reads "Select required
  fields. Please contact the Admin if no periods are available."
- Proceed on an existing requisition opens it (43 s on test behind a loading modal while products
  load). Proceed on a new period sends `POST v2/requisitions/initiate?emergency&facility&program`
  with an `Idempotency-Key` and no `suggestedPeriod`, then opens the new record (Patients tab
  when the template enables it, otherwise Full Supply). Failure: toast "Could not initiate
  requisition" with the server's reason hidden.
- Problems: generic initiate error; "Program not supported" alert followed by a silently empty
  table; every Search sends `unfinished=true`, which deletes drafts before the support start date
  and 403s for users without DELETE (srmanager1 got a 403 with only CREATE); phone layout is a
  narrow sideways-scrolling strip.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Periods | `GET requisitions/periodsForInitiate` | `programId`, `facilityId`, `emergency` (never `unfinished`) | `id, name, startDate, endDate, requisitionId?, requisitionStatus?` | CREATE or AUTHORIZE at facility/program | `period.service.js:58-99` |
| Support start date | `GET facilities/{id}` (existing `facilityOptions`) | | `supportedPrograms[].{id, supportStartDate}` | none | not called by legacy (Decisions) |
| Initiate | `POST v2/requisitions/initiate` | `program`, `facility`, `emergency`; header `Idempotency-Key`; empty body; no `suggestedPeriod` | response `id` | CREATE | `requisition-initiate.controller.js:130-211` |
| Picker | existing `prefetchFacilityProgramOptions` reads | | | | [FM-18] |

Errors carry `messageKey` and an English-only `message` (the backend has one catalog; the
support error names raw ids). Map the known keys to our own translations and fall back to the
server text only for unknown keys, through `toRequisitionFailure` (`lib/failure.ts:11`):
- Periods: 400 `requisition.error.facilityDoesNotSupportProgram` (legacy's "Program Not
  Supported" / "This program is inactive, please check with Admin."), 403 (`NoAccess` through
  `ListError`).
- Initiate: 400 `finishPreviousRequisition`, `periodShouldBeOldestAndNotAssociated`,
  `incorrectSuggestedPeriod` (no current emergency period), template not found; 403; 409
  `idempotencyKey.alreadyUsed`.
- `emergency` is a required boolean on both calls: always send `emergency=false` for Regular.

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.initiate.tsx`. Search schema:
  `facilityProgramSearchSchema` plus `emergency: z.boolean().optional().catch(undefined)`
  (Regular is the default and stays out of the URL).
- Loader: `requirePermissions` any of CREATE, DELETE, AUTHORIZE; prefetch picker options with
  CREATE and AUTHORIZE grants; when the selection is complete and `validSelection` passes and the
  user holds CREATE or AUTHORIZE at the exact pair (`hasProgramGrant`), prefetch periods and the
  facility, unawaited. Model: Transaction History.
- `periodsForInitiateOptions({ programId, facilityId, emergency })` under
  `queryKeys.requisitions` (FM-41 actions already invalidate it), `staleTime: 0` so every visit
  and Search refetches, as legacy.
- Body: picker outside `QueryBoundary`; table inside with `DataTableSkeleton pagination="none"`
  and `ListError` with retry (it turns 403 into `NoAccess`; pass the mapped support message for
  the 400). The route has a `pendingComponent` (model `TransactionHistoryPending`), since the
  loader awaits rights.
- Picker grants: `useFacilityProgramOptions` with CREATE and AUTHORIZE grants merged in a
  `useMemo`, as Transaction History (`:215`); `prefetchFacilityProgramOptions` takes none.
- Regular/Emergency is route draft state beside the picker's draft, reset from the URL on Back
  as the picker resets itself (`facility-program-selector.tsx:85-89`), and merged in `onSearch`.
- Proceed (new): `useSessionMutation` with `retry: false`, `requireOnline()` first, an
  idempotency key from `randomId()`. The server records the key before validating and creates
  the requisition before answering, so:
  - a definite 4xx answer (400, 403) takes a new key for the next attempt;
  - an uncertain outcome (no response, 5xx, gateway error) or a 409 may hide a created
    requisition: refetch the periods first, which shows any new requisition as an Open row,
    and take a new key only after that refetch settles. A retry never reuses a consumed key
    and never creates a second emergency requisition unseen.
  On success invalidate `queryKeys.requisitions.all` and navigate to
  `/requisitions/view/$requisitionId` with history state `requisitionReturn` (below); no cache
  seed, since the initiate response has no ETag and the detail loader refetches. Call
  `assertSessionScope` after each await (invalidation, refetch) before navigating or toasting;
  `useSessionMutation` checks only when the whole callback returns. While pending every Proceed is disabled and the clicked one shows
  a spinner.
- Proceed (existing): a `Link` to the record with the same history state.
- Return target: the detail route reads `router.state.location.state.requisitionReturn`
  (`{ to: '/requisitions/initiate', search }`), declared in a `HistoryState` module merge as
  `_protected.administration.users.tsx:47` does, and widens `opening`'s `to`
  (`$requisitionId.tsx:348`). Every detail-page search change keeps the current history state:
  tab and line jumps (`:842`), grid paging and filters (`requisition-grid.tsx:350`) and closing
  directly loaded dialogs (`use-search-navigation.ts:34`, `:61`, via `keepState`). The target then
  survives tab switches, paging and reloads. Applies to the finish
  navigation and the `DetailError`/`RequisitionError` back link. Without it, today's View
  Requisitions return; legacy falls back to Create/Authorize, but our detail page lives under
  View Requisitions. Breadcrumbs stay Requisitions / View Requisitions.

### Rules

- Rows: sort by `endDate` ascending as a guard (server already returns them in order). Regular
  lists drop periods whose `startDate` is before the program's `supportStartDate` at that
  facility, when set; emergency lists are not filtered (the server already limits current
  periods, and open emergency requisitions may sit in older ones).
- Active row: emergency, or the first regular row left after that filter, as the server counts
  it when initiating (`PeriodService.java:330-336`). Status text: the requisition status label
  when `requisitionStatus` is set; otherwise "Not Yet Started" on active rows and "Previous R&R
  Pending" on others.
- Proceed shows on active rows only: Open when the row has `requisitionId` (any right), Start
  when it has none and the user holds CREATE at the facility/program. Active new-period rows
  without CREATE show no button, as legacy.
- Emergency rows may repeat a period (one per open emergency requisition); key rows by
  `requisitionId ?? id`.
- Never send `suggestedPeriod`: the server picks the period and keeps the order rules.

### Risks And Edge Cases

- Every period list on test is long (up to 108 rows) and emergency lists are empty today; test
  emergency rows with a fixture.
- A first regular row with SUBMITTED status opens for AUTHORIZE-only users; the detail page then
  needs VIEW (Decisions).

## UI/UX

**Port**: My Facility / Supervised Facility, Facility, Program, Regular/Emergency, Search; the
five columns; Proceed only on active rows; the status texts; the empty message; the URL search.

**Improve**:
- Same picker row as Stock (no card, `Separator` below, shared field width); Type is a segmented
  Regular/Emergency control in the same row.
- Before a search the table shows the legacy message; after an empty search, "No periods
  available for this facility and program. Please contact the Admin." so the two states differ.
- Initiate and period errors show the server's reason in a toast or `ListError`, not a generic
  error or a silently empty table.
- Phones: one card per period, the period name in the band with Proceed as its action, rows Start
  Date, End Date, R&R Status.
- Status as the same badge as View Requisitions; "Not Yet Started" and "Previous R&R Pending" as
  muted text.
- The action button reads "Proceed" on every row, as legacy, with an accessible name that
  includes the period.

**Drop**: the left sidebar layout (the app's pickers sit above the table); the 43 s loading modal
(the requisition page has its own loading state); the "You are not authorized" modal (the app's
No Access page); saving each new requisition on the device for offline use (offline waits for
[FM-164]/[FM-167]).

States: picker skeleton, table skeleton, empty before search, empty after search, list error with
retry, Proceed pending, offline (Proceed disabled with toast). RTL: logical classes only; date
order follows the page language.

## Decisions

- **No `unfinished=true`** on the periods call. Legacy sends it, but it deletes drafts dated
  before the support start date and refuses users without DELETE. Hide those periods in the UI
  with the facility's support start date instead ([FM-39] Decision). This is the one deliberate
  API difference from legacy.
- **No `suggestedPeriod`** on initiate, as legacy; the server chooses the period.
- **Search stays enabled** and validates on press, as legacy and every other picker in the app,
  rather than a disabled button. It still sends nothing until both fields are chosen (user,
  2026-10-29: follow legacy).
- **Rights**: screen and menu on CREATE, DELETE or AUTHORIZE; picker on CREATE and AUTHORIZE;
  Start on CREATE at the exact pair; Open for any active row with a requisition.
- **Detail access stays on VIEW**. The server's `GET v2/requisitions/{id}` needs VIEW anyway, and
  every demo role with CREATE or AUTHORIZE holds VIEW too.
- **Return to Create/Authorize** after Submit, Authorize, Delete or Skip when the record was
  opened from here, as legacy returns to its previous screen.
- **Regular stays out of the URL**; Emergency is `emergency=true`.

## Implementation Notes

- Steps 1-6 use the shared picker slot, initiation API/query types, pure row rules and an
  unpaged table with cards below 672px. Known server errors are translated, including missing
  templates and consumed idempotency keys. A generic period-loading title covers other failures.
- Picker validation remains authoritative. The loader prefetches results only when cached
  picker sources establish a valid, granted selection; on a cold visit the body validates after
  the picker loads and starts periods and facility reads together. No loader waits for pickers.
- After an uncertain initiation outcome, failed period reconciliation keeps initiation blocked.
  The next Proceed click retries reconciliation only; a successful refresh reveals any created
  requisition before another initiation can be attempted with a fresh key.
- Step 7 preserves the return target through detail search updates using an opt-in `keepState`
  default in `useSearchNavigation`, including direct-link dialog closes. The finish workflow and
  record error link use the saved target; View Requisitions remains the fallback.
- Step 8 synchronizes all five catalogs. Browser checks, including Arabic, phone screenshots,
  real-server network captures and console checks, were not performed because the implementation
  brief explicitly prohibits browser work and real-server writes. Responsive action workflows
  are covered with local fixtures instead. These browser checks remain for review.
- Step 9 corrects the skeleton pagination documentation to `pagination="none"` and its actual
  `"default"` default value.
