# FM-15: Route guards from access rights

https://openlmis.atlassian.net/browse/FM-15 · Parent: [FM-7](https://openlmis.atlassian.net/browse/FM-7) Auth & session plumbing

## Scope

Declare each page's opening rights once, on its route, and make the page guard, the menu, the
command palette, the breadcrumbs, the account menu and Home's Add User shortcut read them from
there. Delete the separate menu rights list. Add an administrator test.

Not in scope, kept as they are on purpose:

- Scoped checks loaders already run (exact facility/program grants, supervisory nodes,
  requisition group membership, BUQ access).
- Home's dashboard data gates, which decide what data to fetch, not whether a page opens.
- Action buttons gated by their own right (for example Reverse on transaction details).
- The offline capability list in `src/routes/-offline-pages.ts`, a separate offline policy.

## Summary

Every page already checks rights before it opens and shows No Access when they are missing. But
each page's right is also written a second time, in a separate list that decides what the menu,
command palette and breadcrumbs offer, and a third time for a few links such as Settings in the
account menu. These copies must be kept in step by hand; a mismatch shows a menu entry that leads
to No Access, or hides a page the user can open.

Legacy declares the rights once on each route and its menu reads them from there. The new UI will
do the same: each route states its rights next to its definition, the page check reads them, and
every link looks them up from the route it points to. Nothing changes for users; the copies simply
can no longer drift.

## Acceptance Criteria

| AC | How it is met | How it is checked |
|---|---|---|
| Each route declares its required rights in one place, next to the route | `staticData.rights` on the route; guards, nav, palette, breadcrumbs, account links and Home's shortcut read it; `NAV_RIGHTS` deleted | Registry test over every protected route; static check that declaring routes call the guard |
| Opens with at least one of its rights, blocked otherwise | `requireRouteRights` keeps `requirePermissions`' any-of semantics | `access.test.ts` |
| Program, facility or node scoped rights checked as legacy | Unchanged: stock exact grants, requisition supervision and approval membership, BUQ access | Existing stock, requisition and BUQ route tests stay green |
| Blocked user sees access denied, no flash | Unchanged awaited loader check; one real route test holds the permissions response and asserts the page never mounts | That route test |
| Home and Profile open for every signed-in user | Listed as open routes; no rights declared | Registry test |
| Tests cover no rights, some rights and an administrator | Registry test runs the real route tree for no rights, some rights and all rights | Registry test |

## Legacy Today

- The menu and the transition guard live in `openlmis-auth-ui`.
  `openlmis-navigation/navigation-state.service.js` `canViewState` shows an entry when the user has
  any of the state's `accessRights` (all of them with `areAllRightsRequired`) and its optional
  `canAccess` function passes. `auth-state-router/auth-state-router.service.js` blocks the
  transition with the same `accessRights` and shows an error alert, staying on the current page.
- Requisitions View declares no `accessRights`; it uses `canAccess` with
  `hasRoleWithRightAndFacility(REQUISITION_VIEW)`, which our supervision-role special case mirrors.
- Scoped rights are checked by each state's resolves.
- All-of rights are not needed by any migrated route, so the new UI supports any-of only.

## Agent Brief

- **API map**: none new. Rights come from `permissionsOptions(userId)` (`GET /users/{id}/permissionStrings`).
- **Declaration**: move the `StaticDataRouteOption` augmentation from
  `src/components/app-shell/app-breadcrumbs.tsx` to `src/types/router.d.ts` (keep a type import so
  the file stays a module) and add `rights?: readonly string[]`.
- **Lookup**: `routeRights(route)` walks `route` then its `parentRoute`s and returns the nearest
  declared `rights`, so an index route (`/settings/`, `/profile/`) inherits its layout's rights.
  `routesByPath` keys have no trailing slash and prefer the index child.
- **Guard**: `requireRouteRights(queryClient, route)` in `src/features/auth/lib/access.ts` returns
  `requirePermissions(queryClient, routeRights(route))`. A route with no declared rights fails
  closed with a programming error. An empty list means no right opens it through the standard
  guard (used only by custom-guard routes).
- **Shared helpers** take the rights from the route instead of a constant, keeping their session
  checks, query order and exact grants:
  - `-stock-event-program-picker.tsx` `loadStockEventPrograms` (also used by Physical Inventory)
  - `-stock-event-editor.tsx` (`EVENT_KINDS[kind].right` becomes the route's declaration)
  - `-stock-card-access.ts` `stockCardAccess`
  - `-buq-access.ts` `loadBuqAccess`, `loadApproveAccess`, `loadNationalAccess`
  - Physical Inventory draft and the reports dashboard route (object-form loaders,
    keep `staleReloadMode: 'blocking'` and the dashboard availability check)
- **Custom guards** (declare rights for links, keep their own check, listed in the registry test):
  - `/requisitions/view` and `/requisitions/view/$requisitionId`: supervision roles and device copies
  - `/offline-events`: open with device work or offline, otherwise the declared rights
  - `/settings`: the `SYSTEM_SETTINGS` flag first (`notFound`), then `requireRouteRights`
- **Detail routes** declare their own rights where they differ from the list (shipment detail also
  accepts `ORDERS_VIEW`), otherwise the same rights as their list.
- **Links**: `canOpen`/`navWithinRights` take a `rightsFor(to)` lookup. Hooks build it with
  `useRouter()` (never import `router` or `routeTree` into `nav-access.ts`: that forms an import
  cycle). An unresolved path is hidden, except the open set (Home, Profile). Keep the Offline
  Events and Requisitions View special cases. `useAccountLinks` uses `canOpen('/settings')` plus the
  flag. Home's Add User shortcut uses `canOpen('/administration/users')`, keeping its offline
  disabled state.
- **Delete**: `src/lib/nav-rights.ts` and `registerNavRights` in `src/routes/-offline-pages.ts`;
  drop test imports of `-offline-pages` that existed only for menu rights.
- **Code splitting**: `staticData` is never split. Vite splits stock-management loaders
  (`vite.config.ts`), but split loaders still receive `route`, so the guard works the same.
- **Docs**: update the AGENTS.md lines about `NAV_RIGHTS`, `src/lib/nav-rights.ts` and registering
  navigation rights.
- **Tests**:
  - Registry test on the real `router` (as `integrations/tanstack-router.test.ts` does): every
    `/(protected)/_protected` route in `routesById` resolves rights or is in the open or
    custom-guard list; every live nav and account link resolves; no rights, some rights and all
    rights (administrator, flags on) give the expected entries.
  - Static check: every route file declaring `rights:` calls `requireRouteRights` or a listed helper.
  - `access.test.ts`: inherited rights, fail closed without a declaration.
  - One real route denial test with a held permissions response: the page never mounts.
  - Fixture updates: copy `staticData` into rebuilt test routes (about 20 files, e.g.
    `-stock-on-hand.test.tsx`), pass `route: Route` to direct loader calls (`-reports.test.ts`,
    `-requisition-initiate.test.tsx`, `-requisition-convert.test.tsx`, `-requisition-approval.test.tsx`,
    `-requisition-batch.test.tsx`, `-reason-edit.test.tsx`, `-requisition-group-edit.test.tsx`,
    `-_protected.orders.view.test.ts`, `-shipment.test.ts`), give `renderPage` a lookup for shell
    tests, and move the route-level `canOpen` assertions into the registry test.
- **Risks**: a route that declares rights but skips the guard; covered by the static check.

## Decisions

- Declare rights in `staticData`, as legacy declares `accessRights` on the state, rather than in a
  central map: the rights sit next to the route, as the AC asks.
- Keep the guard in each route's loader, not the `_protected` layout's `beforeLoad`, so denial stays
  at the page boundary and the layout's own lifecycle is untouched.
- Fail closed: a missing declaration blocks the page and hides its links.

## Implementation Notes

- The Rejection Reasons and Rejection Reason Categories detail URLs only redirect to their
  guarded lists. The registry lists these redirects explicitly. Their destinations apply the
  opening rights after the redirect, as before.
