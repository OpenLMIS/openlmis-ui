## Summary

After a facility authorizes its forecast, a district approver opens it from the Approve list,
checks it and either approves it or sends it back with reasons. An approved forecast moves on to
the next level; a rejected one goes back to the facility to be corrected.

Legacy shows the same grid as the facility sees, with every field locked, and Approve, Reject,
Cancel and View Source of Fund at the bottom. It downloads every product in the system before
showing anything, shows Approve and Reject on any forecast opened by address, asks twice before a
rejection, and does not fit a phone: buttons overlap and the dialogs run off the screen.

The new page reuses the forecast grid already built for facilities, read-only, with the approver's
two actions. It opens only forecasts waiting for this approver, asks once before approving,
rejects from one dialog, shows the server's error in place, and returns to the list. It works on a
phone and in Arabic.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Enter | permissions, `GET /users/{id}/programs` | user id | program `code === 'BUQ'` | `APPROVE_BUQ` anywhere | `buq.routes.js:137-144` |
| Membership | `GET /bottomUpQuantifications/forApproval` (cached from the list) | `programId` | `id` | `APPROVE_BUQ` | none (legacy opens any id) |
| Forecast and lookups | as FM-105 (`GET /bottomUpQuantifications/{id}`, products by id, facility, remarks, sources, currency, periods) | | as FM-105 | any BUQ right | `useFacilityDemandForecasting.js:98-133` |
| Approve | `POST /bottomUpQuantifications/{id}/approve` | the forecast as read, unchanged | DTO | `APPROVE_BUQ`, unscoped | `FacilityDemandingForecasting.jsx:244-308` |
| Reasons | `GET /rejectionReasons` (requisition service) | none | `id`, `name`, `active`, `rejectionReasonCategory` (`name`, `active`) | authenticated | `RejectionCommentsForm.jsx:64-103` |
| Reject | `POST /bottomUpQuantifications/{id}/reject` | `{ rejectionReasons: uuid[], generalComments }` | DTO | `APPROVE_BUQ`, `MOH_APPROVAL` or `PORALG_APPROVAL`, unscoped | `FacilityDemandingForecasting.jsx:220-242` |

Approve accepts AUTHORIZED or IN_APPROVAL (400
`buq.error.approve.mustBeAuthorizedOrInApprovalToBeApproved`) and validates the lines (required,
non-negative, remark when Verified differs from Forecasted). Reject accepts AUTHORIZED,
IN_APPROVAL or APPROVED and checks neither reasons nor comment length. Errors `{messageKey,
message}`; 403 without the right; 404 for a missing forecast.

### Data Flow

- Route `_protected.buq.approve_.$id.tsx` (no nesting), `preload: false`, `crumbKey`: the loader
  blocks on `loadApproveAccess` (FM-106), `ensureQueryData(buqsForApprovalOptions(programId))` and a
  fresh forecast read (`fetchQuery` with `staleTime: 0` on enter, cached on `stay`); a forecast
  missing from the list throws `notFound`. Lookups prefetch without awaiting, as FM-105.
- The editor: `ForecastForm` takes the actions from one helper; approve mode gives
  `['approve', 'reject']` and no editing. Approve reuses the FM-105 confirmation, mutation, failure
  dialog and leave flag; Reject opens its own dialog in the URL (`?dialog=reject`).
- Writes through `useSessionMutation`, then invalidate `[...buq.all, 'list']` (list and stats) and
  return to `/buq/approve` with the list search from history state (`buqListSearch`).
- The list: an Actions column with Review (`Button` in the table, `CardActions` in cards), passing
  the list search in history state, as Forecast on Create / Authorize.

### Server-Side Work

- Products by id and periods from the BUQ schedule (FM-105) instead of every product and period.
- Reasons stay one unpaged read filtered in the browser: the endpoint's category filter is ignored
  when `active` is set (`RejectionReasonController.java:170-195`) and the list is small.

### Rules

- The approver changes nothing; the approve body is the forecast exactly as read, so a stale or
  partial body never overwrites lines or funding (Risks).
- Approve and Reject only for forecasts in the user's approve list (AUTHORIZED or IN_APPROVAL at
  their node); others are Not Found. The backend checks neither node nor facility.
- Approve requires complete funding, as legacy; a forecast authorized without it shows the FM-105
  invalid-funding message instead of sending.
- Reject requires at least one reason; comments optional, at most 4000 characters, counted.
- Reasons offered: category `BUQ`, reason and category active.
- After a decision: toast, refresh list and stats, return to the list with its search.

### Risks And Edge Cases

- Approve saves the posted body; an empty line list deletes every line. Sending the read forecast
  unchanged avoids both.
- After an approve that moves the forecast to the parent node it stays in the list when the user
  also approves at the parent (vault, two-node test); "leaves the list" holds for one level.
- A district approver could reject an APPROVED forecast by address; it is not in their list, so
  the page refuses it.
- Reasons from the requisition service; a deployment without a `BUQ` category shows the empty
  reasons text and Reject stays disabled.
- A deleted remark or source used in the forecast makes the read 500 (vault bug); shown as the
  load error.

## UI/UX

**Port**: the grid, details, totals and funding dialog of FM-105, all read-only; Approve with a
confirmation; Reject with reasons of category BUQ, at least one, and General comments up to 4000;
Cancel to the list; the toasts.

**Improve**:
- Opens only forecasts waiting for this approver; others are Not Found with a link to the list.
- Reasons as a searchable chip picker, active ones only; a character counter on the comments.
- One step to reject: the dialog is the confirmation, since it already asks for the reasons.
- The server's error in place (FM-105 failure dialog), never a toast plus a modal.
- Returns to the list with its page after either decision, also when opened by address.
- The row action reads Review, distinct from the column View menu.
- Cards and a sticky footer that fit a phone; dialogs at `size="table"`, one column.

**Drop**: the second rejection confirmation; inactive reasons; downloading every product and
period; the loading modal.

States: loading (real header, skeleton grid), not found, load error with retry, ready, approving,
rejecting, server refusal. RTL with logical classes; names in `<bdi>`.

## Decisions

- **One editor for both roles**: approve mode is an action set on the FM-105 editor, not a copy.
- **Approve body is the forecast as read**: guards the backend saving whatever is posted.
- **Membership from the approve list**: the backend checks no scope, so the page opens only ids
  in `forApproval`.
- **Reject without a second confirmation** (AGENTS.md: confirm only when needed); Approve keeps its
  confirmation, as Submit and Authorize.
- **Row action labelled Review** (user, 2026-11-10), named "Review {facility}, {period}" for screen
  readers, so it is not confused with the column View menu beside it.
- **Real writes on the local instance** (user, 2026-11-10): forecasts prepared, submitted and
  authorized on N003 for the approve and reject checks, removed after. The instance now keeps its
  data across restarts (production profile, user, 2026-11-10).
- **Branch from FM-106**, which is not merged.
