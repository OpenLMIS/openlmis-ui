# FM-93: View Orders, with FM-89: Fulfill Orders List

https://openlmis.atlassian.net/browse/FM-93 · https://openlmis.atlassian.net/browse/FM-89 ·
Parent: FM-88 Fulfillment

## Scope

One PR delivers both order lists under the Orders menu:

- **View Orders** (FM-93): orders a supplying facility received, with Print, Download,
  Retry Transfer and Edit for orders still being created.
- **Fulfill Orders** (FM-89): orders waiting to be fulfilled, each opening its shipment in the
  new UI (FM-90).

It also updates the supporting flows:

- Rows configure `usePrintReport` with their report request; Start/Continue Fulfillment links to
  the new shipment screen.
- `fetchReport` can return the server's file name.
- The Create Orders editor returns to View Orders when opened from there, and refreshes the
  order lists after its writes.
- Conversion and manual creation invalidate the order list prefix and Home counts, including
  partial manual creation, so returning within the 30-second cache window shows new orders.
- Supplier names use facility-by-id reads for small grant sets and cached minimal facilities
  for larger sets. PR #126 keeps background downloads separate from foreground picker queries.
- Orders, Convert, View Requisitions and Approve loading tables do not suspend on the
  deployment time zone.
- Arabic order screens and related labels consistently use أمر for order.

Out of scope:

- The shipment screen (FM-90) and proof of delivery screens (FM-91, FM-92), planned separately
  and merged into this PR.
- Offline. Legacy has none for these screens.

## Summary

Warehouses fulfil orders that come from approved requisitions or from Create Orders. Legacy
has two lists for them:

- **View Orders** shows every order a chosen supplying facility received. Users can narrow it
  by requesting facility, program, status and period, print an order, download it as CSV,
  retry an order whose file transfer failed, and continue editing an order still being
  created.
- **Fulfill Orders** shows only the orders still to be fulfilled (Ordered or Fulfilling).
  Users can narrow it by requesting facility, program and status, and sort it newest or
  oldest first. Each row opens the shipment screen.

The new screens keep legacy's columns, labels, filters and actions. They also fix legacy
problems:

- Statuses read as words instead of codes such as `TRANSFER_FAILED`.
- Filters apply as you choose them and return to page 1.
- The sort choice survives a reload.
- View Orders asks for a supplying facility instead of claiming "No orders found" before
  any search.
- Both lists become cards on phones.

Start and Continue Fulfillment open the new shipment screen (FM-90, merged into this PR), which
returns to Fulfill Orders with its filters kept.

### Backend facts to respect

- **Sorting:**
  - Only `Order` fields sort: `orderCode`, `emergency`, `createdDate`, `status`.
  - `lastUpdatedDate` and names give a 500.
  - The server adds no tiebreaker. `emergency` or `status` alone repeats and skips rows
    across pages, and even `createdDate` ties: three test orders share
    `2016-04-30T16:45:22Z`.
  - Always append `sort=createdDate,desc` and then `sort=id,asc` after the chosen sort.
    The server takes repeated `sort`, and `id` is a sortable `Order` field.
- **Invalid params give 400**, so the URL schemas must validate:
  - unknown statuses
  - malformed UUIDs (supplier, requester, program)
  - non-ISO dates
- **Arrays.** Send repeated params with `paramsSerializer: { indexes: null }`, as
  `src/features/home/api/api.ts`.
- **Null periods.** `processingPeriod` is `null` on requisition-less orders (24 of 28 at
  Ntcheu on test), so render it blank. Any period filter excludes those orders on the
  server, as in legacy.
- **Print:**
  - `lang` accepts `en`, `fr` and `pt`; anything else, including `ar`, returns the English
    PDF with 200.
  - A PODS user can see a row through the list yet get 403 on Print or Download, because
    `canViewOrder` checks the program. Show the usual refused toast.
- **Export errors.** 400 and 404 bodies are Spring's `{message}`; 403 is localized.
  `fetchReport` decoding covers both.

### Data flow

**View Orders** (`/orders/view`):

- **Search params:**
  - `supplyingFacilityId`, `requestingFacilityId`, `programId` (UUIDs).
  - `status` (one of the 8 legacy statuses, case-insensitive on input, stored uppercase).
  - `periodStart`, `periodEnd` (`dateFilterSchema`).
  - `tableSearchSchema()` page, size, sort and dir. Sortable columns are `orderCode`,
    `emergency` and `createdDate`; the default is `createdDate` descending.
- **Loader:**
  - Awaits `requirePermissions(queryClient, [RIGHTS.ordersView, RIGHTS.podsManage])`.
  - Prefetches without awaiting: `viewSupplierFacilitiesOptions(permissions)`,
    `programsOptions()` and `deploymentTimeZoneOptions()`.
  - Decides requester and order prefetches from `viewOrderSupplierIds(permissions)` immediately
    after permissions, without waiting for facility names.
  - A granted URL supplier starts `orderRequestingFacilitiesOptions([supplierId])`; a valid
    date range also starts `ordersSearchOptions(params)` after checking the grant id and dates.
  - The picker alone needs the supplier lookup: it reuses cached minimal facilities or reads
    up to 100 unique sorted supplier ids through `facilitiesByIdsOptions`; larger sets fetch
    minimal facilities. Both paths use the query cache.
  - The page still validates the supplier against the returned facility list before showing
    results. A granted supplier absent from that list may send one orders/requester read
    while the page shows refusal. This trade-off removes the linked-page waterfall.
- **Supplier ids** (`viewOrderSuppliers(permissions, facilities)`): the `ORDERS_VIEW`
  facility grants by name, then the facilities of `PODS_MANAGE` program grants by name,
  deduplicated (Decision 3).
- **Picker:**
  - It keeps a draft until Search, as View Requisitions does. A cleared draft is distinct
    from an untouched draft: clearing or changing it hides old results, pagination, Filters
    and View; Search on an empty field shows the required error.
  - A sole supplier is picked in the draft but not searched.
  - Search pushes a history entry.
  - Search writes the URL immediately, clearing `requestingFacilityId` when the supplier
    changes and retaining it otherwise. Re-searching the same supplier refreshes the list.
- **Refused link.** A URL supplier the picker cannot offer shows the refused state and
  sends no request without a grant; a granted but absent supplier may prefetch as above.
- **Inverted dates.** Start after End in the URL shows the invalid range state with Clear
  Dates (`invalidDateRange`), and sends no orders request.

**Fulfill Orders** (`/orders/fulfillment`):

- **Search params:**
  - `requestingFacilityId`, `programId` (UUIDs).
  - `status`: `ORDERED` or `FULFILLING`; anything else is dropped, and none means both.
  - Table params, with the same sorting as View Orders.
- **Loader:**
  - Awaits `requirePermissions([RIGHTS.shipmentsView, RIGHTS.shipmentsEdit])`.
  - Prefetches orders, programs, the time zone and requester ids immediately after permissions.
    Facility names never hold up rows.
- **Ordering facility options** (`fulfillOrderSupplierIds`):
  - `/orders/requestingFacilities` over the facility grants for `ORDERS_VIEW`,
    `SHIPMENTS_VIEW` and `SHIPMENTS_EDIT` (Decision 4).
  - A non-suspending minimal facilities query names requesters lazily once ids are available.
  - No such grants means no options and no request.

**Query keys and invalidation:**

- `queryKeys.orders.list(params)` for searches.
- `[...queryKeys.orders.all, 'requesting-facilities', ids.toSorted()]` for options.
- Retry Transfer invalidates `queryKeys.orders.all` and `queryKeys.home.all`, so the Home
  "Orders" count follows.
- The Create Orders editor's send and delete, including partly successful batches,
  invalidate the list prefix `[...queryKeys.orders.all, 'list']`. `queryKeys.orders.list()`
  would not match parameterized keys.
- Convert refresh invalidates requisitions, Home and that order list prefix, including
  uncertain outcomes. Manual Create Orders invalidates the prefix and Home when any order
  was created, including partly successful batches.

**Shared:**

- The toolbar stays outside the table `QueryBoundary`; rows read `useDeferredValue(search)`.
- Requester options and programs use non-suspending queries. Their filters are disabled until
  loaded, and lookup failures offer retry without replacing the picker, toolbar or table.
- Loading tables in Orders, Convert, View Requisitions and Approve use the deployment time
  zone only in loaded results; skeletons build columns with a fixed UTC zone.
- Background requisition downloads retain their separate query keys, session and abort checks, as established by #126.
- Filter changes replace history and return to page 1; paging and sorting push history.

**Model:** View Requisitions (`_protected.requisitions.view.tsx`,
`requisition-search-picker.tsx`, `requisitions-table.tsx`, `requisitions-toolbar.tsx`) for
the picker, its states, filters, header sort and `DataTableViewOptions sort`.

### Rules

- **View Orders, CREATING:** the row offers only Edit, shown with the `ORDER_CREATE` right
  (Decision 6). Edit passes return state for View Orders.
- **View Orders, other statuses:**
  - Print and Download.
  - Retry Transfer when status is TRANSFER_FAILED and the user has an `ORDERS_TRANSFER`
    facility grant at the order's supplying facility.
- **Retry outcomes:**
  - Every Retry is disabled while one runs.
  - `{result: true}`: "Transfer Successful" toast, then the list refreshes.
  - `{result: false}`: error toast with legacy's sentence.
  - 4xx: error toast with the server's localized message, falling back to legacy's
    sentence.
  - No confirmation, as legacy.
- **Fulfill Orders:**
  - FULFILLING gives Continue Fulfillment; every other status gives Start Fulfillment
    (`order.js:57-59`).
  - The button links to the new shipment screen.
- **Facility cells** on both screens show `code - name` from `facility`. District is
  `facility.geographicZone.name`, as legacy.
- **Print** sends the page language as `lang`.

### Risks and edge cases

- **Admin-sized supplier lists.** smanager1 and administrator get about 1,000 suppliers. The
  combobox searches them, and the minimal facilities list is shared and cached.
- **Timing.** Small supplier sets use facilities-by-id instead of the 386 KB minimal list.
  Large sets share minimal facilities, and the picker renders at most 50 matches while
  searching every supplier. Step 6 measures from the Sign In click.
- **PODS-only users.** On View Orders they get legacy's supplier list, and every search
  returns no orders, as in legacy.
- **Arabic Print.** Arabic users get the English PDF; the server has no Arabic template.

## Decisions

1. **Supplier picker follows View Requisitions**: a draft with Search, and a sole option
   pre-picked but not searched. This matches legacy and the closest app screen.
2. **Supplier names reuse foreground queries (#126)**: cached minimal facilities first, otherwise
   facilities-by-id for up to 100 sorted unique grant ids, or minimal facilities for larger
   sets. The loader uses grant ids without awaiting names; the page still refuses missing
   facilities. A granted supplier missing from the lookup may prefetch once while refused.
3. **View Orders' suppliers keep legacy's list**: `ORDERS_VIEW` facilities, then `PODS_MANAGE`
   facilities, each by name.
4. **Fulfill Orders' ordering facilities come from `ORDERS_VIEW`, `SHIPMENTS_VIEW` and
   `SHIPMENTS_EDIT` suppliers.** Legacy uses `ORDERS_VIEW` only and, without it, lists every
   requesting facility on the server: a clear failure for the shipment-only users the page
   is for. Loader and results use the same sorted grant ids, so requester query keys agree.
   Minimal facilities name requesters lazily without blocking orders.
5. **Status labels everywhere**, CREATING included. The View Orders status filter keeps
   legacy's 8 statuses.
6. **Edit on CREATING orders shows only with `ORDER_CREATE`**, the right its page requires
   (AGENTS.md: render only what rights allow). Legacy showed the button and refused on open.
7. **Header sort with `createdDate` and `id` tiebreakers**, limited to fields the server
   sorts, so paging never repeats or skips rows.
8. **The Create Orders editor returns to View Orders** when opened from there, per the
   draft-editor return rule. Conversion and manual creation refresh all parameterized order
   lists and Home counts so cached lists reflect new orders immediately.
9. **Programs never suspend the picker or toolbar.** Their filter stays disabled while
   unavailable, and errors offer retry in place on both order lists.
10. **Loading tables use fixed UTC columns**, including Orders, Convert, View
    Requisitions and Approve. Background downloads stay separate from foreground reads (#126).
11. **Arabic uses أمر consistently** across order screens and related labels. Every row/card
    action name includes its order number, with legacy action wording preserved.

12. **All columns show by default**, including all 12 View Orders columns at 1440 px with the sidebar, as legacy, rather than hiding lower-priority ones behind View. Cells keep values on one line, so at 1440 px the widest lists scroll sideways with Actions pinned (the user's choice on 2026-11-09); phones use cards and View can hide columns.
13. **The full supplier list is virtualized**, including all 1,009 administrator suppliers, keeping search responsive.
