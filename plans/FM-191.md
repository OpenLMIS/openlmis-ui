## Scope

Scope direction confirmed by the user: match legacy offline requisition behavior.

- Add Offline columns to View Requisitions and Approve Requisitions.
- Keep View Requisitions' Offline filter, URL state and local search. Keep Approve's visible
  Program-only filter and its existing program-scoped offline search behavior.
- Make these lists usable offline against complete copies saved by this user on this deployment.
- Automatically retain complete single and batch copies after successful online opens, including
  clean copies. Reopen saved single requisitions and saved batches offline, with the editing
  capabilities legacy supports, using the existing draft writers.
- Cache resolved facility/program choices and access inputs through the existing download coordinator.
- Remove a saved single-requisition copy after confirmation, protecting concurrent edits and
  unresolved batch work.

The full saved-copy work is necessary to deliver the offline search deferred by
[FM-48](FM-48.md), rather than showing Offline for a draft that cannot be opened offline.
The ticket's five short acceptance criteria do not explicitly describe cold detail reopening;
the user confirmed that matching legacy is the intended scope.

Not included: unrelated offline initiation or order creation, automatic requisition upload, new
mutation queues or backend changes. Do not defer legacy-supported offline batch reopening or
product editing. Port each action's actual offline availability rather than inventing a new
blanket restriction or downloading unrelated catalogues. Shared shell changes are limited to registering these feature routes.

## Summary

Users will see which requisitions are saved on this device, find only their saved copies,
and remove a copy without deleting the server requisition. Opening a requisition online will
save the data needed to reopen it without a connection. Saved copies and unsynced edits will
remain separate, so a clean saved copy does not count as work waiting to sync.

Legacy already keeps full copies automatically. The new app currently keeps only edits;
those edits depend on information held in memory or fetched from the server. This work adds
the missing saved copy, clearer availability feedback and safer removal.

## Legacy Today

### View Requisitions

Actual route: `https://test.openlmis.org/#!/requisitions/view`.
The internal state is `requisitions.search`; `/#!/requisitions/search` is not its URL.
The user needs VIEW access and chooses a facility before searching.

- Columns include Offline and actions View Requisition / Remove Offline Requisition.
- Filters include Program, Status, Offline and initiated dates. The Offline URL value is
  local-only and is removed before a normal server search.
- Offline Only, or disconnection, searches locally stored requisitions instead of the server.
- Remove confirms, deletes the full local copy and updates the row. It never calls server DELETE.
- Facility choices are prepared at sign-in and cached for later offline use.

### Approve Requisitions

Route: `https://test.openlmis.org/#!/requisitions/approvalList`.
The visible filter contains Program only. The table includes Offline but no remove action.
Source supports `offline=true` only when a program is supplied; without it the route still
requests the server. Batch selection has separate cached records and a separate offline editor.

### Cache Lifecycle And Legacy Problems

- A successful single-detail online read automatically stores a clean full copy and status
  messages. Successful Save/status actions retain clean copies. Unsynced copies remain separate
  from the newest server response. Legacy also has an `onlineOnly` exclusion store.
- Batch reads similarly cache clean batch DTOs. List Offline markers check either cache.
- A batch-only marker does not guarantee the single-detail View action works offline.
  Removal deletes only the full cache, so it can leave batch-only data behind.
- Local status filtering reads `status` while the route supplies `requisitionStatus`;
  selected sorting is not explicitly applied in local cache paging. Timestamp end-date
  comparisons can exclude part of the final day. These are defects to improve, not port.
- Full records depend on additional cached reference data. Copying the requisition JSON alone
  would not make the React detail page usable offline.

## Agent Brief

### Existing Code And Missing Pieces

- `hooks/use-requisition-draft.ts` stores sparse changes, modified date, ETag and baseline
  headers; it removes unchanged drafts. Preserve this behavior and existing conflict/rebase logic.
- `hooks/use-batch-drafts.ts` stores independent quantities and possibly `unresolvedApproval`.
  These are recovery records, not a complete single-detail copy.
- `lib/unsynced-device-work.ts` counts dirty work. Clean copies must never raise the count.
- `api/queries.ts:requisitionGridQueries` requires products, approved-product identities,
  processing period, currency and program. Detail also reads facility, status messages and
  policy inputs. Those server-only queries currently prevent cold offline opening.
- `features/auth/lib/requisition-access.ts:requireRequisitionView` resolves roles and
  supervision nodes. Generic OfflineAccess has no role definitions or full supervised-facility
  choices, so it is not sufficient by itself.
- `routes/-offline-pages.ts` currently permits only already-open requisition details to remain
  mounted offline; list and cold detail routing must be deliberately extended.

### Stored Data And Publication

1. Add feature-owned complete-copy storage for single and batch representations, separate from
   both delta draft tables. Share identity/readiness helpers, not incompatible payload types.
   Each bundle has owner, format, copy revision/generation, timestamps, full baseline record, exact
   product/approved-product references, rendering/policy references, status messages and compact
   list metadata with facility/program/period ids as well as labels.
2. Add a feature-owned access/choices dataset using `defineDownloadProvider`, registered through
   `routes/-device-work-provider.tsx`. Resolve the existing VIEW and APPROVE rules using fresh
   generic access and role/node lookups. Publish only complete matching generations through the
   coordinator. Refresh on sign-in, force and periodic renewal; never publish partial choices.
3. Reuse GETs already needed on online open. Do not bulk-download every list result or entire
   product catalogue. Resolve the record's versioned availableProducts too, as legacy does,
   so full/non-full-supply pickers remain usable offline. Validate completeness and owner for
   the opened record or batch, then commit atomically. Only complete copies get Offline = Yes.
4. Keep the dirty draft tied to its matching baseline. A background/fresh server response must
   not replace that baseline while changes exist. Preserve it until the existing explicit
   Sync/rebase/Update flow resolves the newer version. Sync retains a clean complete copy.
5. Existing delta-only format-1 records survive upgrade unchanged and remain in unsynced counts.
   They cannot be reconstructed offline. Enrich on the next authorized online open; otherwise
   explain that the user must connect to finish saving the copy. Never delete an orphaned delta.
6. Reserve one new schema version after rebasing; current researched schema ends at 15. Preserve
   all released schemas. Generic ownership helpers, revisioned transactions and session checks
   remain authoritative.
7. Retain clean copies as legacy does. Do not introduce the proposed 50-copy eviction limit.
   Measure realistic single/batch/reference sizes and report quota failures honestly; keep earlier
   complete copies and unsynced work intact. A future retention change needs a separate product
   decision. Never claim availability after a failed commit.
8. Batch-only availability means the batch route is reopenable, not that a full single record
   exists. Preserve legacy's distinction in View actions. Opening a saved batch offline must not
   fetch full single records to manufacture readiness. Keep the existing batch draft overlay,
   per-record errors, exact approval policy and unresolved-attempt recovery.
9. Confirmed removal must survive in-flight captures and already-open writers. A later deliberate
   authorized online open can create a new copy: legacy list removal deletes the full cache
   without adding an `onlineOnly` exclusion. Do not invent permanent removal preferences.
   Retain minimal coordination metadata to reject stale work, without retaining deleted payloads.

## Decisions

The user confirmed: "Can you simply match the Legacy here?" This supersedes the earlier
proposal to add Approve filtering or defer batch reopening/product behavior.

1. Automatically keep complete single and batch copies, including clean copies, and reopen them
   offline. Preserve existing revisioned edits and conflict/recovery safeguards.
2. Match View's Offline filter/removal and Approve's Offline marker and Program-only visible
   filter. No new all-program offline browsing or extra Approve Offline control.
3. Match offline editing and local autosave. Add no new Save control. Sync and actual server
   operations still need a connection. No new queue or silent resend policy.
4. Retain clean copies without the proposed 50-copy eviction limit. Protect confirmed removal
   against stale writers and never evict dirty work or uncertain-attempt evidence.
5. Keep the existing app's owner-scoped Dexie store, phone cards, translations and accessibility.
   Do not copy legacy's status/date/sort defects, unsafe races or obsolete ApplicationCache.
6. A batch marker does not imply a full single-detail copy. Make the appropriate saved route
   available rather than suppressing batch readiness or fabricating a single copy.
