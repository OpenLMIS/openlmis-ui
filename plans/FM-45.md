# FM-45: Approval List

https://openlmis.atlassian.net/browse/FM-45 · Parent: [FM-39] Requisitions

Shipped in one PR with [FM-43] (approve mode), branch `feat/fm-45-43-approve`. Approve mode is
planned in [FM-43](FM-43.md); this plan covers the list.

## Scope

- New Approve Requisitions page at `/requisitions/approve`, the live `nav.requisitions.approve`
  entry.
- Selection, the same-program note, Select All/None and View Selected Requisitions behind
  `BATCH_APPROVE_SCREEN`, as legacy. Until [FM-46] ships, View Selected opens legacy's batch
  approval screen (Decisions).
- Not in scope: the batch approval screen itself ([FM-46]); the Offline column, which needs the
  requisition offline pass and moves to [FM-191] with View Requisitions' Offline column.

## Summary

Approvers use this page to see every requisition waiting for their approval. In legacy it is a
paged table, newest authorized first with emergency requisitions on top, with a Program filter
and a View Requisition button per row. When batch approval is switched on for the deployment,
rows get checkboxes and View Selected Requisitions opens several requisitions of one program
together.

The new page keeps all of that, keeps sort, filter and page in the address so reload and Back
work, shows cards on phones, and refuses users without the approve right instead of showing them
an empty table. Opening a requisition and approving or rejecting it returns to the same page of
the list.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| List | `GET requisitions/requisitionsForApproval` | `program?`, `page`, `size`, `sort=emergency,desc` then `sort=authorizedDate,desc\|asc` | `id, emergency, program.{id,name}, facility.{code,name}, processingPeriod.{name,startDate,endDate}, statusChanges.SUBMITTED/AUTHORIZED.changeDate, extraData` | APPROVE roles by node | `requisition-approval.routes.js`, `RequisitionService.java:433-455` |
| Program options | none: from every role assignment whose role holds APPROVE, home facility or supervisory node, with a program (`userRecordOptions`, `rolesOptions`), named through `programsOptions` | | | | `requisition-approval.service.js:91,123-134` |
| Dates | `GET /localeSettings` (`deploymentTimeZoneOptions`) | | time zone | public | Date Submitted and Authorized are timestamps |

Unknown sort fields such as `program.name` return 500 (`RequisitionRepositoryImpl.java:612-641`),
so only the Date Authorized order is offered, as legacy; `emergency,desc` always goes first.

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.approve.tsx`; loader awaits
  `requireRight(queryClient, RIGHTS.requisitionApprove)` and prefetches the page, the user record,
  roles, programs and `deploymentTimeZoneOptions`, unawaited. `pendingComponent` with the real
  header and `DataTableSkeleton`.
- Search schema: `tableSearchSchema(['authorizedDate'])` with `dir` (default desc, Newest
  Authorized; asc is Oldest Authorized), page and size (default 20, as View Requisitions),
  `program` (uuid). Defaults stay out of the URL. Sort is a Date Authorized header sort and goes
  to View for cards (`searchSort`).
- Program options are computed in the route from the user record, roles and programs (features
  cannot import auth) and passed to the toolbar as props.
- `approvalListOptions(search)` under `queryKeys.requisitions` (refreshed by FM-41's action
  invalidation); `useDeferredValue` rows, `DataTableSkeleton` first load, dimmed later.
- Selection: by id with program id and a label, across pages, cleared on filter or sort change
  (`useFilterScoped`, with a value type holding program id and label); only rendered with
  `useFlag('BATCH_APPROVE_SCREEN')`. View Selected is hidden when `useBackToLegacy` reports no
  legacy UI.
- Return state: `RequisitionReturn` becomes a union of Create/Authorize and Approve targets;
  `returnState(target)` in `lib/requisition-return.ts` builds either.
  `RequisitionError` picks its back label from the target (new `requisitions.requisition.back-approve`). The detail breadcrumb parent stays View
  Requisitions (Decisions).

### Rules

- Same-program check on every selected row, not the visible page; none selected or mixed programs
  open an AlertDialog with legacy's messages and keep the selection.
- Facility cell `code - name`; dates plain dates in the page language; split partner copies

- Program filter options: programs of every APPROVE role assignment, home facility or
  supervisory node, as legacy, sorted by name.

### Risks And Edge Cases

- A program offered by the filter may return no rows (home-facility APPROVE, or nothing
  pending); the no-matches state with Clear Filters covers it.
- The list shrinks as records are approved; a page past the end clamps, as AGENTS.md.

## UI/UX

**Port**: columns, sort options, Program filter, View per row, selection behind the flag, the
note and both errors.

**Improve**: route guard with No Access; one toolbar (Filters, View, Sort in View for cards);
Clear Filters works; Emergency as `FlagBadge`; selection survives paging; cards on phones; return to
the same list page after approve or reject.

**Drop**: legacy's Search/Cancel inside the filter (filters apply live); the Offline column until
[FM-191].

## Decisions

- **View Selected opens legacy batch approval** until [FM-46], through the leave-guarded Back To
  Legacy path, so deployments with `BATCH_APPROVE_SCREEN` keep the capability (user, 2026-10-30).
- **Page size 20**, as View Requisitions, instead of legacy's 10.
- **Selection keeps ticks across pages**, unlike legacy's page-only selection; the same-program
  check covers every tick.
- **The requisition page's breadcrumb stays Requisitions / View Requisitions** when opened from
  this list; the footer actions and the error back link return here.
- **Offline column moves to [FM-191]** with the rest of requisition offline.

## Implementation Notes

- Browser, Arabic visual and live network checks are deferred to review, as the build brief
  forbids browser use and server access. All transport in workflow tests is mocked.
- Date Authorized uses the shared sortable header and card View sort controls. The default
  remains newest authorized with emergency requisitions first.
- Selection and Clear remain available without a neighboring legacy UI; only View Selected
  is hidden. An empty later page also clamps to page one when no pending records remain.
- View Requisitions and Approve Requisitions share cells, View actions, table/card rendering,
  skeletons and column/card definitions through `components/requisition-list-parts.tsx`.
- Selection labels use the translated Emergency label; the empty list has its own explanatory
  sentence rather than repeating the page description.
