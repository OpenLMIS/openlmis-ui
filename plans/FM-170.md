# FM-170: Global App Configuration (Branding, Theme & Feature Flags)

https://openlmis.atlassian.net/browse/FM-170 · Story · Subtasks: FM-171 Spike: where the
app configuration lives, FM-172 Load app configuration at startup, FM-173 Branding
settings page, FM-174 Theme selection, FM-176 Feature flags managed in the UI

This is the umbrella plan. Each subtask has its own plan with the detail; this file holds
what they share and the order they ship in.

## Summary

Every OpenLMIS deployment wants its own logo, name and colours, and its own set of
optional features. Today all of that is fixed when the UI is built, in legacy and in the
new app alike: a new logo means a new image, and a feature flag means editing an
environment file and restarting a container.

After this story an administrator opens **Administration > System Settings** and changes
the logo, the app name, the colour theme and the feature flags. Everyone gets the change
on their next page load. Nothing is rebuilt or redeployed.

No OpenLMIS service can store this today, so the backend gets one small addition in
referencedata: a single configuration record that anyone can read (the login page needs it
before sign in) and only an administrator with the System Settings right can change.

## Legacy Today

- Branding is compiled in. Country forks (Malawi, Angola, SELV, SIGLUS) rebrand by
  overriding image files, SCSS variables and `applicationTitle`, then rebuilding. The tab
  title is always "OpenLMIS" on test.openlmis.org, the login and header logos are CSS
  background images with no alt text.
- There is no dark mode, no theme choice and no settings page for any of this.
- Feature flags are container environment variables written into the bundle at start
  (`featureFlagService`). On test.openlmis.org one placeholder was never filled
  (`${CATCHMENT_POPULATION_CALC_AUTO}`), and neither was the analytics id (`UA-CHANGE-ME`):
  build-time config gets forgotten in practice.
- The only runtime config legacy reads is `GET /localeSettings`, after sign in, cached in
  localStorage. Screenshots: `.screenshots/FM-170/legacy-*.png`.

## Shared Decisions

| Decision | Reason |
|---|---|
| One configuration record in referencedata, `/api/appConfiguration` | referencedata already has a public read (`/localeSettings`), the change history (Javers), Redis, and the `SYSTEM_SETTINGS_MANAGE` right. A new service would add a container to every deployment for one table. Detail in FM-171. |
| Public read, admin write guarded by `SYSTEM_SETTINGS_MANAGE` | The login page needs the logo and name before sign in. The right already exists in every database and guards fulfillment's system settings, so no new right. |
| Built-in defaults live in the UI, the database stores what an admin changed | The app always starts, even when the backend is old, down or has never been configured. |
| Feature flags: admin value, then deployment `config.json`, then code default | Existing deployments keep their `BATCH_APPROVE_SCREEN=true` style env vars on day one, and an admin can still override. |
| Config is loaded at boot into a module store, not only the Query cache | The Query cache is cleared on every user change (`src/integrations/tanstack-query.ts:25`), and the login page needs it with no user at all. |
| One page, **Administration > System Settings**, with Branding, Theme and Feature Flags tabs | One place for deployment-wide settings, named after the right that guards it. The header renders once in the layout route, as on Profile. More settings become new tabs. |
| One PR per subtask, in order, from this worktree | Each stays reviewable; later ones build on FM-172's store. |

## Order

1. **FM-171** spike: decision record and the referencedata change (a PR in
   `openlmis-referencedata`, not this repo).
2. **FM-172** boot loading, defaults, last-known cache, flag registry skeleton. Works
   before the backend ships: a 404 means defaults.
3. **FM-173** System Settings page with the Branding tab.
4. **FM-174** Theme tab and presets.
5. **FM-176** Feature Flags tab.

Defaults taken for the smaller questions, recorded in the subtask plans: SVG logos refused
(FM-171), the favicon uses the logo (FM-173), the user's theme switch gains a way back to
the default (FM-174), the legacy flags are shown now with a badge (FM-176), and dual boot is
documented rather than solved: a flag changed in the new UI does not reach legacy screens,
which keep reading their container env (`docs/deployment/deployment.md`, FM-176).
