# FM-62: Stock management (epic research)

https://openlmis.atlassian.net/browse/FM-62

Shared research and roadmap for the whole epic, done before any story plan. It covers the
administration already migrated, the foundations delivered with each stock screen, and
the stock stories themselves. Missing shared pieces are built with their first consumer,
rather than all being prerequisites before stock work can start. Each
story still gets its own `plans/<KEY>.md` before code; this file is the shared ground they
build on. Screenshots of every legacy screen are in `.screenshots/FM-62/` (desktop, phone,
admin).

Backend behaviour the UI works around along the way is recorded under FM-177 Potential BE
improvements, one ticket per finding.

## Summary

Stock Management is the menu storeroom managers use every day: record stock going out
(Issue), coming in (Receive), corrections (Adjustments), opening kits (Unpack), counting
(Physical inventory), and looking it up (Stock on Hand, Stock card, Transaction History).

Legacy works, but it is slow and fragile with real product lists. On a program with 10,000
approved products, it downloads all of them before showing a screen, although only the few
with stock are offered. Receive takes 26 to 45 s, Adjustment about 42 s on UAT. Physical
inventory cannot even save a draft for such a program: the server refuses the 1.2 MB
request, and the "All changes are saved" indicator is wrong, because the local copy does not
fit in browser storage. The backend already has paged and filtered endpoints that fix most
of this, so the new UI can be much faster without backend changes.

The epic has no separate phone screens: each screen is responsive and replaces both the
desktop and the legacy React phone version.

  `programId` and `facilityId`, the pair the existing source/destination endpoints accept.
- Merged FM-143 supplies shared orderable search and by-ID/by-trade-item lookups.
  Reuse those additions; a stock lot lookup still needs its own shared query.
- FM-9 and FM-10 contain wider requirements than the first stock screen needs. Reuse the

### Contracts And Acceptance Gaps

- Use the v2 stock-summary contract for FM-69 initially. It provides product grouping,
  fulfillment/lot entries, code/name/lot filters and `nonEmptyOnly`. The v1 contract pages
  individual stock cards and has no equivalent filters, so it is not a drop-in replacement.
  Measure v2 on the large program before promising a load time; server paging does not
  mean the server avoids building the full set before paging.
- The v2 endpoint does not accept an `includeInactive` filter. Legacy filters child stock
  card entries by their `active` flag after paging, removes empty groups, but keeps the
  server's page total. It uses the unfiltered summary for doses and visible children for
  packs. FM-69's plan must resolve consistent displayed rows, totals and balances.
  `nonEmptyOnly` means a summary has card entries, not a positive balance.
- Stock Card expands physical-inventory adjustments into individual reason rows and
  reconstructs their running balances before pagination. Preserve this in FM-70, along
  with document/reversal links to FM-76 detail or an explicitly documented legacy handoff.
- Stock on Hand printing produces the facility/program report; its legacy endpoint does
  not accept the screen's product/lot/inactive/page filters.
- The v1 endpoint explicitly needs `STOCK_CARDS_VIEW`. Do not use it for event product
  pickers without checking access for a user who holds only `STOCK_ADJUST`.
- FM-69 and FM-70 explicitly require offline data in Jira. The agreed online-first delivery
  is an initial milestone, not completion of either story. Record the remaining offline
  acceptance checks in each story plan and keep them open until the offline pass covers them.
- FM-63 requires working target screens and Physical Inventory draft status. A shared
  program table can be delivered with the first event, but five links to missing pages
  would not satisfy the story.
- Each selected story still needs its own plan with the full API map and acceptance checks.
  This review updates the epic's sequencing; it does not authorize implementation or
  changes to Jira.

Other findings:

- **Rights are per facility and program.** Legacy checks `RIGHT|facility|program`
  permission strings in the browser. For stock-event submission, the server also requires
  the user's home facility to support the program (`403 program.not.supported`).
- **Transaction History and reversal need stockmanagement 5.4.0.** They do not exist in
  5.3.1, and only movements recorded on 5.4.0 or later can be reversed.
- **Unpack events carry no `eventOrigin`**, so they never show in Transaction History.
- **Physical inventory "autosave" is local only**, and silently fails when browser
  storage is full. The server keeps one draft per program and facility, shared by all users.
- **Issue, Receive, Adjustment and Unpack lines are in memory only**: a reload loses them.
- **The offline queue removes an event before sending it**, so a failed send can lose it.
- **Validation gaps:** "1.5" becomes 15; a future date is accepted by the client (the server
  rejects it); an end date before the start is accepted; Unpack shows no over-stock error;
  raw translation keys and wrong messages ("Adjustments have invalid fields" on Issue).
- **Packs/Doses:** quantities are stored in doses; packs input is
  `packs x netContent + remainder`. The toggle shows only when the `QUANTITY_UNIT_OPTION`
  flag is `BOTH`, default unit Doses.

## Agent Brief

### What already exists in the new UI

- Nav: the Stock Management group is in `NAV_GROUPS` with six `'#'` entries
  (`src/lib/config.ts:94`). No Transaction History entry yet.
- Translations: nav labels and stock right labels only.
- Patterns to copy: Users list (server-paged list), Edit User Roles (draft page,

  with inline fields), add-role dialog (lookups in a form dialog).
- Offline: `getLocalDb()` with no tables yet, `useOnline`, `useOfflineFailure`.

### What is missing

- **Rights per facility and program.** `toRights()` keeps only the right name
  (`src/features/auth/lib/rights.ts:15`). Stock needs grants `{right, facilityId,
  programId}` from the same permission strings, and `STOCK_*` in `RIGHTS` and `NAV_RIGHTS`.
- **Home facility context:** a shared read of the user's `homeFacilityId`; the facility
  itself is already available through `reference-data`'s `facilityOptions(id)`.
- **Stock lookups:** orderables, lots, valid reasons, valid sources and destinations, approved
  products. Stock-owned queries: stock card summaries, stock cards, physical inventories,
  stock events.
- **Components:** editable line table (the `DataTable` is read-only and truncates cells),
  Packs/Doses fields and toggle, quantity formatting and authenticated PDF printing.
  Date fields, calendar/date formatting, checkboxes, confirm dialogs and row selection
  already exist; reversal still needs its own per-line rules.

### Server-side work: how to avoid legacy's slowness

| Need | Endpoint | Local cost |
|---|---|---|
| Products with stock (Issue, Adjustment, Unpack) | v1 `GET /api/stockCardSummaries?program&facility&page&size` (DB paged, orderable and lot resolved) | 1.4 s |
| One product's stock | `GET /api/v2/stockCardSummaries?facilityId&programId&orderableId=` | 0.9 s |
| Receive product search | `GET /api/facilities/{id}/approvedProducts?programId&orderableCode/orderableName&page&size` | 0.7 s |
| Lots of one product | `GET /api/lots?tradeItemId=` | fast |
| New lot on Receive | `lot:{lotCode, expirationDate}` in the stock event (5.4.0) | Backend can create inline lots without a separate lot POST; legacy's UI gate still needs a story decision |
| Stock on Hand | v2 with `nonEmptyOnly=true&page&size` | 6-7 s on the server for a large program; v1 cannot preserve grouping and filters, so compare only approaches that preserve those capabilities |

Product pickers search the server as the user types instead of loading every product.

Legacy Receive and add-product dialogs gate new lots with `LOTS_MANAGE`; physical inventory
creates lots before draft save. Preserve the gate unless the corresponding story explicitly
approves changing it. Backend inline-lot support alone does not establish unchanged UI parity.

### Submit contract

`POST /api/stockEvents` with `{programId, facilityId, signature, eventOrigin, lineItems}`.
`sourceId`/`destinationId` are the valid source/destination `node.id`, not the facility id.
Physical inventory submits the same endpoint with `resourceId` and absolute quantities.
Reverse is `POST /api/stockEvents/{id}/cancel`, with per-line `lineErrors` on a 400.
Stock events are not idempotent: a submit with an unknown result is never resent blindly.

### Test data

The local demo data cannot exercise most of this: no kits, every lot expired, no events
in Transaction History, only 2 Essential Meds products with stock, one VVM product without
stock. Read-only data is enough to begin FM-69/FM-70. Event and reversal checks need a kit,
current lots and useful events. Use disposable fixtures or obtain explicit authorization
for seed writes; the shared server stays read-only during routine browser checks.

## Decisions

- **Core administration first.** The setup screens stock depends on were migrated first.
  Data Import is deferred by the user on 2026-10-05; stock uses existing backend data and
  does not need a migrated bulk-import page.
- **Online first.** Every screen is built and shipped online; offline comes after, in one
  pass over the screens legacy runs offline.
- **Full parity with legacy.** Same screens, fields, rules and flows; no behaviour
  changes. What changes is how the data is loaded (paged and searched on the server), so the
  screens are fast, and legacy's defects are fixed: the 413 on draft save, storage quota
  failures, "1.5" read as 15, unchecked future and reversed dates, raw keys, wrong messages.
- **Target the latest backend**: stockmanagement 5.4.1 as of 2026-10-05. Transaction
  History and reversal require 5.4.0 or later; their contracts are unchanged in 5.4.1.
- **Offline as legacy.** Issue, Receive, Adjustment, Physical inventory (list and draft),
  Stock on Hand, Stock card and the pending offline events work offline after an online
  visit; Unpack and Transaction History do not. Receive offline keeps the program's
  approved products on the device (about 10 MB for Essential Meds), in Dexie, never
  localStorage.
- **Barcode scanning is in scope** for the event screens, shown when the deployment turns
  it on, as legacy's `GS1_SCANNING` flag does.
- **Packs/Doses follows the deployment flags** (`QUANTITY_UNIT_OPTION`,
  `DEFAULT_QUANTITY_UNIT`), as legacy.
- **Physical inventory lists every approved product**, grouped by category, as legacy.
  The draft save sends only lines that hold a count, reason or VVM status, so a large
  program never hits the 413; the grid still shows every line.
- **Unpack sends no `eventOrigin`**, as legacy, so unpacks stay out of Transaction History.
- **Responsive screens only**, no phone copies, as the epic says. The phone layout of
  each screen follows the legacy phone flow where one exists (physical inventory one line
  per step, Stock on Hand rows that expand into lots).
- **Keep legacy's rules where the server does not enforce them**: quantity vs stock on
  hand per reason type, unaccounted quantity 0, expired lots hidden on Issue, new lot expiry
  not in the past, date not after today.
- **Physical inventory Submit stays blocked until every active line has a count**, as
  legacy, even for a program of 10,000 lines. Making large inventories lighter is later
  work, outside this epic.

## Steps (proposed order)

1. **Admin Tier 1**, ordered so each screen's pickers reuse the lookups the one before
   built: Facility types, Programs, Facilities (list + add, edit), Products (list + add, then
   the four edit tabs), Lots, Reasons, Valid sources and destinations. These are shipped.
   Data Import is deferred and not a stock prerequisite.

   home facility lookup, stock-view rights/nav, the FM-18 picker, summary/card queries,
   product/lot hydration, quantity formatting and authenticated PDF printing. Defer event
   lookups, editable controls and event fixtures until their consumers.

   lookups and packs/doses display.
4. **FM-70 Stock card + FM-76 Event detail**, then **FM-71 Transaction history** list (FM-75).
