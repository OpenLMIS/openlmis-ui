# FM-101: Update Status And Transfer

https://openlmis.atlassian.net/browse/FM-101 · Parent: FM-97 Cold chain equipment

## Scope

- Equipment Functional Status and Transfer as two more modes of the FM-100 equipment dialog, in
  the list URL; they replace the legacy links from the list and the details.
- RTM alerts in the status mode with Dismiss and View History (alert history report), as legacy.
- No backend change. Builds on `feat/fm-100-equipment-details-edit` (PRs #122, #125, #127).
  Kept small: reuse FM-99 and FM-100 parts, tests for workflows only.

Research baseline, 2026-11-04: legacy walked on the local ref-distro (cce 1.5.2) as administrator,
divo1, vsrmanager1, wclerk1, every write stubbed. Evidence in `.screenshots/FM-101/`.

## Summary

Managers mark equipment as working or broken and move it to another facility.

Legacy opens "Equipment Functional Status" from the list's pencil or the details: the item, its
current status and active RTM alerts (dismissable, with an alert history report), then a status
select that asks for a reason for Awaiting Repair and Unserviceable and a decommission date for
Unserviceable. Update is never disabled; errors show behind "This form is invalid". Transfer
picks a program, facility and year of installation; no demo role holds the transfer right, so on
UAT the modal showed only the name and Cancel.

The new UI shows both in the same dialog as the details. Update stays disabled until the form is
complete, reads the item fresh, saves only the status and shows the change in the list. Transfer
offers only facilities the user may transfer to.

## Legacy Today

- Status `#!/cce/inventory/<id>/statusUpdate`: title Equipment Functional Status; name; Facility,
  Equipment Type; Current Status. RTM Alerts block when the item has alert records: View History,
  each active alert with Dismiss (EDIT), start time and English text, or "No active alerts".
  Update Functional Status (EDIT): select prefilled with the current status (Functioning, Awaiting
  Repair, Unserviceable, Needs attention); reason (7 options) for Awaiting Repair and Unserviceable;
  Decommission Date for Unserviceable; changing the status clears both. Update never disabled.
  Dirty Cancel asks. Save: whole-record PUT, toast, back to the previous screen, list reloaded.
- View History opens the "CCE Alert History" PDF (alerts of the past 30 days) in a new tab.
- Transfer `#!/cce/inventory/<id>/transfer`, from the details for CCE_INVENTORY_TRANSFER: facility
  program picker (rights of the last module, not TRANSFER), year of installation (1900-2100);
  `PUT .../transfer`; English toasts hardcoded. No demo user holds the right.
- vsrmanager1 (VIEW) gets a read-only status view; wclerk1 not authorized.

### Data Flow

- `inventorySearchSchema`: `edit: true` becomes `action: 'edit' | 'status' | 'transfer'`, in
  `CLOSED_INVENTORY_DIALOGS`; the loader drops `edit` and `status` without EDIT grants and
  `transfer` without TRANSFER grants; the guard watches `action`.
- The list's pencil opens `item=<id>&action=status` (new entry); the details buttons replace with
  history state kept. Cancel returns to the details; Update and Transfer close the dialog.
- Alerts read `inventoryAlertsOptions([id])`; the status form waits for their first answer under the
  dialog skeleton, so arriving alerts never move it; a failed load shows an error with Try Again.
  Dismiss marks the alert dismissed in the cache, then invalidates `inventoryItems.all`.
- Update: fresh GET, `toStatusUpdate`, PUT; Transfer: PUT. Both, and FM-100 Edit, share
  `useItemSave`: wait for `inventoryItems.all` except alerts (Transfer: the lists only), invalidate
  `home.all`, toast, close (Edit returns to the details). A failed refresh after a saved PUT still
  counts as saved: toast and close, never a save error that a retry would send again. A failed
  `/cceAlerts` never blocks the form.

### Rules

- Statuses and reasons as legacy (status order as the app); reason for Awaiting Repair and Unserviceable, date for
  Unserviceable; changing the status clears both; the status starts at the current one.
- Update and Transfer disabled until valid (Decisions). The status form validates after the first
  Update (asterisks mark required fields); Transfer validates on change so the year range shows.
  The first focused control in status mode follows DOM order (View History once alerts are cached).
- The status PUT keeps every other field of the fresh record, power as FM-100.
- Transfer targets come from TRANSFER grants (with VIEW), not from VIEW/EDIT as legacy: Program,
  then its granted facilities, without legacy's My/Supervised switch; submit labelled Update as
  legacy.
- Year of installation uses the FM-99 rule (1000-9999).
- No code comments; types hold only the fields the screens read.

### Risks And Edge Cases

- Nobody on the demo data holds TRANSFER, so transfer is checked against stubs only.
- The alert history report covers only the past 30 days; demo alerts are from 2018.
- A status change sends a server notification; real saves only with the user's go-ahead.

## UI/UX

**Port**: status modal content and order, statuses, reasons and rules, alerts with Dismiss and
View History, transfer fields, rights per item.

**Improve**: modes of one URL dialog; Update disabled until complete with messages at the fields;
fresh read before the PUT; transfer targets that the server accepts; translated toasts; alert
text in the page language.

**Drop**: the read-only status view for VIEW users (AC 7, Decisions). View History stays the
alert report.

States: loading, not found, no access, load error with retry, saving, server error, no alerts.

## Decisions

- **View History opens the RTM alert history report, as legacy** (user, 2026-11-04); AC 5's
  status history needs a backend endpoint master lacks.
- **Update disabled until the form is complete** (user, 2026-11-04), as the ticket asks.
- **Transfer in this PR** (user, 2026-11-04): program, facility and year of installation, the
  fields the server requires; checked against stubs.
- **Dismiss alerts as legacy** (user, 2026-11-04).
- **One dialog with modes** (`action`), so the details, edit, status and transfer replace one
  another.
- **Status order as the rest of the app** (user, 2026-11-04): Functioning, Needs Attention,
  Awaiting Repair, Unserviceable; legacy lists Needs attention last.
- **Reason and date as legacy and the server** (user, 2026-11-05): a reason for Awaiting Repair
  and Unserviceable, a decommission date for Unserviceable only; Needs Attention asks for
  neither, although AC 3 names both for every non-functioning status.
- **Status pencil and Update Status for EDIT only** (user, 2026-11-04), as AC 7; legacy also
  gives VIEW users a read-only status view.
