# FM-130: Requisition Group Add/Edit

https://openlmis.atlassian.net/browse/FM-130 · Parent: FM-124 Admin: facilities & supply chain

Ships in one PR with [FM-129](FM-129.md) (list) and [FM-131](FM-131.md) (view). This plan
carries the shared detail: API map, data flow, files, rules and tests for all three. Epic
context: [FM-39](FM-39.md), Tier 1 row 3.

## Scope

- **Add and Edit pages** for a requisition group: one editor with Name, Code and Supervisory
  Node, then two tabs.
  - Programs And Schedules: rows added from a dialog, each removed with a trash button.
  - Facilities: members, with a name filter and pages, added one at a time from a dialog
    (legacy's single pick from every facility) and removed with a trash button.
- **The same editor in read-only mode** for [FM-131](FM-131.md).
- **Shared pieces:**
  - a processing schedules lookup in `reference-data`, to the contract the FM-144 build uses;
  - `zone-filter.ts` moved unchanged from Facilities to `reference-data`, as the Nodes build
    plans to;
  - Products' `program-filter.ts` moved to `reference-data`, so the list can use it.

Out of scope:

- deleting a group: legacy has no delete, and the API marks it "avoid using";
- the group's description: legacy never shows it; it is kept on save;
- the audit log.

## Summary

A requisition group joins a set of facilities (its members) to one supervisory node and gives
it, per program, the processing schedule whose periods those facilities requisition for. That
link is what lets a facility start a requisition at all, and it decides who supervises and
approves it. Saving a group changes which facilities supervisors can see.

In the old UI, Add and Edit are the same full page. It has Name, Code and Supervisory Node, then
two tabs:

- **Programs and Schedules:** a row of Program, Processing Schedule, Drop Off Facility and
  Direct Delivery, with Add. The table under it has a Remove button per row.
- **Facilities:** pick one facility from a list of all 2,734 and press Add. The member table
  shows Facility Name, Geographic Zone, Facility Type, Facility Enabled and Remove. It has a
  name filter and pages of 10.

Everything is sent with one Save. It works, but:

- **Filtering or paging the members loses unsaved changes**: the page reloads the group from
  the server.
- **Save skips the form check**, so a missing name reaches the server.
- **Some saves fail with a server error.** Leaving Direct Delivery unticked can do it, and so
  can a second schedule for the same program, which legacy allows but the server refuses.
- **A refused duplicate facility still shows** in the members table on Edit.
- Edit says "Created requisition group successfully".
- Adding members one by one is slow for groups of 300.
- The bottom bar covers the last rows.

The new screens keep the same fields, tabs and single Save, and fix those:

- **Members:** the filter and pages never touch the draft.
- **Members are added as in legacy:** pick one facility from every facility, by name. Members
  already in the group are not offered.
- **One schedule per program**, as the server requires. A program already listed is not offered
  again.
- **Checks before saving:**
  - required fields, and the server's 50-character limits, are checked before anything is sent;
  - Save opens the tab with the first problem;
  - leaving with unsaved changes asks first.
- **Messages:** "Requisition Group Saved" for both Add and Edit, and the server's own message
  when it refuses (a code in use, or a node that already has a group).
- **Layout:** the footer never covers the tables, and the page works on a phone and in Arabic.

**Save body** (built by `toRequisitionGroupBody`):

```json
{
  "id": "<edit only, equal to the path id>",
  "code": "RGFP1",
  "name": "RG Family Planning 1",
  "description": "<as read; omitted on add>",
  "supervisoryNode": { "id": "..." },
  "requisitionGroupProgramSchedules": [
    {
      "id": "<kept for saved rows, omitted for new ones>",
      "program": { "id": "..." },
      "processingSchedule": { "id": "..." },
      "directDelivery": false,
      "dropOffFacility": { "id": "..." }
    }
  ],
  "memberFacilities": [{ "id": "...", "code": "..." }]
}
```

- **Members need `code`.** The server builds the member set as a `HashSet<Facility>` whose
  equality uses the code (`Facility.java:178`). Bare `{id}` items would all have a null code
  and collapse into one member.
- **`directDelivery` is always a boolean.** The server unboxes it, so legacy's unticked box
  (undefined) can fail with a server error.
- **`dropOffFacility` is omitted** when none is picked.
- **The body `id` equals the path on PUT.** The server loads by the path id but uses the body id:
  - for the duplicate-code check: without it, the group finds its own code and fails
    `code.duplicated`;
  - for the node-assigned check;
  - as the parent of new schedule rows.
  A PUT to an unknown id would create a new group, so the edit route reads the group first.
- **Saved schedule rows first, new rows last.** `updateProgramSchedulesListFrom` matches each
  saved row with `obj.getId().equals(...)`. A new row (null `id`) placed before a match throws,
  and the save fails with a 500. `toRequisitionGroupBody` orders them, whatever order the table
  shows.
- **A program removed and added back reuses its saved row id.** The table is unique on group
  and program, and Hibernate inserts before it deletes orphans. A new row for a program that
  still has a saved row would therefore break that constraint. With the reused id, the server
  updates the schedule, drop-off and direct delivery in place.
- **PUT replaces wholesale.** Members are replaced; schedules are reconciled by item id, and
  any left out are deleted.
- **A missing processing schedule is a 500**, not a validation error; the dialog's schema is
  the only guard.

**Server errors** (`referenceData.error.requisitionGroup.*`), shown through `serverMessage` in an
`ErrorAlert`:

- `code.required`, `name.required`, `supervisoryNode.required`, `supervisoryNode.nonExistent`;
- `code.duplicated` "The Requisition Group code cannot be duplicated";
- `supervisoryNode.assigned`: the node already has another group;
- `requisitionGroupProgramSchedule.program.duplicated`;
- the `*.tooLong` limits (name and code 50, description 250);
- `facility.nonExistent`.

`description` and `dropOffFacility` are left out of the detail JSON when empty, so they are
optional in the types.

Saving publishes `RegenerateRightAssignmentsEvent`, which rebuilds permission strings after
commit, asynchronously (`RequisitionGroupController.java:211`).

### Data Flow

- **Routes**, all requiring `REQUISITION_GROUPS_MANAGE`:
  - `/administration/requisition-groups/new`
    (`_protected.administration.requisition-groups_.new.tsx`);
  - `/administration/requisition-groups/$id/edit`
    (`_protected.administration.requisition-groups_.$id_.edit.tsx`);
  - the view, `/administration/requisition-groups/$id`
    (`_protected.administration.requisition-groups_.$id.tsx`), in [FM-131](FM-131.md).
  - Each sets `staticData.crumbKey`, so the trail is Home / Administration / Requisition Groups
    / Add, Edit or View, with Requisition Groups linked.
- **Edit loader:**
  - `preload: false`;
  - on `cause !== 'stay'`, `fetchQuery({...requisitionGroupOptions(id), staleTime: 0})`
    alongside `requireRight`;
  - on `stay` (tab, member filter or page changes), `ensureQueryData`, as
    `reasons_.$id.tsx`. The detail is up to 613 kB and must not be read again on every tab
    switch.
  - A 404 shows the not-found panel, as `facilities_.$id.tsx`.
  - The PUT sends the whole record. The fresh read on entry is the guard, as Edit Facility: no
    second read before saving, since this screen owns every field it sends except
    `description`, which it passes through.
- **Lookups:** both routes prefetch nodes, programs, schedules and minimal facilities without
  awaiting them (`prefetchRequisitionGroupLookups`). Each lookup field sits in its own
  `LookupBoundary`.
- **URL:**
  - `tab` (`programs` default, `facilities`);
  - the members table's `q`, `page`, `size`, `sort`, `dir`: plain keys, since the editor has
    one URL table, as Edit User Roles (`tableSearchSchema([...]).extend({tab, q})` in
    `users/lib/roles-search.ts`);
  - filter typing replaces history; paging adds entries;
  - tab and member state never remount the editor or reset the draft.
- **Return to list:** the list links pass `requisitionGroupsListSearch` in history state. New,
  edit and view snapshot it once, and Save and Cancel navigate back with it, as Reasons.
  - Every editor search update (tab, member filter, page, sort) keeps it, with
    `state: (previous) => previous`, as the facility editor's tab navigation does.
- **Leaving while saving:** `useDiscardGuard(changed, {pending: mutation.isPending, allowLeave})`.
  Cancel is disabled while saving, and `leaving` is set only after a successful save. In
  `readOnly` the guard is off (nothing is dirty) and submission returns early.
- **Keys** (`src/lib/key-factory.ts`):
  - `requisitionGroups` scope: `list(body+paging)` and `detail(id)`;
  - `processingSchedules` scope: `list()`;
  - member search reuses Facilities' `queryKeys.facilities.list(query)`, moved to
    `reference-data` (Change below), so facility saves refresh it.
- **After a save:**
  - invalidate `queryKeys.requisitionGroups.all`;
  - the signed-in user's permissions are not refreshed (Decisions);
  - toast, then go back to the list.

### Risks And Edge Cases

- **Large groups:** 336 members render one page at a time; the filter runs over the draft
  array, so it stays cheap.
- **Two admins editing one group:** there is no version; last save wins, as legacy. The fresh
  read on entry is the guard.
- **A group deleted through the API while Edit is open:** the PUT would recreate it under a new
  id. There is no delete in any UI, and the API marks delete "avoid using". Checking first
  would mean another read of up to 613 kB (about 1 to 4 s) on every save, and it would still
  only narrow the race. So the save does not check first; the risk is accepted.
- **Rights after save:** the server rebuilds permission strings asynchronously after the save.
  An admin who supervises through this group sees the change on the next sign-in, as legacy.
- **Drop-off names** come from the minimal facilities lookup. Until it loads, the cell shows a
  skeleton; a facility missing from it shows its id.
- **Real saves** run on test.openlmis.org only after the user approves each one. Use a new
  group with code `FM130-TEST` and a node with no group. Groups cannot be deleted through the
  UI, so prefer a single create and one edit of it.

## Decisions

- **One editor component** for Add, Edit and View (`readOnly`), as the tickets ask.
- **One schedule per program**, enforced in the dialog, because the server refuses more.
  Legacy's looser client check is a defect.
- **Members are picked one at a time, as legacy** (agreed 2026-10-14): a `ComboboxField` over
  minimal facilities, then `GET /facilities/{id}` for the picked one. The multi-pick dialog on
  the facility search was considered and declined.
- **Members sent as `{id, code}`.** That is the smallest body the server keeps correctly; legacy
  sends whole facilities.
- **No rights refresh after a save.** A group decides which facilities its node's supervisors
  see. But the server rebuilds permission strings asynchronously after the save, so an
  immediate re-read would usually still return the old ones. `invalidateUserQueries` is
  reserved for saves that change a user, and Facilities, whose saves change supervision just
  as much, does not refresh either. The change shows on the next sign-in, as legacy.
- **No reread before saving:** the screen owns every field it sends; description passes
  through from the fresh read on entry.
- **Browser checks let `POST /requisitionGroups/search` through** (agreed 2026-10-14): it only
  reads. Every write stays stubbed.
- **Supervisory node picker offers every node**, as legacy. A node taken by another group is
  refused by the server, with its message. Filtering them out would need the node lookup
  widened, which the Nodes build owns.
