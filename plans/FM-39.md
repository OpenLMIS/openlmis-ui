## Summary

Requisitions is how health facilities ask for stock each period. A facility user opens the
requisition for a period, fills in what they received, used and have left, and the system
works out how much to order. The facility's supervisor authorizes it, approvers up the
supervision chain review and adjust quantities, and a supply planner finally turns it into an
order for a warehouse. Supply planners can also create orders by hand, without a requisition.

Legacy works, but its main screen is a heavy spreadsheet calculated in the browser, it keeps
drafts in browser storage that can be lost, and some pages are slow: signing in downloads
about 10 MB of products, the requisition group list downloads 5 MB, and the manual order
screen takes about 40 s to load. The requisition lists (View, Approve, Convert) already page
on the server.

Before requisitions can run on a fresh deployment, administrators must be able to set up
schedules and periods, the supervision chain, requisition groups and requisition templates.
Those four admin screens are not migrated yet. Everything else requisitions reads (programs,
products, prices, facility approvals, facilities, users and roles) is already migrated and
complete. Legacy admin keeps working beside the new UI, so existing setup supports development
in the meantime.

The new UI keeps every screen, rule and flow of legacy, loads faster, and fixes legacy's
defects. Like Stock, it ships online first, then gets an offline pass.

Findings:

- **Rights are scoped** to facility and program, and approve/reject to the requisition's
  current supervisory node. Demo names mislead: srmanager2 and srmanager4 have no AUTHORIZE.
- **"All changes are saved" means browser storage**, written 500 ms after each edit. Sync
  with Server is a server save. Submit, Authorize, Approve, Reject and Print in edit mode
  save first; Delete and Skip do not. A failed save (version conflict or lost permission)
  reloads the page and deletes the local draft, losing edits.
- **Outdated drafts**: opening a record with local edits compares it with the server; when
  the server copy is newer, a red banner offers Update, which discards local edits after a
  confirmation. Batch approval has the same banner.
- **Signing in downloads about 10 MB of products** (6 to 15 s) to hydrate requisition lines
  by exact product version.
- **Admin is slow too**: the requisition group list is 5.4 MB, the supply line facility
  lookup 4.2 MB.
- **Offline**: no per-record checkbox. Opening a record caches it; View has a Search Offline
  checkbox, an Offline column and Remove Offline; Approve shows the Offline column. Offline,
  edits stay local and every action, including Print, is disabled.
- **Batch approval** shows records in server order with locally edited ones appended, not in
  selection order. `BATCH_APPROVE_SCREEN` only shows the selection column, All/None,
  instructions and View Selected; the batch page itself is not gated.
- **Defects**: raw translation keys on rejection reason pages and node edit; `false` shown as
  text on templates; fixed footers cover grid rows; reopened non-full lines lose their remove
  button; patients data stored per disease rather than per requisition; a validation operator
  error; failed Sync deletes edits.
- **Not walked live** (no data, or would need a write): rejected state, TB patients grid,
  successful status changes, manual order table. Source evidence covers them.

## Agent Brief

### What Already Exists In The New UI

- **Picker policy**: `facilityProgramOptions` (`src/lib/facility-program-selection.ts`) takes
  any grants; routes pass requisition grants. `FacilityProgramSelector` has only `options`,
  `applied`, `onSearch` and `onDraftChange`, so no slot for Regular/Emergency.
- **Rights**: `parsePermissions`, `hasProgramGrant`, `requirePermissions`. `RIGHTS`
  (`src/features/auth/lib/rights.ts`) holds `REQUISITION_VIEW`, `REQUISITION_APPROVE`,
  `ORDERS_EDIT`, `ORDERS_VIEW`, `PODS_MANAGE`, `USERS_MANAGE` and the migrated admin and stock
  rights.
- **Lookups** in `reference-data`: `orderablesByIdentitiesOptions` (exact product versions,
  batched), `supervisoryNodesOptions` (type `{id, code, name, facility}`, used by the role
  dialogs), approved products, facilities, programs, user record and programs, zones and
  levels, display categories.
- **Editable cells**: `QuantityField`, inline `SelectField`/`TextareaField` with `hideErrors`
  tooltips, invalid-page pager, `useFitColumnVisibility`. Physical Inventory has category
  bands, per-row subscriptions and keyed drafts.
- **Packs/Doses**: `QuantityValue`, `QuantityUnitToggle`, `useQuantityUnit`.
- **Writes and output**: `useSessionMutation`, `settleFew`, `useDiscardGuard`, the
  serialized local writer and "Saved On This Device" indicator from Physical Inventory,
  `usePrintReport`, `fetchReport`, `openReport`.
- **Lists**: `selectionColumn`, `DataTableSelectionBar`, `useFilterScoped`, table search
  helpers.
- **Home** reads approval, convert and search counts under its own `home` key scope.
- **Flags**: `BATCH_APPROVE_SCREEN` (default off) and `SHOW_REQUISITION_LESS_ORDER` (default
  on) exist with no consumers; both defaults match legacy.
- **Nav**: every Requisitions and Orders entry is `'#'`; Create Orders sits under
  Requisitions, as legacy.
- **Dexie**: only `physicalInventoryDrafts`.

### What Is Missing

- Rights: `REQUISITION_CREATE`, `_AUTHORIZE`, `_DELETE`, `ORDER_CREATE`, each admin screen's
  right, and their `NAV_RIGHTS` entries (each added with its screen).
- **Warehouse grants**: fulfillment rights arrive as `RIGHT|warehouseId` without a program;
  `parsePermissions` drops them. Convert to Order needs them kept.
- Features: `requisitions`, `orders`, and one per admin screen.
- `reference-data` additions: processing periods and schedules, rejection reasons, supply
  lines, and widening `supervisoryNodesOptions` (parent, children, partners) under its
  existing key so node saves refresh the role dialogs. Approved-product lookup by exact
  version (`POST facilityTypeApprovedProducts/search`) is new.
- Key scopes in `src/lib/key-factory.ts`: `requisitions`, `orders`, `processingSchedules`,
  `processingPeriods`, `requisitionGroups`, `requisitionTemplates`, `supplyLines`,
  `supplyPartners`, `rejectionReasons`, `geographicZones`, `idealStockAmounts`.
- **A template-driven grid**: columns compiled from the requisition's embedded template, a
  calculation library, group rows, a totals footer, virtualization.
- **Batch grid**: two header levels, sticky Code/Name and totals, scrolling both ways.
- **Dynamic closable facility tabs** with a dirty dot (Create Order).
- **Currency**: read the `/localeSettings` currency fields, as legacy's formatter does ([FM-44](FM-44.md)).

### Calculation Rules

**The new UI must compute exactly as the server does.** On save the server recalculates only
some values: D, E, C, Y, N, P, H, I and S on non-skipped full-supply lines of regular
requisitions only, and packs and cost on every non-skipped line, emergency and non-full
included. It rejects others that do not match: a mismatched stock on hand, a
calculated C or E sent non-null, and H, I, S mismatches on status change. Status changes
recalculate N, P, packs and cost. Exact formulas, rounding and the 33-column catalog are in
`research-b-legacy-source-api.md` section 2 and Appendix A.

- Key columns by `name`, never by indicator: `skipped` and `calculatedOrderQuantityIsa` both
  use S. Render the template's own labels, definitions and order.
- Packs to ship: `floor(q/s)`, plus one only when the remainder is strictly greater than the
  pack rounding threshold; a positive quantity rounding to zero becomes 1 pack unless round
  to zero is set; 0 packs when q is 0 or less or net content is 0.
- Cost per line is packs times the program price per pack. Full and non-full totals sum
  non-skipped lines. Batch totals sum raw line costs and round only for display, as legacy.
- Where legacy's browser formulas differ from the server, follow the server: adjusted
  consumption when consumed is 0 and Z is entered (server 0); average consumption with the
  current-period setting (server `ceil(N/2)`); the pre-approval order quantity (server:
  requested if set, else ISA quantity on stock-based templates or calculated quantity on
  others).
- Stock-based templates read A, B, C, D, E, X, P from stock cards; those cells are read-only
  and must be sent unchanged. Beginning balance otherwise comes from the previous period's
  stock on hand when column A is shown; B is prefilled from a submitted proof of delivery.
- Patients: the client computes TC to TH and the server never computes TE to TH. Before
  approval a save stores TC to TH as sent; during approval it keeps only B and TC, so TE to
  TH are re-derived for display after every load, as legacy does. TC per product code from the patients grid (nine codes); TE = TC x TD
  and TF = 2 x TE (both 0 when E is empty); TG = max(TF - E, 0); TH = floor(TG / net
  content). TE to TH show as not available when doses per patient is 0. `patientsData` is a
  JSON string; scope it to the requisition.
- Supplying-facility stock (SF) is read-only server data for approvers.

### Rules

**Status and rights**

- INITIATED and REJECTED edit with CREATE; SUBMITTED with AUTHORIZE; AUTHORIZED and
  IN_APPROVAL with APPROVE (approved quantity, remarks, configured unskip). On the TB Monthly
  program (keyed on the program name, as legacy), approvers also edit TC, B and remarks;
  creators cannot. Everything else is read-only.
- Save checks APPROVE at facility and program; approve and reject check the current node.
  Handle 403 on actions cleanly.
- `skipAuthorization` turns Submit into "Submit and Authorize". A supply line can end
  approval before the top node; a locally fulfilled supplier releases automatically; a
  report-only period becomes Released Without Order.
- A split requisition (supply partners) cannot be rejected; the approval list shows N/A for
  its submitted and authorized dates.

**Products and skipping**

- Regular requisitions hold every approved full-supply product (stock-based templates only
  those with stock card data) and cannot add or remove them; show the membership the server
  returns, never invent missing lines. Emergency requisitions start empty and add from the requisition's own available
  products. Non-full Add Product offers the requisition's available products snapshot only.
  Removal follows supply and status, not a transient flag (fixes the lost remove button).
- Skip period requires a regular requisition and a program that allows skipping; it does not
  require a displayed Skip column. Line skip controls offer All, This Page and None when the
  Skip column is displayed.
  Line skip needs every user-input cell empty (0 counts as empty) and is never allowed once
  Approved or Released. Hidden skipped lines come back through Add Product.
- Product name filter, Show Skipped and the skipped count; Pack Size after the product name;
  losses and adjustments in a dialog; Show Details splits full and non-full totals; status
  history dialog; supplying-facility stock header, access-denied banner and highlight when
  approved quantity exceeds it.

**Validation**

- Required: every shown user-input column except skip, remarks, adjustments, explanation,
  requested quantity, adjusted consumption and new patients. Requested quantity is required
  for non-full supply, emergency, or when no calculated quantity column is shown; an
  explanation is required when it differs from the calculated quantity.
- Stock on hand and consumed cannot be negative and must balance when both are user input;
  stockout days at most 30 times the period's months.
- Submit and Authorize validate every page and tab (including a complete Patients grid),
  refuse all-skipped, and ask for the physical stock count date on regular requisitions when
  the program enables it (not in the future). Approve validates every line; Reject saves
  without validating.

**Enforced only in the UI or database** (the new UI must enforce them itself)

- Line skip only when empty; approver unskip; remarks 250 and explanation 255 characters;
  numbers at most 2,147,483,647; batch selections from one program; manual order Create only
  when every tab is saved and has lines above 0.

**Lists and orders**

- Search results do not grant opening: detail and Print need VIEW for the record.
- Manual order drafts are server orders in CREATING, quantities in doses; Send converts to
  packs. Create shows a summary dialog first.

### Data Flow

- Lists ([FM-45], [FM-47], [FM-48]) follow AGENTS.md's List Pages section.
- The requisition page blocks on the record (not found, rights by status) and defers
  hydration. One draft lives above the tabs, keyed by line id, as the facility editors do
  with `?tab=`, so tab switches never remount or reset it.
- Drafts autosave locally in Dexie and Sync writes the server, keeping the newest ETag and
  `modifiedDate` from each response. A newer server copy shows the outdated banner with
  Update.
- Every action invalidates the list, the record and Home's `home` scope.

### Files

- `src/features/requisitions/` (api; lib with template compiler, calculations, statuses and
  capabilities; components) and `src/features/orders/`, which owns its own stock summary
  fetch. Routes compose them; neither imports the other or Stock.
- Admin features: `processing-schedules`, `supervisory-nodes`, `requisition-groups`,
  `requisition-templates`, `rejection-reasons`, `supply-lines`, `supply-partners`,
  `ideal-stock-amounts`, `geographic-zones`. Templates and groups stay in their own features;
  requisitions read the embedded template.
- `src/features/reference-data/`: periods, schedules, rejection reasons, supply lines, the
  widened nodes lookup, approved products by version.
- `src/components/editable-grid/`: rendering, keyed draft paging, group and total rows, error
  focus and virtualization. Not registry-bound (it may use app hooks), unlike `data-table/`.
  The first requisition grid ([FM-44]) lives in `src/features/requisitions/`; it is extracted
  here when Stock adopts it (batch approval stays in the same feature), and Stock adopts it without
  behaviour changes.

### Translations

New `requisitions.*`, `orders.*` and one namespace per admin screen. Template column labels and
definitions are server data, not translation keys.

### Risks

- Grid size: a full-supply grid can hold hundreds of lines with about 15 columns; batch
  multiplies by requisitions. The first slice ([FM-44]) measures real records and a 500-line
  fixture and sets the [FM-27] budget; the batch layout is decided with [FM-46] against the same
  budget.
- Historic product versions: always hydrate by exact version, never the latest.
- Approval rights live on the server (node chain); the browser can only predict them.
- Admin lists with fixed server order (groups, nodes) offer only that order or sort locally.

## Decisions

- **Administration first, by tier** (confirmed 2026-10-14). Tier 1 before the editor stories;
  Tier 2 before or with the story that uses it. The read-only slice runs in parallel with
  Tier 1.
- **Parity for admin setup** (confirmed 2026-10-14): supervisory nodes and supply lines are
  created through the API, as legacy; no new screens for them.
- **Offline as legacy** (confirmed 2026-10-14): the offline pass covers the same routes and
  actions legacy supports offline.
- **Test fixtures on test.openlmis.org** (confirmed 2026-10-14): 2026 periods, TB grants and
  supply line, a rejected requisition and a template with the rejection window are created
  there, each write approved by the user first.
- **Manual order Print** (confirmed 2026-10-14): uses the standard order print instead of
  legacy's Angola-specific report, which core lacks.
- **VIEW-only users** (confirmed 2026-10-14): may open a requisition read-only, as the API
  allows.
- **Online first**, then one offline pass, as Stock.
- **Stock consistency** (2026-10-27): requisition screens follow the Stock Management design and
  reuse its components; [FM-48](FM-48.md) and [FM-44](FM-44.md) map each piece. Divergences are
  flagged, never a requisition-only pattern.
- **Full parity with legacy**; fix its defects; backend services on master only.
- **Calculations match the server**, which recalculates some values and rejects mismatched
  others; where legacy's browser differs, the server wins.
- **Save/Sync ([FM-41] AC)**: local autosave on the device, explicit Sync writes the server;
  Submit, Authorize, Approve, Reject and edit-mode Print save first. Drafts go to Dexie.
- **Manual order drafts ([FM-50] AC)**: saved on the server as CREATING orders, as legacy.
- **Template snapshot**: the editor uses the template embedded in the requisition.
- **Cell errors** ([FM-52] "inline message" AC): follow the repository's editor table
  convention, as the Stock screens: invalid cells are highlighted and show their message in
  a tooltip on hover or focus (`hideErrors`), and an invalid Submit, Authorize or Approve
  opens a dialog and focuses the first invalid cell on its page and tab. The message sits on
  the cell, which meets the AC; `review-pr` checks it in the browser.
- **No `unfinished=true`**: the period table hides pre-start periods itself; legacy's
  deletion of old drafts as a side effect of listing periods is not reproduced.
- **First slice** (2026-10-16): [FM-48] View plus [FM-44] read-only, in one PR. The [FM-56]
  layout spike is dropped: the slice decides the grid architecture and the [FM-27] budget from
  real data ([FM-44](FM-44.md)).
