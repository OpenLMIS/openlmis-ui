# FM-14: Token Handling + Expiry/Logout

https://openlmis.atlassian.net/browse/FM-14 · Parent: FM-7 Auth & session plumbing

## Scope

This PR changes what happens when the server stops accepting the user's session, and
tightens sign-out. When the session expires, a Session Expired dialog opens over the page,
and the page and any unsaved work stay where they were. It also:

- keeps the token's expiry,
- stops a sign-in from being mistaken for an expired session,
- ignores rejections that belong to an older session,
- keeps other `/v2` tabs in step,
- brings a signed-out user back to the page they asked for after signing in (FM-7).

The dialog is mounted at the root, so it reaches every page. That is the feature itself,
not a ride-along.

Out of scope:

- rights for a single program, facility or supervisory node (FM-15);
- loading the home facility and programs (FM-16);
- anything offline (FM-175, FM-166).

## Summary

The server keeps a user signed in for 30 minutes after their last action. When that time
runs out, or the server is restarted, every screen's next request is refused.

**In the old UI** a sign-in box opens over the page, with no word about why. Everything
the user typed stays on screen, and once they sign in the page carries on as if nothing
happened. Behind the scenes it also wipes everything the browser had saved for the site,
so signing back in takes about 14 seconds while it all reloads.

**In the new UI today** the user is dropped onto the sign-in page:

- There is no message about why.
- Unsaved changes are lost without a warning.
- After signing in they land on Home, not the page they were on.
- One expired session sets off the sign-out up to 16 times, once for every screen
  request that was refused.

**The new UI will do what the old one does, and explain it.** A Session Expired dialog
opens over the page and says the user was signed out for inactivity and that their work
is kept. They type their password and carry on from where they were: anything that was
loading finishes, and a Save they pressed goes through. If they would rather not, Sign
Out ends the session properly, and asks first when there is unsaved work.

It also fixes a few smaller things:

- Opening a link while signed out leads to that page after signing in, not to Home.
- Signing out in one tab signs out the other open tabs too, as the guide already
  promises.
- Signing out with an expired session no longer reports that sign-out failed.

## Agent Brief

### API Map

| Step | Method and path | Params | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| Sign in, and sign in again | `POST /api/oauth/token` | `grant_type=password`; body `username`, `password` (form-encoded); `Authorization: Basic base64(clientId:secret)` | `access_token`, `expires_in`, `referenceDataUserId`, `username` | none | `login.service.js:56-66,101-112` |
| Sign out | `POST /api/users/auth/logout` | Bearer | none (200 "You have successfully logged out!") | authenticated | `login.service.js:137-179`; auth `UserController.java:196-208` |
| Any session request | any | Bearer | `401` body `{"error":"invalid_token"}`, header `WWW-Authenticate: Bearer ... error="invalid_token"` | varies | `access-token.interceptor.js:82-109` |

Contract facts:

- **No refresh token.** `user-client` has the `password` grant only.
- **Validity is sliding.** It is `TOKEN_DURATION`, 1800 s by default. Every call to a
  non-auth service slides it through `check_token` (auth `CustomTokenServices.java:31-53`).
  `expires_in` is the time left on the token at grant time; 173 s was seen once. It is a
  lower bound, not a lifetime.
- **One token per user and client, shared by both UIs.** A grant for the same user
  returns the existing live token, and our logout revokes it for legacy too. Every token
  is lost when the auth service restarts, since the store is in memory.
- **A `401` on `/api/oauth/token` is not an expired session.** It means bad client
  credentials, a deployment fault. A wrong password or a locked account is a `400`
  `invalid_grant`.
- **Expired, revoked and unknown tokens look the same on other services**:
  `401 invalid_token`.

### Data Flow

The session state lives in `useLoginData`, with two new fields:

- `expiresAt: number | null`, from `expires_in`. It is a lower bound, and nothing ends a
  session on it (see Decisions).
- `expired: boolean`. It keeps `referenceDataUserId`, `username` and the refused
  `accessToken`. Keeping the token lets `syncLegacySession` tell the legacy UI's dead token
  from a new one; dropping it made a second tab bring the session back with the dead token.

Because the user id stays the same, the query cache survives a same-user sign-in again,
through the existing subscription in `src/integrations/tanstack-query.ts`. Keep the
persist `version` at 0: the default shallow merge fills the new fields for stored v0
records, and a version bump with no `migrate` would sign everyone out on deploy.

`src/features/auth/lib/session.ts` (new) owns the wait:

- `waitForSession(userId)` resolves with the current token once the session is live. It
  follows the store rather than being settled by hand, so there is no `renewSession` or
  `endSession`: the store signing out, or holding another user, rejects every waiter with
  a `SessionEndedError`.
- The session counts as renewed when the store holds a live token for the same
  `referenceDataUserId`, whether from the dialog, another tab, or the legacy UI through
  `syncLegacySession`.

`src/integrations/axios.ts`:

- **Request:**
  - A request that already has an `Authorization` header keeps it. That is the login
    Basic header.
  - While `expired`, a session request is not sent. It awaits `waitForSession` first.
  - Each request records the token it was sent with.
- **Response `401`:**
  - Skipped for requests marked `session: false`, which are login and logout.
  - If the token it was sent with is no longer current and a live token exists, it is an
    older session's failure: resend with the current token.
  - Otherwise mark the session `expired` (idempotent), await `waitForSession`, and resend
    the original config once. A `401` on the resend expires the session again rather
    than looping.
  - The user id is checked on renewal, and a different user rejects the wait.
  - Each request records the user it was sent for (`sentFor`). A refusal of a request sent
    for someone who is no longer signed in rejects with `SessionEndedError` instead of
    being resent as the new user.

The query client:

- Its `retry` stops retrying `401` and `403`, since neither gets better.
- A query waiting on the session stays pending, so Suspense shows its skeleton and no
  error UI flashes.

`src/components/session-expired-dialog.tsx`:

- Mounted in `src/routes/__root.tsx`, so it also covers a route whose loader is waiting,
  and a reload while expired.
- It renders while `isAuthenticated && expired` and the route is not `/login`.
- **Sign In** calls `authApi.login({ username, password })` directly for an inline error,
  then `setLoginData`, which also clears `expired`.
- **Sign Out** runs `whenLeaveAllowed`, then the existing logout, then navigates to
  `/login`, like Log Out in the avatar menu. No `redirect`: signing out on purpose is
  usually a change of user. Both buttons are disabled while either runs.
- `useDialogTarget` keeps the username through the close animation, so the dialog never
  empties as it fades.

`src/routes/login.tsx`:

- `validateSearch` takes `redirect`, validated by `safeRedirect()` in `src/lib/redirect.ts`.
  It must be an internal path that starts with `/`, not `//` or `/\`, with no scheme, and
  not `/login`. Anything else falls back to `/home`.
- After sign-in it navigates to `redirect`.
- `_protected.tsx` throws `redirect({ to: '/login', search: loginSearch(location) })`.
  `loginSearch` carries `location.href` (router-internal, without `/v2`) except from Home,
  where signing in lands anyway.

`src/index.tsx`: the `storage` listener calls `syncOtherTab(key)` in the store, which
rehydrates on our own key, `login-data-storage`, and runs the legacy sync on legacy's key or
on a wipe (`null`). It resolves `true` when it signed this tab out, and the listener then
goes to `/login`:

- If another tab signed out, go to `/login`.
- If another tab renewed the session, the dialog closes and the waits resume.

### Rules

- **Only the same user may continue.** The dialog shows the username read-only. Switching
  user goes through Sign Out, so no draft or queued write is ever sent as someone else
  (offline plan: no cross-user mixing).
- **A queued request is resent once, after sign-in.** A `401` means the server refused
  the request before acting on it, so resending a write is safe. It is not an uncertain
  write.
- **The login request's own `Authorization: Basic` is never replaced by Bearer.**
- **A `401` on login or logout never opens the dialog.**
  - On login it is a client credentials fault: show the generic error.
  - On logout it means already signed out.
- **Mapping sign-in errors:**
  - A `400` (`invalid_grant`) shows the wrong-password message, as legacy does. Legacy
    also shows it for a locked account.
  - No response (network) shows the cannot-connect message.
  - Anything else shows the generic error.

### Risks and Edge Cases

- **Suspense and loaders wait with no timeout while the dialog is open.** That is
  intended: the dialog is the only way out.
- **The legacy UI signs in again in another tab.** `syncLegacySession` adopts the new
  token for a legacy-sourced session, which resumes the waits.
- **The legacy UI wipes localStorage** on its own `401`, which fires a `storage` event with
  key `null`. There is no rehydrate for it:
  - An own session saves itself again, so a reload keeps working.
  - A legacy-sourced session expires rather than clears, since legacy wipes its keys the
    same way on a sign-out and on a refused token. The page and its draft stay behind the
    dialog, where the user can sign in again or Sign Out.
- **The dialog is open and the user is not the same person.** Sign Out is the path.
  Their draft goes through the discard prompt, never to the new user.
- **The auth service restarts mid-save.** Handled the same as an expiry.
- **Revoking the shared token.** Our logout revokes it, which also signs out legacy, and
  anyone else, from the same account. That is kept as is (see Decisions).
- **A `401` from a request that was in flight when the user signed out.** The store is
  already clear, so ignore it: no dialog without
  `isAuthenticated`.

## Decisions

- **A dialog over the page, not the sign-in page.** The ticket's wording would lose the
  user's work every 30 idle minutes. Legacy already does sign-in in place, and the
  offline plan requires it ("does not delete drafts or eject the user from the editor").
  The message the ticket asks for is in the dialog. The sign-in page is still where Sign
  Out leads.
- **Where the token is stored, recorded as the AC asks:**
  - It is persisted in `localStorage` under `login-data-storage` through the zustand
    store.
  - It is shared one way with legacy: we adopt legacy's session and never publish ours.
    This was decided in FM-11 and is recorded in `docs/deployment/deployment.md`.
  - It is the same server token as legacy for the same user.
- **`expires_in` is kept, but nothing signs the user out on it.** Expiry slides with every
  call, so a client countdown would sign users out early. The `401` stays the source of
  truth. `expiresAt` is kept for the offline work (FM-166) to judge whether a session is
  likely alive before an upload.
- **No proactive check on boot** (`check_token`). It would slide the token itself and adds
  a request to every load, for no gain over the first real `401`.
- **Resend refused requests after sign-in, writes included.** A `401` is a refusal before
  processing, so it is safe, and it matches legacy.
- **Same user only in the dialog.** Switching user goes through Sign Out, so nothing is
  sent as someone else.
- **The resend stays simple:** each refused request is resent once, from the same
  interceptor that caught it, after the shared wait settles. No separate queue or replay
  store.
- **Logout keeps revoking the server token,** which signs the same account out of both
  UIs. Ending a session should end it everywhere. Legacy's logout not revoking looks like
  a bug.
- **Cross-tab sync and the deep-link return ride along.** They are small, in the same
  code, and the second is an FM-7 criterion. Without the first, a second tab keeps a
  session that has been signed out, against `docs/dual-boot/dual-boot.md`.
