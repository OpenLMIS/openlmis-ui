# FM-144: Processing Schedules

https://openlmis.atlassian.net/browse/FM-144 · Parent: FM-139 Admin: Products & Programs ·
Epic plan: [FM-39](FM-39.md), Administration First, Tier 1 row 1

## Scope

Administration > Processing Schedules: the list of schedules, adding a schedule, and each
schedule's periods with Add Period. Requisitions read what this screen sets: a facility can
only start a requisition for a period of the schedule its requisition group assigns.

Shared piece this PR adds: a processing schedules lookup in `reference-data`, which the
Requisition Groups build (FM-129 to FM-131) picks from. Its contract is fixed in the epic
brief (see Agent Brief, Files) so both builds converge.

Out of scope, as legacy:

- editing or deleting a schedule, and editing or deleting a period. Legacy only adds
  schedules and appends periods (FM-39 Out Of Scope);
- searching or filtering schedules. The API has no filter and deployments have a handful.

## Summary

A processing schedule is a named run of reporting periods, such as Monthly or Quarterly.
Each period has a name, a start date and an end date, and may be marked Report Only, meaning
its requisitions report stock but do not order. Periods follow each other with no gaps: each
new period starts the day after the last one ends.

In the old UI, Administration > Processing Schedules is a table of code and name with Add
Processing Schedule and an Edit button per row. Add opens a short window (code, name,
description). Edit opens a window titled `Add Processing Period for "SCH001" schedule` with an
add form on top (name, description, start and end dates, Report Only) and the schedule's
periods below, ten at a time, oldest first. The start date is filled in for you and locked
once a schedule has periods. It works, but:

- Every save asks "Do you want to...?" first.
- A refused save shows the server's reason in an alert plus a generic "Failed to save" toast.
- A typed end date before the start date is not caught, and a one-day period passes the form
  but the server refuses it.
- On a phone the form and a 108-row table are squeezed into one narrow window.

The new screen keeps the same data, rules and flow, and fixes those:

- The schedules table keeps the same columns and labels, and can be sorted
  by code or name. Add Processing Schedule opens the same short dialog.
- Edit opens the same window as today: the add form on top and the schedule's periods below,
  ten at a time, oldest first. The start date is filled in and locked exactly as today, and
  the end date cannot be on or before it.
- After adding, the window stays open with the form cleared, and the table shows the page
  holding the new period.
- The server's reason for refusing a period (for example a gap or overlap) shows inside the
  dialog, which keeps what was typed. A code or name already in use is flagged on the field.
- No confirmation before saving. It works on a phone and in Arabic.

Errors:

- Schedule: `400 referenceData.error.processingSchedule.code.duplicated` / `.name.duplicated`
  (unique ignoring case, from DB indexes; no validator). Mapped onto their fields; anything
  else shows the server message. A null code or name is a raw 400, so the client requires both.
- Period (`ProcessingPeriodValidator.java:43-82`, first error only, `{messageKey, message}`):
  name blank, schedule missing, start or end missing, `startDate.after.endDate` "Start date
  should be before end date" (end must be strictly after start), and
  `processingPeriod.gap.between.lastEndDate.and.startDate` "Start date should be one day after
  last added end date" (compared with the last period by end date; any gap or overlap; the
  first period may start anywhere). No name uniqueness.
- `404 referenceData.error.processingSchedule.notFound` for an unknown schedule id; a badly
  formed id is a `400` ("Invalid UUID string"). `GET /processingPeriods` with an unknown
  `processingScheduleId` is a 404 with `...notFound.with.id`, never reached since the detail
  read fails first.
- An unknown sort property is a `500` on both GETs, so each schema allows only its listed
  fields. Several sorts apply the direction to the last field only; send one.

`extraData` is stored as sent; a missing one is stored as `{}`. Demo data holds strings
(`"true"`/`"false"` on Monthly A, B and C; `{}` elsewhere); legacy writes a boolean.
Requisition reads it with `Boolean.parseBoolean` on a null-safe map, so all of these work.

### Data Flow

- **List route** `src/routes/(protected)/_protected.administration.processing-schedules.tsx`:
  loader awaits `requireRight(RIGHTS.processingSchedulesManage)`, prefetches the page from
  `loaderDeps`, deferred. Dependencies include only the page query, not `schedule`. The
  dialog fetches the duplicate-check lookup fresh with `staleTime: 0` on each opening; the
  loader does not prefetch it. URL: `page`, `size`, `sort`, `dir` from `tableSearchSchema(['code',
  'name'])`, `DEFAULT_SCHEDULES_SORT = { id: 'code', desc: false }` passed to `toSortParam`
  and the table's sorting helpers and kept out of the URL; `schedule=new`.
- **Periods dialog** on the list route: `?periods=<schedule id>` (a GUID; anything else is
  dropped by the schema) with `periodsPage` and a fixed page size of 10. Paging replaces the dialog entry
  and preserves its history state so Cancel still returns to the originating list. These stay out of `loaderDeps`. Opening adds history; Cancel and Escape call
  `closeDialog()`, which clears both dialog params. The dialog reads the schedule detail and the
  latest period fresh on every opening (`useOpening()` in both keys), and the periods page
  through `periodsListOptions` with `sort=startDate,asc`. A detail 404 shows `DialogNotFound`;
  other failures show `DialogLoadError`. The table has its own `QueryBoundary` with
  `ListError`; later pages keep the dimmed rows until ready.
- **Keys:** `queryKeys.processingSchedules.list(query)` (page), `.list()` (lookup, the
  reference-data contract), `[...detail(id), opening]`; `queryKeys.processingPeriods.list(query)`
  (page) and `[...processingPeriods.all, 'latest', scheduleId, opening]`. Every save
  invalidates `processingSchedules.all` and `processingPeriods.all`.
- **After Add Period:** the mutation creates the period, then calls `fetchLatestPeriod`
  for the post-save count, returning `{ saved, total }`. If that read fails, it uses the
  opening count plus one. Options-level success shows the toast and invalidates both scopes.
  Only the per-call `mutateAsync` success, after `isCurrent()`, resets the form (start = the
  saved end + 1 day, locked) and replaces `periodsPage` with
  `landingPage({ total, size: PERIODS_PAGE_SIZE })`, so a save finishing after
  the dialog closed cannot navigate. The dialog stays open, as legacy.
- **After a refused period:** keep the dialog and values, show the message, refetch the
  latest period, then check `isCurrent()` and `form.setFieldValue('startDate', ...)` when the
  start is locked, so a gap caused by another admin's save shows the right start.
- **Add Schedule:** toast, invalidate, `closeDialog()`, back on the list's page, as legacy.
- **Nothing client-side** beyond the duplicate check: the server pages, sorts and counts.

### Rules

- Schedule: code and name required, trimmed, whitespace alone is empty; unique ignoring case
  (checked against the lookup, then the server keys); description optional, trimmed, omitted
  when blank. Legacy `processing-schedule-add.html`.
- Period: name required and trimmed; description optional, trimmed, omitted when blank; start
  and end required valid dates sent as `yyyy-MM-dd`; end strictly after start (server rule;
  stricter than legacy's inclusive picker, which lets the server refuse it).
- Start: when the schedule has periods (`totalElements > 0` of the latest read), prefilled
  with latest `endDate` + 1 day and locked. Legacy locks on the current page's rows, so a page
  past the end unlocked it; ours does not. With no periods, empty and editable, `latest` =
  end - 1 day once an end is picked, with legacy's hint as its description.
- The hint "The first start date should match when your organization will begin
  requisitioning and reporting." also stays as an info tooltip on the periods table's Start
  Date header, as legacy.
- Report Only reads true for `true` or `"true"` only; `"false"`, `false` and missing are not
  (legacy's loose `==` also took `1`, which no data holds). Writes `extraData: {reportOnly:
  true}` when on and no `extraData` when off, legacy's body for an untouched box; legacy's
  ticked-then-unticked `{reportOnly: false}` reads the same.
- `processingSchedule` in the period body is the loaded `GET /processingSchedules/{id}`
  object, as legacy. The server rebuilds a schedule from it and requires `name`, so `{id}`
  alone is a 500; there is no cascade, so it never changes the stored schedule.

### Risks and Edge Cases

- Another admin adds a period while the dialog is open: the server refuses with the gap
  message, the dialog shows it and moves the locked start.
- A schedule with no periods: start editable and required; the first save sets the run.
- The latest read sorts by start date while the server validates against the latest end date;
  periods never overlap, so they agree, as legacy relies on.
- Deep link to an unknown schedule id: not found inside the dialog; a malformed id opens no
  dialog.
- Midnight and DST: the day arithmetic uses local calendar dates from `parseDateValue`,
  never `Date` arithmetic on UTC timestamps.

## Decisions

- **Periods live in the Edit dialog, as legacy**: `?periods=<id>` over the list, the add
  form on top, the periods table below, Cancel in the footer. Changed 2026-10-14 at the
  user's request for legacy parity, replacing the earlier periods page. It departs on purpose
  from AGENTS.md's page for child tables and Add-button-above-the-table pattern.
- **Compact periods layout:** a 36rem dialog with Start Date and End Date side by side.
  The compact table scrolls under a sticky header while the form and centered pagination
  remain visible. Periods always use 10 rows per page with no page-size picker. On short
  screens the body can scroll to keep every form field and table control reachable.
  Report Only aligns to the start, including in Arabic.
- **Legacy's labels, order and action name are kept**: Processing Schedule Code and Name,
  Edit, oldest periods first.
- **No confirmation before saving**, as every migrated admin dialog.
- **Report Only is written as legacy's untouched-or-ticked body**; read accepts boolean or
  string.
- **End strictly after start on the client**, since the server refuses anything else.
- **Same endpoints and request bodies as legacy.** Schedules add supported `sort` values,
  `code,asc` by default (legacy sends none and gets database order); periods always send
  `startDate,asc`, legacy's order made explicit, with no sort headers.
- **Add Schedule returns to the list**, as legacy.
- **Shared lookup in `reference-data`** with the brief's exact contract and key, so the
  Requisition Groups build converges; if it merges first, one copy is kept on rebase.
