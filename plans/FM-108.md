## Summary

After district approvers approve facility forecasts, the national level (MOH or PORALG) gives the
final approval. The approver picks an area (country, zone or region) and a forecasting period,
sees every approved forecast there with its cost split by product group, ticks the ones to accept
and approves them together.

Legacy shows a "Consolidated Summary" page: Group and Forecasting period on the left with Search,
totals per product group, and a table of facilities with checkboxes and Final Approval at the
bottom. Final Approval is always clickable and complains only after the confirmation when nothing
is ticked, a failed approval shows nothing, one total shows the wrong group and totals lose their
cents, and the group names can read "undefined".

The new page keeps the same search, table and bulk approval, with Search and Final Approval
enabled only when they can work, correct totals, the facility names loaded in one request instead
of one per row, a clear empty state, the server's error in the dialog, and a layout that works on
a phone and in Arabic.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Enter | permissions, `GET /users/{id}/programs` | user id | program `code === 'BUQ'` | `MOH_APPROVAL` or `PORALG_APPROVAL` anywhere | `buq.routes.js:76-86,187` |
| Groups | `GET /bottomUpQuantifications/supervisedGeographicZones` | `programId` | `{country: {zone: {region: [district]}}}` ids | MOH or PORALG | `useGeographicZoneGroup.jsx:17-25` |
| Group names | `GET /geographicZones` (existing `geographicZonesOptions`) | none | `id`, `name`, `level` | authenticated | `useGeographicZoneGroup.jsx:56-58` |
| Periods | processing schedules, then periods of the BUQ schedule (FM-103) | `processingScheduleId` | `id`, `name`, `startDate` | authenticated | `useBuqCommonFunctions.jsx:31-49` |
| Search | `GET /bottomUpQuantifications/forFinalApproval` | `programId`, `processingPeriodId`, `geographicZoneId`; no paging | `content[].bottomUpQuantification` (`id`, `facilityId`, `status`), `content[].calculatedGroupsCosts` (group name to "123.45 USD") | MOH or PORALG | `MohForFinalApproval.jsx:40-51` |
| Facilities | `GET /facilities` by ids (existing `facilitiesByIdsOptions`) | ids | `name`, `type.name` | authenticated | per row `facilityService.get` (`:53-76`) |
| Final Approval | `POST /bottomUpQuantifications/finalApprove` | `id` repeated, no body | list of DTOs | MOH or PORALG, unscoped | `MohForFinalApproval.jsx:88-104` |

`forFinalApproval` returns only APPROVED forecasts at the nodes where the user holds MOH or
PORALG, for the program and period, inside the zone; MOH alone sees non-primary facility types,
PORALG alone primary ones (`BottomUpQuantificationService.java:687-790,913-942`). Paging is
applied before the zone and type filters and `totalElements` is the filtered page size, so it is
read unpaged: without `page` and `size` the service falls back to one page of `Integer.MAX_VALUE`
(`CustomWebMvcConfigurerAdapter.java:50-53`). Cost groups come from the `product_groups` table (seeded Pharmaceuticals, Medical
supplies, Radiology (X-rays consumables), Diagnostics supplies, Dental supplies, Others), every
group present, amount and currency code as text. `finalApprove` is one transaction: an unknown id
gives 404 `buq.error.bottomUpQuantification.notFound` and nothing is saved; it checks neither
status nor scope. Errors `{messageKey, message}`; 403 without the right.

### Data Flow

- Route `_protected.buq.national-approval.tsx`: the loader blocks on `loadNationalAccess`
  (beside `loadApproveAccess`, reusing `currentUser` and `prefetchBuqPeriods`: `requireRight` with
  both rights, user programs, `approveAccess`), then prefetches without awaiting the supervised
  zones, all zones and the BUQ periods; with `zone` and `period` in the URL (`loaderDeps` holds only
  those two) it also prefetches the list and its facilities.
- URL search: the national schema extends `buqListSearchSchema` with `zone` and `period`, so
  `useBuqTable` takes it unchanged; defaults stay out. A linked `zone` outside the supervised tree
  or `period` outside the BUQ schedule is left blank, never substituted. The picker keeps a draft
  until Search writes `zone` and `period`; while the draft differs from the URL the rows, the
  selection bar and Final Approval are hidden, as the facility/program picker.
- Draft defaults, as legacy: the first group and the latest BUQ period; no automatic search. A
  changed draft replaces the whole results boundary with the choose prompt until Search; Search on
  the shown choice reads the list again, as legacy.
- List: `buqsForFinalApprovalOptions` keyed `queryKeys.buq.list({ national: { programId, periodId,
  zoneId } })`, then `facilitiesByIdsOptions(nationalFacilityIds(...))`, the same key in the loader;
  rows and totals read the list through `useDeferredValue`, so a refetch keeps the shown rows until
  their facilities load; paged locally through `useBuqTable` with row selection added.
- Selection and the open confirmation: component state scoped to the search (`useFilterScoped`,
  `withoutIds`), out of the URL; a new search clears the picks and closes the confirmation.
- Final Approval: confirmation; `useSessionMutation` rereads the list for the URL's zone and period
  (`fetchQuery` with `staleTime: 0`), keeps the picked ids still in it, sends them in batches of
  100 with a session check before each, then invalidates every BUQ list and detail, removes the
  approved ids from the selection (and from the open confirmation after a partial failure) and
  toasts.

### Server-Side Work

- Facilities by ids in one request instead of one per row; periods from the BUQ schedule (FM-103)
  instead of every period; zones and programs read once.
- Stays client-side because the API cannot do it: paging (broken server paging), zone names
  (`supervisedGeographicZones` returns ids), facility name and type (the DTO has ids only), group
  totals of the summary.

### Rules

- Final Approval sends only picked forecasts still in a fresh read of the list (APPROVED at the
  user's nodes); the backend checks neither status nor scope. Picked ones that left the list are
  dropped from the selection and counted in the toast; when none was left, an info toast says so.
- A later batch failing keeps the dialog open with how many were approved and the server message;
  the approved ones leave the selection.
- After approval focus moves to the labelled results section; the remaining rows stay shown while
  facilities reload.
- The confirmation names the report when one is picked; skipped reports get their own info toast,
  so the two-line toast never cuts them off.
- Ids go in batches of 100 (`BY_IDS_BATCH`), one request at a time; each batch is atomic on the
  server; a failed batch stops the rest, its forecasts stay picked and the dialog shows the error.
- Search enabled only with a group and a period; Final Approval only with a selection.
- Group options: tree depth 1 to 3 of the supervised tree, as legacy (on the demo, depth 3 is a
  district). No supervised zones: an empty message replaces the picker.
- Columns: the five legacy groups by name (Pharmaceuticals, Medical supplies, Radiology (X-rays
  consumables), Diagnostics supplies, Dental supplies), fixed, so the skeleton matches; Others and
  any other group only in the summary, as legacy. Amounts parsed as decimals, never `parseInt`,
  shown in the deployment currency format.
- Summary above the table, in the list's boundary, only with rows; totals over every row, as legacy.
- Rows are APPROVED by construction; Status shows the badge, the explanation in the header's info
  tooltip, and as text above the cards, where there is no header and tooltips do not open on tap.
- After approval: toast with the count, approved ids leave the selection, every BUQ list refreshed.

### Risks And Edge Cases

- The list holds only forecasts APPROVED at nodes where the user has MOH or PORALG; after a
  two-level approval it sits at the parent node. The empty state says so.
- PORALG alone sees only primary health care types; in the demo data every type is non-primary,
  so a PORALG-only user sees an empty list.
- Product group names are deployment data; a renamed or added group shows only in the summary's
  Others.
- Products whose codes match no group prefix (all demo products) cost only Others, so the table
  shows zeros and only the summary has the cost, as legacy.
- The cost text's currency code may differ from the deployment currency settings; the amount is
  shown in the deployment format (as the forecast grid).
- Many picked ids make a long query string (about 40 characters each); batches of 100 keep it near
  4 KB but give up one transaction for the whole selection: a later batch can fail after earlier
  ones were approved, and the dialog says which remain.
- The zones tree is built from the user's permission facilities at levels 1 to 4; a deployment with
  facilities at level 3 (the demo) gives a tree without districts.

## Decisions

- **Row action moved to FM-109** (user, 2026-11-12), with the national grid and its route.
- **First group preselected, as legacy** (review-pr: one Search click instead of three).
- **Selection bar as a page footer**, as Approve Requisitions (`placement="footer"`, rendered after
  `Workspace` through a slot the route owns); the disabled Final Approval stays above it for the
  empty selection the AC names.
- **Select All kept** although Approve Requisitions now has none: the AC asks for all rows at once.
- **Header checkbox picks the page, Select All picks every row**: the page rule of AGENTS.md, and the
  AC's "all at once" through the selection bar, as legacy's header did.
- **Columns as legacy**: the five groups in the table, Others only in the summary (AC).
- **Batches of 100 ids**: keeps the URL short at country level; partial approval reported.
- **Final Approval keeps a confirmation**: it changes several forecasts at once and cannot be
  undone.
- **Send only ids from a fresh list**: guards the backend approving any status.
- **Real writes on the local instance** for the browser check: forecasts prepared, authorized and
  approved on N003, then final-approved as testbuq4 and removed after (as FM-107).
- **Branch from FM-107**, which is not merged.
