# FM-67: Kit Unpack

https://openlmis.atlassian.net/browse/FM-67 · Parent: [FM-62](https://openlmis.atlassian.net/browse/FM-62) Stock management

## Scope

The Unpack screen for one program at the user's home facility, and its page on the shared stock
program picker ([FM-63](https://openlmis.atlassian.net/browse/FM-63)). Unpack is a third kind in
the shared stock event editor that Adjustments ([FM-66](https://openlmis.atlassian.net/browse/FM-66))
built and Issue ([FM-64](https://openlmis.atlassian.net/browse/FM-64)) generalised. Every place
Unpack differs becomes a policy field of `EventKindConfig` that every kind sets; no component
checks for Unpack by name.

In this PR:

- The policy fields Unpack needs, set for Adjustment and Issue to what they do today, in their own
  commits before any Unpack code.
- Unpack's kind, routes, nav entry, payload expansion, reason configuration and copy.
- Kit contents (`orderable.children`) typed in `reference-data`, shared with Products.

Not in this PR:

- Offline. Legacy does not open Unpack offline (the route has no `isOffline` and the nav link is
  disabled offline), so neither does the new screen. One legacy path remains: a user who already
  has the editor open and loses the connection can still submit, and legacy queues the event
  locally, with raw keys on the Submit label and toast (`adjustment-creation-toolbar.html:7-9`,
  `stock-event-repository-impl.js:64-71`, controller `:617-620`). The new screen does not queue: an
  offline Submit gets the shared offline failure and keeps the draft. The offline pass (FM-166)
  decides whether Unpack joins the queue; recorded there, not built here.
- Receive ([FM-65](https://openlmis.atlassian.net/browse/FM-65)), planned in parallel. The shared
  policy names below are proposed to its plan; see Shared With Receive.
- Physical Inventory ([FM-68](https://openlmis.atlassian.net/browse/FM-68)). Unpack does not wait
  for it.

## Summary

Some products are kits: a box that holds a fixed set of other products, such as a delivery kit
with gloves, a cord clamp and a razor blade. An administrator records a kit's contents on the
product's Kit Unpack List tab. When a storeroom manager opens kits, they record it on the Unpack
screen: the kits go down and the products inside go up.

In legacy, the manager picks a program, then picks a kit (and its lot, if the kit has lots) and
clicks Add. Each line shows the kit, its pack size, stock on hand, the quantity to unpack and the
date. Clear empties the list; Submit asks "Do you, administrator, wish to confirm the 2 stock
unpacking events?" and records one event: each kit line takes stock off the kit, and each product
inside gets the kit quantity times its count in the kit. There is no signature, no reason to pick
and no print. The event does not appear in Transaction History, only on the stock cards.

The new screen works the same way, on the same editor as Adjustments and Issue, with these
changes:

- A quantity above the kit's stock on hand is refused on the line. Legacy forgets this check, so
  the server refuses the whole event with a technical message.
- Decimals, negative numbers, zero and future dates get a clear message. Legacy turns "1.5" into
  15, shows raw message keys for zero and for the Total Quantity header, and sends a typed future
  date.
- Adding the same kit twice works. In legacy, two lines of one kit (even different lots) share
  one copy of the kit's contents, so the event sends wrong amounts and the server refuses it.
- If the deployment's kit unpack reasons are missing or wrong, the screen says so before the
  manager fills it in, instead of failing on Submit.
- One screen works on desktop, tablet and phone. Legacy has no phone version of Unpack.
- An empty kit picker says no kits have stock in this program; an unmatched search keeps the
  shared no-matches message.
- Both quantity sizing modes reserve readable placeholders and at least five digits per input.
  Every stock event layout sizes the quantity column in its header, including pack separators,
  so narrow tables scroll sideways without shrinking the controls.

  content line ends up `q1 x q2 x count` with the last line's date, and the server refuses it

- **Submit:** invalid lines raise "Adjustments have invalid fields" (Adjustments' key). Valid lines
  ask "Do you, {username}, wish to confirm the {number} stock unpacking events?" (Confirm, Cancel),
  counting kit lines; no signature (`:433-460`). Success toast "Stock unpacking event has
  successfully been submitted", then Stock On Hand for the facility and program; no print.
  Failure shows the server's message and keeps the lines.
- **Expansion** (`adjustment-creation.controller.js:718-740`, on a copy of the lines):

  ```js
  lineItem.orderable.children.forEach(function(constituent) {
      constituent.reason = { id: UNPACK_REASONS.UNPACKED_FROM_KIT_REASON_ID };
      constituent.occurredDate = lineItem.occurredDate;
      constituent.quantity = lineItem.quantity * constituent.quantity;
  });
  ```

  The payload (`adjustment-creation.service.js:79-164`) lists every kit line first, then each
  kit's contents in turn:

  | Line | `orderableId` | `lotId` | `quantity` | `reasonId` | `occurredDate` | Other |
  |---|---|---|---|---|---|---|
  | Kit (debit) | kit | kit line's lot or `null` | doses | `KIT_UNPACK_REASON_ID` | line date | `extraData.vvmStatus` if set |
  | Content (credit) | `child.orderable.id` | `null` | kit line's doses x `child.quantity` | `UNPACKED_FROM_KIT_REASON_ID` | kit line's date | `extraData: {}` |

  Event: `programId`, `facilityId`, `signature: null`, no `eventOrigin`, no document number. The
  multiplier uses the kit line's doses, not packs, and the server uses the same formula.
- **Reasons:** two build constants with the ids of the reasons stockmanagement's migration
  `20190325160137376__add_kit_unpacking_reason.sql` creates: "Unpack Kit"
  `9b4b653a-f319-4a1b-bb80-8d6b4dd6cc12` (`DEBIT`, `AGGREGATION`) and "Unpacked From Kit"
  `0676fdea-9ba8-4e6d-ae26-bb14f0dcfecd` (`CREDIT`, `AGGREGATION`), set in
  `openlmis-stockmanagement-ui/config.json` and compiled into test's bundle. Legacy also loads
  valid reasons filtered to `AGGREGATION` but never uses them; on test none is assigned.
- **Server** (stockmanagement):
  - `DefaultUnpackKitValidator:50-128` treats an event as an unpack when a line has the server's
    configured unpack reason (`stockmanagement.kit.unpack.reasonId`, same default id). Each such
    line's product must be a kit; the other lines, summed per product, must equal exactly the kit
    quantities times the contents, or it refuses "not fully accounted for" / "extra constituents
    were credited".
  - `ReasonExistenceValidator` checks only that a reason exists: no valid reason assignment needed.
  - `ApprovedOrderableValidator` only refuses product ids that do not exist: its "approved" list
    is a plain `GET /orderables?id=` of the line products (`StockEventProcessContextBuilder:166-174`).
    Contents not approved for the facility type are accepted and get stock cards, but stay out of
    Stock On Hand, whose v2 list is built from approved products.
  - An event with no reason on any line and no source or destination is a physical inventory
    (`StockEventDto:124-128`); every legacy content line carries its reason anyway.
  - When the event is not detected as an unpack (the server's reason id differs from the one
    sent), `DefaultAdjustmentReasonValidator` runs and refuses it: "Reason category AGGREGATION is
    not valid for this adjustment event."
  - `LotValidator` checks only lines with a lot, so a lot-tracked content product is credited to
    its no-lot card, as legacy.
  - Content quantities are summed per product with `summingInt`
    (`DefaultUnpackKitValidator:76-83`), so a total above the Java int maximum wraps.
  - Below-zero stock is refused during recalculation with "would make the stock on hand below
    zero", which is what an over-stock unpack shows today.
  - Stock cards are created for contents with no card yet.
  - `eventOrigin` is optional; without it the event has no document number, cannot be reversed, and
    never matches Transaction History's `eventOrigin IN (...)` filter.
- **Referencedata:** `children: [{ orderable: { id }, quantity }]` on every orderable in
  `GET /api/orderables` (no `versionNumber`); no kit filter.
- **Timing on test:** Family Planning ready in about 0.9 s; Essential Meds about 24 s (2 MB v2 list
  plus 256 orderable requests).
- **Phone:** no separate flow; the desktop table scrolls sideways at 390 px.
- **Test data on test.openlmis.org:** no kits. All 10,233 orderables have empty `children`. Both
  reasons exist; neither is assigned in valid reasons, which the server does not need.

### Data Flow

- **Routes:** `/stock-management/unpack` (picker) and `/stock-management/unpack/$programId`, search
  `page`, `size`, `keyword`, through the shared `-stock-event-program-picker.tsx` and
  `-stock-event-editor.tsx`.
- **Loader:** the shared editor loader, unchanged in what it blocks on. It prefetches, deferred,
  the stock cards always, valid reasons only when the kind picks reasons
  (`reasons !== null`), destinations only for `counterparty: 'destination'`, and the reasons list
  when the kind expands kits (`contents.type: 'kit'`).
- **Kits offered:** `kitCards(cards)`: `children.length > 0` and `stockOnHand !== 0`, as legacy;
  expired lots stay. The picker label and the product column read "Kit" through the kind's copy.
- **Fresh kits at Submit:** each draft line keeps the kit record it was added with (`newEventLine`
  copies `card.orderable`), from the 30 s stock query, so an administrator may have changed a
  kit's contents since. Products' saves refresh `orderables.list` but not the stock list, so
  re-adding the kit would not help either. So Submit refreshes the draft's kits **before**
  validating and confirming, with
  `fetchQuery({ ...orderablesByIdsOptions(kitIds), staleTime: 0 })` (a key Products' saves already
  invalidate), as a kind step that runs only for `contents.type: 'kit'`:
  - The editor's pending state covers the refresh, validation and the post, not only the POST
    mutation: Submit, Clear, Add, every line control and dialog dismissal stay disabled, and the
    discard guard sees it as pending. So nothing can change between what the user confirms and
    what is posted.
  - `mutation.isCurrent()` is checked before the read and after it settles, success or failure.
    `fetchByIds` (reference-data, behind `fetchOrderablesByIds`) captures `getSessionScope()` and
    checks it before each batch, as AGENTS.md requires of multi-request operations; every caller
    gains this.
  - A failed or offline read shows the existing failure dialog and keeps the draft.
  - The fresh `children` are written into every line of each kit, keeping quantities, dates and
    lots, then the form validates against them. A draft that captured a broken kit (no count,
    a negative count, no contents) therefore recovers on the next Submit once an administrator
    fixes the kit, rather than failing validation before any refresh could run.
  - When any kit's contents changed, Submit stops with "Kit Contents Changed" and the updated
    lines on screen. The dialog names the changed kits and asks the user to submit again.
    The stock list is refreshed so the picker and newly added lines use the fresh contents.
    Otherwise the confirmation opens; Confirm posts with no further read,
    expanding from the lines' just-refreshed contents.
  This keeps the event matching the server's reconciliation, which would otherwise refuse it as
  "not fully accounted for". A change saved between the refresh and the post is refused by the
  server with its message. Products' own fresh whole-record reads are untouched.
- **Reason check:** `unpackReasons(reasons, config)` resolves the configured ids against the
  reasons list: the debit must be `DEBIT` and `AGGREGATION`, the credit `CREDIT` and `AGGREGATION`,
  as agreed for this ticket. This is stricter than legacy and the server, which check only that the reasons
  exist; it can only block a deployment that points the ids at reasons of another category, which
  legacy's reason screen cannot create (type and category are locked on edit). A missing setting,
  an unknown id or a wrong type or category renders a "Kit Unpack Is Not Set Up" alert above the
  table naming the setting, and keeps Add and Submit disabled. A failed reasons request shows the
  shared load error with retry.
- **Expansion:** pure `expandKitLines(lineItems, childrenPerItem, reasons)` in `lib/kit-unpack.ts`
  takes the built line items and each kit line's fresh children separately, returning a new array
  (kit lines with the
  debit reason, then each kit line's contents in order) and never mutates its inputs, the cached
  kits or the draft.
  Every line expands from its own quantity, so two lines of one kit give the server the totals it
  expects. `contentTotalsTooLarge` returns the indexes contributing to content product totals above
  the Java int maximum, so the form refuses them on their quantity fields. The server sums these
  quantities in an `int`. `eventPayload` stays the single builder and
  calls the kind's expansion last.
- **Confirmation:** `confirmation: 'confirm'` opens `SubmitConfirmDialog`, an AlertDialog with a
  title ("Confirm Kit Unpack", which legacy lacks) and legacy's sentence, "Do you, {user}, wish to
  confirm the {count} stock unpacking events?" (ICU plural), counting kit lines. It reuses the
  editor's existing `username` prop, which both routes already pass from the auth store. Confirm
  calls the same `confirmSubmit` with no signature; Cancel keeps the draft. Issue and Adjustment
  keep the signature.
- **After submit:** success toast, stock queries invalidated as today, then Stock On Hand for the
  facility and program, as Adjustments. No print.
- **Draft, filter, paging, Clear, session checks:** unchanged shared behaviour. The discard
  guard now covers the pending post for every kind, a deliberate improvement.

### Shared With Receive

Proposed to FM-65 before either builds, so both plans use the same names:

- **Field names and values:** `counterparty` gains `'source'` (Receive owns it);
  `confirmation: 'signature' | 'confirm'`; `scanning: boolean`; `layout: 'measured' | 'thresholds'`;
  `reasons: ((assignments) => Reason[]) | null`; `eventOrigin: ... | null`;
  `contents: { type: 'none' } | { type: 'kit'; copy: ... }` (Receive sets `type: 'none'`); `copy` gains `pickerTitle`, `make`,
  `pageDescription`, `editorTitle`, `editorDescription`, `product`, `clearTitle`,
  `clearDescription`. The crumb stays a literal `crumbKey` in each route's `staticData`.
- **Ownership:** Unpack owns `contents`, `confirmation`, `scanning`, `layout`, nullable `reasons`
  and `eventOrigin`, and the copy fields. Receive owns `'source'`, its product source (approved
  products searched on demand, which Unpack does not touch, since Unpack keeps `cardFilter` over
  stock cards) and new-lot scan policy. Neither adds options for the other.
- **Query keys:** Unpack adds none. It reuses `queryKeys.orderables.list` and `reasons.list`.
  Receive adds the valid sources lookup beside `validDestinations`.
- **Runtime config:** both follow `defaultIssueReasonId` (Receive: `defaultReceiveReasonId`;
  Unpack: `kitUnpackReasonId`, `unpackedFromKitReasonId`).
- **Commits:** shared editor changes land in their own `refactor:` commits ahead of the kind's
  `feat:` commit. Whichever merges second rebases onto it, adopts the merged names, and reruns
  every kind's regression checks (unit, component, route tests, and the stubbed browser pass on
  Adjustments, Issue and its own kind).

### Risks And Edge Cases

- **Server's unpack reason differs from the UI's.** The server detects an unpack by its own
  configured reason id. If a deployment changed one side only, the server runs its adjustment
  check instead and refuses the event ("Reason category AGGREGATION is not valid for this
  adjustment event."); the error dialog shows that and keeps the lines. The deployment guide says
  both must match; the UI cannot read the server's setting.
- **Contents not approved for the facility type:** the server accepts them and creates their
  stock cards, but Stock On Hand does not list them, as in legacy. An administrator setting up a
  kit should approve its contents; the deployment guide's kit note says so.
- **Kit contents changed during the draft:** caught at Submit (above). Contents changed after the
  fresh read and before the post are refused by the server with its message.
- **Backdated unpack dipping a kit card below zero, or two lines of one kit lot exceeding stock
  together:** refused by the server, as on Issue.
- **Slow product list on large programs:** same as Issue (about 17 to 22 s for Essential Meds on
  test); only the Kit picker waits.
- **Reverse:** unpacks have no `eventOrigin`, so they are not in Transaction History and cannot be
  reversed, as legacy.
- **FM-68 conflict:** Physical Inventory's branch also widens `Orderable`. Whichever merges second
  combines both fields.

## Decisions

- **Full legacy parity in logic**, including the payload, the kits offered (expired lots stay),
  the confirmation and the landing. The fixes are the over-stock check (the ticket's AC), the
  input defects FM-62 lists, the raw keys, and two lines of one kit, which legacy cannot submit.
- **Online only.** An offline Submit fails and keeps the draft; legacy's queued path for an
  already-open editor goes to the offline pass to decide.
- **Contents are read from the kit's `children`** through reference-data; no separate lookup.
  For strict parity (decided 2026-10-12) the screen does not show a kit's contents, so the
  content products are never hydrated: the expansion needs only their ids and counts. Submit
  expands from a fresh `orderablesByIdsOptions` read of the kits, a key Products' saves already
  invalidate, not from the 30 s stock list.
- **Receive is not messaged** (decided 2026-10-12). The Shared With Receive section stays a
  proposal in this plan; whichever of FM-65 and FM-67 merges second rebases onto the other and
  adopts its names.
- **The reasons are verified against `GET /stockCardLineItemReasons`**, not valid reasons:
  stockmanagement does not need them assigned, and on test they are not, so a valid reasons check
  would always fail. This swaps legacy's unused valid reasons call for this one.
- **Reason ids come from `config.json`**, as `defaultIssueReasonId`; the code has no default, so a
  missing value shows the not-set-up state. The container's entrypoint defaults unset values to
  the standard migration ids, as legacy's `config.json` and the server do, so existing
  deployments work without new settings.
- **No `eventOrigin`**, as legacy, so unpacks stay out of Transaction History.
- **Policies, not kind checks:** Unpack adds `contents`, `confirmation`, `scanning`, `layout` and
  nullable `reasons`/`eventOrigin`; Issue's existing `kind === 'issue'` layout checks become
  `layout`, so Receive can share them.
- **The real submit check runs on test.openlmis.org** as `srmanager2`, after the test data above
  is created with the user's permission.
