# FM-111: Reports

https://openlmis.atlassian.net/browse/FM-111

## Scope

Planning for the Reports epic and its four stories: FM-112, the port-or-rewrite spike;
FM-113, View Reports; FM-114, report parameters and output; FM-115, embedded dashboards.
Research date: 14 November 2026. This is a proposal, not implementation approval.

Recommendation: rebuild the user-facing screens while retaining the existing Jasper
templates, report calculations, output services and configured dashboard definitions.
The decision and its limits are in [FM-112](FM-112.md). Country reporting requirements
are unknown; the user explicitly requested technical exploration without them.

Administration of dashboard reports and categories remains in FM-162 and FM-163 under
FM-154. Template administration, analytics/data-pipeline replacement, new country
reports, deployment changes and offline reporting are outside this proposal. Shared
shell/authentication changes and backend fixes get separate scoped PRs if required.

FM-111 is an Epic. Do not transition it through ticket closeout automation.

## Summary

Reports lets users find a report, choose its inputs and generate a file, or open a
dashboard. The legacy test instance currently offers six downloadable reports in one
category. It also has seven dashboard records, although none is available to the demo
account and the configured dashboard host cannot be reached.

The new UI should keep those reporting capabilities and calculations. Reports will
remain grouped by category. Each report will open a form with the same fields, labels
and choices, presented using the app's existing controls. The proposed output choices
are PDF, CSV, XLS, XLSX and HTML, preserving all five legacy choices.

The improvements are clearer report titles, complete searchable choices, reliable
dependent fields, useful errors, and layouts that work on phones and in Arabic.
Dashboard integration must be verified against a working configuration before it is
called complete. This research does not establish which reports countries need or
whether the current report calculations satisfy those needs.

### Data Flow

- Proposed routes: `/reports`, `/reports/$module/$reportId/generate`, and
  `/reports/dashboards/$dashboardId`. Keep module identity to avoid collisions and support
  configured report modules. Generated route-tree code is never edited manually.
- Await the REPORTS_VIEW guard, then prefetch catalog/category/dashboard queries without
  awaiting them. Render Workspace/header immediately. Use QueryBoundary around category
  content, with independent recoverable failures so a dashboard outage does not erase
  the usable Jasper catalog. A failed module must be named, not silently treated as empty.
- Parameter/detail routes may await metadata to establish existence/access. Keep lookup
  loading inside the form. Independent choices load in parallel; a failed optional lookup
  has Retry and an explanation, without destroying other typed values.
- Add query scopes for templates, report categories and available dashboards. Viewer keys
  and option results are owner/session scoped; dashboard availability is not a global
  administrative list. Future FM-162/163 saves invalidate the corresponding roots.
- Keep form values local, not in URL query strings. Route module/id identify the report;
  return links keep list context if later added. Do not persist guest tokens or report
  output in offline storage. Generation uses identity checks and the existing delivery
  lifecycle so late responses cannot open for another signed-in user.
- Module list and Superset host are deployment-varying. Preserve the configured legacy
  module set rather than deriving it from the six observed IDs. Add runtime config only
  where needed, defaulting core modules to common,requisitions; map legacy SUPERSET_URL
  into runtime configuration as part of the dashboard story, not a compiled-in hostname.

### Server-Side Work

Keep report calculations, data permissions and exports on existing servers. Browser work
is grouping the small catalog, rendering/validating metadata controls and hosting output.
Do not move SQL, Jasper logic or Superset chart calculations into React.

Legacy loads entire option sets and searches them locally, without explicit page loops.
Fetch complete paged results for parity and virtualize large controls. Where endpoint
search can preserve the same set and submitted value, use server search/paging rather
than downloading every product up front. Search By Name and Search By Code remain
distinct for orderables. Verify selected values remain selectable outside the current
page. Query keys include endpoint, method, normalized body, dependencies and identity;
identical lookup requests can share cache results.

Dashboard discovery in reviewed master pages candidate rights first, then pages the
filtered reports again. A simple client page loop is not proven to recover every item.
Establish a reliable deployed unpaged contract or fix filtering-before-paging in a
separate backend PR. Do not report a partial dashboard inventory as complete.

has been established. No cross-feature imports except reference-data.

### Business Rules And Deliberate Corrections

1. REPORTS_VIEW is unscoped. Report-specific generation/dashboard rights remain separate;
   general access or administrator status does not imply every dashboard is available.
2. Render controls by metadata semantics: datepickers, booleanSelect, lookup/static
   choices, integer, then source-supported text. DTO Java classes can still be selects.
   An empty or failed lookup must not silently become a free-text input. No multiselect
   renderer is evidenced by the deployed forms or generic legacy markup.
3. Preserve false and zero values. Integer input is nonnegative whole-number text;
   legacy's report control permits Number.MAX_SAFE_INTEGER rather than imposing Java int
   bounds. Verify the receiving report's actual limit before choosing a stricter bound.
   Reporting Rate DueDays may stay blank for the server's default of 10. Do not introduce
   a negative-days feature or a new date-range restriction without an established rule.
4. Keep observed blank defaults and returned parameter order. Non-null defaults and
   unusual dependency/property metadata need explicit fixtures before support is claimed.
5. On dependency change/clear, clear the child value and cancel/ignore stale option
   responses. Timeliness Period depends on Program; Reporting Rate Period does not.
6. Parse selectBody as JSON and send its actual content, defaulting an absent POST body
   to {}. Timeliness requests level 3 in metadata but legacy hardcodes level 2 whenever a
   body exists. Recommend honoring metadata, explicitly pending approval because it
   changes offered districts. Reporting Rate remains level 2.
7. Use same-origin API option paths, supported read methods and encoded dependency
   values. Do not execute arbitrary metadata JavaScript or send bearer credentials to
   external URLs. Unsupported/malformed metadata shows a useful error rather than a
   fabricated empty list. Do not silently rewrite historical GET endpoints into POSTs.
8. Serialize dates as YYYY-MM-DD without timezone shifts, retain exact parameter-name
   case, encode query values and omit unset optional values. Do not copy literal
   undefined parameters or token-bearing report URLs from legacy.
9. Group by category ID, with a safe uncategorized fallback. Do not merge different
   categories merely because their names match, or lose reports with absent categories.

### Output And Dashboard Integration

Proposed formats: PDF opens through an authenticated blob; CSV, XLS and XLSX download;
HTML downloads as a file. This preserves format availability while avoiding insertion
of generated HTML into the app. HTML's delivery differs from legacy's new tab and needs
approval. Verify complete HTML assets before promising a standalone usable HTML export.
No client-side spreadsheet/PDF conversion library is needed. Check actual file signatures,
extensions, names and error blobs: reviewed common XLS export advertises an XLSX MIME type.
The client-only POST /api/reports/generate is not a human-user runtime endpoint.

Dashboard mode is metadata/configuration driven:

- embeddedUuid: use a compatible bundled Superset Embedded SDK and the existing guest
  token callback. Token issuance/renewal must be authorized server-side for that enabled
  dashboard. Reviewed backend only checks REPORTS_VIEW and registered UUID existence;
  it omits the dashboard-specific right/enabled check. This source finding needs a
  separate backend fix and acceptance tests before this mode is signed off. Client
  membership checks cannot repair the endpoint's authorization gap.
- URL-only SUPERSET: preserve a verified cookie/OAuth integration. Legacy calls
  `<Superset>/oauth-init/openlmis?redirect_url=...`, may perform credential verification
  and OAuth approval through `/api/oauth/token` and `/api/oauth/authorize`, returns via
  Superset `/oauth-authorized/openlmis`, and requests `/lang/change/{locale}` before
  hosting the configured URL with standalone=true. Do not assume an iframe inherits
  Axios Authorization or copy credentials into legacy localStorage. Plan exact requests
  and consent behavior in FM-115 after a working environment is available.
- POWERBI is supported by source as a URL iframe but not present in this inventory.
  Record that branch in FM-115 rather than silently treating every dashboard as Superset.

Both modes need valid host/configuration, allowed embedding origins and compatible frame
headers. OAuth also needs working callbacks/cookies. An iframe load event alone cannot
prove success rather than a login/error page. Shell Arabic support does not establish
Arabic charts: legacy's Superset locale allowlist is en/fr/pt. Keep server credentials
server-side and guest tokens in memory. Do not invent a replacement token service.

### Home Dashboard Embedding: Additional Source Exploration

The user additionally requested exploration of embedding on the dashboard. This section
records source behavior; it does not approve implementation or claim successful live
embedding. Home and Reports use different legacy hosts around the same report metadata.

Home is extended by referencedata-ui's home template, which includes
`openlmis-home-page-report` beneath notifications and alerts. Its controller skips work
when initially offline, then requests
`GET /api/reports/dashboardReports/availableReports?showOnHomePage=true` and chooses
`content[0]`. No record means no report panel. The save service clears Show On Home Page
on other records when one is saved with that flag, so the intended model is one configured
Home report, not a grid of every dashboard. Do not change that setting during research.

Home discovery still filters enabled reports by their individual rightName, but
deliberately skips the general REPORTS_VIEW check. Reports navigation/viewer requires
REPORTS_VIEW. The guest-token endpoint always requires REPORTS_VIEW, creating a source
contract mismatch for a user entitled only to the Home report. Validate and resolve
that mismatch explicitly; do not silently add a new global Home access requirement.
The discovery pagination and guest-token authorization defects described above also apply.

| Mode | Home Host | Reports Viewer Host |
| --- | --- | --- |
| SUPERSET with embeddedUuid | SDK mounts configured UUID using SUPERSET_URL and guest-token callback; no OAuth check | Same SDK and token callback; skips OAuth modal |
| URL-only SUPERSET | Checks existing Superset authorization with cookies; renders configured URL only if isAuthorized=true; authorization event reloads Home | Resolves OAuth modal first, changes Superset locale, then renders URL with standalone=true and a manual authorization link |
| Non-Superset, including POWERBI | Trusted configured URL in iframe, no Superset authorization | Trusted configured URL in iframe, no Superset authorization |

Home's URL-only branch does not itself present the Reports viewer OAuth dialog. A
false authorization result leaves the panel hidden, and its discovery/authorization
promises have no local failure presentation. Unlike the viewer, it does not append
standalone=true or request a Superset locale change. Preserve these distinctions in
the compatibility evidence; recommend a useful in-place authorization/error state
rather than silently copying an invisible panel.

In both Embedded UUID hosts, the legacy downloads
`SUPERSET_URL/static/superset-embedded-sdk.js`, evaluates it with new Function, then calls
embedDashboard with id, supersetDomain, mountPoint and fetchGuestToken. The callback
reads the OpenLMIS guest-token endpoint; the report service obtains a Superset guest
token through its server-side admin login/CSRF flow. Admin credentials remain on that
server. Both hosts hide the dashboard title, retain chart controls and tabs, and show
filters initially collapsed. The SDK still creates an iframe; this is not a port of
Superset chart code into the app.

The SDK mount element remains in the DOM while hidden through ng-show. The viewer also
defers mounting with $timeout to avoid the cached-SDK/missing-element race. Home sizes
its panel at 95vw by 90vh, with the injected iframe stretched to fill it. Those viewport
dimensions should become container-fitting layout in the new shell.

Neither reviewed controller retains the returned embed handle or defines a teardown
hook; Home also registers a root authorization listener without retaining its removal
function. These are source lifecycle risks, not reproduced leaks. For a React host,
mount after the element ref exists, cancel obsolete initialization, dispose the SDK
instance/listeners on unmount or identity/report change, and verify token renewal/error
behavior against the chosen SDK version. Do not copy remote code evaluation or loosen
the app's CSP to support it. Bundle a compatible SDK instead.

The legacy layout generates CSP allowances from SUPERSET_URL/EXTERNAL_DOMAINS, including
frame-src and unsafe-eval for its loader. The new UI needs the actual embedding origin
and deployment frame policy; it does not need legacy's script evaluation workaround.
Superset configuration must independently permit the app's origin and guest access.

The React Home currently renders its own requisition/order/CCE summaries and charts;
it does not fetch availableReports or embed configured report dashboards. Proposed
reuse is one Reports-owned embed host composed by both routes. The Home route can
import Reports alongside Home and place the host beneath its existing dashboard;
Home feature components must not import the Reports feature. Keep Home's report query
independent, deferred and online-only, and include showOnHomePage plus session identity
in its query key. An embed failure must leave other Home cards usable.

## UI/UX

| Area | Port | Improve / Deliberate Difference |
| --- | --- | --- |
| Catalog | Category headings and report links; same visible report set | Responsive category cards; omit empty groups; separate recoverable failures |

dashboards. Category Card composition contains ordinary accessible links. Forms use
the existing labelled fields and one Format choice group, PDF selected by default.

requests while invalid or already pending. Show errors on submit then correction. No
new generic report table, custom chart platform or ornamental redesign is needed.
