# FM-158: Equipment Catalog Upload

## Scope

The Administration > Equipment page (legacy "Manage Cold Chain Equipment Catalog"): export the
CCE catalog as CSV and upload an edited CSV. As the ticket asks, the CSV export/upload workflow
built for Ideal Stock Amounts becomes one shared component used by both pages; Ideal Stock
Amounts keeps its behaviour and English text, only its implementation and generic keys move.
Adds the `CCE_MANAGE` right, the route, navigation and translations.

Out of scope: any backend change (services stay on master, nothing is proposed to them); a
catalog list or editor; the CCE inventory screens; Data Import.

## Summary

The equipment catalog lists the cold chain equipment models (refrigerators, freezers, cold
boxes) that facilities pick from when they register equipment. Administrators maintain it by
downloading the whole catalog as a spreadsheet, editing it and uploading it back. Each row
updates the matching model or adds a new one; nothing is deleted, and a model is retired by
marking it archived. The whole file is accepted or rejected at once.

Legacy does this on one page: Export, a block of instructions, a file picker and Upload. The
instructions spill sideways on phones, Upload is always enabled, and a failed upload shows a
toast, a modal and an inline error for the same problem.

The new page is the same screen administrators already use for Ideal Stock Amounts: one card
with an Export section and an Upload section, an Update Instructions dialog, a clear file
chooser, the server's error on the page with the file kept, and a success message with the
number of records processed. Both pages now share one component, so they stay identical and
later CSV pages can reuse it.

### Rules

- Client checks only that a file is chosen, its name ends in `.csv` in any case and it is not
  empty; never judge by MIME type. The server owns everything else.
- Send the original bytes; never parse, split or rewrite the CSV. Name the multipart part
  `file` with the name's extension lowercased (`file.name.replace(/\.csv$/i, '.csv')`): the
  server's `.csv` check is case-sensitive (`BaseController.java:126-132`). Set
  `Content-Type: multipart/form-data` explicitly (the client defaults to JSON) and a
  300,000 ms timeout on the upload only.
- Validate the upload response: `amount` is an integer >= 0; anything else is an uncertain
  outcome. A header-only file succeeds with 0.
- The upload is all or nothing (`@Transactional`, 250-row chunks) and the server reports only
  the first error, so the page shows one message.
- Keep the file after any failure, as legacy; reset after success, without a reload.
- Never retry the POST automatically. No response, timeout or 5xx is an uncertain outcome: keep
  the file and say to export and check before retrying.
- Show the server `message` as text when it is a real message. Ideal Stock Amounts passes
  `referenceData.error.upload.file.empty` (no English text) to map to the empty-file text; CCE
  passes none, its `cce.error.file.empty` reads "File is empty.". Spring, HTML and 5xx bodies get
  the translated fallback; 413 the file-too-large text.
- Explain known CCE refusals (user, 2026-10-30): read the `messageKey` and the values inside the
  English `message` (`messages_en.properties`, `CsvHeaderValidator.java`, `csv/processor/`) and
  show a translated sentence that says what to change, with the server's own text below it
  ("Server message: ..."). Unknown keys, or a message whose format does not match, show the
  server text alone, as today, so the page is never less informative than legacy:

  | `messageKey` and server values | Shown (English) |
  |---|---|
  | `cce.error.upload.header.invalid`, `[maker, foo]` (every unknown heading, lowercased) | The file has columns the catalog does not use: maker, foo. Compare the headings with an exported catalog; letter case does not matter. |
  | the same key with a heading starting with U+FEFF | The file starts with a hidden byte order mark, which Excel adds when saving as CSV UTF-8. Save it as CSV (Comma delimited) and upload it again. |
  | `cce.error.upload.mandatory.columns.missing`, `[Type, Model]` (every missing column) | Required columns are missing: Type, Model. Add them back from an exported catalog. |
  | `cce.error.upload.header.missing`, column number | Column {column} has no heading. Copy the headings from an exported catalog. |
  | `cce.error.upload.record.invalid`, row N, `'x' could not be parsed as an EnergySource` | Line {N+1}: "x" is not an energy source. Use ELECTRIC, SOLAR, GASOLINE or NOT_APPLICABLE, in capital letters. |
  | the same, `... as a StorageTemperature` | Line {N+1}: "x" is not a storage temperature. Use PLUS4 to PLUS1, ZERO or MINUS1 to MINUS20, in capital letters. |
  | the same, `... as Dimensions` | Line {N+1}: "x" is not a valid size. Enter three whole numbers separated by commas, for example 60,70,90. |
  | the same, `... as an Integer` | Line {N+1}: "x" is not a whole number. |
  | the same, any other reason | Line {N+1}: {server reason} |
  | the same, `null value encountered` (an empty required cell; the server's `NotNull` rejects it while parsing, so `cce.error.catalog.field.required` never reaches a CSV upload) | Line {N+1}: a required cell is empty. Every line needs a value in From PQS catalog, Type, Model, Manufacturer, Energy source, Storage temperature, Archived. |
  | `cce.error.catalog.duplicateInFile`, manufacturer and model (raised for the same manufacturer and model, or the same PQS equipment code and model, `CatalogItemWriter`) | The file has more than one line for the same model: manufacturer {manufacturer} and model {model}, or one PQS equipment code with that model. Keep only one of them. |

  The server counts data rows from 1, so its row N is spreadsheet line N + 1. It still stops at
  the first refused line, so the page names one problem per upload, except the header checks,
  which list every unknown or missing column at once.
- Failure stays on the page (no failure toast); success and export failure use toasts with a
  Title Case title and a description.
- Catalog facts the instructions rely on: headers match in any case and order; mandatory
  columns are From PQS catalog, Type, Model, Manufacturer, Energy source, Storage temperature,
  Archived; Energy source and Storage temperature are exact-case values; a row matching an
  existing model replaces the whole record, so an empty cell clears the stored value; rows
  are never deleted (`CatalogItemWriter.java:50-147`, `CsvBeanReader.java:65-67`).
- Functions at the server boundary declare their return types, as `uploadIdealStockAmounts`
  does today: `exportCsv(path): Promise<Blob>`, `uploadCsv(path, file): Promise<UploadResult>`
  and the feature wrappers `exportCatalog`/`uploadCatalog` and their Ideal Stock Amounts
  counterparts. `UploadResult` is `z.infer<typeof uploadResultSchema>`, the only upload result
  type; the per-feature result types go.
- Never log or report the `AxiosError`, the `FormData` or the file's content: the error's
  `config` carries the bearer `Authorization` header and the request body. Server messages
  render as React text only, never as HTML. Export keeps the bearer header through
  `fetchReport`; no token ever goes into a URL. Today the upload logs nothing, and it stays
  that way: every failure is shown on the page only.
- RTL follows AGENTS.md (Right-to-left support). Only logical utilities in the moved and new
  code. No icon on this page flips: Download, Upload, Paperclip, BookOpen, Refrigerator and the
  spinner have no reading direction. The instructions `<ol>` keeps its markers at the inline
  start. Filenames keep `FileField`'s `dir="auto"`. The server's English `message` is shown
  inside an isolated `dir="auto"` element (`ErrorAlert`'s `description` widens from `string`
  to `ReactNode`, a compatible change), so its punctuation and quoted headers stay in order in
  the Arabic page. The success count and file size use the page language's number formatting,
  as on Ideal Stock Amounts today.
- Code comments follow AGENTS.md: only where the reason is not obvious from the code, one line,
  a full sentence ending with a period, no ticket or issue keys, no em dashes; clear names
  first. One-line `/** ... */` on exported helpers and on props whose purpose is not obvious
  (as in `form-fields.tsx`), `//` above a surprising line (as in `download-file.ts`); every
  `biome-ignore` states its reason. Moved code keeps its existing comments.

### Risks And Edge Cases

- Excel "CSV UTF-8" adds a BOM; the server then rejects the first header (confirmed: 400,
  "Invalid Headers in upload file: [from pqs catalog]." with the invisible BOM inside the
  brackets, so the named header looks correct to the user). Show its message; do not rewrite
  the file.
- The server counts data rows, not file lines: "row 1" is the first line after the header, so
  it is line 2 in a spreadsheet. The explained message names the spreadsheet line (Rules).
- The explanations read the service's English `message` text. If a later cce release rewords
  it, the regex stops matching and the page falls back to the server text, as legacy; the test
  pins today's formats.
- Exact-case enums and whole-record replacement are covered by the instructions text, not by
  client parsing; a wrong case or a malformed Dimensions value gets a 400 naming the row and
  value (confirmed).
- Export checks no right on the server; the page stays gated as legacy.
- Size limits: the gateway nginx in ref-distro sets `CLIENT_MAX_BODY_SIZE=1m`, and the cce
  service keeps Spring Boot 2.2.2 multipart defaults (1 MB per file, 10 MB per request). A larger
  file gets a non-localized 413 from nginx; the file-too-large text applies. The test catalog is
  about 110 KiB.
- The extraction touches a shipped page: the moved suites and the Ideal Stock Amounts browser
  check guard it.
- The CCE inventory screens will read the catalog; their plan must invalidate that lookup after
  an upload.
- Upload failures reach nobody but the user: the app has no reporter beyond the browser
  console, so the team learns of an uncertain upload only if the user tells them.
- The service ships English messages only: known keys get a translated explanation, the rest
  show the English server text, which an Arabic page keeps in reading order.
- Other screens pass `serverMessage` text to `ErrorAlert` without isolation too (reasons, valid
  assignments). Widening `description` lets them adopt the same element later; changing them
  is outside this PR.

## Decisions

- **No backend change.** Only the cce endpoints on master; gaps are recorded as risks.
- **One shared CSV transfer component** in `src/components/file-transfer/` for both pages, as
  the ticket asks; feature APIs stay in their features and routes compose the shared
  component, the layout Valid Destinations and Valid Sources use with `valid-assignments/`.
- **Instructions as on Ideal Stock Amounts** (user, 2026-10-30: follow the previous plans): the
  concise Export / Edit / Upload steps and note in the shared dialog carry the legacy content;
  the legacy wording is kept in this plan only.
- **Ideal Stock Amounts unchanged** for users; only generic keys move to `file-transfer.*`.
- **Route `/administration/equipment-catalog`**, feature folder `cce-catalog`, so the CCE
  inventory screens keep their own names.
- **File kept after a failed upload**, as legacy CCE.
- **Browser checks on a local OpenLMIS instance** (user, 2026-10-30): real uploads happen only
  there; the shared test server takes no writes (its demo account was also refused that day).
- **One new test file**: the moved Ideal Stock Amounts suites cover the shared workflow; the
  test audit confirmed they detect every risk mutation. They gain a real response fixture, two
  assertions for the endpoint path and export filename the shared code now receives, and one
  case for explained errors; only the CCE error reading gets its own pure test (Tests).
- **Contract as the team works today** (team, 2026-10-30): API types by hand, no central
  contract check or generated types; the existing `uploadResultSchema` and error narrowing
  move unchanged, and the API functions get explicit return types since it is easy here.
- **Upload failures stay on the page** (team, 2026-10-30): the app has no third-party
  observability yet, so nothing is logged or sent; a reporter is a later improvement.
- **App-wide gaps stay out of this PR**: telemetry, normalized error parsing, security headers
  in `docker/nginx.conf.template`, token storage (kept in localStorage for legacy coexistence)
  and the login hook logging the whole `AxiosError` (a bug to fix, per the team) reach every
  page or another screen, so they get their own PRs. This plan only avoids adding to them.

- **Explained upload errors on the CCE page** (user, 2026-10-30): known `messageKey` values get a
  translated sentence with what to change, the server text stays below, unknown ones show the
  server text alone. No client-side CSV or header check: the server stays the only validator.
