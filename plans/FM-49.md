# FM-49: Create Order: Pick Facility

https://openlmis.atlassian.net/browse/FM-49 · Parent: [FM-39] Requisitions

Shipped in one PR with [FM-50] (the order table), branch `feat/fm-49-50-create-order`. The order
table, drafts and the API work shared by both screens are planned in [FM-50](FM-50.md).

## Scope

- New Create Orders page at `/requisitions/create-orders`, the live `nav.requisitions.create-orders`
  entry, behind `ORDER_CREATE` and shown in the menu only with `SHOW_REQUISITION_LESS_ORDER` on.
- Program, Requesting Facilities (added to a list), Supplying Facility and Create Order, which
  creates one draft order per requesting facility and opens the order table.
- Not in scope: the order table ([FM-50]); a list of existing drafts (legacy reopens drafts from
  View Orders, not yet migrated).

## Summary

A supply planner can order products for facilities without a requisition. On this first screen
they pick the program, the facilities that need products and the warehouse that will supply them.
Legacy offers every facility where the planner may create orders, and only the warehouses that
supply all of the chosen facilities for that program. Create Order immediately creates an empty
draft order per facility on the server and opens them side by side.

The new page keeps the same choices and rules and works on phones. It explains why no supplying
facility is offered when the chosen facilities share no supplier (legacy leaves the list empty),
and it stops before creating drafts the planner could not open afterwards: opening a draft also
needs a right to view orders, which legacy does not check, leaving such planners with drafts they
cannot see.

## Agent Brief

### API Map

| Step | Method And Path | Params / Body | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Program options | `GET users/{id}/programs` (`userProgramsOptions`) | | `id, name` | own user | `order-create-form.jsx#L91-L99` |
| Requesting options | none: `ORDER_CREATE` grants from `permissionsOptions`, named through `minimalFacilitiesOptions` | | `id, code, name` | | `facility.service.js#L171-L215` |
| Nodes per facility | `GET supervisoryNodes` | `programId, facilityId` | `id` | none | `helper#L30-L46` |
| Supply lines per node | `GET supplyLines` | `programId, supervisoryNodeId` | `supplyingFacility.id` | none | `helper#L49-L56` |
| Create drafts | `POST orders/requisitionLess`, one per facility | `{emergency: true, createdBy, program, requestingFacility, receivingFacility, supplyingFacility, facility}` (ids; requesting = receiving = facility), as legacy | `id` | `ORDER_CREATE` at the receiving facility, any program | `helper#L1-L19` |

The server ignores `emergency` (forces false) and checks `ORDER_CREATE` at the receiving facility
whatever the program, so legacy's program-independent list never meets a refusal.

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.create-orders.tsx`. Loader awaits
  `requirePermissions` for `ORDER_CREATE`, prefetches user programs and minimal facilities
  unawaited. The route computes, from the permissions, the requesting options and a
  `canReadOrders(programId, supplierId, facilityIds)` check, and passes them as props (features
  cannot import auth).
- Read check (needed by [FM-50]'s order reads): `ORDERS_VIEW`, `ORDERS_EDIT`, `SHIPMENTS_VIEW` or
  `SHIPMENTS_EDIT` at the supplying facility (fulfillment strings `RIGHT|facility`), or `PODS_VIEW`
  or `PODS_MANAGE` at every chosen facility for the program. `parsePermissions` drops the facility
  of two-part strings: extend it and the `Permissions` type to keep facility-only grants, and add
  `facilityGrants(permissions, right)` over them in `src/lib/permissions.ts`.
  Without a read right, Create Order stays disabled with a note saying why.
- The draft (program, facility ids, supplying facility) is local state, not in the URL (legacy
  keeps none, and the next step writes to the server).
- Supplying options: `supplyingFacilitiesOptions({programId, facilityIds})` in the orders feature,
  keyed by program and the sorted ids: nodes per facility in parallel, intersect, supply lines per
  node, supplier ids named through minimal facilities. Reference-data gains
  `facilitySupervisoryNodesOptions({programId, facilityId})` and
  `supplyLinesOptions({programId, supervisoryNodeId})`; the supply-lines management feature keeps
  its own list.
- Create: `useSessionMutation` over `settleFew` of the POSTs. All succeed: navigate (push) to the
  table with the ids in the path. Some fail: navigate with the created ids and a warning toast naming the
  failed facilities (no rollback writes). All fail: stay, error toast with the server message.

### Rules

- Requesting list: distinct facilities of `ORDER_CREATE` grants, sorted by name, independent of the
  program, as legacy and the server's check. A deliberate exception to AGENTS.md's exact-grant rule,
  recorded there.
- Facilities already in the list are left out of the picker.
- Supplying list: supervisory nodes common to every chosen facility (direct nodes only, as legacy),
  their supply lines' supplying facilities, distinct, sorted by name; cleared when the program or
  facilities change; a sole option is picked automatically. Sole program picked automatically.

### Risks And Edge Cases

- Administrator has about 1,000 requesting options: the combobox filters locally with at most
  50 rendered matches, as other long facility lists do.
- A lost POST response can leave a stray empty draft on the server; legacy has the same, and it can
  be deleted from legacy View Orders.

## UI/UX

**Port**: the three choices, the facility list with remove, auto-picks, the supplier rule, and
Create Order creating the drafts.

**Improve**: a message when no warehouse supplies all chosen facilities; a note and a disabled
Create Order when the planner could not open the drafts; error toasts on create failures; picked
facilities leave the picker; No Access instead of a silent jump Home; phone cards.

**Drop**: the facility list's client pager ("Showing N item(s) out of N total").

Layout, in legacy's order since the supplier depends on the facilities: Program as a picker field;
a `PickerAdd` row for Requesting Facility with a separate Add button; the Facility table; then
Supplying Facility. Create Order is the header action (`size="lg"`).

## Decisions

- **Legacy's option rules are kept exactly**, including the program-independent requesting list.
- **Picking a facility needs Add**, the app's inline picker rule, where legacy adds on pick.
- **Title Create Orders**, matching the menu and breadcrumb; legacy's heading says Create Order.
- **Create Order writes drafts immediately**, as legacy: the draft lives on the server ([FM-50]).
- **Partial create failures open what was created** rather than rolling back with more writes.
