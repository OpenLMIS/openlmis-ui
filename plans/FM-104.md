## Summary

After a forecast is prepared, the facility fills it in and sends it on (Create), and an
authorizer at the facility approves it for the district (Authorize). This page is where they
find the forecasts waiting for them: drafts, forecasts sent back by an approver, and
forecasts waiting for authorization.

Legacy shows a plain table of these forecasts with a Forecast button on every row, even when
the user is not allowed to open that forecast; the refusal comes only after the click. The
statuses are raw codes, a failed load looks like an empty list, and on a phone the page
scrolls sideways.

The new page shows the same list with translated statuses, separates "no forecasts" from "could
not load", and switches to cards on a phone. The Forecast action that opens a forecast comes with
the new forecast grid, and will appear only on the rows the user can work on.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Enter | permissions, `GET /users/{id}`, `GET /users/{id}/programs`, `GET /facilities/{home}` | user id | `homeFacilityId`; program `code === 'BUQ'`; facility `name`, `supportedPrograms` | either right at home for BUQ | `buq.routes.js:73-120` |
| Periods | `GET /processingSchedules`, `GET /processingPeriods` | `processingScheduleId` of code `BUQ` | `id`, `name`, `startDate` | authenticated | per-row `GET /processingPeriods/{id}` |
| List | `GET /bottomUpQuantifications` | `facility`, `status=DRAFT&status=SUBMITTED&status=REJECTED`, every page | `id`, `processingPeriodId`, `targetYear`, `status` | any BUQ right | `useGetBuqsByStatus.jsx` |

The list accepts only `status`, `facility` and paging; anything else is 400.

### Data Flow

- Loader as Prepare BUQ: blocks on `requirePermissions(queryClient, [RIGHTS.createForecasting,
  RIGHTS.authorizeForecasting])`, the user, programs and home facility; prefetches schedules,
  periods and the list without awaiting.
- Access: `prepareAccess` becomes `buqAccess({ home, programs, permissions, rights })` returning
  `BuqAccess` (was `PrepareAccess`), ready when any of `rights` is an exact `hasProgramGrant` at
  home for BUQ. Prepare BUQ passes `rights: [RIGHTS.prepareBuq]`.
- Queries: the same `preparedBuqsOptions(facility)` and `buqPeriodsOptions(scheduleId)` as Prepare
  BUQ (same call, same statuses), so both pages share one cache entry.
- Rows are built by one shared helper (period name and start mapped from the periods, sorted by
  `targetYear` then period start), used by both pages. Legacy sorts by period start only; the
  orders match because `targetYear` is the period's end year
  (`BottomUpQuantificationService.java:1011`) and BUQ periods do not overlap.
- Paging local and in the URL (`page`, `size`) through the shared search schema; the paged table
  hook and the past-end clamp move out of `prepared-table.tsx` so both tables use them. The
  Quantification For The Year column has the id `targetYear`, so the schema's fixed sort points at
  a real column.

### Server-Side Work

- Period names and start dates come from the schedule's periods already used by Prepare BUQ, not
  one request per row; the unused full period fetch is dropped.
- The list stays fetched whole (one facility, three statuses) and sorted by period start
  locally: the server cannot sort by a period field.

### Risks And Edge Cases

- Prepare BUQ and this page share the list cache: a Prepare or Delete refreshes both.
- A user whose create or authorize grant is on another facility or program passes legacy's
  unscoped check; this page refuses them (exact home grant), as Prepare BUQ does.
- FM-105's grid route sits beside this one as `_protected.buq.create_.$id.tsx` (no nesting, as
  `users_`), so this file stays a page, not a layout.
- Backend bugs affecting this page: a deleted remark or source of funds used in a listed forecast
  makes the list 500 (shown as the list error); authorize is accepted from any status, so the grid
  (FM-105) must gate it.
