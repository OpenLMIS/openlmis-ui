# FM-137: Valid Destinations (and the screen it shares with FM-138 Valid Sources)

https://openlmis.atlassian.net/browse/FM-137 · Parent: FM-124 Admin: Facilities & Supply Chain ·
Sibling: [FM-138 Valid Sources](FM-138.md)

## Scope

Administration > Valid Destinations and Administration > Valid Sources: one screen built
once and used twice, with the list, its filter, row selection with a bulk delete, and an add
dialog. Both tickets ship in one PR. They are Tier 1 rows 12 and 13 of [FM-62](FM-62.md):
Issue offers the valid destinations in "Issue To", Receive the valid sources in "Received
From".

Shared pieces this PR adds, which later screens reuse:

- row selection in `src/components/data-table/`: a checkbox column, select all on the page,
  a selected count and a bulk action bar;
- the shadcn `checkbox` component in `src/components/ui/`, new, so no existing page changes;
- a geographic levels lookup in `reference-data`, and a facilities-by-ids lookup.

Out of scope:
- a geographic zone filter: the API has one but legacy doesn't, so it's left out for now;
- editing an assignment: legacy has no edit, and the API has no `PUT` or detail `GET`;
- managing organizations: there's no legacy screen, and FM-62 lists them as "API only";
- sorting: the API answers `500` to a sort on the name, and legacy has none.

## Summary

A valid destination says "facilities of this type, in this program, may issue stock to this
place". A valid source says the same for receiving. The place is either a facility or an
organization, such as an NGO, which is a name with no facility behind it. An optional geo
level affinity narrows it further: a district store with affinity "District" is offered
only to facilities in its own district.

In the old UI, Administration > Valid Destinations is a table of Program, Facility Type,
Name and Geo Zone, ten rows a page, with a checkbox per row. A Filter popover takes a
facility and a program together and shows what that facility may issue to in that program.
Add Valid Destination opens a window with Program, Facility Type, Is Facility or Is
Organization, the facility or organization, and Geo Level Affinity. Delete Selected sits in
a bar at the bottom. Valid Sources is the same screen. It works, but:

- **Slow:** each page load downloads every facility in the system (4 MB, 2,738 here) and
  every zone, just to show the zone column, so rows take 3 to 5 seconds to appear. Every
  page, filter or cancelled window loads it all again.
- **Bulk delete:** it reports success even when deletes fail. Cancelling its confirm shows
  "Failed to delete selected Valid Destinations". The confirm never says how many rows go.
- **Filter:** a "Facility" filter that sounds like a search for the destination's name, but
  it's the facility that would do the issuing. Filtering from page 4 shows an empty table.
- **Add:**
  - adding something that already exists says "saved" and quietly ignores a new geo level
    affinity;
  - a user without the separate right to manage organizations can't open Add at all;
  - the geo level affinity is set but never shown.

The new screens keep the same data, rules and flow, and fix those:

- **Loading:** rows load in well under a second. Zones come from one small request for the
  facilities on the page, not every facility.
- **Filter:** reads "Available To" and asks for the program as well when only one is
  picked, since the server needs both. A new filter starts from page 1.
- **Selection:**
  - selected rows stay selected across pages;
  - a bar at the bottom shows how many are selected, with Clear and Delete;
  - the confirm names the count;
  - a delete that fails is reported, and those rows stay selected so they can be tried again;
  - each row also has its own Delete in its "..." menu.
- **Add:**
  - Program and Facility Type are checked;
  - the facility picker is searchable;
  - organizations are offered only to users who may see them, and everyone else can still
    add facilities;
  - adding one that already exists says so instead of "saved".
- **Geo Level Affinity column:** shown when there's room, so admins can see what they set.
- Both screens work on a phone and in Arabic.

Stock screens in the old UI keep a copy of these lists from sign-in, so a change reaches
them the next time the user signs in. That is legacy's behaviour, and this screen does not
change it.

## Agent Brief

### API Map

`{kind}` is `validDestinations` or `validSources`. All are stockmanagement endpoints, reached
through the same `/api` client.

| Step | Method and path | Params | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| List | `GET /{kind}` | `page`, `size`, `sort=programId,asc&sort=facilityTypeId,asc&sort=id,asc`; `programId` + `facilityId` together or neither | `id`, `programId`, `facilityTypeId`, `node.referenceId`, `node.refDataFacility`, `name`, `geoLevelAffinityId`, `totalElements` | none on the server; the page needs the manage right | `admin-valid-destination-list.routes.js:34-43` |
| Zone per row | `GET /facilities?id=…&id=…` | the page's facility `node.referenceId`s (organizations left out) | `id`, `geographicZone.name` | signed in | replaces legacy's full `GET /facilities` + `GET /geographicZones` |
| Program names, filter, add | `GET /programs` (`programsOptions`) | | `id`, `name` | | routes L52-56 |
| Type names, add | `GET /facilityTypes?active=true` (`facilityTypesOptions`) | | `id`, `name` | | routes L58-62 |
| Facility pickers | `GET /facilities/minimal` (`minimalFacilitiesOptions`) | | `id`, `name` | | legacy uses the full list |
| Geo levels | `GET /geographicLevels` | | `id`, `name`, `levelNumber` | | add routes |
| Organizations | `GET /organizations` | plain array | `id`, `name` | `STOCK_ORGANIZATIONS_MANAGE` | add routes |
| Add | `POST /{kind}` | `{programId, facilityTypeId, node: {referenceId}, geoLevelAffinityId?}` | `201` new, `200` already existed | `STOCK_DESTINATIONS_MANAGE` / `STOCK_SOURCES_MANAGE` | `valid-destination-add.controller.js:223-251` |
| Delete | `DELETE /{kind}/{id}` | | `204`; `400 …assignment.notFound` when already gone | same | `valid-destination-list.controller.js:337-371` |

Server facts (stockmanagement master `c3ff4fd`, no `migration` branch):

- **List paging:** unfiltered lists are paged in the database. With program and facility,
  the server loads the assignments for the program and the facility's type, drops facility
  nodes that fail geo affinity, and pages that in memory. `totalElements` is right either way.
- **List params:**
  - without a `sort` the order is unstable across pages (the same rows came back on page 0
    twice), so always send one;
  - `sort=name` is `500`;
  - any other param, such as `facilityTypeId`, is `400 stockmanagement.error.invalid.params`.
- **`POST` is idempotent** on program + facility type + node. It ignores
  `geoLevelAffinityId` in that match, and doesn't check the level id.
- **`400` errors** carry a `messageKey` and a `message`: program, facility type or node not
  found, and the missing node reference.
- **No bulk delete**, and no detail `GET` (`405`).

### Data Flow

- **Routes** `_protected.administration.valid-destinations.tsx` and `…valid-sources.tsx`.
  Each renders its own feature's page, which hands its API and `kind`
  (`'destinations' | 'sources'`) to the shared screen in `src/components/valid-assignments/`.
  - The loader awaits `requireRight(qc, RIGHTS.stockDestinationsManage)` (or sources) and
    returns `{ canPickOrganizations: rights.has(RIGHTS.stockOrganizationsManage) }`.
  - It then prefetches, without waiting, the list for `loaderDeps`, programs and facility
    types.
- **URL:**
  - `page`, `size` (from `tableSearchSchema([])`, no sort fields);
  - `facilityId` and `programId` (`z.guid()`, each falling back when invalid);
  - `assignment=new` for the add dialog (`useSearchNavigation(CLOSED_DIALOGS)`).
- **Query:** `toAssignmentsQuery(search)` sends the filter pair only when both are set, so
  a half-set filter never reaches the server.
- **Keys:** add `validDestinations`, `validSources`, `organizations`, `geographicLevels` to
  `src/lib/key-factory.ts`. List key `[kind, 'list', query]`.
- **Zones:** the table runs `useQuery(facilitiesByIdsOptions(ids))` for the page's facility
  ids. It doesn't suspend: the Geo Zone cells show a skeleton until it answers, and a
  failure leaves them blank. Rows never wait on zones.
- **Selection:** state lives in the page component, keyed by assignment id, holding
  `{id, name}` so the confirm and the bar work for rows on other pages. It's not in the
  URL, as a list of ids would make the link huge. A filter change clears it; paging keeps it.
- **Delete confirm:** local state, not the URL, since the selection it acts on isn't in the
  URL either.
- **After a delete:**
  - deleted ids leave the selection, and failed ones stay;
  - the list is invalidated;
  - a page that is now past the end clamps back, as Products does.
- **Add dialog:** lazy-loaded on first open, like Add Product. It reads programs, types,
  minimal facilities, geo levels and (when allowed) organizations. Each picker has its own
  boundary, as on Add Facility. Save: `POST`, then invalidate the list, close, and toast by
  status.

### Server-Side Work

| Legacy in the browser | New UI |
| --- | --- |
| Downloads all 2,738 facilities and 205 zones to show a zone per row | One `GET /facilities?id=` for the facilities on the page (14 ids: 24 KB, 0.1 s) |
| Facility pickers over the full 4 MB list | `facilities/minimal` (already cached by Facilities and Users), searched in the combobox |
| Paging | Server paging, as legacy |

### Rules

- **Filter:**
  - `programId` and `facilityId` are sent together or not at all (server `400` otherwise);
  - a change returns to page 1 (legacy's empty-page bug).
- **Add:**
  - Program, Facility Type and the picked facility or organization are required;
  - Geo Level Affinity is optional;
  - switching Facility or Organization keeps each side's pick, as legacy does, but only the
    shown one is sent.
- **Organizations:** offered only with `STOCK_ORGANIZATIONS_MANAGE`. Without it, the choice
  is hidden and the node is a facility.
- **Save result:**
  - `201`: toast "Valid Destination Added";
  - `200`: toast "Already a Valid Destination", whose description says nothing was changed,
    including the geo level affinity;
  - errors: the server's `message` in `ErrorAlert`, the dialog stays open.
- **Delete:**
  - a `400 …assignment.notFound` counts as deleted (someone else removed it);
  - any other failure keeps the row selected and is counted in the error toast.

### Risks and Edge Cases

- A facility node whose facility was deleted: no zone comes back for it, so its zone cell
  stays blank, where legacy's lookup threw.
- An organization row has `refDataFacility: false`. Its zone cell shows "Organization",
  muted.
- A program or type missing from the lookups (inactive types are filtered out): show the
  id's short form muted, as Facilities does for unknown zones.
- A selection holding rows a filter now hides: the filter change clears it, so a delete
  never removes unseen rows.
- Deleting every row on the last page: clamp to the new last page.
- 50 rows locally; a large deployment may have thousands. Paging and the per-page zone
  lookup keep the cost flat.

## Decisions

- **Two features, one shared screen.** `valid-destinations` and `valid-sources` each own
  their API, queries and types. The screen they both render lives in
  `src/components/valid-assignments/`, since a feature may not import another. The tickets
  ask for one component; only labels, endpoints and the right differ.
- **One PR and one plan.** FM-138's plan points here.
- **Selection in memory, not the URL.** Legacy keeps it in sessionStorage behind a URL key,
  so a reload keeps it; ours doesn't survive a reload. A list of ids in the URL would be
  unwieldy, and a reload mid-delete is rare. It survives paging, as legacy, and a filter
  change clears it, unlike legacy, so a delete never reaches rows the user can't see.
- **The delete confirm is local state.** It's a confirm for the in-memory selection, not a
  dialog worth linking to. The add dialog stays URL-owned.
- **Zone from a per-page batch lookup**, not the full facilities and zones lists.
- **Filter label "Available To".** Legacy's "Facility" reads as a name search, but it's the
  facility doing the issuing or receiving.
- **Organizations behind their own right.** Matches the server, and lets users without it
  still add facility nodes.
- **No sort, a fixed server order** (`programId, facilityTypeId, id`) so pages don't repeat
  rows.

- **No geographic zone filter for now**, as legacy (decided 2026-10-02).
- **The selection doesn't survive a reload** (decided 2026-10-02).
