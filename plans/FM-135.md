## Summary

Supply partners let administrators choose which facilities and products another supplier
will fulfil. Requisitions use those choices when splitting an approved request between
suppliers. Legacy lists each partner's code and name and creates partners through a short
dialog. The new screen keeps that flow, uses the migrated table and dialog patterns, and
shows useful server errors. After creating a partner, an Add Associations toast action
offers to open its editor.

## Agent Brief

### API Map

All paths are relative to `/api`. Both calls need `SUPPLY_PARTNERS_MANAGE`.

| Step | Method And Path | Params Or Body | Fields Used | Legacy Ref |
|---|---|---|---|---|
| List | `GET /supplyPartners` | `page` zero-based, `size` 1-100 | `content[].id/code/name`, `totalElements`, paging metadata | RDUI list routes, supply-partner-resource |
| Add | `POST /supplyPartners` | `{code,name,associations:[]}`; omit `id` | 201 DTO `id/code/name/associations` | RDUI add service and resource |

The collection filters only by `id` and `supervisoryNodeId`. Code/name filters yield 400;
the shared `SearchParams` removes `sort`, so it is ignored, not rejected. Send only
`page` and `size` from this list. Database ordering is unspecified. Keep server
paging and record the possibility of page movement during concurrent changes; a UI sort
would misrepresent the server contract. The list response also carries associations, but
the list does not hydrate or render them.

Code uniqueness is case-insensitive and server-enforced, including concurrent creates. Validation returns
localized `message` and `messageKey`; show `serverMessage(error)` in the dialog and keep
the fields for correction. Distinguish 403, offline and other failures using existing
error helpers. Relevant server messages are `code.required`, `name.required`,
`code.duplicated` and `id.provided` (`RD main/resources/messages_en.properties:215-229`).

## Stage 3 Implementation

The association editor and nested product picker now complete the stage-2 boundary.
The URL owns opening, closing and nested state; one copied association survives picker
navigation and changes the page draft only after association submission. Program and node
choices exclude used pairs in both directions. Required membership validation keeps its
Program, Node, Facilities, Products order.

Facility choices require the separate supervisory-node management right. Saved members
and product choices use hydrated selected facilities independently of that right. Removing
a facility performs a fresh unpaged approval read with `staleTime: 0`, then publishes both
membership arrays in one association-field update. Failure keeps both arrays; the last
facility clears products without a lookup. The warning and removed-product summary match
approved legacy pruning. Existing products unavailable for adding are retained until an
explicit removal, selection change or facility pruning.

The page guard includes association and picker dirtiness, while one local guard handles
same-path association close/switch. Product-picker Cancel and Back discard only the picker
selection. Association close waits for the URL guard before hiding the modal, so Keep
Editing preserves the copy. Incompatible direct links are replaced safely; a fresh new
association link cannot invent the in-session context needed by its nested picker.

No new backend calls or policy deviations were introduced. This stage stops for browser
and Opus review. English/Arabic layout, real navigation/focus and the stubbed end-to-end
workflows remain the parent's browser validation boundary. No shared-server write has
been authorized or performed.

## Correctness Review Response

Nested product URLs are normalized whenever the current association copy has no facilities,
including an Edit copy cleared before browser Forward. A valid saved-association deep link
with facilities retains its nested picker. Re-adding facilities after normalization does
not open the picker without a new action.

Facility removal requires a successful, idle selected-facility lookup. Initial failures,
refetches, paused requests and cached-data errors disable every facility removal, including
last-facility clearing. Errors retain Retry; cached reference errors also show the existing
error control in both the page and association. The removal helper requires an explicit
lookup-ready flag without a default. Its caller reads that flag and the facility records
from the same live query state using unique sorted selected ids.

After a successful lookup, missing selected facilities can be explicitly removed one at a time. While another selected
facility remains unresolved, each such removal changes only the facility ids and preserves
all product ids without an approval request. Removing the final unresolved member performs
the existing fresh atomic approval lookup once all remaining types are known; failure
retains that member and every product. Removing the last facility still clears all products.
Resolved facility removal stays disabled while remaining types are unresolved, and the
API helper rejects that unsafe path explicitly. Pending lookup/product/removal gates stay
in place. Products are never pruned against a partial set of known types.

The existing recovery interaction covers a failed lookup without data, successful Retry,
a pending cached refetch, cached-data failure and another successful Retry before explicit
recovery of two genuinely missing members. Failure gates first reproduced enabled removal;
the helper regression separately reproduced clearing the last facility with a false lookup
status. Both now reject that path. The first genuine missing-member removal preserves a
product absent from known approvals, sends no lookup and keeps Update blocked. The final
missing removal makes one fresh lookup, retains the approved product and enables Update.
Unsafe resolved removals remain blocked throughout recovery. Parent browser probes cover
these transitions with backend writes blocked.

The user-approved presentation uses matching tight field spacing for Code and Name. Code
is disabled without helper text. English association counts use title case, and the two
View controls use the default contained Button treatment with their existing URL identity.
The outer Add/Edit Association dialog uses the existing 36rem table size; the nested
Add Products picker keeps its existing size and responsive layout.

Association guidance lives in info popovers directly beside the Supervisory Node, Facilities
and Products labels in both Add and Edit, including locked selectors. The fulfilment descriptions
stay visible with tighter heading spacing; selection, pruning and save behavior is unchanged.
