# FM-209: Onboarding Tour: Orders (View Orders, Fulfillment, Proof Of Delivery)

https://openlmis.atlassian.net/browse/FM-209 · Parent: [FM-199] Guided onboarding tours for new users
(React Joyride, isolated module)

Stacked on FM-208 (PR #159).

## Scope

- **In:** five tours, one per route:
  - View Orders (`/orders/view`);
  - Fulfill Orders (`/orders/fulfillment`);
  - the shipment screen (`/orders/fulfillment/$orderId`);
  - Manage Proof Of Delivery (`/orders/proof-of-delivery`);
  - the proof of delivery screen (`/orders/proof-of-delivery/$podId`).
- **In:** `data-tour` attributes on loaded parts, plain wrapper divs where a part has no single root,
  new keys in `TOUR_ANCHORS`. Shared `list-*` anchors (FM-207) and `orderSummary`, `orderUnit` (FM-208)
  are reused.
- **Out:** module changes; dialogs (shipment confirm, cancel, POD confirm) and the Filters popover
  contents, which steps describe; the order drafts editor reached from View Orders' Edit (FM-208).

## Summary

The Orders screens get a Show Guide button, so warehouse and facility staff can learn them in place:

- **View Orders:** pick a supplying facility and Search, filter, read the list, and use each order's
  actions (print, download, retry a failed transfer, or continue an order still being created).
- **Fulfill Orders:** filter, sort newest or oldest, and start or continue fulfilling an order.
- **Shipment:** the order summary, packs or doses, the lines with the fill quantity to ship, and Save
  Draft, Print, Cancel Order, Delete Draft and Confirm Shipment.
- **Manage Proof Of Delivery:** pick the program and facility, read the list, and Manage or Print a proof
  of delivery.
- **Proof Of Delivery:** Print, the order summary, the lines with the quantity accepted, the delivery
  details, and Save and Confirm.

A screen shows only the steps for the parts it has. Legacy has no guide.

## Legacy Today

No guide (FM-200).

## User Flows

From the FM-93 and FM-91 plans:

- **View Orders:** pick a supplying facility, Search; Filters narrow by requesting facility, program,
  status and period; each order prints, downloads as CSV, retries a failed transfer, or (when still
  Creating) opens the order drafts editor (FM-208).
- **Fulfill Orders:** Start Fulfilling or Continue opens the shipment; the shipment returns to the list
  with its filters.
- **Shipment:** fill quantities per lot, Save Draft, Print the pick-pack list, Confirm Shipment (asks to
  confirm), Delete Draft, Cancel Order.
- **Manage Proof Of Delivery:** program plus requesting or supplying facility, Search; Manage opens the
  proof of delivery, Print opens its PDF.
- **Proof Of Delivery:** record quantity accepted, VVM, reason and notes per lot (returned is computed),
  who delivered, who received and the date; Save, then Confirm (asks to confirm), which marks the order
  Received.

### Rules

- **Anchor only where the control works** ([vault A70]): View Orders supplier picker only with suppliers;
  fill and accepted inputs exist only when editable; footers only when they hold actions; Print not
  offline.
- **No anchors on loading parts:** skeletons already carry `aria-busy`. Filter fields inside the popover
  load without it, so no step anchors inside the popover.
- **Anchor on the control or its own group,** not a full-width row.
- **Copy:** labels as each screen shows them per locale; true in both layouts; generic where rows differ
  (row actions vary by status and rights). Buttons that turn into icon buttons in cards (Start
  Fulfilling or Continue, Manage, Print) are named by their label and described as the row's button, so
  the text holds on narrow screens. Footer and actions copy never promises a button the user may not
  have (the shipment end group can hold only Cancel Order).

### Risks

- **Test data:** test.openlmis.org may have no Ordered/Fulfilling orders or Initiated PODs for
  `administrator`; serve an existing record with the needed status by a read-only GET stub, as FM-208 did.
- **Opening a shipment writes:** an Ordered order the user can edit creates a shipment draft on open
  (`createShipmentDraftOnce`, a POST). Browser checks either open a Fulfilling order whose draft exists,
  or fulfil the draft POST from a crafted body built from the order's lines; a plain `{}` stub leaves the
  editor in its error state. Never let the POST through.
- **Wide tables:** View Orders (11 columns), the shipment and POD grids scroll sideways at 672-1100 px;
  column steps reveal their header, other targets are scrolled into view by the runner.
- **Shipment CCE status** loads after mount without `aria-busy`; the summary step anchors the whole
  summary, whose copy does not depend on it.

## UI/UX

- **Improve:** a guide where legacy has none.
- **Phone:** column steps fall back to the first control and the list; sort steps drop on cards.
- **Arabic:** placements mirror through the module.

## Decisions

1. **One tour file for the five screens**, separate ids per route.
2. **Reuse `orderSummary` and `orderUnit`** from FM-208: the same parts of the same order screens.
3. **View Orders row actions through the Actions header**, not a row button, since rows differ.
4. **No steps inside dialogs or the Filters popover.**
5. **Shipment footer in two steps** (plan review): its groups sit at opposite ends of one row, so one
   anchor would spotlight the whole footer and a wrapper would break its layout.
