## Summary

Administrators maintain the reasons that can explain a rejected requisition. Every reason
has a name, code, category and active state. The new UI keeps the paginated list,
category choices and Save/Cancel flow, and uses dialogs for both Add and Edit. It provides
a translated Edit dialog title and list breadcrumb, orders the list consistently, and preserves
the draft when a save fails. These shared lookups will also serve the approval screen.

## Agent Brief

### API Map

Paths are under `/api` in requisition. Every UI entry uses `USERS_MANAGE`; controllers
do not enforce a resource right.

| Step | Method And Path | Params Or Body | Fields Used | Legacy / Backend Ref |
|---|---|---|---|---|
| List and later FM-43 lookup | `GET /rejectionReasons` | First request without params; read every returned page | Page metadata; `id, name, code, active, rejectionReasonCategory` | REQUI list route `:34-36`; REQ reason controller `:74-85` |
| Category picker | `GET /rejectionReasonCategories` | Full shared lookup, no active filter | `id, name, code, active` | REQUI Add/view route `:36`, `:46`; FM-146 map |
| Open Edit | `GET /rejectionReasons/{id}` | UUID | Whole saved record | REQUI view route `:38-43`; REQ controller `:94-105` |
| Add | `POST /rejectionReasons` | `{name, code, active, rejectionReasonCategory: wholeCategory}` | Saved record, 201 | REQUI Add controller `:71`; REQ controller `:115-131` |
| Save Edit | `POST /rejectionReasons` | `{...saved, name, code, active, rejectionReasonCategory: wholeCategory}` | Saved record, 201; ID retained | REQUI view controller `:67`; REQ controller `:115-131`; domain importer copies ID |

Unused contracts: `PUT /rejectionReasons/{id}` (200, upsert) and
`GET /rejectionReasons/search?name&code&active&rejectionReasonCategoryId` (Set/array).
Do not call `/search`: it has no useful paging/sort and its active branch ignores the
other filters. No-filter search returns 400; it is not a collection replacement.

### Shared Reads And Data Flow

- `RejectionReason = { id: string; code: string; name: string; active: boolean;
  rejectionReasonCategory: RejectionReasonCategory }` belongs in reference-data types.
  Normalize nullable booleans to the legacy unchecked presentation. Keep all other
  returned fields available for a whole-record save; do not rebuild saved records from
  only the visible fields.
- `fetchRejectionReasons()` and `rejectionReasonsOptions()` live in reference-data under
  exactly `queryKeys.rejectionReasons.list()`. Reuse FM-146's full-collection strategy:
  no-param first GET, then every additional response page if any, session checks and
  atomic result publication. Current server returns all data in one response. Do not
  depend on ordering across server page requests or promise snapshot consistency.
- List loader awaits `requireRight`, then starts non-awaited `prefetchQuery`.
  List uses the same 30-second freshness override as the category list; query identity
  stays shared with future consumers. Header/toolbar render outside `QueryBoundary`.
- Local Name search, sort and paging use URL `page`, `size`, `sort`, `name`;
  `reason=new` controls Add and `reason=<uuid>` controls Edit. Sortable fields: Name, Code, Category label and Active,
  Name ascending by default, then Code/ID as ties. Sort/filter before slicing; clamp
  invalid pages and keep navigation state as FM-146 describes. No extra category or
  Active filters in this scope.
- The embedded category supplies list labels without another categories request.
  Fetch categories when Add opens or Edit needs them. This is one shared query, not
  another feature import or a second full-resource cache.
- Edit reads fresh details on every dialog opening with an appended `useOpening()`
  key; details are not prefetched by the list loader. Capture a stable saved record and
  draft. Loading, not-found and retry states stay inside the dialog. The category field
  owns `LookupBoundary`/`QueryBoundary` so Name/Code render independently and survive
  category loading or retry.
- The required category field uses `SelectField`, justified by the current single
  category and legacy's small controlled vocabulary. Options show Name and a translated
  inactive marker when appropriate. Store category ID in the draft, resolve it to the
  full latest lookup object for the payload. Edit selects by ID, not object identity.
  On Add, auto-pick a sole category once when the lookup first resolves and the field
  is untouched; multiple options start unselected. Do not overwrite a user's choice
  or an Edit selection on refetch. A missing/unavailable selected category
  keeps its saved label visible via a disabled item built from the embedded saved
  category, marked Unavailable; explain the problem and block save until a valid
  category is selected or a successful lookup resolves it. An empty categories list
  explains that a category must first be added in the Categories screen; no nested Add.
- A category load error renders an in-field retry; it must not erase typed Name/Code.
  Save cannot proceed while category data is unavailable/pending. Expiry, same-user
  renewal and identity switches use existing shared session behavior.
- Add and Edit share the URL-owned `RejectionReasonFormDialog` and `withForm` field
  set. List search stays in the same URL beside the dialog target; Close uses standard
  Back/replacement behavior. Old `/$id` URLs redirect with validated list settings.
  No page editor, sticky page footer, return HistoryState or Edit crumb is needed.
- Dirty Edit dialogs guard Cancel, Escape, Close, browser Back and leaving the page
  through the feature-local dialog discard hook, including unload/sign-out behavior.
  Add retains its existing dismissal behavior. Both use `useSessionMutation`, keep
  input on errors, block duplicate submission/closing during mutation and bypass the
  discard guard after a successful write before closing to the originating list.
- Reason save invalidates `queryKeys.rejectionReasons.all`. Category save invalidates
  BOTH scopes, including reason details, because reasons embed their category.
  Invalidation does not reset an already-open dialog's draft.

### Rules And Failure Responses

- Name, Code and Category required on Add and Edit. Whitespace-only Name/Code invalid;
  category must resolve to a loaded existing ID. No arbitrary text limits. Validate
  trimmed text for emptiness while preserving the entered value in the save body.
- Active starts off, sole category auto-selected on Add, inactive categories selectable,
  and no rule forces active reason/category values to agree. Always write a boolean.
- Send the whole category object `{id, name, code, active}`, not just `{id}`; preserve
  the whole saved reason and overlay its changed fields. This is a category reference,
  not a category mutation. The relation has no cascade save.
- Current master schema has NOT NULL Name/Code/category FK and UNIQUE Name AND Code.
  These constraints are case-sensitive and scoped to their own table. Keep server
  validation authoritative; no case-insensitive unique-name rule in the frontend.
- Duplicate name/code maps to HTTP 400 and
  `requisition.error.rejectionReason.name.duplicated` /
  `requisition.error.rejectionReason.code.duplicated`. Use `ErrorAlert` with
  `serverMessage` or translated fallback, retaining the draft. These write responses
  were verified in source, not exercised live. Unknown category FK errors may be unmapped.
- The prompt's missing-items key is not the current master key. PUT's null name/code
  check emits `validation.missing.mandatory.items`. Required UI checks prevent that
  class of error for the actual POST save too.
- GET missing ID returns 404; treat it as not found. Upserts are not a UI Create path.
  The API has no revision token; simultaneous saves can overwrite, as in legacy.

### Duplicate-Name Finding

The earlier brief said only reason Code is unique. Current Flyway SQL at
`REQ/src/main/resources/db/migration/20201013132010206__create_schema_for_rejection_reasons_managment.sql:26-29`
declares both code and name unique for BOTH resources, consistent with the entity
annotations and duplicate-name error mappings. Therefore a duplicate-name collapse
is not a reproducible defect on a database following master migrations.

`RejectionReasonDto` AND `RejectionReason` still use name-based equality/hashCode
(`REQ/src/main/java/org/openlmis/requisition/dto/RejectionReasonDto.java:46-62`;
`domain/RejectionReason.java:124-139`). If a nonstandard deployment lacks the unique-name
constraint, the HashSet drops same-name rows before sending the response; the UI cannot
recover them, and totals also reflect the collapsed set. Do not add frontend name-based
deduplication or try merging `/search` responses. Record this conditional limitation
here and in review evidence. A confirmed deployment/schema mismatch should get a separate
backend follow-up; this task does not authorize creating or commenting on Jira tickets.
No duplicate-name live write is necessary or authorized to establish the master schema.

## Decisions

- Same PR, feature, collection keys and staged workflow as FM-146; FM-43 will consume
  reference-data directly without depending on an admin feature.
- Use dialogs for both Add and Edit under the latest explicit user instruction. This
  supersedes the earlier approval to retain an Edit page. The one-tab strip is omitted.
- Use `SelectField`: existing taxonomy currently has one category and legacy uses a
  select. A searchable ComboboxField is the alternative if real deployments prove the
  inventory large; it is not required to build the present screen.
- Include inactive categories, preselect the sole category on Add and keep reason Active
  independent. With multiple categories, start unselected. Store ID in the draft and
  serialize the whole selected category object; preserve Edit selections across refetch.
- Use collection POST including ID for Edit, matching the actual legacy controller,
  despite the unused PUT method documented in the earlier research.
- Read the complete collection starting with the no-param legacy request; follow every
  additional page if returned; sort/filter/page locally with deterministic ties.
- Correct the suspected duplicate-name collapse: master migrations enforce unique names.
  Document conditional risk for divergent schemas, no confirmed backend ticket or extra
  frontend uniqueness policy.
- Local Name search is the only extra filter; show server duplicate messages inline.
