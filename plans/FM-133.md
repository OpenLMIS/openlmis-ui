# FM-133: Supervisory Node Edit

https://openlmis.atlassian.net/browse/FM-133 · Parent: FM-124 Admin: facilities & supply chain

Built in one PR with [FM-132](FM-132.md) (the list). Tier 1 row 2 of [FM-39](FM-39.md).

## Scope

The Edit Supervisory Node page: the node's own fields, its child nodes and its partner nodes,
saved together with one Update. It uses FM-132's `supervisoryNodesByIdsOptions` (this
feature, over the shared `src/lib/fetch-by-ids.ts`) for table rows.

Out of scope: creating or deleting a node (legacy has neither; API only).

## Summary

Editing a node sets its code, name, facility, parent node and description, and which nodes sit
under it (child nodes) or beside it (partner nodes). Parents and children decide where a
requisition goes for approval next, so a mistake here changes who approves what.

In the old UI the page takes 8 to 15 seconds to open, because it downloads every node (twice
when opened by link) before showing anything. Its child table is often wrong: for a node with
86 children it shows "No child nodes assigned" above a pager counting all 511 nodes. The empty
partner table shows a raw message key, and turning a page in the child table reloads the whole
screen and silently throws away unsaved changes.

The new page keeps the same fields, sections, rules and confirmations, and fixes those:

- It opens on the node's own read, with the child and partner tables a moment later. Only the
  Parent Node field and the Add pickers wait for the full node list, which is shared with the
  role screens for ten minutes.
- Each table pages its own rows with the right count and never loses work; both have a
  translated empty message.
- Each table has an inline searchable node picker with Add, as legacy, leaving out the same
  nodes as legacy: the node itself, nodes already in that table and, for children, its parent.
- Remove asks first, as legacy. Nothing is saved until Update Supervisory Node, which saves
  everything and returns to the list on the same page and filters. Cancel, or leaving with
  unsaved changes, asks before discarding them.

## Legacy Today

Route `/#!/administration/supervisoryNodes/supervisoryNodes/:id?page&size` (a child state of
the list, so list params ride along and the list's resolves rerun). Screenshots:
`.screenshots/FM-133/legacy-edit-*`; raw traffic and the captured `PUT` body in
`.screenshots/FM-133/edit*.json`.

- Fields: Code and Supervisory Node Name (required), Associated Facility (all 2,734 minimal
  facilities, in id order), Parent Node (all nodes except itself, its children and the child
  being picked), Description. Every select is a searchable select2 with a clear "x", so
  Facility and Parent can be cleared (saved as none).
- Child Nodes: node select plus Add (excludes itself, its children and its parent); table of
  Name, Code, Facility, Edit (opens that node, no unsaved-changes prompt) and Remove Child
  Node; 10 a page, paged by reloading the route, which drops unsaved edits. The table is often
  empty with a pager reading "out of 511 total" (ARV-1 with 86 children; SN1 after an Add).
- Partner Nodes: select plus Add (excludes itself and its partners; children and parent are
  offered); table of Name, Code, Facility, Edit and Remove Partner Node, not paged; empty text
  is the raw key `adminSupervisoryNodeEdit.noPartnerNodes`.
- Remove asks "Do you really want to remove the child node?" with Remove Child Node and
  Cancel (partners: "...the partner node?", Remove Partner Node). Remove only changes the copy
  on the page.
- Add with nothing picked, or Update with Code or Name empty, shows "This field is required"
  under the field and a "This form is invalid" alert with Close.
- Update: `PUT supervisoryNodes/{id}` with the whole object as loaded (including
  `partnerNodeOf` and `requisitionGroup`, plus a junk `repository` the server ignores). Toast
  "Supervisory node updated successfully", back to the list reloaded. Failure shows a "Failed
  to update supervisory node" notification and an alert with the server's message (shared
  `form-server-validation.directive.js:131`). A loading modal blocks the page while saving.
- Cancel goes straight back with no prompt, keeping list page but not filters.
- Load: unpaged `GET supervisoryNodes` (357 kB, 4 to 8 s), `GET supervisoryNodes/{id}`
  (11.5 kB for SN1), the list's own four requests again, facilities from the sign-in cache;
  7.7 s from the list, 10.8 s by link.
- Source: `openlmis-referencedata-ui/src/admin-supervisory-node-edit/`
  (`routes.js:37-61`, `supervisory-node-edit.controller.js:125-208`,
  `supervisory-node-edit.html:8-86`, `admin-supervisory-node-edit-service.js:68-121`) and
  `referencedata-supervisory-node/supervisory-node.js:56-145`.

Backend behaviour the save relies on (referencedata master, verified on test):

- Whole record: an omitted `description`, `facility`, `parentNode`, `childNodes`,
  `partnerNodes`, `partnerNodeOf` or `extraData` is cleared. `requisitionGroup` must be the
  node's current one: omitted is `requisitionGroup.required`, different is
  `requisitionGroup.save.failed`, both 400 (`SupervisoryNodeBuilder.java:50-111`,
  `SupervisoryNodeValidator.java:64-123`).
- Refs need only `{ id }`; unknown keys are ignored. A ref to a deleted record is a 400
  (`facility.notFound`, `supervisoryNode.notFound`).
- Children: old children lose their parent, new children are moved here from any other parent
  (`SupervisoryNode.java:188-200`). Partners likewise move from another owner (`:205-217`).
  The parent is set as given (`:174-182`).
- Validation: code and name required and unique ignoring case; first error only, as a 400 with
  a message. No check for self, loops or duplicates.
- Every `PUT` rebuilds the right assignments table after commit, in the background
  (`RightAssignmentService.java:106-118`).

### Data Flow

- Route `/administration/supervisory-nodes/$id`, `preload: false`, `staticData.crumbKey`.
  Loader: `Promise.all` of `requireRight(...)` and the node read (blocks: a 404 needs its page),
  as the facility edit loader does. On `cause: 'enter'` the read is
  `fetchQuery({...supervisoryNodeOptions(id), staleTime: 0})`; on `stay` (table page changes)
  it is `ensureQueryData`, as Reasons does. The full node and minimal facility lookups prefetch
  as soon as the right check resolves. After the detail read, prefetch the initial visible page
  of saved children and partners from the URL using
  the same `visibleSavedIds` helper as the tables. Later draft-page changes leave by-id
  loading to the tables, so removed rows are not prefetched from the original record.
- Keys: detail `queryKeys.supervisoryNodes.detail(id)`; rows keyed on sorted saved ids from each
  visible draft page; added rows use their picked details, and deferred paging keeps previous
  rows visible while the next page loads; all under `supervisoryNodes.all`.
- Draft (one form, `useAppForm`): `{ code, name, description, facilityId, parentId, children,
  partners }`, starting from the loaded node, with `key={node.id}`. `children` and `partners`
  are ids plus, for nodes added on this page, the picked node's `name`, `code` and facility id,
  so added rows never need the picker list.
- Saved rows render from the by-id lookup and facility names from the minimal facilities
  lookup; the tables suspend on those two only, never on the full node list. An id the lookup
  does not return renders with blank cells. Code, Name and Description render at once; Associated Facility, Parent Node
  and the two tables each sit in their own `LookupBoundary`/`QueryBoundary`.
- URL: `childPage`, `childSize`, `partnerPage`, `partnerSize`, validated with defaults out of
  the URL; pages clamp past the end, as `event-line-table.tsx` and the User Roles editor do.
  Page changes add history (`useSearchNavigation`) and pass `keepState`, so
  `supervisoryNodesListSearch` survives paging and reload; the draft survives too.
- Breadcrumb: Home / Administration / Supervisory Nodes / Edit Supervisory Node; the list crumb
  links without filters, as Edit Facility (the list search lives in history state, not the edit
  URL).
- Save through `useSessionMutation`: the page goes `inert` and the discard guard gets
  `pending` (as the facility editor and legacy's loading modal), then reread the node, build the
  body (Rules), `PUT`, check the session scope after each await, return to the list with
  `supervisoryNodesListSearch`, invalidate `queryKeys.supervisoryNodes.all` without refetching,
  refresh only the active list query and toast. Picker lookups refetch when next used.
  A failure keeps the draft and the page and opens the save-error alert.

### Server-Side Work

lookup. The pickers still use every node, as legacy and the role dialogs do, because
`ComboboxField` has no server search; the list is cached ten minutes and shared with the role
screens.

### Rules

All exclusions are legacy's (`supervisory-node-edit.controller.js:172-208`,
`supervisory-node.js:82-131`):

- Child picker excludes the node itself, draft children and the draft parent.
- Parent picker excludes the node itself and draft children.
- Partner picker excludes the node itself and draft partners (children and parent stay
  offered).

Fields and save:

- Code and name required (trimmed), with "This field is required" under the field. Update with
  either empty opens legacy's "This form is invalid" alert with Close; closing focuses the first
  invalid field. Add stays disabled until a node is picked.
- A failed save opens an alert titled "Failed to update supervisory node" with the server's
  message (`serverMessage`), as legacy's notification plus alert; uniqueness is the server's.
- Associated Facility and Parent Node are optional and clearable (`clearLabel`).
- Body: start from the reread node (`requisitionGroup`, `partnerNodeOf`, `extraData` kept).
  Each scalar the user changed (code, name, description, facility, parent) takes the draft
  value; the others keep the reread value. Children are the reread children minus those the user
  removed plus those added, each id once; partners the same. Refs are sent as `{ id }`.
- Conflict: if the merged parent is the node itself or one of its merged children (another save
  changed the hierarchy since load), nothing is sent; an alert says the node changed and offers
  Reload, which rereads it and starts a fresh draft. Indirect loops stay allowed, as legacy.
- Added rows go at the end, as legacy; after Add the picker clears and keeps focus, and the
  table moves to the page holding the new row.
- Remove opens legacy's confirm; after confirming, focus moves to the next row's Remove, then
  the previous, then the picker; removing the last row of a page goes back a page.
- Row actions are an Edit (pencil) and a Remove (trash) icon button, as legacy has both. Edit
  opens that node's page (the discard guard asks first) and carries
  `supervisoryNodesListSearch` forward.
- The tables hide Facility when narrower than 512 px, so phones need no sideways scroll.

### Risks and Edge Cases

- Adding a child or partner that belongs to another node moves it, as the server and legacy do.
- Removing or moving the partner CHAZ-1.1, or children of ARV-1, can leave the CHAZ supply
  partner pointing at a node that no longer fits, so its next save fails. Legacy allows the
  same; the server checks nothing. Real write checks avoid ARV-1 and CHAZ-1.1.
- Legacy and the server accept loops (a grandparent as a child, a node's owner as its partner).
  Under parity the pickers do not block them; noted for FM-177 as a backend finding.
- With the backend's `REDIS_CACHING` flag on (off on test and by default), the reread can
  return a stale copy of a node whose child was moved by another save.
- The right assignments rebuild after a save runs in the background (Decisions).
- A real save on test changes routing data that cannot be undone by deleting; real write checks
  need the user's go-ahead per request, on a test node.
- Nodes without a facility (ARV-1.1, CHAZ-1.1) or a requisition group (CHAZ-1, CHAZ-1.1) must
  render and save.

## Decisions

- **Legacy's exclusions only**: no loop check beyond legacy's direct-parent rule, under the
  standing parity rule that allowed records stay legacy's.
- **Remove keeps legacy's confirm**, and the row keeps Edit, as two icon buttons.
- **Reread before saving and apply only this page's changes**, rather than sending the loaded
  copy back: the save is a whole record and also moves nodes away from other parents, so an old
  copy would undo other edits.
- **A merge that would make the parent also a child is refused**, with Reload, rather than
  sent: legacy never lets a user send that combination, and only another admin's save in the
  meantime can produce it.
- **No permission refresh after save**, as legacy: the server rebuilds rights in the
  background after the save, so an immediate refresh would read the old rights; they are read
  fresh at the next sign-in.
- **Pickers use the full node list**, shared and cached, as the role dialogs do; a
  server-search form combobox would be new shared work.
- **Table pages in the URL**, as legacy and the other draft editors, with `stay` loads reusing
  the cached node so a page turn never rereads it.

- **One real save on test** is allowed (user, 2026-10-14): SN1.1 resaved unchanged, to confirm
  the body is accepted. ARV-1 and CHAZ-1.1 are never written. All other checks stay stubbed.
