# FM-172: Load App Configuration at Startup

https://openlmis.atlassian.net/browse/FM-172 · Parent: FM-170 Global app configuration
(branding, theme & feature flags)

## Scope

This PR makes the app read the global configuration before its first render, and makes the
logo, app name, favicon, tab title, theme and feature flags come from it with built-in
defaults behind every field. It adds the typed feature flag helper and the theme preset
mechanism with the one current preset.

It reaches every page (logo, title, theme), which is the point of the ticket, so it cannot
be split further. It adds no settings page (FM-173), no other presets (FM-174) and no flag
labels or page (FM-176). It works before the backend ships: a `404` means "not configured",
so production behaviour is unchanged until referencedata has the endpoint.

## Summary

When the app opens, it now asks the server for the deployment's branding, theme and
feature flags, the same way it already loads translations, and waits for the answer before
drawing anything. The login page, the sidebar, the favicon and the browser tab then show the
configured logo and name, in the configured colours.

If the server is slow, the app waits at most three seconds and then uses what it saw last
time on this browser, or the built-in OpenLMIS look if it has never seen anything. If the
server is down or has no configuration, the app still starts, exactly as it looks today.

Feature flags are read through one helper, so a screen never draws with a flag in one state
and then flips.

## Acceptance Criteria

| AC | How it is met | How it is checked |
|---|---|---|
| Loaded once at startup, before first paint | `loadAppConfiguration()` joins the boot `Promise.all` in `src/index.tsx` before `render` | Unit test: one request per boot; browser: network panel shows one call before the root renders |
| Sidebar, login, favicon and tab title use the logo and name | `Logo` and `useAppName()` read the store; `applyBranding()` sets the favicon and base title at boot | Browser, with a stubbed config: custom logo and name on login, sidebar, tab, favicon |
| Theme and default appearance applied before first paint, no flash | `startApplyingAppConfiguration()` injects the preset's tokens and sets the light or dark class before `render` | Browser: stub `dark` default, reload with cleared storage, first frame is dark |
| Flags resolved before first render, one typed helper | `getFlag()` / `useFlag()` over a typed registry, resolved from the boot store | Unit tests; `tsc` rejects an unknown flag key |
| A missing setting falls back to its default | Lenient zod schema: each field falls back on its own | Unit tests per field |
| Request fails: defaults, no console errors | Failure and `404` resolve to defaults silently | Unit tests; browser with the endpoint aborted |
| Slow request: last known config or defaults after a timeout | 3 s `AbortController`; last good response kept in localStorage | Unit tests with fake timers |
| Asset URLs respect the base path | Built-in logo and favicon via `BASE_URL`; uploaded logo URL comes from the API, which is not under the base path | Unit test; build with `VITE_BASE_PATH=/v2` |
| Loading and fallback covered by unit tests | See Tests | `pnpm test:run` |

## Legacy Today

Legacy loads nothing like this. Its tab title is "OpenLMIS" on every page, and the logos
are CSS background images compiled into `openlmis.css`. Its one runtime setting,
`/localeSettings`, is fetched after sign in, never revalidated, and kept in localStorage.
On failure it falls back to build-time constants, which is the model followed here, but
network-first rather than cache-only.

## Agent Brief

### API Map

| Step | Method and path | Params | Fields used | Right | Legacy ref |
|---|---|---|---|---|---|
| Boot | `GET /api/appConfiguration` | no `Authorization`, `cache: 'no-cache'` | `appName`, `showAppName`, `logo.url`, `theme.preset`, `theme.defaultAppearance`, `featureFlags` | none | none (new, FM-171) |
| Logo | `GET /api/appConfiguration/logo?v=<hash>` | via `<img>` and `<link rel=icon>` | image | none | none |

Plain `fetch`, like `loadRuntimeConfig()`, not the axios client: the client attaches a
bearer token when one exists, and a stale token on a public path gets a `401` from Spring
(FM-171 Rules). The path is `${import.meta.env.VITE_API_BASE_URL || '/api'}/appConfiguration`;
the dev proxy already forwards `/api`.

### Data Flow

- Boot: `await Promise.all([initI18n(), loadRuntimeConfig(), loadAppConfiguration()])`.
- `loadAppConfiguration()`:
  1. Fetch with a 3 s timeout (the same budget as FM-175's service worker rule).
  2. `200`: parse, store, write the raw response to localStorage `openlmis-ui.app-configuration`.
  3. `404`: use defaults and remove the cached copy (the server has none).
  4. Timeout, network error, `5xx`, bad JSON: use the cached copy if present, else defaults.
     A timed-out request is abandoned, not applied later, so the page never changes after
     it renders.
  Never throws, never logs.
- Store: a zustand store `useAppConfigurationStore` holding the parsed configuration, read
  with `getAppConfiguration()` outside React. Not the Query cache, which is cleared on
  every user change. FM-173 writes to it after a save.
- `applyBranding()` before render: `document.title` to the app name; the icon `<link>` to
  the logo URL or `${BASE_URL}olmis.png`.
- `applyThemePreset()` before render: writes one `<style id="app-theme">` with the preset's
  tokens as `:root { ... } :root.dark { ... }` (specificity beats `.dark` in
  `globals.css`); `src/lib/appearance.ts` resolves light or dark from the user's choice in
  localStorage `theme`, else the configured default appearance, else the device.
- Flags: `getFlag(key)` resolves admin value (store), then deployment value
  (`config.json` `featureFlags`, parsed in `runtime-config.ts`), then the registry default.
  A value of the wrong type or outside an enum's options is skipped at that layer.

### Rules

- Every field falls back on its own: a bad `theme` never discards a good `appName`.
- An unknown preset name falls back to `blue`.
- The uploaded logo URL is used as given (root-absolute `/api/...`); only built-in assets
  use `BASE_URL`.
- The strings `login.subtitle`, `home.summary.default`, `users.description`,
  `users.empty-description` and `users.form.create-description` take `{appName}`. "Powered by OpenLMIS" and the service account strings about the OpenLMIS
  API keep the product name, since they are about the platform, not the deployment.

### Translations

No new keys. Five existing strings gain `{appName}` in en, pt and ar.

### Risks and Edge Cases

- Built on FM-175, merged first: `loadRuntimeConfig()` keeps its reload on reconnect, and
  the service worker has no rule for `/api`, so the configuration always comes from the network
  or the local copy.
- Boot now waits for up to three requests in parallel; the slowest bounds first paint at
  about 3 s on a dead server, where today it would be the translations' own wait.
- Legacy wipes the whole origin's localStorage on a `401`, which drops the cached copy.
  The next boot fetches again; nothing breaks.
- A logo that 404s after a restore without its bytes: `onError` falls back.
- A server without the endpoint answers `404`, which the browser itself logs as a failed
  resource; the app handles it silently and uses the defaults.
- FM-175's service worker has no rule for `/api/appConfiguration/logo`, so an uploaded logo
  is not available offline; `onError` shows the built-in one.

## UI/UX

- **Improve:** the sidebar shows the app name beside the logo when expanded, which legacy
  hides with `text-indent`. The logo gets real alt text (the app name).
- **Improve:** the tab title follows the app name everywhere; today only login sets one.
- **Port:** the login page layout is unchanged apart from the logo and name.
- A wide logo is capped by height (`h-5` in the sidebar, or `h-6 max-w-44` when the name is
  hidden; `h-12` on login) with `w-auto`; FM-173 advises a shape on upload.

## Decisions

1. **Network first with a 3 s timeout, not stale-while-revalidate.** SWR would show a new
   logo only on the second reload, and the AC says the first.
2. **A late answer after the timeout is dropped**, so nothing changes under the user.
3. **Zustand store, not the Query cache**, since the cache is cleared on user change.
4. **Flag helper lands here** with the registry shape and the legacy flags as data;
   labels and the page come in FM-176.
5. **Theme mechanism lands here** with one preset, so FM-174 is presets plus a tab.

## As Built

- The parsed configuration keeps `version`, `appName`, `showAppName` (default true),
  `logo` (`url`, `contentType`), `theme` and `featureFlags`. A logo URL must be root-relative
  (`/api/...`), never `//host`.
- The expanded sidebar shows the name beside the logo in a `lg` ghost button with
  `width="shrink"`, so a long name truncates; the collapsed rail keeps the logo alone. The logo is
  `h-5`, or `h-6 max-w-44` when `showAppName` is off and the logo stands alone, carrying the name
  as its alt text.
- The five flags from FM-176 are registered here with their legacy defaults, so `getFlag` and
  `useFlag` are typed from the start.
- next-themes is replaced by `src/lib/appearance.ts`, a small store that keeps the `theme` key,
  follows the configured default when the user has no choice, and follows other tabs through the
  `storage` event. next-themes read the default only at mount and logged React 19's script-tag
  warning on every page.
- `src/lib/apply-app-configuration.ts` owns the side effects: title, favicon, preset tokens and
  the light or dark class, kept in step with both stores and the device setting.
- The favicon falls back to the built-in logo when the configured one fails to load.
- `applyBranding()` writes the name into the `<title id="app-title">` from `index.html`, so a
  page's own title, such as Sign In's, is never overwritten; a change of light or dark only
  touches the appearance.
- `useFlag()` follows the store, so a flag saved on the Feature Flags tab reaches the same
  session at once.
