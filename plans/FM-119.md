# FM-119: Roles

https://openlmis.atlassian.net/browse/FM-119 · Parent: FM-116 Admin: Users & Access

## Scope

Administration > Roles: the list, and one dialog to create or edit a role. It also moves
the role type and right label helpers out of `features/users` into `reference-data` so
both features can use them, and adds a `MultiComboboxField` (chips) and a
`TextareaField` to the form kit.

It also carries two fixes to the Users screens found while testing them, described under
Users Fixes.

Out of scope: deleting a role, as legacy has no delete and the API marks it "avoid using";
editing a role assignment on Edit User Roles, which legacy does not offer either.

## Summary

A role is a named set of rights, such as "Program Supervisor" with Approve Requisition and
View Requisition. Administrators create roles here, then give them to users on the Edit
User Roles page, which the new UI already has.

In the old UI, Roles is a table of every role with its type, description and how many
users hold it. Create Role first asks for one of four types (Supervision, Fulfillment,
Administration, Reports), then shows Name, Description and a checkbox for each right of
that type. Edit shows the same form with the type fixed. It works, but:

- Seven rights show raw codes such as `adminRoleForm.priceChangesView`, and Reports rights
  show made-up names like "Stockouts Right".
- The list cannot be searched, filtered or sorted, and breaks on a phone.
- Reloading the create form throws the user back to the type step.
- A duplicate name is only caught by the server, after Save.
- Saving an edit asks "Are you sure?" without saying what the change affects.
- A user who may see roles but not change them gets the Create and Edit buttons anyway,
  and an error when they use them.

The new screen keeps the same model and fixes these:

- A list you can search by name, filter by type and sort by any column.
- Create Role opens a dialog: pick the type, then fill in the name, description and
  rights. Edit opens the same dialog with the type fixed.
- Rights are picked from a searchable list, and the chosen ones show as chips with proper,
  translated names.
- A duplicate name is flagged as you type.
- Changing a role that users have asks first and says how many users it reaches.
- Only people allowed to change roles see Create and Edit.
- It works on a phone and in Arabic.

## Agent Brief

### API Map

All referencedata, under the shared axios client.

| Step | Method and path | Params | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| List | `GET /roles` | none; any param returns 400 | `id, name, description, rights[].type, count` | token only | `referencedata-role.service.js:34`, `RoleController.java:82` |
| Type step | none | | the four types are fixed | | legacy groups `GET /rights`; we do not need it |
| Rights for a type | `GET /rights/search` | `type` | `id, name, type` | `RIGHTS_VIEW` | `referencedata-right.service.js:33`, `RightController.java:196` |
| Edit | `GET /roles/{id}` | | `name, description, rights[].name/type` | token only | `RoleController.java:112` |
| Create | `POST /roles` | body `{name, description, rights: [{id, name, type}]}` | returned role | `USER_ROLES_MANAGE` | `RoleController.java:164` |
| Update | `PUT /roles/{id}` | body `{id, name, description, rights}` | returned role | `USER_ROLES_MANAGE` | `RoleController.java:187` |

Errors: `400 referenceData.error.role.mustBeUnique` (name, case-insensitive),
`mustHaveARight`, `rightsAreDifferentTypes`, `404 role.notFound`. Bodies are
`{messageKey, message}`. The duplicate may also surface as a 500 at commit, which only a
real write would show, so the form checks names itself and treats either as a save error.

### Rights

| Right | Gives |
| --- | --- |
| `USERS_MANAGE` | The page, the list and the nav entry, as legacy |
| `RIGHTS_VIEW` | The rights of a role: the View Rights row action and the rights picker |
| `USER_ROLES_MANAGE` | Create Role and Edit |

Create and Edit need `USER_ROLES_MANAGE` and `RIGHTS_VIEW` together, since the dialog cannot
pick rights without the second. The route loader reads the user's rights once and passes
plain flags down (`canViewRights`, `canEditRoles`); the feature has no auth imports. A
`?role=` link opened without the rights shows `NoAccess` in the dialog.

### Data Flow

- Loader awaits `requireRight(USERS_MANAGE)` and the rights set, then
  `prefetchQuery(rolesOptions())` deferred. The list uses the existing lookup with a short
  `staleTime` so it is fresh on open, like legacy's refetch.
- URL: `page`, `size`, `sort` (`name`, `type`, `count`), `q`, `type` for the filter, the
  dialog as `role=new` or `role=<id>`, and `roleType=<TYPE>` once a type is picked on create,
  so a reload lands on the form step. `rights=<id>` opens View Rights. Opening pushes and
  closing steps Back; moving between the steps replaces the entry, so the browser's Back
  closes the dialog and the dialog's own Back button returns to the type step.
- Sorting, filtering and paging are client-side, as `GET /roles` cannot do any of them.
  Copy `role-assignments-table.tsx`: filter, sort, slice, then `useTable` with
  `manualPagination` and `rowCount = matching.length`. Default sort by name.
- Dialog: edit loads `roleDetailOptions(id)` inside a `QueryBoundary` with a field skeleton,
  as the user dialog does; a missing role shows Not Found in the dialog. Rights for the type
  are fetched in the dialog and the picker suspends on its own.
- Save: `useMutation`, then `invalidateQueries(queryKeys.roles.all)` (this also refreshes the
  10-minute lookup the Edit User Roles page uses) and the signed-in user's `rightsOptions`,
  since editing a role they hold changes their rights. The dialog closes; the list shows
  the change.

### Rules

- A role's type is its first right's type (`role-type.service.js:49`, `Role.getRightType()`).
  A role with no rights shows "No Type" and, on edit, starts at the type step
  (`adminRoleForm.selectTypeForExistingRole`).
- Name and Description required, at least one right (`role-form.html:8-14`; server
  `Role.java:113`).
- Names are unique, ignoring case (`unq_role_name ON roles (LOWER(name))`). Check against
  the loaded list, skipping the role being edited; the server stays the final check.
- The type cannot change on edit (legacy). Users hold assignments shaped for that type.
- Saving an edit to a role with `count > 0` asks first; with no users it saves at once.
- Send rights as `{id, name, type}` only; legacy's `checked` flag is noise.

### Risks and Edge Cases

- Administration has 34 rights; the picker lists all of them without typing, so its list
  needs the scroll fade the other pickers have.
- Reports rights are created at runtime by dashboard reports, so a deployment can have
  rights with no label; they fall back to words from the code.
- Editing a role changes every holder's rights on the server; the signed-in user's cached
  rights are invalidated after save.
- Two admins editing one role: the last save wins, as in legacy.

## Users Fixes

Two problems in the finished Users screens, added to this ticket.

### Status Out Of Step

OpenLMIS keeps a user's status twice: `active` on the reference data user, which the Users
list and its status filter show, and `enabled` on the auth account, which decides sign-in
and which the Edit User form shows, as legacy's does. Both UIs save the switch to both, so
they only differ in data made elsewhere. On test every inactive user checked (15 of 15)
is `active: false` but `enabled: true`: the list says Inactive, the form says Active.

- Keep the form on `enabled`, since it is what lets the user in; showing `active` would lock
  a user out on an unchanged save.
- When the two differ, show an `Alert warning` above the Active switch saying which way they
  differ and that saving applies the switch to both. `statusMismatch(details)` in
  `user-form.ts` returns `listed-inactive`, `listed-active` or none; unit tested first.
- Keep the Status column and filter. A list of `enabled` flags would take one auth call per
  row; there is no batch endpoint.

### Password Rules

The auth service checks (`PasswordResetRequestDtoValidator.java`, `PasswordStrengthValidator.java`):

| Rule | Server message key |
| --- | --- |
| 8 to 72 characters, only the letters A to Z and digits (`^[a-zA-Z0-9]{8,72}$`) | `users.passwordReset.invalidPasswordLength` for either |
| At least one digit | `users.passwordReset.notContainNumber` |
| No spaces | `users.passwordReset.containSpaces` |
| Does not contain the username, first or last name, ignoring case | `users.passwordReset.containUserDetails` |
| zxcvbn score of at least 2 | `users.passwordReset.tooWeak`, with English suggestions |

It reports only the first failure, the length message also covers symbols, and the
dialog only mentions "8 characters and 1 number". A password such as `v9&kznqG0C2(` is
rejected as "size must be between 8 and 72".

- `passwordChecks(password, user)` in `password-form.ts` runs the four fixed rules; the
  schema takes the user so it can check the names. Unit tested first.
- The dialog lists the rules under the field and ticks each one off as the password meets
  it; on submit the first unmet rule is the field error.
- The strength error, the only one the server sends with its message key
  (`users.passwordReset.tooWeak`), is shown in our own translated words: the password is too
  easy to guess, so make it longer. The fixed rules come back as English text in place of a
  key, so they are caught before sending instead; anything else shows the server's message.
- The error title follows the dialog: Could Not Set Password or Could Not Reset Password.
- Strength stays a server check: a browser port of zxcvbn can score differently from the
  Java one and is a large download.

## Decisions

- Create and Edit are one dialog with a type step, not pages: the form is short.
- Rights are a multi-select with chips, not checkboxes.
- Manage Users opens the list, View Rights shows a role's rights, and Manage User Roles with
  View Rights allows Create and Edit.
- The confirm on save only appears when users have the role, and says how many.
- Types appear in the same order as the Edit User Roles tabs (Supervision, Fulfillment,
  Reports, Administration) everywhere, rather than legacy's picker order, so one app has
  one order.
- The four types are fixed in code, not grouped from `GET /rights`, which saves a call.
- Reports rights use their `rights.*` labels instead of legacy's title-cased codes.
- No Delete, matching legacy.
