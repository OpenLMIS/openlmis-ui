## Scope

product picker, with the list/add screen in FM-135. Keep backend services unchanged on
master. Do not build partner-node management or requisition splitting here.

Planning baseline: frontend `2c29977c`, referencedata master `9f258aa`, legacy UI
`b9c7646`, requisition `836d2b8`, checked 2026-10-15. No implementation before approval.

## Summary

An administrator assigns each supply partner a program and partner supervisory node,
then chooses the facilities and products that supplier will fulfil. Legacy holds these
changes in one draft until Update Supply Partner saves them together. The new editor
keeps that model, adds protection for unsaved work, fixes incorrect View dialogs after
paging, and shows the server's useful error detail. Product selection works across pages
without closing when searching. Users who cannot load supervised facilities get a clear
message in that section while retaining access to the partner page.

All paths are relative to `/api`. Lookup GETs have no additional admin-right check except
the supervised-facilities call; ordinary authentication still applies.

| Save | `PUT /supplyPartners/{id}` | Whole DTO below | 200 partner DTO | `SUPPLY_PARTNERS_MANAGE` | RDUI edit service/resource |
| Programs | `GET /programs` | None | `id,code,name` | None additional | RDUI repository and association service |

checks mismatch, but the builder relies on the body id to load the existing partner.

### Data Flow And Saving

- List/edit routes require `SUPPLY_PARTNERS_MANAGE`; do not add a second route right.
  Routes read permissions and pass plain capability flags into the feature.
- Editor route `_protected.administration.supply-partners_.$id.tsx` has
  `preload:false`. Block on a fresh raw partner read on `cause:'enter'`
  (`fetchQuery`, `staleTime:0`); reuse on `stay` for query/dialog/paging changes, following
  `-requisition-group-route.tsx`. Key the initial draft by the entry's read timestamp,
  not by dialog query or table page. Pending/error/404 have the real page shell and Back.
  Keep the initial saved snapshot and entry key stable across `stay` loads; pre-save refresh
  uses a direct API read without updating the draft-seeding detail cache. Only explicit
  Reload or a new route entry replaces them. The supervisory-node save helper is the
  direct-read precedent; do not copy Groups' current cache timestamp on every stay load.
- Defer lookup hydration under bounded subtrees using `QueryBoundary`/`LookupBoundary`.
  Fetch only ids held by this partner for its initial table; load the full node list when
  the association dialog first needs options. Parallelize independent lookups. Query keys
  retain shared lookup ownership, while raw partner queries use `queryKeys.supplyPartners`.
- Keep authoritative ids in the draft separately from presentation maps. Never silently
  replace failed lookups with raw ids or discard members. Failed hydration shows retry;
  missing referenced records show a translated unavailable state. Block Update until
  required ids resolve or the affected association/member is explicitly removed.
- One page form holds Name and every association. `useSessionMutation` owns writes;
  preserve the draft and show `serverMessage` on failure. Pending blocks edits, close and
  page exits. On success invalidate `queryKeys.supplyPartners.all`, then return to the
  original list search using history state, with a success title and description.
- Before changed PUT, reread the partner, compare a canonical id-based snapshot with
  the opening baseline, and refuse a conflicting whole-record overwrite, retaining the
  draft. Snapshot = code, name, and per program/node pair the sorted facility ids and
  orderable ids. Ignore association ids (rebuilt on every PUT), hrefs and all ordering.
  Follow the supervisory-node editor's pre-save conflict alert and Reload pattern.
  Reload explicitly discards the draft: fetch fresh data, replace the URL without dialog
  params, and remount using a new readAt/revision. Do not use `router.invalidate()` alone,
  because a `stay` loader intentionally retains cached data. A 404 must not be followed by
  PUT: the endpoint otherwise upserts.
  There is no ETag/version; this reduces stale overwrites but cannot close the GET/PUT race.
  An unchanged draft does not need a PUT; return to the list without a false save toast.
- `useDiscardGuard` receives `pageDirty || associationCopyDirty || productSelectionDirty`,
  protecting page navigation, sign-out and browser exits even if only a modal has changed.
  Same-path query changes preserve the page draft. A feature-local `useBlocker` protects
  same-path changes that close or switch a dirty association. Cancel, Escape, the close
  button and Back use that same guard and `DiscardChangesDialog`; only one discard prompt
  appears, with pathname changes handled by the page guard. Opening/closing only `products`
  does not trigger the association guard. FormDialog already disables outside dismissal.
  Product-picker Cancel discards only its selection edits. External identity changes drop
  drafts through the protected layout; mutation callbacks check identity after awaits.

### URL State And Draft Identity

- Main editor `page,size` belong to its associations table, independently from the
  originating list state retained in history.
- `association=new` or `association=<programId>:<nodeId>` opens the editor copy.
  `products=true` opens the nested picker while keeping the same association parameter.
  `view=facilities|products&viewAssociation=<programId>:<nodeId>` opens a read-only View.
  Validate mutually incompatible dialog states and use `DialogNotFound` for a missing
  requested pair, never silently start a new association for an invalid edit link.
- Main table row identity is the program/node pair, not page index. View and Remove take
  that identity. New associations get their final pair on submit; no index-based links.
- Compose `useSearchNavigation` in feature-specific route glue: preserve parent modal
  params when opening the nested picker; close only the child when appropriate. A direct
  nested link closes to its association, not the underlying page. Preserve history state
  on table changes. Do not change shared navigation semantics for this feature.
- Normalize incompatible states with replace: `products` without `association` is dropped;
  `association` wins over `view`. A fresh direct link to `association=new&products=true`
  opens only the empty association. In-session opening after selecting facilities in a new
  association must still work. Do not unconditionally strip `products` for `association=new`.
  Remove confirmations remain component state and close when their target disappears.
- Dialog search and paging may remain local, reset per opening, since they neither select
  server records nor seed the page draft. `useOpening` can key per-opening UI state if the
  component is retained; it does not require new server detail keys for draft-only dialogs.

### Association Rules

1. Program and Supervisory Node are required and immutable for an existing association.
   Offer only nodes with `partnerNodeOf`. Exclude a used program/node pair among the
   partner's other draft associations, preserving the current pair when editing. Filter
   both node choices for the selected program and program choices for the selected node.
2. Changing Program or Node in a new association immediately clears facilities, products
   and outstanding picker state. Fetch choices only for the current pair; ignore obsolete
   results. Adding a facility keeps the selected products.
3. Load facilities using the selected partner node's **parent** `partnerNodeOf.id` and
   chosen program **id**. Exclude already selected facilities. This endpoint pages an
   unordered Set in memory; use one unpaged GET as legacy `getAll` does, avoiding page
   slicing of unstable iteration order. Master's fallback page is `Integer.MAX_VALUE`
   (`CustomWebMvcConfigurerAdapter.java:57-61`). Do not send page/size on this lookup.
4. A missing `SUPERVISORY_NODES_MANAGE` right shows in-place No Access beside the disabled
   facility picker, explaining the extra right needed. Handle an actual 403 identically.
   Keep existing Name/associations visible. Do not convert refusal to an empty list, and
   do not clear existing members merely because choices could not load.
5. Product choices use hydrated **selected-facility records** (`type.code`), not legacy's
   supervised-only choices. This deliberate fix allows Add Products and removal/pruning
   even when the facility picker shows No Access. With the right present, label saved
   facilities absent from supervision as no longer supervised; never silently remove them.
   The server validates all associations again on PUT. Choices use unique **type codes** and chosen
   program **code**. No facilities means no request and no options. Send one unpaged GET,
   matching legacy `getAll`: the query has no stable ordering, so paging could skip valid
   products. Master defaults the page size to `Integer.MAX_VALUE`. Dedupe by orderable id
   and prefer the greatest returned product version if duplicated.
   Keep the default active approvals, as legacy. Backend validation also accepts inactive
   FTAPs; do not silently delete existing selections merely because they are not offered
   for a new selection. Show such selected items separately with unavailable-for-add text
   and permit deliberate removal; Add Products must never silently erase hidden selections.
   The explicit facility-removal action below is the exception: it reconciles the whole
   selected set against active approvals and reports what was pruned.
6. **Approved, matching legacy (2026-10-16):** removing a facility recomputes approved choices for
   remaining types and removes only products absent from that set; last facility removes
   all. Warning: "Removing a facility removes products that are no longer approved for
   the remaining facility types." This also prunes products already unavailable for adding,
   matching legacy; show the removed product count and names in a status/summary after the
   action. Read approvals fresh before destructive pruning with
   `queryClient.fetchQuery({ ...facilityTypeApprovedOrderablesOptions(filter), staleTime: 0 })`;
   never prune from the 10-minute picker cache, since Products approval edits invalidate
   only their per-product key. Stage removal/pruning atomically: lookup failure keeps the
   facility and products unchanged, with retry. Never interpret failure as no approvals.
7. Association submit requires at least one facility and product and a unique program/node
   pair. Validate `.length`, not arrays coerced to numbers. Local error text should apply
   to both Add and Edit, with correct spelling. Update changes only the copied page draft.
8. Nested picker preselects current products and returns the **whole** selection, including
   deselections. Name contains OR code starts with, case-insensitive; one live search,
   standard client pagination (including the shared page-size control). Search never submits the form. Use
   `selectionColumn`, stable ids and a map retaining selections across pages/searches.
   This is an explicit exception to bulk-action filter-clears-selection: the selection is
   the edited membership, matching legacy. Header selects the current page only.
9. Remove Association confirms, changes the draft only and clamps a now-empty final page.
   The unpaged tables show Facility Name/Facility Code and Product Name/Product Code, with
   trash actions labelled Remove plus item identity; they scroll in the dialog body.
   Add Products is disabled without facilities, with an Add A Facility First hint.
   View dialogs show Name
   and Code, same local search predicate, paging, no matches with Clear Search, and Close.

### Server Validation And Limits

Show localized `message` through `serverMessage`, with translated fallback, for code/name
required, duplicate code, duplicate association, missing facilities/products, invalid
partner node, facility not supervised for the program, unapproved product and global
program/node/facility/product overlap across partners. Keep the draft on every failure.

The whole controller is transactional. The builder loads the managed entity, clears its
associations, then checks `findAll()` while adding new associations one by one. The JPA
identity map returns the same cleared instance, so its original associations should not
cause `globalUnique` on unchanged PUT, independently of flushing. Separately, replacing
association rows relies on deletes reaching the database before inserts with the same
unique program/node/partner key. Both are **source-based inferences**, not real-save
results; controller tests mock the builder. After approval, prefer disposable local
backend fixtures to check unchanged and changed association PUTs if a local service is
available. Otherwise retain this verification limit. No live test-server PUT is authorized.
Do not introduce a UI workaround that drops associations.
Other partners can change after opening, so the server remains the final validator.
