## Summary

A supervisory node is a point in the approval chain: a requisition from a facility goes to
its group's node, then up through parent nodes until it is approved. Nodes can also have
partner nodes, used when one requisition is split between suppliers.

In the old UI, Administration > Supervisory Nodes is a table of 10 nodes a page with Name,
Code, Facility, Child Nodes (a count), Geographic Zone and Partner Nodes, and an Edit button.
A Filter button opens a name box and a zone list. It works, but it is slow: every load and
every page change downloads all 511 nodes (357 kB, 4 to 9 s on test, about 14 s on UAT) only
to name partner nodes. A search with no results downloads every facility (4 MB).

The new list shows the same columns and filters and pages on the server, as legacy. It asks
only for what the visible page needs: the page of nodes, the facilities of those nodes and the
names of their partner nodes. Name search and the zone filter sit in the toolbar, as on
Facilities, and stay in the address so a link or Back keeps them. Edit is in each row's "..."
menu and returns to the same page and filters.

## Legacy Today

Route `/#!/administration/supervisoryNodes?name&zoneId&nodesPage&nodesSize`, guard
`SUPERVISORY_NODES_MANAGE`. Screenshots: `.screenshots/FM-132/legacy-list-*`,
`legacy-filter-open-*`, `legacy-partner-popover-desktop.png`.

- 10 rows a page; pager reads "Showing 10 item(s) out of 511 total". Rows come in database
  order (SN1, SN1.1, SN11.2, SN2...), not by name.
- Facility is the node's facility name; Geographic Zone is that facility's own zone. Both are
  blank for the 2 nodes without a facility.
- Child Nodes is the count of child nodes.
- Partner Nodes: blank for none, the partner's name for one, "N Partner Nodes" with a popover
  of names for more. Only one node on test has a partner (SN-LILONGWE-DIST-ARV-1).
- Filter popover: Name (contains, case-insensitive) and Geographic Zone (all 205 zones,
  exact match on the facility's zone). Both are searchable selects with a clear "x", and
  both are sent to the server.
- Load: `GET supervisoryNodes?page&size` (46 kB, 2 to 4 s; page 0 holds the three nodes with
  72 to 91 children), `GET geographicZones` (252 kB), `GET facilities?id=...` (12 kB), and an
  unpaged `GET supervisoryNodes` (357 kB, 4 to 9 s) to name partners, because it reads
  partner ids from `extraData.partnerNodeIds`, which is always empty. All four repeat on every
  page change. A page with no facilities sends `GET facilities` with no ids: 4.18 MB.
- Legacy source: `openlmis-referencedata-ui/src/admin-supervisory-node-list/`
  (`admin-supervisory-node-list.routes.js:29-80`, `supervisory-node-list.html:35-50`,

## Agent Brief

### API Map

| Step | Method and path | Params | Fields used | Right | Legacy ref |
|---|---|---|---|---|---|
| Page of nodes | `GET /api/supervisoryNodes` | `name`, `zoneId`, `page`, `size` (no `sort`: ignored, and any unknown param is a 400) | `id, code, name, facility.id, childNodes.length, partnerNodes[].id`, `totalElements` | none on GET | `admin-supervisory-node-list.routes.js:36` |
| Facility and zone names | `GET /api/facilities?id=...` through `facilitiesByIdsOptions` | ids of the page's facilities; skipped when there are none | `name`, `geographicZone.name` | none | `routes.js:43-56` |
| Partner names | `GET /api/supervisoryNodes?id=...&page&size` through `supervisoryNodesByIdsOptions` (this feature) | partner ids on the page, repeated `id` params, at most 100 a request; skipped when there are none (no ids would list all, a bad id is a 500) | `id, name` | none | `routes.js:59-70` (unpaged there) |
| Zones for the filter | `GET /api/geographicZones` through `geographicZonesOptions` | none | `id, name, level.name` | none | `routes.js:72-80` |

The node DTO carries only `{id, href}` for facility, parent, children and partners
(`SupervisoryNodeDto.java`), so the facility and partner lookups are needed.

### Data Flow

- Loader: `loaderDeps` from the search; `await requireRight(...)`, then unawaited
  `prefetchQuery` of the list and `geographicZonesOptions()`.
- `supervisoryNodesPageOptions(query)` under `queryKeys.supervisoryNodes.list(query)`: its query
  function reads the page, then the facilities and partner nodes by id in parallel, and returns
  rows with `facilityName`, `zoneName` and `partners: {id, name}[]` resolved, plus the total.
  One query, so the table never shows half-resolved rows, as Lots' `fetchLotRows` does. A
  failed name lookup fails the page and shows `ListError` with retry. The mapping is a pure
  `toNodeRows(page, facilities, partners)` in `lib/node-rows.ts`.
- URL: `page`, `size`, `name`, `zoneId`; no `sort`/`dir` (`.omit` as Lots does). Defaults stay
  out of the URL. Row Edit passes `supervisoryNodesListSearch` in history state.

### Server-Side Work

Paging and both filters stay on the server, as legacy. Partner names move from an unpaged
download to an id lookup of the visible page. Sorting cannot move to the server; rows keep the
server's order, which was stable across repeated reads on test.

### Risks and Edge Cases

- Page 0 itself takes 2 to 4 s on test (it carries 72 to 91 child refs per big node); the
  gain is in skipping the 357 kB download and in later pages (about 0.5 s).
- Without ORDER BY, Postgres may reorder rows after updates; a node could shift pages after a
  save. Legacy has the same behaviour.
- `zoneId` that is not a UUID is ignored by the server; the schema drops it first.

## UI/UX

- **Port**: the columns and their content, server paging, name and zone filters, server
  order, the partner popover.
- **Improve**: filters in the toolbar instead of a popover, live in the URL; the zone filter
  shows each zone's level; Edit returns with page and filters (legacy drops the filters);
  empty, no-matches (with Clear Filters) and error-with-retry states.
- **Columns**: every legacy column shows at laptop width and none hides by default; narrower
  tables scroll sideways. The View menu lets a user hide Code, Facility, Child Nodes, Zone or
  Partner Nodes; Name and actions always stay.
- **Drop**: the separate Filter popover, its Cancel and Search buttons; the unpaged downloads.
- Row action is the end-of-row "..." menu with Edit, as on every list. Table cells with no
  value stay blank. Arabic: logical classes, popover sides `inline-start/end`.

## Decisions

- **Server order, no sorting**, as legacy: the API ignores `sort`, and sorting locally would
  mean downloading all 511 nodes, the slowness this ticket removes.
- **One query resolves a page's names** before rows render, rather than separate cell
  lookups, so rows never flicker from blank to filled.
- **Name-only search**, as legacy; no code search (the API has `code`, but legacy never offers
  it, and the single-box rule keeps name-only lists name-only).

- **By-id paging is shared from `src/lib/`**, moved out of `reference-data` unchanged, and the
  node lookup stays in this feature (user, 2026-10-14).
