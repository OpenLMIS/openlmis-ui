# FM-145: Reasons

https://openlmis.atlassian.net/browse/FM-145 · Parent: FM-139 Admin: Products & Programs

## Scope

Administration > Reasons: the list of stock reasons, adding one, and editing one with its
tags and the program and facility type pairs it is used in. It is Tier 1 row 11 of
[FM-62](FM-62.md): Adjustment, the Issue and Receive reasons, physical inventory reasons and
Reverse all read what this screen sets.

Shared pieces this PR adds, which later screens reuse:

- `TagsField` in `src/components/form/`: type to add a tag, pick from suggestions, remove with
  its x;
- a reasons lookup in `reference-data`, which the stock screens read later.

Out of scope:

- deleting a reason: legacy has no delete and the API has none;
- a reason's description: legacy never shows it, so it is not shown either, but it is kept on save
  (legacy wipes it, see Decisions);
- filtering by category or type: legacy has no filter, and 19 reasons fit on two pages.

## Summary

A reason says why stock moved: "Transfer In", "Damage", "Expired". Each one is a Credit or
a Debit, a Transfer or an Adjustment, may let the user type a note ("Allow Free Text"), and
carries tags that later screens use to find it (such as `cancelMovement` for Reverse). A reason
is only offered where it is assigned: per program and facility type, and each assignment can
hide it from the stock and requisition forms without removing it.

In the old UI, Administration > Reasons is one table of every reason, with Name, Category, Type,
Allow Free Text and an Edit button. Add Reason opens a window with the reason's fields, its tags
and a "Where is this reason used?" table of program and facility type pairs. Edit opens the same
form as a page. It works, but:

- **The edit page checks nothing.** Update Reason sends an empty or duplicate name to the
  server, and the only answer is the server's error text in a popup.
- **Its bottom bar covers the last rows** of the pair table, on desktop and phone.
- **Saving can lose a pair.** Turning Show off on a saved pair sends a delete and an add at the
  same moment; when the add lands first, the pair is gone.
- **A failed save can't be retried.** If the reason saved but a pair did not, pressing Add
  again tries to create the reason twice and fails on its own name.
- **Editing wipes the reason's description**, which the form never sends back.
- The list shows raw codes (`ADJUSTMENT`, `DEBIT`), has no order, and is cut off on a phone.
  Unpack Kit's category shows as blank on edit.

The new screen keeps the same fields, rules and flow, and fixes those:

- **List:** sorted by name, with a name search and pages, and the category and type in words.
  Edit is in the row's "..." menu.
- **Add and Edit:** both are one page with the same form. Both check the
  name is filled in and not used by another reason before anything is sent. Category and Type can't be
  changed once a reason exists, as in legacy, and always show their value.
- **Tags:** type a tag and press Enter or comma, or pick an existing tag from the suggestions;
  remove it with its x.
- **Where Is This Reason Used:** add a program and facility type with Show on or off; the same
  pair can't be added twice. Show can be switched on a saved pair directly, rather than removing
  and adding it again.
- **Save:** one Save for the reason and its pairs. A pair that fails is named, and Save again
  retries only what is still not saved.
- The footer never covers the form, and the page works on a phone and in Arabic.

Stock screens in the old UI keep a copy of the reason assignments from sign-in, so a change
reaches them the next time the user signs in. That is legacy's behaviour, and this screen does
not change it.

## Legacy Today

Measured on the local instance (stockmanagement 5.4.0, stockmanagement-ui 2.2.0), 19 reasons.
Screenshots are in `.screenshots/FM-145/` (`legacy-*`).

- **Routes:** `/#!/administration/reasons` (list), `/reasons/add` (a modal over the list),
  `/reasons/:id` (a page). Menu: Administration > Reasons. All three need
  `STOCK_CARD_LINE_ITEM_REASONS_MANAGE`.
- **List:** Name, Category, Type (raw codes), Allow Free Text (a tick), Edit. No order, search,
  sort or pages. Empty: "There are no matches for reason."
- **Form (add and edit):**
  - Name\*;
  - Category\* (Transfer, Adjustment);
  - Type\* (radios Credit, Debit);
  - Free Text ("Allow Free Text entry with this Reason", off);
  - Tags, with the help text "Tags give a flexible way to group reasons. Their semantic sense rests
    with the implementer.";
  - "Where is this reason used?", with the text "Add any program and facility type where this
    reason can be used, and set whether to show the reason in the Requisition form and Stock
    adjustment form:".
  - The pair row has Program\* (all programs), Facility Type\* (active ones) and Show (on), plus
    Add. The table under it has Program, Facility Type, Show (tick) and Remove. Empty: "There are
    no matches for assignment".
- **Add:** required fields show "This field is required" after the first submit, and a "This
  form is invalid" popup. Duplicate name, case-insensitive against the loaded list: "The reason
  name is duplicated". Duplicate pair, whatever Show is: "Given valid reason assignment exists."
  Cancel or x closes at once. Success toast "Reason saved successfully", then the list reloads.
- **Edit:** title "Edit Reason", fixed bottom bar with Cancel and Update Reason. Category and
  Type disabled. No client checks at all. Remove changes only the table; everything is sent on
  Update. Changing Show means Remove and Add again. No confirm on leaving.
- **Tags:** suggestions from the existing tags after 2 characters, matched anywhere, any case.
  Enter, Tab, comma or leaving the box adds. Trimmed; under 3 characters is refused silently.
  Duplicates (any case) refused: "This tag is already added". Backspace in an empty box removes
  the last tag.
- **Problems:** listed in the Summary. Also: the facility type names come from active types only,
  so a pair with an inactive type shows a blank cell.

### Data Flow

- **List** `/administration/reasons`: the loader awaits `requireRight`, then prefetches
  `reasonsOptions()` without awaiting it, `staleTime: LIST_FRESH_FOR`, as Roles. The URL holds
  `page`, `size`, `sort`, `dir` and `q`. Filter, sort and page in the browser
  (`src/features/reasons/lib/reasons-list.ts`, like `roles-list.ts`), clamping a page past the
  end. The default sort is name ascending; Category and Type sort by their label.
- **Add** `/administration/reasons/new` and **Edit** `/administration/reasons/$id`: one
  `ReasonEditor`, like `facility-editor.tsx`.
  - The Edit loader runs `Promise.all([requireRight, fetchQuery({...reasonDetailOptions(id),
    staleTime: 0}), fetchQuery({...validReasonsOptions(id), staleTime: 0})])`, since the save sends
    the whole record back and diffs the pairs against what is stored. A missing reason shows a
    not-found panel, as `facilities_.$id.tsx`.
  - Both routes prefetch types, categories, tags, programs and facility types without awaiting
    them. Each lookup field sits in its own `LookupBoundary`.
  - Both pages are `crumbKey` children of Reasons. The list link passes its search in history
    state (`reasonsListSearch`), so Save and Cancel return to the same page, sort and search.
- **Query keys:** add `reasons` and `validReasons` scopes to `key-factory.ts`:
  - `reasons.list()`;
  - `reasons.detail(id)`;
  - `[...reasons.all, 'tags']`, `'types'` and `'categories'`;
  - `validReasons.list({reason: id})`.
- **After a save:** invalidate `reasons.all` (list, detail and tags) and
  `validReasons.list({reason})`.

### Server-Side Work

Nothing to move: no reason endpoint can page, sort or filter, so the list is filtered, sorted
and paged in the browser behind the URL, as Roles is. The name check runs against the same
list, since the server only refuses an exact-case duplicate. Names for the pairs come from
the programs and facility types lookups, since `validReasons` returns only ids.

### Save

1. Add: `POST` the reason. Edit: `PUT` it, sending the record read fresh with the form's fields,
   so `description` and anything else the form doesn't show stays as stored.
2. Diff the draft pairs against the saved ones by program and facility type:
   - gone or with a changed `hidden`: `DELETE` its saved id;
   - new or with a changed `hidden`: `POST` it.
3. Send every `DELETE` first, then the `POST`s, five at a time (`settleFew` in
   `src/lib/settle-few.ts`, which Valid Destinations' bulk delete now shares). That way the server never answers a re-added pair with the old row. A `DELETE`
   answered `reasonAssignment.notFound` counts as done.
4. If every request succeeded: toast "Reason Saved", then go back to the list.
5. If something failed: stay, show an `ErrorAlert` naming the failed pairs (with the server's
   reason when there is only one), and keep the draft. The save returns the pairs now stored,
   so the next Save diffs against them and retries only what is still missing.
   - On Add, the page keeps the reason it created, so a retry updates that reason rather than
     creating it again. The address stays `/reasons/new`, since moving to `/reasons/$id` would
     reload the page and lose the draft.

### Risks and Edge Cases

- A pair whose facility type is inactive: its name comes from the full facility types lookup,
  and `Unknown` if it is gone.
- Two admins editing one reason: the `PUT` sends the record read when the page opened. As
  Programs and Facility Types do, a fresh read on every opening is the guard; there is no
  version to conflict on.
- Turning Show off and on again before saving is no change, and sends nothing.
- A tag shared by other reasons stays in the suggestions after this reason drops it, since the
  server lists distinct tags across reasons.

## Decisions

- **Add is a page, not a modal**, one editor for Add and Edit, as Add Facility: the form has
  tags and a table of pairs, which AGENTS.md puts on a page. The ticket's modal is dropped
  (agreed with the user).
- **Category and Type are read-only on edit**, as legacy, and the server refuses a change.
- **Description is kept** by sending the record read fresh, rather than wiping it as legacy does.
- **The edit page checks the name** as Add does; legacy's missing check is a defect.
- **Pairs are sent on Save, deletes first.** That fixes legacy's lost pair, and a failed save
  is retried by diffing against what is stored, not by sending everything again.
- **Show switches inline** on a saved pair rather than Remove and Add, which sends the same
  requests.
- **Tags keep legacy's rules**, the 3 character minimum included, with a message instead of
  silently keeping the text.
- **Reasons lookup in `reference-data`**, since Adjustment, Issue, Receive and Reverse read it
  later; the writes, detail, tags, types and categories stay in `src/features/reasons/`.
- **Types and categories come from their endpoints**, as legacy, with a label per known code and
  the raw code for anything new.
