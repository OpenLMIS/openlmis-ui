# FM-176: Feature Flags Managed in the UI

https://openlmis.atlassian.net/browse/FM-176 · Parent: FM-170 Global app configuration
(branding, theme & feature flags)

## Scope

This PR adds the **Feature Flags** tab to Settings, the labels and descriptions for
every registered flag, and the deployment layer: `config.json` carries the legacy flag env
vars, so a deployment's `settings.env` keeps working. It builds on FM-172 (registry,
resolver, `getFlag`/`useFlag`) and FM-173 (page, rights, save pattern).

It does not migrate any flagged screen, does not touch backend flags (Togglz or
`CATCHMENT_POPULATION_CALC_AUTO`), and does not change the legacy UI, which keeps reading its
own container env during dual boot.

## Summary

Some OpenLMIS features are optional: batch approval of requisitions, barcode scanning in
stock management, the Packs and Doses switch, the requisition-less order menu entry. Today a
deployment turns them on by editing an environment file and restarting the UI.

In the new UI an administrator sees every optional feature on one tab and can search it by
name, key or screen. Each shows whether it is on, and what it does and which screen uses it
behind an info button. A value set by the deployment says so, and a value changed here stands
out, with what it would go back to. They change it with a switch or a list, or reset one flag
to fall back to the deployment's value or the default. Everyone gets the change on their next page load.

Existing deployments lose nothing: the same environment variables still set the starting
values. A setting changed here only reaches screens in the new UI; the old screens keep
their environment settings until they move over.

## Legacy Today

| Flag | Default | Used by | Behaviour |
|---|---|---|---|
| `BATCH_APPROVE_SCREEN` | false | Requisitions > Approve | Shows the checkbox column, Select All / None, and View Selected Requisitions. On test.openlmis.org it is on. |
| `GS1_SCANNING` | false | Physical inventory draft, stock adjustments (issue, receive, adjust) | Shows the GTIN scan input. |
| `QUANTITY_UNIT_OPTION` | `BOTH` | 8 stock and requisition screens | `PACKS` or `DOSES` hides the Packs/Doses toggle; `BOTH` shows it. |
| `DEFAULT_QUANTITY_UNIT` | `DOSES` | The same screens | The unit used until the user picks one (kept in localStorage `quantityUnit`). |
| `SHOW_REQUISITION_LESS_ORDER` | true | Orders > Create Order | Shows the menu entry; the route stays open with `ORDER_CREATE`. Build time only in legacy. |
| `CATCHMENT_POPULATION_CALC_AUTO` | false | Geographic zones | Also read by referencedata at startup; server-enforced. |

Legacy's `featureFlagService.set()` only accepts `'true'`/`'false'`, so the two enum flags
always read back as their defaults through it (source: `openlmis-ui-components/src/openlmis-feature-flag/feature-flag.service.js`;
the AngularJS toggle reads the env value directly as a workaround). The new registry types
enums properly. No legacy screen lets anyone change a flag.

### Registry (data in `src/lib/feature-flags.ts`)

`BATCH_APPROVE_SCREEN`, `GS1_SCANNING` and `SHOW_REQUISITION_LESS_ORDER` as booleans;
`QUANTITY_UNIT_OPTION` as an enum of `PACKS`, `DOSES`, `BOTH`; `DEFAULT_QUANTITY_UNIT` as an
enum of `PACKS`, `DOSES`. The defaults are legacy's. Each carries `labelKey`,
`descriptionKey` and the screen it affects (`usedByKey`); enums also carry `optionKeys`.

### Deployment Layer

- `docker/config.json.template`: `"featureFlags": { "BATCH_APPROVE_SCREEN": "${BATCH_APPROVE_SCREEN}", ... }`

  list.
- `docker-compose.yml`: pass them through.
- Parsing (FM-172 resolver): an empty string means unset; `"true"`/`"false"` for booleans;
  an enum value outside its options is ignored.

### Rules

- The page sends every override it holds, including keys it does not know (a newer UI
  version's flags), so a save never deletes another version's settings.
- A value set by hand to what the flag would inherit (deployment, else default) is not an
  override, so setting a flag back by hand removes it just as Reset does.
- A stored value is an override even when it equals what the flag would inherit, so it shows as
  changed here, with Reset, never as set by the deployment.
- The "Changed here" line and the effective value are computed from the draft, so they move as
  the admin edits.
- A change hidden by the search is kept, and Save stores it.
- The page never shows a flag outside the registry, and never shows backend flags.

### Risks and Edge Cases

- No flagged screen is in the new UI today, so changing a flag has no visible effect yet. The
  page does not say so per flag; the deployment docs cover dual boot.

- Dual boot: legacy keeps its container env, so the two UIs can disagree on a screen that
  exists in both. Once a screen migrates, the new UI's value is the one users see.
- An admin value for a flag later removed from the registry stays in the database, unused
  and preserved (Rules); harmless.

## UI/UX

- **Layout:** a search box above one `SettingsList` row per flag: the label, an info button
  (a popover with the description and "Used by"), and for a changed value a small destructive
  Reset; the control at the end. Under the label, the flag key in a muted monospace line, for
  operators matching it to their `settings.env`, followed by " · Set by the deployment" when the
  deployment sets it. A value changed here gets a primary bar on the row's start edge and
  "Changed here · The default is **X**" or "Changed here · The deployment sets **X**".
- **Search:** filters by name, key, description or screen, kept in the URL; no match shows
  "No Feature Flags Match" with Clear Filters, which also returns focus to the search box.
- **Controls:** a `SwitchField` for booleans, a `SelectField` for enums (AGENTS.md form
  rules).
- **Footer:** Cancel and Save, as on the other tabs; the discard guard covers tab switches.
  No Reset To Defaults in the header: each flag's own Reset removes its override.
- **Improve over legacy:** a flag is visible and changeable at all; its source is explained;
  enums actually work.
- **States:** the same page states as Branding, except that loading holds no header button.

## Decisions

1. **All flags are public** in the read, so the login page and boot need no second request;
   a flag is never a secret, by rule.
2. **Backend-enforced flags are not shown.** `CATCHMENT_POPULATION_CALC_AUTO` is read by
   referencedata at startup, so a UI switch would lie; the Togglz flags are backend
   behaviour. Both stay in the deployment's env, documented.
3. **Enums typed properly**, fixing legacy's enum bug rather than porting it.
4. **Unknown overrides are preserved** on save.

5. **The five legacy flags are shown now**, with the "Applies once this screen moves to the
   new UI" note, so deployments can set them ahead of the screens, rather than shipping an
   empty tab. The note: Reversed as built; see As Built. The flags are still shown.
6. **No whole-tab Reset To Defaults.** Each changed flag has its own Reset, which is how FM-170's
   "Reset to defaults" criterion is met for flags.

## As Built

- Each flag's draft is `{ value, overridden }`. Setting a value by hand marks it overridden when
  it differs from the inherited one; Reset clears it and moves focus to the flag's control.
- The tab is a `useAppForm` form: a `SwitchField` or `SelectField` per flag in `layout="row"`
  inside a `SettingsList`, with the info button and, for a changed value, Reset as the row's
  action, named "Reset <flag>" for screen readers.
- `src/features/system-settings/lib/flags.ts` holds `toFlagDraft`, `inheritedFlag`,
  `buildFlagOverrides` (keeps unknown keys, stores the overridden flags only) and
  `isFlagsChanged`.
- The registry in `src/lib/feature-flags.ts` gained `labelKey`, `descriptionKey`, `usedByKey`
  and, for enums, `optionKeys`, all typed as message keys.
- `docker/config.json.template` carries the five variables under `featureFlags`; the entrypoint
  exports each with an empty default and `envsubst` fills them, so an unset one means "no value".
- Each row shows the label, an info button and, for a value changed here, a small destructive
  Reset. The flag key sits under the label; what the flag does and which screens use it are
  behind the info button.
- The "Applies once this screen moves to the new UI" note and the registry's `inNewUi` are gone:
  the page does not tell an administrator which screens have moved.
- A search box ("Search By Name, Key Or Screen") replaces the intro sentence and filters the
  flags by name, key, description or screen; the route keeps it in the URL with `replace`
  navigation. A search that hides a changed flag keeps the change, and Save still stores it; no
  match shows "No Feature Flags Match" with Clear Filters, which also returns focus to the search
  box.
- Only a change stands out. No source badges: a value from the deployment adds "Set by the
  deployment" after the key, and a value changed here gets a primary bar on the row's start edge
  and a line saying what Reset goes back to ("Changed here · The default is Off" or "Changed
  here · The deployment sets On").
- There is no whole-tab Reset To Defaults on Feature Flags, and the loading state holds no header
  button for one: the per-flag Reset is how an override is removed, and how FM-170's "Reset to
  defaults" criterion is met here.
