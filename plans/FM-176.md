# FM-176: Feature Flags Managed in the UI

https://openlmis.atlassian.net/browse/FM-176 · Parent: FM-170 Global app configuration
(branding, theme & feature flags)

## Scope

This PR adds the **Feature Flags** tab to System Settings, the labels and descriptions for
every registered flag, and the deployment layer: `config.json` carries the legacy flag env
vars, so a deployment's `settings.env` keeps working. It builds on FM-172 (registry,
resolver, `getFlag`/`useFlag`) and FM-173 (page, rights, save pattern).

It does not migrate any flagged screen, does not touch backend flags (Togglz or
`CATCHMENT_POPULATION_CALC_AUTO`), and does not change the legacy UI, which keeps reading its
own container env during dual boot.

## Summary

Some OpenLMIS features are optional: batch approval of requisitions, barcode scanning in
stock management, the Packs and Doses switch, the requisition-less order menu entry. Today a
deployment turns them on by editing an environment file and restarting the UI.

In the new UI an administrator sees every optional feature on one tab, with what it does,
which screen uses it, whether it is on, and where that value comes from: changed here, set
by the deployment, or the default. They change it with a switch or a list, or reset it to
fall back to the deployment's value. Everyone gets the change on their next page load.

Existing deployments lose nothing: the same environment variables still set the starting
values. A setting changed here only reaches screens in the new UI; the old screens keep
their environment settings until they move over.

## Legacy Today

| Flag | Default | Used by | Behaviour |
|---|---|---|---|
| `BATCH_APPROVE_SCREEN` | false | Requisitions > Approve | Shows the checkbox column, Select All / None, and View Selected Requisitions. On test.openlmis.org it is on. |
| `GS1_SCANNING` | false | Physical inventory draft, stock adjustments (issue, receive, adjust) | Shows the GTIN scan input. |
| `QUANTITY_UNIT_OPTION` | `BOTH` | 8 stock and requisition screens | `PACKS` or `DOSES` hides the Packs/Doses toggle; `BOTH` shows it. |
| `DEFAULT_QUANTITY_UNIT` | `DOSES` | The same screens | The unit used until the user picks one (kept in localStorage `quantityUnit`). |
| `SHOW_REQUISITION_LESS_ORDER` | true | Orders > Create Order | Shows the menu entry; the route stays open with `ORDER_CREATE`. Build time only in legacy. |
| `CATCHMENT_POPULATION_CALC_AUTO` | false | Geographic zones | Also read by referencedata at startup; server-enforced. |

Legacy's `featureFlagService.set()` only accepts `'true'`/`'false'`, so the two enum flags
always read back as their defaults through it (source: `openlmis-ui-components/src/openlmis-feature-flag/feature-flag.service.js`;
the AngularJS toggle reads the env value directly as a workaround). The new registry types
enums properly. No legacy screen lets anyone change a flag.

### Registry (data in `src/lib/feature-flags.ts`)

`BATCH_APPROVE_SCREEN`, `GS1_SCANNING` and `SHOW_REQUISITION_LESS_ORDER` as booleans;
`QUANTITY_UNIT_OPTION` as an enum of `PACKS`, `DOSES`, `BOTH`; `DEFAULT_QUANTITY_UNIT` as an
enum of `PACKS`, `DOSES`. The defaults are legacy's. Each also names the screen it affects
(`usedByKey`) and whether that screen is in the new UI yet (`inNewUi`, false for all five
today).

### Deployment Layer

- `docker/config.json.template`: `"featureFlags": { "BATCH_APPROVE_SCREEN": "${BATCH_APPROVE_SCREEN}", ... }`
  for the five flags.
- `docker/entrypoint.sh`: export each with an empty default and add it to the `envsubst`
  list.
- `docker-compose.yml`: pass them through.
- Parsing (FM-172 resolver): an empty string means unset; `"true"`/`"false"` for booleans;
  an enum value outside its options is ignored.

### Rules

- The page sends every override it holds, including keys it does not know (a newer UI
  version's flags), so a save never deletes another version's settings.
- Changing a control makes an admin override even when it matches the deployment value;
  only Reset removes one.
- The source badge and the effective value are computed from the draft, so they move as
  the admin edits.
- The page never shows a flag outside the registry, and never shows backend flags.

### Translations

`system-settings.tabs.feature-flags`; `system-settings.flags.description`,
`.source.admin` "Changed Here", `.source.deployment` "From Deployment", `.source.default`
"Default", `.reset`, `.used-by`, `.not-in-new-ui` "Applies once this screen moves to the
new UI", `.saved-title`, `.saved-description`; per flag
`feature-flags.<key>.label`, `.description`, `.used-by`, and for enums
`feature-flags.<key>.option.<value>`. Keys are kebab-case versions of the flag names, e.g.
`feature-flags.batch-approve-screen.label`.

### Tests (written first)

- `feature-flags.test.ts`: source is `admin`, `deployment` or `default` in each case;
  registry keys and translation keys line up.
- `flag-overrides.test.ts`: reset drops a key; unknown keys survive; a changed control adds
  a key even when it equals the default.
- `runtime-config` parsing of empty, boolean and enum strings.
- Browser (review-pr), writes stubbed: every flag listed with the right control; source
  badges with a stubbed `config.json` value; change, save, reload; reset one; discard
  prompt; no right; Arabic; phone.

### Risks and Edge Cases

- Every registered flag is "not in the new UI" today, so changing one has no visible effect
  yet. The badge says so; see Open Questions.
- Dual boot: legacy keeps its container env, so the two UIs can disagree on a screen that
  exists in both. Once a screen migrates, the new UI's value is the one users see.
- An admin value for a flag later removed from the registry stays in the database, unused
  and preserved (Rules); harmless.

## UI/UX

- **Layout:** one card per flag in a single column: label, description, "Used by" line, the
  control at the end, the source badge and Reset under the label. The flag key in a muted
  monospace line, for operators matching it to their `settings.env`.
- **Controls:** a `SwitchField` for booleans, a `SelectField` for enums (AGENTS.md form
  rules).
- **Footer:** Cancel and Save, as on the other tabs; the discard guard covers tab switches.
- **Improve over legacy:** a flag is visible and changeable at all; its source is explained;
  enums actually work.
- **States:** the same page states as Branding.

## Decisions

1. **All flags are public** in the read, so the login page and boot need no second request;
   a flag is never a secret, by rule.
2. **Backend-enforced flags are not shown.** `CATCHMENT_POPULATION_CALC_AUTO` is read by
   referencedata at startup, so a UI switch would lie; the Togglz flags are backend
   behaviour. Both stay in the deployment's env, documented.
3. **Enums typed properly**, fixing legacy's enum bug rather than porting it.
4. **Unknown overrides are preserved** on save.

5. **The five legacy flags are shown now**, with the "Applies once this screen moves to the
   new UI" badge, so deployments can set them ahead of the screens, rather than shipping an
   empty tab.

## As Built

- The draft is plain component state, `Partial<Record<FeatureFlagKey, value>>`, not form fields:
  there is nothing to validate, since every control can only hold an allowed value. Each row is a
  `SettingsRowFrame` with the stock `Switch` or `Select`, named by its label.
- `src/features/system-settings/lib/flags.ts` holds `toFlagDraft` (only known flags of the right
  type), `buildFlagOverrides` (keeps unknown keys, drops reset ones) and `isFlagsChanged`.
- The registry in `src/lib/feature-flags.ts` gained `labelKey`, `descriptionKey`, `usedByKey`,
  `inNewUi` and, for enums, `optionKeys`; a test checks every key is in `en.json`.
- `docker/config.json.template` carries the five variables under `featureFlags`; the entrypoint
  exports each with an empty default and `envsubst` fills them, so an unset one means "no value".
