## Summary

Supply lines show which facility supplies a program at a point in the supervision chain.
Administrators can browse them, filter by supplying facility and program, inspect the
facilities served by a node, and open a supply line's details. Both legacy screens are
read-only.

The new UI keeps those screens, fields and return behavior. Filters apply as soon as they
change, and the address keeps the filters, page and sorting. The list loads less data:
served facilities wait until their popover opens, and the facility filter uses the shared
compact lookup. The details page presents the same four values as readable text and keeps
Cancel below them.

### Sort Contract

`RD/repository/custom/impl/SupplyLineRepositoryImpl.java:167-182` uses the sort property as
`sl.<property>` in JPQL; it neither ignores unknown sorts nor translates the obsolete javadoc
name `supplyingFacilityName`. Live requests verified 200 and changed order for
`supplyingFacility.name`, `supervisoryNode.code` and `program.name`. Expose those three

### Performance And Expansion Decision

Authenticated GETs on test.openlmis.org, five consecutive samples each, page 0 / size 10 /
legacy supplying-facility sort. Sizes describe uncompressed response bodies, not gzip or
bytes on the wire; timings include download from this machine and are not a browser render
benchmark. All these requests returned 200 and
`totalElements=1007`.

| Expansion | Bytes | Time Range | Suitability |
|---|---|---|---|
| Legacy: node/group/members, supplying facility, program | 193,896 | 294-360 ms | Correct, but eagerly repeats full member objects |
| Supplying facility and program only | 31,855 | 281-301 ms | Unusable: node has id/href, no code |
| Node, supplying facility and program | 39,795 | 283-349 ms | Chosen: all displayed values, about 79% fewer bytes |
| Node/group, supplying facility and program | 43,563 | 324-371 ms | No benefit for the displayed columns |

Important: shallow node/group expansions can contain `memberFacilities: []` even when the
group has 25 real members. Ignore that shallow field completely. Only the lazy request with
the full member expansion determines populated versus empty popover content.

The chosen lazy request was measured separately, five GETs per node:

| Node Case | Full Members | Bytes | Time Range |
|---|---|---|---|
| Code 17, populated | 25 | 52,262 | 139-184 ms |
| SN2, largest group | 337 | 410,887 | 341-374 ms |
| Code 211, empty group | 0 | 2,519 | 137-151 ms |
| CHAZ node, no group | 0 | 1,451 | 133-139 ms |

Request only the opened node, with no program or supplier filter: group membership belongs
to the node, so one result suffices even when it has several supply lines. Cache by node id
under `supplyLines`, share across rows/programs and reopenings, with ten-minute stale time.
Do not prefetch this query in the list loader or mount it enabled for every row. Empty/missing
group and an empty result yield the legacy empty message after a successful lazy read.
A failed request is a retryable failure, never an empty membership list.

Alternatives checked: `GET /supervisoryNodes/{id}?expand=...` ignores expansion and still
returns a group reference; `GET /requisitionGroups/{id}` works (25-member example 59,524 bytes,
149-163 ms), but the narrowed supply-line request is smaller and keeps legacy's endpoint.
No new shared lookup or cross-feature dependency is needed.

Raw evidence: `.screenshots/FM-134/results.json`, `results2.json`, `heavy.json`, `light.json`,
`detail.json`, and `lazy-results.json` with the runnable `lazy-measure.mjs`.
The legacy/chosen list rows and lazy timings use the final repeat in `lazy-results.json`;
the two rejected expansion alternatives use the earlier research samples. The final repeat
also confirms all three primary sorts in both directions with the id tie-breaker.
The backend always fetch-joins group members in its repository even without member expansion
(`SupplyLineRepositoryImpl.java:75-84`); the plan reduces transferred data and eager UI work,
not that database join. Browser speed will be measured after implementation.

### Data Flow

- Routes: `/administration/supply-lines` and `/administration/supply-lines/$id`. Use the
  trailing underscore detail route file so it does not mount the list and its lookups.
- List loader awaits only the right check, then calls `prefetchQuery` without awaiting the
  list. Toolbar and shell remain outside its `QueryBoundary`; rows read deferred search.
  Each filter uses non-suspending `useQuery` inside mounted Filters content, as other
  toolbars do, with an individual loading/error/retry state. Start these lookups when that
  content mounts. A lookup failure never hides the rows or the other filter. Sort facility
  options by name locally; the unchanged minimal lookup is unpaged and guarantees no order.
- Query options stay in `src/features/supply-lines/api/queries.ts`: list under
  `queryKeys.supplyLines.list(query)`, detail under `.detail(id)`, served facilities under
  `[...queryKeys.supplyLines.all, 'servedFacilities', nodeId]`. Separate shapes and keys.
- Search: `page`, `size`, `sort`, `dir`, `supplyingFacilityId`, `programId`. GUID filter
  validation drops malformed values; defaults stay out of the URL. Filter/clear/size/sort
  changes reset page 1. Filtering replaces history; paging/sorting add entries. Request
  page is zero-based, URL page one-based. Clamp linked pages past the end as Nodes does.
- Row View passes the complete validated list search in the detail URL and in history state
  `supplyLinesListSearch`. Detail validates the same schema. Set `staticData.crumbKey` to
  `supply-lines.view.title` and `crumbParentSearch` to parse that search for the list crumb.
  Cancel uses the captured originating history search, falling back to detail URL search for
  direct links. Every return link, including not-found/error returns, keeps the list search.
  Declare the `HistoryState` augmentation in the list route, as Nodes does. Keep history
  state because the brief requests that originating-return convention; URL search is the
  durable copy needed by breadcrumbs and shared links, as on Stock On Hand. Both are set
  from the same validated search in the opening link and never edited independently here.
- Detail loader checks the right first, validates the id, then returns `ensureQueryData` of
  `supplyLineOptions(id)`. It blocks because a missing record needs its own page; supply a
  matching `pendingComponent`. This is read-only: no whole-record save or fresh-on-entry
  machinery is needed. Detail uses no facility/program/node lookups.

### Risks And Edge Cases

- Never use shallow members for the popover. Missing node id leaves the node cell blank and
  makes no request; missing node code stays blank as other missing table values do.
- A node's one-row lazy response can be heavy (SN2 about 411 kB); it is intentional on demand,
  cached and scrollable. No list-wide preloading or duplicate per-program reads.
- Lists/groups may change between initial page and popover. Read the current node membership
  returned by the lazy call; successful no-result means no assigned facilities. Do not retain
  another node's content while the next node loads.
- One broken lookup must not block list rows. A valid filter id not in today's lookup still
  filters the server and can be cleared; do not silently choose a different option. Preserve
  a readable selected label where available from the current rows/picked option.
- Parent/read endpoints have no explicit admin-right enforcement in master. This PR gates
  access in the UI; it makes no backend authorization change.
- Identity changes use the app's protected-layout remount and query cache clearing. Do not
  add a separate identity cache or access localStorage for auth.

## Decisions

1. **Read-only parity:** list plus a page, no Add/Edit/Delete or extra confirmation.
2. **Node code everywhere legacy shows it**, including server sorting by that code.
3. **Only three verified sort fields**, default supplying facility ascending, with id as a
   deterministic tie-breaker. Unsupported sorts are rejected by the UI schema.
4. **Light list plus lazy full member expansion for one node.** It preserves every column
   and popover, reduces this ten-row response by about 79%, and uses the same endpoint.
   Shallow empty arrays are never trusted for membership.
5. **Existing minimal facilities and programs lookups**, isolated from row loading. No All
   option, warehouse-only narrowing, active-only restriction or new shared lookup.
6. **Filters apply live in the URL**, resetting page 1; legacy's extra Search/Cancel is
   removed in line with the brief and app conventions.
7. **Readable SettingsItem values on a narrow page**, retaining field order and Cancel.
   Required disabled controls convey no useful validation on a read-only screen.
8. **Detail URL carries complete list search**, with history state for the originating return
   and `crumbParentSearch` for the list breadcrumb, reloads and shared links.
9. **Both UI loaders check the right before fetching.** Master's read controllers do not
   check the admin right; do not claim they do.
10. **Parallel-work boundaries stay narrow.** Rebase before PR and preserve every other
    build's scopes, rights, nav entries and translations. No reference-data refactor.
