# FM-91: Manage Proof Of Delivery, with FM-92: Proof Of Delivery

https://openlmis.atlassian.net/browse/FM-91 · https://openlmis.atlassian.net/browse/FM-92 ·
Parent: FM-88 Fulfillment

## Scope

This PR adds two screens:

- **Manage Proof Of Delivery** (`/orders/proof-of-delivery`): finds the orders whose proof of
  delivery a facility can open.
- **Proof Of Delivery** (`/orders/proof-of-delivery/<podId>`): records what arrived and confirms it.

**Branching.** FM-90 (Shipment) and this PR change the same order files. To avoid conflicts, both
build on one shared groundwork commit on top of PR #133 (Steps). Neither PR is merged yet.

Out of scope: offline. Legacy keeps nothing offline here beyond its general caches.

## Summary

When a warehouse ships an order, OpenLMIS creates a proof of delivery for the receiving facility. The
facility checks the delivery and records, for each product and lot:

- how much it accepted
- what it returned, and why
- any notes

It also records who delivered it, who received it and the date. Confirming marks the order
Received and adds the accepted stock to the facility.

Legacy has two pages:

- a search page that lists orders by program and facility, where each order can open or print its
  proof of delivery
- the proof of delivery page itself

The new screens keep all of it, and also:

- make the order list sortable and predictable
- show statuses as words
- give emergency orders a labelled badge
- show the received date correctly (legacy showed one day early)
- print without unexpected saves
- edit only where the server allows
- never leave a field the user cannot correct
- work on a phone

### Manage Proof Of Delivery (`/#!/orders/manage`)

**Rights.** Any of `PODS_MANAGE`, `PODS_VIEW` or `SHIPMENTS_EDIT` opens the page, without facility
or program scope. A user without them sees "You are not authorized".

**Fields:**

| Field | Options | Shown | Auto-picked |
|---|---|---|---|
| Requesting Facility | facilities in the user's `PODS_MANAGE`/`PODS_VIEW` grants (any program), by name | only when there are options | when it is the sole option |
| Supplying Facility | facilities in `SHIPMENTS_EDIT`/`SHIPMENTS_VIEW` grants, by name | only when there are options | never |
| Program | the user's programs | always | when it is the sole option |

- **Clearable choices.** Every select can be cleared (select2 `allowClear`).
- **Search.** It needs Program plus Requesting **or** Supplying Facility. Otherwise each field shows
  "This field is required" with an alert "This form is invalid".
- **Auto-picks.** The loader applies a sole program and a sole requesting facility to its request,
  even when the URL has a supplier. It does not write them to the URL, so the first search runs
  with the title still plain.
- **Paging.** A new search keeps the current page.

**Title:**

- "Manage Proof of Delivery for {facility}: {program}" with a requesting facility in the URL.
- "Manage Proof of Delivery for {program}" with only a program.
- Otherwise "Manage Proof of Delivery".

**List:**

- **Request.** `GET /api/orders` with `programId`, `requestingFacilityId` and/or
  `supplyingFacilityId`, and `status` repeated: TRANSFER_FAILED, READY_TO_PACK, RECEIVED, SHIPPED,
  IN_ROUTE.
- **Paging and order.** Server paging (10 per page), with no sort, so the order is undefined.
- **Columns:**
  - Order no.
  - Order status (raw enum)
  - Requesting Facility
  - Supplying depot
  - Program
  - Period
  - Order date (date only)
  - Emergency (check or blank)
  - Actions: Manage and Print on every row
- **Empty state.** "No proofs of delivery found." also shows before any search.

**Actions:**

- **Manage.** `GET /api/proofsOfDelivery?orderId`, takes `content[0]`, then opens `/#!/pod/<id>`.
- **Print.** Opens a tab, does the same lookup, then
  `/api/proofsOfDelivery/<id>/print?format=pdf&lang=<locale>`.
- **No POD.** No POD, or a failed lookup, gives "No order found".
- **When a POD exists.** Only once a shipment exists, whether confirmed in the UI or imported.
  - On test all 13 listed orders have one, including 8 In Route and 1 Ready To Pack.
  - Transfer Failed orders, unimported external shipments and the rights gap under Agent Brief have
    none.

### Proof Of Delivery (`/#!/pod/<id>`)

**Loading:**

1. `GET /api/proofsOfDelivery/{id}?expand=shipment.order`.
2. Products (latest versions) and lots by id.
3. `GET /api/orderableFulfills?id=…`.
4. `GET /api/validReasons?program&facilityType=<order.facility.type>&reasonType=DEBIT`. Hidden
   reasons are dropped; there is no category filter.

On test the DEBIT reasons are Transfer Out, Damage, Expired, Stolen, Lost, Passed open-vial time
limit and Cold chain failure.

**Breadcrumb:** Home / Orders / Manage Proof of Delivery / View Proof of Delivery.

**Header:**

- **Title.** "Proof of Delivery for {program}".
- **Fields:**
  - Order No.
  - Order Status (raw)
  - Ordering Facility (code - name)
  - Order Date (date and time)
  - Reporting Period (start - end)
  - Supplying Facility
- **Print.**
- **Emergency band.** Coloured by the order's emergency flag, but its text is blank (it calls an
  undefined function).

**Grid.** There is no paging; every line renders.

- **Rows.** Order lines sorted by product name, each followed by its fulfilling products, then
  their lots.
- **Repetition.** A product that fulfils itself shows twice.
- **Columns:**
  - Product Name, Product Unit, Quantity Ordered
  - Quantity Shipped
  - Lot Code ("No Lot Defined")
  - Quantity Accepted
  - VVM Status: only when a line uses VVM; Stage 1 or Stage 2; raw enum when read-only
  - Quantity Returned, Rejection Reason, Notes
- **Hidden lines.** POD lines matching no order line are not shown, but they are still sent and
  validated, so a blank one makes Confirm fail.

**Rules.** Messages show inline as the user leaves each line.

- **Returned.** Shipped − accepted, clamped to 0..shipped; 0 while accepted is blank.
- **Accepted:**
  - Required.
  - No more than shipped: "You can't accept more stock than was shipped".
  - The input strips non-digits.
- **Reason:**
  - Required when returned > 0.
  - Given while returned is 0: "You can't specify reason for rejections if not rejecting anything".
  - Never cleared automatically.
- **VVM:** required when accepted > 0 on a VVM line, and not allowed when accepted is 0.
- **Footer fields.** Delivered By, Received By and Received Date are required to confirm. The date
  picker has no limits and sends `yyyy-MM-dd`.

**Edit.**

- `PODS_MANAGE` at the **requesting** facility and program, while the POD is INITIATED. The server
  checks the **receiving** facility.
- Read-only users see text and Print only.

**Save.**

- `PUT /api/proofsOfDelivery/{id}`: the whole object, status INITIATED, no validation.
- Toasts: "Proof of Delivery has been saved" or "Failed to save Proof of Delivery".

**Confirm:**

1. The form must be valid, otherwise the "This form is invalid" alert shows.
2. Prompt: "Are you sure you want to confirm this Proof of Delivery?"
3. Domain validation runs; a failure there shows only the "Failed to confirm Proof of Delivery"
   toast.
4. The same PUT is sent with status CONFIRMED.
5. On success: "Proof of Delivery has been confirmed", then back to the list.

**Print.**

- An INITIATED POD is **saved first**, even for read-only viewers.
- A failed save closes the tab and shows the save failure.
- Then `/api/proofsOfDelivery/{id}/print?format=pdf&lang=…` opens.

**Problems seen:**

- **Date.** A received date of 2026-11-10 showed as 09/11/2026; the PDF shows 10/11/2026.
- **Phone.** A squeezed table, with the sticky footer covering rows.
- **Wording.** "No order found" shows when the POD is missing.

**Timing:**

- **Orders list:** 343-649 ms.
- **Open, in stages:**
  - lookup: 273-664 ms
  - POD: 496-766 ms
  - products and fulfils: about 160 ms each
- **Actions:**
  - Save: 386 ms
  - Confirm: 793 ms
  - PDF: 489-646 ms

## Agent Brief

### API map

| Step | Method and path | Params / body | Fields used | Right (server) |
|---|---|---|---|---|
| Programs | `userProgramsOptions` | user id | `id, name` | none |
| Facility names | `viewSupplierFacilitiesOptions`, generalised to take ids (≤ 100 by id, else minimal facilities) | ids from grants | `id, code, name` | none |
| List | `searchOrders` with a `pod` kind | `programId`, `requestingFacilityId`, `supplyingFacilityId`, `status` × 5, `page`, `size`, `sort` (+ `createdDate,desc`, `id,asc` tiebreakers) | order list fields + `requestingFacility.name`, `supplyingFacility.name` | rows limited to supplier grants (`ORDERS_*`, `SHIPMENTS_*`) or requester grants (`PODS_*`, any program) |
| Find POD | `GET /api/proofsOfDelivery` | `orderId` (one UUID; repeats ignored) | `content[0].{id, lineItems[].{orderable.{id, versionNumber}, lot.id}}` | filtered: `PODS_*` at the receiving facility within those grants' programs, or `SHIPMENTS_EDIT` at the supplier |
| POD | `GET /api/proofsOfDelivery/{id}` | `expand=shipment.order` | `id, status, receivedBy, deliveredBy, receivedDate, lineItems[].{id, orderable.{id, versionNumber}, lot, quantityAccepted, quantityRejected, rejectionReasonId, vvmStatus, useVvm, notes}`; `shipment.{id, lineItems[].{orderable.id, lot, quantityShipped}}`; `shipment.order.{orderCode, status, emergency, createdDate, facility.{code, name, type.id}, receivingFacility.id, supplyingFacility.name, program.{id, name}, processingPeriod.{startDate, endDate}, orderLineItems[].{orderable (full: name, dispensable.displayUnit, meta.versionNumber), orderedQuantity}}` | `PODS_MANAGE`/`PODS_VIEW` at receiving facility + program, or `SHIPMENTS_EDIT` at supplier |
| Products | `orderablesByIdentitiesOptions` | POD line ids + versions | `fullProductName, dispensable.displayUnit` | none |
| Lots | `lotsByIdsOptions` | lot ids | `lotCode, expirationDate` | none |
| Fulfils | `orderableFulfillsOptions` | ordered product ids | `canFulfillForMe` | none |
| Reasons | `validReasonsOptions({ program, facilityType })`, then keep `!hidden && reason.reasonType === 'DEBIT'` | | `reason.{id, name}` | none |
| Save / Confirm | `PUT /api/proofsOfDelivery/{id}` | `{shipment:{id}, status, receivedBy, deliveredBy, receivedDate, lineItems:[{id, quantityAccepted, quantityRejected, vvmStatus, rejectionReasonId, notes}]}` | status and saved fields | `PODS_MANAGE` at receiving facility + program |
| Print | `GET /api/proofsOfDelivery/{id}/print` | `lang` | PDF blob (`fetchReport`) | as POD read |

**Server facts:**

- **Request body:**
  - `shipment` is required; without it the server answers 500.
  - `lineItems` must not be empty (`lineItems.required`).
  - Ignored: the top-level `id` and each line's orderable, lot and `useVvm`.
  - `status` matters only when it equals CONFIRMED.
- **How lines and fields are saved:**
  - Lines match by `id`; lines left out keep their values.
  - `receivedBy`, `deliveredBy` and `receivedDate` are always overwritten, so always send all three.
  - There is no version check; the last write wins.
- **Save response.** The PUT response is **not expanded**: `shipment` is `{id, href}`. Never put the
  raw response into the expanded POD cache.
- **Confirm checks:**
  - `deliveredBy`, `receivedBy` and `receivedDate` present (`fulfillment.validationError.mustContainValue`)
  - accepted and rejected at least 0 (`mustBeGreaterThanOrEqualToZero`)
  - accepted + rejected = shipped (`fulfillment.error.proofOfDelivery.incorrectSumOfAcceptedAndRejected`)
  - a reason when rejected > 0 (`…reason.missing`)
  - a VVM status when accepted > 0 on VVM lines (`…vvmStatus.incorrectValue`)
  - already confirmed is refused (`…alreadyConfirmed`)
- **Confirm side effects:**
  - The order becomes RECEIVED.
  - A receive stock event (accepted × net content) is posted at the receiving facility, dated
    `receivedDate`. Stock management rejects a future date
    (`stockmanagement.error.event.occurredDate.in.future`, 400). It compares with the server's own
    date, so a deployment ahead of the server's time zone can see "today" refused near midnight.
  - A missing valid source fails with `fulfillment.error.stockEvent.missingSourceDestination`.
  - Everything rolls back on failure.
- **Print.** `lang` defaults to `en`; fulfillment ships English messages only.
- **Rights gap.** The list counts `SHIPMENTS_VIEW` at the supplier and `PODS_*` at the requesting
  facility in any program. The POD lookup needs `SHIPMENTS_EDIT` at the supplier, or `PODS_*` at
  the receiving facility in those grants' programs. Some listed orders therefore cannot open their
  POD, as in legacy.

### Data flow

**List route** (`_protected.orders.proof-of-delivery.tsx`):

- **Search params:** `programId`, `requestingFacilityId`, `supplyingFacilityId` (UUIDs) plus
  `tableSearchSchema()`. Header sort on Order No., Emergency and Order Date, as View Orders.
- **Loader:**
  - Await `requirePermissions([PODS_MANAGE, PODS_VIEW, SHIPMENTS_EDIT])`.
  - Read user programs (cached from sign-in).
  - When the URL lacks them, redirect with `replace` to add a sole program and a sole requesting
    facility, as legacy applies them (Decision 2).
  - Refuse a program the user lacks, or facility ids outside the grants. Show the refused state and
    send no request.
  - Otherwise prefetch the list, facility names and the deployment time zone without awaiting them.
- **Picker:**
  - A draft until Search. Search pushes history and returns to page 1.
  - Results hide while the draft differs from the applied search, as View Orders.
  - Fields use virtualized `ComboboxField`s, clearable.
- **Rows:** Manage (main) and Print in the row "..." menu; `CardActions` on phones.

**Opening a POD from the list:**

- Manage runs `useSessionMutation`: `GET /proofsOfDelivery?orderId`.
- It then prefetches, from that response and the row, before navigating:
  - products and lots, from the POD lines' ids, versions and lot ids
  - reasons, from the row's program and `facility.type.id`
- It navigates with return state (`orderReturnState`) carrying the list search.
- No POD shows "No Proof Of Delivery Found".

**POD route** (`_protected.orders.proof-of-delivery_.$podId.tsx`):

- **Loader:**
  - Starts the rights check and the POD read together.
  - Reads the POD fresh on `cause: 'enter'` (`fetchQuery` with `staleTime: 0`); tab-less stays reuse
    it.
  - Then prefetches fulfils, products, lots, reasons and the deployment time zone.
  - Sets `preload: false`, since the page saves the whole record.
- **Breadcrumb.** `staticData.crumbKey` "View Proof Of Delivery", under Manage Proof Of Delivery.
  The list search in return state, if any, feeds Cancel and the return after Confirm.
- **Form.** One `useAppForm` with per-line fields (`lines.<id>.accepted`, `.reason`, `.vvm`,
  `.notes`) and the footer fields. This is the Create Orders editor and Physical Inventory pattern:
  rows subscribe with `useStore` selectors.
  - Validation is live from the first change, as legacy and the requisition editors. An invalid
    Confirm opens the invalid-submit dialog and reveals the first field.
- **`useDiscardGuard`.** For unsaved changes.
- **After Save.** Merge the response's status, line values and footer fields into the cached POD,
  keeping the expanded `shipment`. Reset the form baseline from the **submitted snapshot**, as the
  Create Orders editor's `mergeSavedLines` does, so edits typed while Save was running stay dirty.
- **After a successful Confirm,** skip `useDiscardGuard` before returning.
- **After Confirm:**
  - Invalidate the POD, `orders.list`, `home`, and the stock summaries (`stockCardSummaries.all`)
    for the receiving facility.
  - Request a refresh of downloaded offline stock for the receiving facility and program.
  - Return to the list in return state, defaulting to Manage Proof Of Delivery.

### Rules

**Grid lines** (`pod-lines.ts`):

- **Grouping and sort:**
  - Group by order line through `canFulfillForMe`, then by fulfilling product, then by lot, as
    legacy.
  - The fulfilling-product row collapses when it is the ordered product itself (Decision 4).
  - Sort by product name.
- **Lines legacy hid:** POD lines under no order line form an "Other Products" group, so the user
  can see and correct everything Confirm validates (Decision 5).
- **Lines with no shipment line** (no `quantityShipped`):
  - Show shipped blank, read-only, outside validation, with a notice: "This line has no shipped
    quantity and must be corrected by an administrator."
  - Save sends them unchanged.
  - Confirm is blocked while a blank one exists. The server skips their quantity checks, but its
    stock event still multiplies a blank accepted quantity and fails.
  - A line that already holds numbers is sent as it is.

**Validation** (`pod-validation.ts`):

- Returned is as legacy.
- Accepted is a whole number, required, and no more than shipped.
- Reason is required when returned > 0 and not allowed when returned = 0.
- VVM is required when accepted > 0 on a VVM line and not allowed when accepted = 0.
- Confirm also requires the three footer fields.
- Received Date may not be later than today in the deployment time zone (Decision 7).
- Save does not check **completeness**, as legacy: blank accepted is sent as `null`, and the footer
  fields may be empty. Save always sends all three footer fields.
- Save does check **format**: malformed or out-of-range numbers (above Java `int`) block Save, and
  Print's save step, with the field highlighted. Legacy stripped such characters silently
  (Decision 11).
- Messages are legacy's.

**Clearing (Decision 6):**

- Reason and VVM selects carry an empty choice ("Select Reason", "Select Status") so the user can
  clear them.
- Automatic clearing happens only on a **valid number**: when accepted becomes a whole number that
  makes returned 0, the reason clears; when accepted becomes 0, VVM clears. A blank accepted value
  (for example, while retyping) clears nothing.
- Both dependent fields revalidate after every accepted change.

**Who may edit:**

- `PODS_MANAGE` at the receiving facility and program, while the POD is INITIATED (Decision 8).
- The route passes `canEdit` as a plain flag.

**Print:**

- **Editable with unsaved changes:** save first, through `usePrintReport`'s `beforeRequest`;
  `openReport` opens the tab in the click.
- **Otherwise:** print directly.
- **Save fails:** the tab closes and the save error shows.
- **From the list:** look up the POD, then print. No POD shows "No Proof Of Delivery Found".

**Dates:**

- List Order Date: date only (`toDateValue` with the deployment time zone).
- Header Order Date: `formatTimestamp`.
- Received Date: `formatDateValue`.

**Statuses** use the order status labels from #133. The POD status shows as a badge: Initiated or
Confirmed.

### Risks

- **Unopenable rows.** Rows whose POD the user cannot open (the rights gap) show "No Proof Of

## Decisions

1. **Search needs Program plus Requesting or Supplying Facility, as legacy.** The ticket's
   "Requesting required" would lock out warehouse users.
2. **Sole program and sole requesting facility are written into the URL** on first visit, with
   `replace`. Legacy applied them silently, leaving a bare URL and a plain title.
3. **The list is sortable like View Orders, newest first.** Legacy had no order.
4. **A product that fulfils itself shows once**, instead of twice.
5. **POD lines under no order line are shown** in an Other Products group. Legacy hid them, yet
   still validated them on Confirm.
6. **Reason and VVM can be cleared, and are cleared automatically when they become invalid.**
   Legacy could clear them by hand, but left a stale reason in an error the user had to find.
7. **Received Date cannot be after today.** The server refuses future dates on Confirm, through
   the stock event.
8. **Editing follows the server: `PODS_MANAGE` at the receiving facility.** Legacy checked the
   requesting facility.
9. **Print does not save for read-only users or unchanged PODs.**
10. **Exact product versions** name the lines, instead of legacy's latest version.
11. **Malformed numbers block Save** instead of being silently stripped (`1.5` became `15`). Blank
    values still save, as legacy.
