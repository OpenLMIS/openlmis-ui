## Scope

The product edit page at `/administration/products/$id`, with four tab routes, plus the two
things [FM-140](FM-140.md) handed over: the Edit action on each Products row, and opening the
new product's edit page after Add Product saves. It is item 6 to 9 of the admin round in
[FM-62](FM-62.md).

One PR, [#40](https://github.com/OpenLMIS/openlmis-ui/pull/40), built one subtask at a time, in order, and merged only once
all four are built and tested:

1. **FM-150 General**: the page, its tabs (each later tab added with its subtask), the General
   form, the Edit row action, and opening a new product after Add.
2. **FM-151 Programs**: the program links table and its add/edit dialog.
3. **FM-152 Facility Types**: the facility type approved products table and its dialog.
4. **FM-153 Kit Unpack List**: the kit contents draft and its product picker.

Out of scope: product versions history, identifiers, trade items, temperatures and
dimensions (no legacy screen edits them, but every save must send them back unchanged), and
a version check on save (the server has none; see Decisions).

## Summary

Administrators open a product from the Products list to change it. In the old UI the edit
screen has four tabs: General (code, name, pack size), Programs (which programs offer the
product, with its category, price and doses), Facility Types (which facility types may stock
it in which program, with stock periods) and Kit Unpack List (for a kit, the products it
unpacks into). It works, but:

- Numbers are silently rewritten: "1.5" becomes 15 and "-5" becomes 5.
- A failed save says only "Failed to ...", never why.
- Leaving a tab with unsaved changes loses them without a word.
- The page opens for users who may not use it, and shows Save buttons that then fail.
- The program window reads "Full Suply", and a retried failed program add can add it twice.
- A kit can be set to contain itself.
- On a phone the tables run off the screen.

The new page keeps the same tabs, fields, rules and saves, and fixes those: numbers are
checked and explained, the server's reason shows on a failed save, unsaved changes ask
before they are lost, each tab shows only what the user's rights allow, the product is read
fresh every time the page opens, and it works on a phone and in Arabic. The Products list
gets an Edit action, and a new product opens straight in this page after it is added.

## Legacy Today

Screenshots: `.screenshots/FM-141/legacy-*` (all tabs and dialogs, desktop and phone).

- **Routes**: `#!/administration/orderables/<id>/general`, `/programs`,
  `/facilityTypeApprovedProducts`, `/kitUnpackList`; the list's search rides along. Breadcrumb
  Home / Administration / Products / Edit Product. Title "Edit <name>".
- **Where the product comes from**: the copy in the list page already loaded, or
  `GET /orderables/{id}` when it is not there. No fresh read; the last save wins.
- **Rights** (route config): the page opens with either right. Programs actions need
  `ORDERABLES_MANAGE`, Facility Types actions `FACILITY_APPROVED_ORDERABLES_MANAGE`. General
  and Kit declare none, so they show Save to anyone and the server answers 403. A user with
  neither right can still open General, Facility Types and Kit by URL (a legacy hole).
- **General**: the Add Product form, Save Product and Cancel at the bottom. Save sends the
  whole product and returns to the list. Toast "The product has been updated successfully".
- **Programs**: "Associated Programs", Program Name and Edit/Remove. Add and Edit open
  "Adding Program" / "Editing <program> Program" with Program (add only, unlinked programs
  only), Full Suply, Doses per Patient, Orderable Display Category (required), Display Order,
  Price per Pack. Every action saves at once by sending the whole product. Remove asks "Are
  you sure you want to remove the program orderable?" and takes the link out. No Cancel.
- **Facility Types**: "Associated Facility Types", one header row per facility type then one
  row per program. Dialog: Facility Type and Program (locked on edit; Program only from the
  product's programs), Max Periods of Stock (required), Emergency Order Point, Min Periods of
  Stock, all decimals. Add first looks for an inactive record of the pair and reactivates it,
  otherwise creates one. Remove sets it inactive. No client check for an already-active pair.
- **Kit Unpack List**: Product Code, Name, Quantity (required whole number, 0 allowed),
  Remove; client paging of 10. "Add Products" opens a server-paged product table with a
  Filter popover (name, code), checkboxes kept across pages, and Unit of Issue. Edits stay on
  the page until "Save Kit Unpack List", which sends the whole product. The demo data has no
  kits (all 10,233 products checked).
- **Problems**: numbers rewritten not rejected; decimals sent as strings; server messages
  never shown; no unsaved-changes warning; the rights holes above; "Full Suply"; a retried
  failed program add pushes the program twice; a kit may contain itself; on a phone tables
  overflow and the toolbar covers rows.

`PUT /orderables/{id}` builds a new version from the body alone: anything left out is lost
(identifiers with the trade item, extra data, price history, children, temperatures). So
every save starts from the record as read, never from form fields alone. The server has no
version check; the last save wins, as in legacy.

### Data Flow

- Layout route `products_.$id`: loader awaits `requireRight` (either right) and the product, a
  must-404 record. On `cause: 'enter'` it reads the product with `fetchQuery` and `staleTime: 0`,
  so every opening reads it fresh; a tab switch (`stay`) takes the cached copy. The route sets
  `preload: false`, since a preloaded match opens on the cache before the fresh read ends. It
  returns the flags `canEditProduct` (`ORDERABLES_MANAGE`) and, from FM-152, `canEditApprovals`
  (`FACILITY_APPROVED_ORDERABLES_MANAGE`).
- Each save reads the product again, applies only its own change to that latest version
  (`saveProductChange`), sets the result into the detail cache and invalidates `orderables` lists,
  so a tab left open never sends back an old copy.
- Tab lookups (display categories, programs, facility types, FTAPs) are deferred prefetches in
  the tab routes, read under a `QueryBoundary`.
- URL: tab path, `?program=new|<programId>` (Programs dialog), `?approval=new|<id>` (FTAP dialog),
  `?remove=<id>` for the remove confirms. The list search travels in history state
  (`productsListSearch`), as `usersListSearch` does.

### Rules

- General: as Add Product ([FM-140](FM-140.md)), Product Code editable as legacy.
- Programs: Program required on add, from programs not yet linked; Orderable Display Category
  required; Doses per Patient and Display Order optional whole numbers up to 2147483647;
  Price per Pack optional, not negative, at most two decimals (the server parses it as money
  in the deployment's currency); Full Supply off by default. Add sets `active: true`.
- Facility Types: Facility Type and Program required, locked on edit; Program from the
  product's programs; Max Periods of Stock required, the other two optional; all decimals,
  not negative. An already-active facility type and program pair is refused before saving.
- Kit: Quantity required whole number from 0 (legacy) to 2147483647; one row per product;
  the kit itself is not offered.

### Tests

`*-form.test.ts` (schemas and body mapping, in particular that every field of the loaded
record survives a save), `api.test.ts` per call, the FTAP add choosing POST or reactivation,

with writes stubbed: each tab and dialog against the legacy screenshots, reload per tab,
Cancel and Save back to the filtered list, discard prompts, Arabic and phone.

### Risks and Edge Cases

- A save that drops a field loses it on the server: the body mapping tests compare a full
  record before and after.
- Two admins editing the same product: the last save wins, as in legacy.
- No kits in the demo data: the kit tab is tested with stubbed products.
- Price precision: more decimals than the currency allows fail on the server; capped at two.

## UI/UX

- **Port**: the four tabs and their order, every field, label and help text, immediate saves
  on Programs and Facility Types, the page-level save on Kit, FTAP reactivation, the grouped
  Facility Types table, Remove as deactivation for FTAPs.
- **Improve**:
  - Read the product fresh on every opening, so a save never overwrites newer data with an
    old copy.
  - Numbers explained, not rewritten; decimals sent as numbers.
  - The server's reason in the form or dialog on a failed save; duplicates on their field.
  - Unsaved changes ask before they are lost, also on tab switch (General and Kit drafts).
  - Each tab shows its actions only with its right; General and Kit read-only without
    `ORDERABLES_MANAGE` instead of a Save that fails; no page at all without either right.
  - "Full Supply" spelled right; a failed program add never duplicates the program.
  - Programs table adds Category, Full Supply and Price per Pack columns (hideable), so the
    links can be checked without opening each one.
  - An already-active facility type and program pair is flagged before saving.
  - Kit picker: a multi-select box that searches the server by code or name as you type
    (FM-184's `q`), picked products shown as chips, the kit itself left out; then their
    quantities are edited in the table. This follows the app's rule for picking several of a
    list (a `MultiComboboxField`, not a column of checkboxes) and replaces legacy's paged
    table with checkboxes.
  - Row actions in "..." menus; works on a phone and in Arabic.
- **Drop**: the "This form is invalid" alert (errors show on the fields); the client paging of
  the kit table (a kit has a handful of rows); the picker's Unit of Issue column, shown in each
  option's label instead, e.g. "C101 - Abortiva (10 tab strip)".
- **States**: page skeleton, product not found, load error with Try Again; per tab the table
  skeleton, empty state (legacy wording), error with Try Again; dialogs loading, not found,
  load error; saving keeps the dialog or footer pending.

## Epic Review (FM-139)

A review of the whole epic (Products, Programs and this page together) changed, in this PR:
decimals take a comma as well as a dot, as Portuguese writes them; the product tabs' tables use the
same headers and the same red Inactive badge as the other lists; focus stays on the list after a
removal; Name and Description follow their text's direction; a nameless facility type shows its
code; the Category column reads names from the lookup; the edit page's loading screen no longer
pulls the tabs' code into the first download; tab load errors no longer blame the connection.

## Decisions

- **One PR for the whole edit**, a subtask at a time: a page with only some of its tabs never
  reaches master (user, 2026-10-02).
- **The last save wins, as legacy**: no version check and no backend ticket for one for now
  (user, 2026-10-01).
- **Either right opens the page, as legacy**, with each tab's actions behind its own right;
  the legacy holes (no right at all, Save buttons that 403) are closed.
- **Every save starts from the record as read**, so nothing the page does not show is lost.
- **Fresh read per opening**, the AGENTS.md rule for records saved whole.
- **After Add Product, the new product opens on General**, as decided on FM-140.
- **Kit quantity allows 0, as legacy**; the kit itself is left out of the picker, since a kit
  that unpacks into itself has no meaning.
