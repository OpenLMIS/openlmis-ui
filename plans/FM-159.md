## Summary

Ideal stock amounts are the target quantities for a facility, commodity type and period.
Some requisition templates use them to calculate replenishment. Administrators download
the current values, edit the spreadsheet, then upload the CSV. The export is also the
starting template; legacy has no separate template download or table of records.

The new page keeps that workflow and the exact instructions in a collapsed disclosure below
the action card. Its two sections lead with export and upload, following the approved
design A. It prevents an upload without a file, accepts uppercase CSV extensions, keeps
the chosen file after a failure and shows readable errors. A successful upload reports
the number of records processed. Equipment catalog and Data Import can reuse its transfer
layout and file field later.

client's general 60-second timeout. Leave the general client and Export timeout unchanged.

Success is 200. Validation errors are 400 `{messageKey, message}`; missing upload rights
give 403. Wrong upload `format` gives 404, while wrong export `format` gives 400 with a

nonnegative integer. Malformed 2xx bodies use the uncertain-outcome error and retain the file.

### CSV Contract And Rules

| Header | Value | Required |
|---|---|---|
| `Facility Code` | Existing facility code | Yes |
| `Commodity Type` | `classificationSystem\|classificationId` | Yes |
| `Period` | `scheduleCode\|periodName` | Yes |
| `Ideal Stock Amount` | Integer from 0 through 2,147,483,647; empty means null | No |

Headers match case-insensitively. Empty/unknown headers and missing mandatory columns
are rejected. A missing amount column or blank amount cell sets the amount to null,
including on existing records; it does not mean keep the old value. An otherwise valid
header-only file succeeds with `amount: 0`, and that is a successful upload.

Rows update matching facility/commodity/period records and insert new ones. The controller
transaction covers every 200-row chunk: any runtime validation failure rolls back the
whole upload. The UI sends the original CSV; it does not parse, rewrite or split its rows.
The server owns header, row, number and reference validation. Error text contains row/
column information where the server provides it; reference-not-found errors can omit it.
Preserve that text without inventing additional locations.

`dto/IdealStockAmountCsvModel.java:39`;
`validate/CsvHeaderValidator.java:36`; `web/csv/parser/CsvBeanReader.java:76`;

own `message`. Use the translated empty-file message in that case.

### Errors, Translations And Toasts

a localized 4xx response whose body also has a string `messageKey`.

If a message only echoes its key, is blank, or has an unexpected shape, use a translated
generic failure. Treat Spring fallback bodies, HTML and 5xx responses as generic failures;
never display their technical `message`. An HTTP 413 gets a translated file-too-large
message without claiming a deployment-specific limit. Never show a raw server key,
stringify an object, or assume a response exists. Show network/offline failure in the same
on-page alert, with export/check guidance before the user chooses to retry.

### Risks And Edge Cases

- Exports are unpaged and materialized by the server. The measured file is about 290 KiB;
  do not fetch it on navigation or parse it into an unnecessary client table.
- Real bulk upload duration is unknown. Use the per-upload five-minute timeout above,
  retaining a finite wait while allowing bulk processing longer than the general limit.
  A timeout, dropped connection or proxy/server failure can leave the outcome uncertain;
  do not automatically retry POST or claim that nothing was saved. Keep the file and
  explain how to export/check before retrying. Existing same-user 401 replay stays as is.
- Reference-data uses Spring Boot 2.2.2 (`build.gradle:8`) and declares no multipart size
  override in its resources. That version defaults to 1 MB per file and 10 MB per request
  ([Spring Boot Multipart Documentation](https://docs.spring.io/spring-boot/docs/2.2.2.RELEASE/reference/htmlsingle/#howto-multipart-file-upload-configuration)).
  Environment/proxy overrides are possible; the effective limit on test is unverified.
  Do not impose that default as a client limit or promise that every larger export can
  round-trip unchanged. Handle rejection without leaking framework messages.
- A BOM in an Excel UTF-8 CSV may fail header validation. This is source-based risk, not a
  live-tested result. Preserve and display the server error; do not silently rewrite CSV.
- Repeated new keys within one backend chunk can produce duplicate records because the
  backend lacks a uniqueness constraint. Do not promise deduplication or add a CSV parser
  under this ticket. The unchanged-export check must use a fresh export and retain bytes.
- Blank amounts deliberately overwrite with null. Keep the exact instructions, and surface
  server outcomes without adding unsupported client numeric rules.
- Authentication still protects Export, but the backend does not enforce this management
  right there. This page and its entry remain gated as legacy; no backend change is proposed.

## Decisions

- Build the reusable panel and FileField here because Equipment catalog is not migrated.
  Keep the generic parts small and presentation-only; APIs stay in the ISA feature.
- Match legacy's full English instruction string exactly, including its imperfect third
  step. The user-approved design A moves it into a collapsed disclosure below the action
  card, while concise section headings and editing hints lead the normal workflow.
- Normalize only the multipart extension, accept CSV regardless of MIME, and preserve
  client zero-size validation plus a server raw-key fallback.
- Use the server's fixed export filename with the existing blob helper; avoid a shared
  download-helper refactor that would affect unrelated screens.
- No query invalidation or page reload: nothing in the app reads ISAs today.
- No backend changes, list editor, template endpoint or CSV row parser.
- Keep route/menu gating even though GET itself checks no management right.
- Upload retries are always manual, including after reconnection or a timeout; show an
  uncertain-outcome message when the server result could not be confirmed.
- Use a five-minute timeout only on the bulk POST. Handle deployment upload-size limits
  through readable errors, without changing the backend or assuming test's configuration.
- Real uploads require separate approval for the two concrete test files. Stub by default.
