# FM-184: Products: Search By Code Or Name In One Parameter

https://openlmis.atlassian.net/browse/FM-184 · Parent: FM-177 Potential BE Improvements ·
Folds in [FM-179](https://openlmis.atlassian.net/browse/FM-179) (list filters pasted into SQL
unescaped) · Unblocks FM-140 (PR #33)

## Scope

Two PRs:

1. **openlmis-referencedata, base `migration`**: a `q` parameter on `GET /api/orderables`
   that matches code or name; FM-179: every filter of the orderables search bound as a
   parameter, `%` and `_` matched literally, and no SQL text in error responses; and the
   problems below, found while planning and handled here as the user decided, recorded on
   FM-184 in Jira:
   - **Slow program-filtered search.** The latest-version check (`concat(id, version) IN
     (...)`) takes about 0.8 s for `code=0363&program=PRG002` locally; "no newer version
     exists" (`NOT EXISTS`, a correlated criteria subquery) takes about 20 ms.
   - **Program totals counted twice** for a product with an inactive and an active link to
     the program (Essential Meds: 10,006 on page 1, 10,005 on the last page).
   - **`POST /api/orderables/search` without `identities`** likely fails building its
     Last-Modified query (`exactCodes` added as one value). Reproduced by a test first.
   - **Last-Modified ignores `tradeItemId`.**
2. **openlmis-ui, PR #33** (FM-140, still open and waiting on this): the Products list swaps
   Search By Code and Search By Name for one Search By Code Or Name box sending `q`.

Proof against regressions: the endpoint's answers (ids, order, totals, Last-Modified, status)
for a fixed set of requests are recorded on the local stack before the change and compared
after it; every difference must be one listed here.

`POST /api/orderables/search` does not get `q`: nothing in the new UI calls it, and its
callers (requisition, fulfillment, legacy caches) only send identities.

## Summary

The products list searches by code and by name separately, and the server only returns
products that match both. So one search box cannot work today: typing "0363" in a box that
sends both finds nothing, because no product has "0363" in its name.

This change lets the server look for a text in either the code or the name, in one request,
still paged, counted and sorted by name, and combined with the program filter. The new
Products list then shows one search box, like the other lists.

While there, it closes a hole in the same search (FM-179): part of it is built by pasting the
typed text into the database query, so a name with an apostrophe breaks the list and the
error shows the query. After this change the text is always passed safely, a `%` or `_`
searches for that character instead of matching anything, and an unexpected database error
says so without showing internals.

Nothing changes for other callers of the endpoint: `code` and `name` keep working.

## Today

Measured on the local stack (referencedata `migration` @ `afca48f3`, 10,233 products).

- `GET /api/orderables?q=...` is a `400` (`referenceData.error.orderable.search.invalidParams`):
  only `id`, `exactCode`, `code`, `name`, `program`, `tradeItemId` are allowed.
- `code=0363` 604, `name=0363` 0, `code=0363&name=0363` **0**; `name=allergy` 136,
  `code=allergy&name=allergy` **0**.
- A `'` in `code`, `name` or `program` is a `500` whose message holds the SQL; `code=%`
  returns every product.
- No OpenLMIS service has a parameter searching several fields; all use separate `code` and
  `name`, ANDed. The new UI already calls its single-box search param `q` (Users, Roles).

### Backend Changes (`openlmis-referencedata`, branch `FM-184` from `origin/migration`)

- `OrderableRepositoryCustom.SearchParams` (:32-44): `String getQ()`.
- `QueryOrderableSearchParams`: `Q = "q"` in `ALL_PARAMETERS` (:46-47), `getQ()` like
  `getCode()` (:80-87).
- `OrderableSearchParams` (POST body): `getQ()` returns `null`; the JSON schema is unchanged.
- `OrderableRepositoryImpl`:
  - patterns are `"%" + EscapeCharacter.DEFAULT.escape(text.toLowerCase()) + "%"`, reusing
    `org.springframework.data.jpa.repository.query.EscapeCharacter` (Spring Data JPA 2.2.3,
    shipped with Spring Boot 2.2.2; escapes `\`, `%`, `_`), not a helper of our own;
  - `prepareParams` (:222-268): code and name use `builder.like(..., pattern, '\\')`; `q` adds
    `or(like(lower(code)), like(lower(fullProductName)))`;
  - `getLastUpdatedQuery` (:294-335): every value a named parameter (`:programCodes`,
    `:exactCodes`, `:code`, `:name`, `:q`), each `LIKE ... ESCAPE '\'`, values set with
    `setParameter`, following `FacilityTypeApprovedProductRepositoryImpl` (:325-345, :387-390);
    remove `toHqlInList` (no other caller) and the `FIXME`; log the SQL without values. Split
    into small helpers if PMD's cyclomatic limit (11) trips.
- No SQL in error bodies, the Spring way: unhandled errors reach Spring Boot's
  `BasicErrorController`, whose `DefaultErrorAttributes` put the exception message in the
  body. Boot 2.2 has no `server.error.include-message` (it arrives in 2.3, default `never`),
  so register a `DefaultErrorAttributes` bean, Boot's extension point for this, that drops
  `message` from the attributes. Errors referencedata already handles keep their own bodies;
  the cause stays in the log.
- `messages_en.properties`: the invalid-params message (:114) names `q`.
- `api-definition.yaml` (:946-976): `q` on `GET /orderables`, and the description; the
  integration tests validate every request against it.
- `CHANGELOG.md` under `15.8.0-SNAPSHOT (WIP)`: `New Functionality:` FM-184, and a new
  `Bug fixes:` block for FM-179.

### Risks and Edge Cases

- **Order of the two PRs.** Before this lands, the server answers `q` with `400`, so the UI
  swap can only merge once the referencedata image with `q` runs wherever the UI is tested:
  locally first, then test.openlmis.org (which runs `migration` since deployment PR #32).
  #33 waits for it, as decided.
- **Literal `%` and `_`** change what `code=%` returns (every product, today; none, after).
  No caller relies on it: the services send ids, exact codes or nothing.
- **Escaping in native SQL.** A `\` inside the SQL text may confuse Hibernate's parameter
  parser; `ESCAPE '\'` is covered by an integration test, with `!` as the fallback escape
  character if it fails.
- **Speed.** The text match is a sequential scan, as today (about 4 ms for 10k rows); `q`
  costs about the same as one filter. The latest-version check is what makes a
  program-filtered search slow; `NOT EXISTS` fixes it here.
- **The latest-version check is shared by every caller** (services, legacy and new UI). The
  before/after comparison covers ids, order and totals for unfiltered, filtered, program,
  id, exact code and trade item requests, so any change in what it returns shows up.
- **Totals change on purpose** for program-filtered searches where a product has two links
  to the program: the first pages drop by one, to the total the last page already showed.
- **Unexpected error bodies lose their message on every referencedata endpoint**, not only
  orderables, since Spring Boot's error attributes are shared. Legacy's error popup then
  shows the status text without the raw exception text.
- **Backend PR merge** needs the core team's review and the user's approval; never merged
  here.

## Decisions

- **FM-179 is folded in**, as the user decided: the Last-Modified query has to change for
  `q` anyway, and doing it with bound parameters is FM-179's fix.
- **The parameter is `q`.** No OpenLMIS API has a precedent; `q` is the new UI's name for its
  single-box search (Users, Roles), short, and common for free-text search. `search` is
  avoided because legacy's select-products modal sends `search` expecting a different match.
- **GET only.** The POST search keeps its body; nothing that needs `q` calls it.
- **`%` and `_` escaped for every contains filter** (`code`, `name`, `q`), so the same text
  always means the same thing.
- **Escaping reuses Spring Data's `EscapeCharacter`**, not a helper of our own, and keeps
  `LIKE` rather than a position search, so a trigram index can speed it up later if needed.
  Other referencedata searches do not escape today; they are left as they are.
- **Spring and JPA first, nothing hand-rolled**: values bound with JPA's `setParameter`,
  escaping by Spring Data's `EscapeCharacter`, error bodies through Spring Boot's
  `DefaultErrorAttributes`. A helper of our own only where nothing fits, with the reason.
- **An unknown `tradeItemId` keeps legacy's answer**: every product, not none (user,
  2026-10-01). Stock management's lot-code search on Stock on Hand sends it with `size` set to
  the number of trade items, so a lot whose trade item no product points to would list the
  first products by name; it cannot happen in the demo data (all 17 lots are linked), and
  the change is left for when it matters.
- **#33 waits for the backend.** It ships the one-box list once `q` runs on the local stack
  and on test, and only then is it ready to merge.
