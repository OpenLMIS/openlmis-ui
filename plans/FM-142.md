# FM-142: Programs

https://openlmis.atlassian.net/browse/FM-142 · Parent: FM-139 Admin: Products & Programs

## Scope

Administration > Programs: the list, adding a program and editing its settings. It is item 2
of the admin round that sets up what Stock Management reads (see [FM-62](FM-62.md),
"Administration first"), after FM-127 Facility Types, whose pattern it follows.

It widens the shared `Program` type in `reference-data` with the fields the screen edits, so
every screen that already reads the programs lookup keeps working from one query.

Out of scope: deleting a program (the API marks it "avoid using" and legacy has no delete),
the audit log, requisition templates (FM-148, FM-149).

FM-140 Products is built in parallel. Both PRs add lines to `rights.ts`, `nav-access.ts`,
`config.ts`, their tests, the locales and `route-tree.gen.ts`; whichever merges second rebases
and regenerates the route tree. This screen needs one right only, so it does not depend on
FM-140's any-of-several-rights support.

## Summary

A program is a line of supply, such as Family Planning or Essential Meds. Products,
requisitions, stock and user roles are all set up per program, and a few settings on the
program change how its requisitions work.

In the old UI, Administration > Programs lists every program by name with its status
(Active or Not Active) and an Edit button. Add Program opens a window with Program Code,
Program Name, Description, Active (ticked) and four requisition settings, each with a line of
help, and the note "Changes are effective immediately!". Edit opens a full page with the same
form. Both ask "Are you sure?" before saving. It works, but:

- The page is shown to people who may manage requisition templates, while saving needs the
  right to manage programs, so some users can open it and then fail on every save.
- Anyone can open the Add Program address directly, even without the right.
- A code already in use is reported after Save in an alert, with a second "creation failed"
  message on top.
- Edit can show old values: after the first visit it reads the program from the browser, not
  the server, until the user signs out.
- Leaving Edit with unsaved changes loses them without asking.
- On a phone the whole desktop page is shrunk to fit.

The new screen keeps the same data, fields, help texts and rules, and fixes those:

- The list shows each program's name, code and status, sorted by name, and pages like every
  other list.
- Add and Edit use the same short form, with the four settings as switches and their help
  texts, and the "Changes are effective immediately" note.
- The page opens for people allowed to manage programs, the same right the server checks on
  every save, so nobody reaches a form they can't save.
- A code already in use is flagged on the field before saving, and again if the server
  refuses it.
- Edit always loads the program fresh from the server.
- It works on a phone and in Arabic.

## Legacy Today

Screenshots: `.screenshots/FM-142/legacy-*` (desktop and phone).

- **Routes:** list `/#!/administration/programs`, Add modal `/#!/administration/programs/add`,
  Edit page `/#!/administration/programs/:id/settings`. The UI lives in the requisition UI repo.
- **Rights:** the list and Edit check `REQUISITION_TEMPLATES_MANAGE`; Add has no check of its
  own and opens for anyone by address. The server checks `PROGRAMS_MANAGE` on create, save and
  delete, and nothing on reads. Only System Administrator holds either right in the demo data,
  and it holds both.
- **List:** `GET /api/programs`, unpaged, sorted by name in the browser. Columns Program,
  Program Settings (Active or Not Active, the only setting shown), Actions (Edit). No paging,
  search or empty message.
- **Form:** Program Code and Program Name (required), Description (textarea), Active (ticked
  for a new program), Display Non-Full Supply Tab, Allow Skipping Periods, Skip Authorization
  Step, Enable field for Date Physical Stock Count Completed, each setting with a help text, and
  "Changes are effective immediately!" at the end. Code is locked on Edit.
- **Save:** a confirm, then the request, a toast ("Program created successfully!" or
  "Program Settings were saved successfully!") and the list reloaded. A refusal shows the
  server message in an alert plus a failure toast; the form stays.
- **Edit:** reads the program from localStorage after the first visit; no unsaved-changes
  prompt; an unknown id shows "Internal application error".

## Agent Brief

### API Map

| Step | Method and path | Params and body | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| List | `POST /programs/search` (FM-183) | `page`, `size`, `sort` | `id, code, name, active`, `totalElements` | none | `program.service.js:36-40`, `admin-program-list.routes.js:34-38` |
| Edit, load | `GET /programs/{id}` | | all nine fields | none | `admin-program-settings.routes.js:41-45` |
| Add | `POST /programs` | `{code, name, description, active, showNonFullSupplyTab, periodsSkippable, skipAuthorization, enableDatePhysicalStockCountCompleted}` | 201, the program | `PROGRAMS_MANAGE` | `program-add.controller.js:84-85` |
| Edit, save | `PUT /programs/{id}` | the whole loaded record with the edited fields, `id` included | 200, the program | `PROGRAMS_MANAGE` | `program-settings.controller.js:62-75` |

Errors:
- `400 referenceData.error.program.code.duplicated` "Program code is not unique." (on code).
- `400 referenceData.error.program.code.isInvariable` (code changed on edit; cannot happen,
  the field is locked).
- `400 referenceData.error.program.notFound.with.id` on `PUT` to an unknown id;
  `404 referenceData.error.program.notFound` on `GET`.
- `403 referenceData.error.unauthorized`.

`PUT` builds the saved row from the body alone, including its `id`, and replaces every field;
a missing flag hits a `NOT NULL` column. So only `PUT` a program loaded from `GET /{id}`, send
every field back, and send flags as `true` or `false`, never left out.

### Data Flow

- Loader: awaits `requireRight(queryClient, RIGHTS.programsManage)`, then prefetches the page
  from `loaderDeps`, deferred, and the unpaged lookup when Add is open. The dialog loads the
  program itself, fresh each time it opens: the detail query has a key that changes with every
  opening, so a copy cached from an earlier open can never be saved over another admin's
  change. Edit loads only the program; Add also loads the list, for the code check.
- URL: `page`, `size`, `sort` (`name`, `code`, `active`; default `name` ascending) and
  `program=new|<id>` for the dialog, through `useSearchNavigation`.
- The server pages, sorts and counts, through `POST /programs/search`, added for this list
  in FM-183 since `GET /programs` cannot change shape (support was added and reverted twice
  upstream). It shipped built first with browser paging; FM-183 moved it to the server.
- Keys: `programsListOptions(query)` for the paged list, `programDetailOptions(id, opening)` for
  one program. A save invalidates `programs.all` (the detail aside), which refreshes the list and
  the program pickers on Edit User Roles, Profile, Products and the product edit page.

### Rules

- Code and name required; whitespace alone counts as empty; trimmed before sending.
- Code is unique exactly as stored, case included, and the server drops all spaces inside a
  code (`Code.java:35`); the client check compares codes with spaces removed, case kept.
- A new program starts Active, the four settings off (`program-add.controller.js:64-68`).
- Code is read-only on edit (`program-form.html:3`) and sent back exactly as stored.
- A null `active` or `showNonFullSupplyTab` shows as off and saves as `false`.

### Risks and Edge Cases

- `PUT` with a stale or partial body overwrites or fails; the dialog always loads the program
  fresh and sends every field.
- Case-sensitive codes: `prg001` and `PRG001` can both exist; the client check matches the
  server, so it does not refuse a code the server would take.

## Decisions

- **The server pages the list**, through `POST /programs/search` (FM-183, `plans/FM-183.md`);
  the screen was first built with browser paging while the backend could not.
- **One shared `Program` type** in `reference-data`, widened, so the lookup and the screen read
  the same query.
- **Program names can be missing**: the server allows a program without a name, so the list
  sorts it first and the form asks for one, instead of failing.
- **`PROGRAMS_MANAGE` guards the page**, the right the server checks on every save, rather than
  legacy's `REQUISITION_TEMPLATES_MANAGE`, as the user decided. The mismatch in legacy is FM-182.
- **Add and Edit share one dialog**, as Users and Facility Types do, rather than legacy's Edit
  page, as the user decided: the form is eight fields with one save.
- **Backend findings** are recorded under FM-177: FM-180 (`PUT` replaces the whole program and
  trusts the body `id`), FM-181 (codes unique and searched with exact case), FM-182 (screen
  right and save right differ), FM-183 (page and sort the list on the server; once it ships,
  this list moves to server paging).
- **Flags are always sent**, `true` or `false`, so a save never leaves a `NOT NULL` column
  empty or a setting null.
