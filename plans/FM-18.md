https://openlmis.atlassian.net/browse/FM-18

## Scope

Build the shared My Facility / Supervised Facility, Program and Facility picker, with
Stock On Hand as its first consumer. Retain permission scopes, add the necessary shared
user/program reads and a controlled URL selection policy. These are required for this
feature, rather than a separate app-shell redesign.

Requisitions and CCE will use the same component when their screens migrate. Their real
integration and same-user UAT comparisons remain acceptance gates, not claims made from
a generic interface alone. FM-8 remains open for its remaining work, including FM-19.
No Jira changes, Data Import, new administrative screens or backend changes are included.

## Summary

Before looking up stock, a user chooses their own facility or a facility they supervise,
then the program and facility. The choices depend on the right needed by that screen.
The new app will provide one shared picker, starting with Stock On Hand, and restore its
choices from a copied link or reload. It will keep the existing list-page appearance,
make dependent choices clear, and show loading and retry states without replacing the page.

## Legacy Today

The selector is `openlmis-facility-program-select`, shared by legacy screens rather than
owned by Stock. Stock registers `STOCK_CARDS_VIEW`. In Supervised mode its actual order
is Mode, Program, then Facility. In My mode the fixed home Facility appears before Program.

It loads four inputs in parallel: minimal facilities, the user's programs, permission
strings and the current user. It finds the home facility within the minimal list.
My Facility offers programs with a matching right and that home facility. Supervised
Facility offers programs with matching grants outside the home facility; once a program
is selected, its facilities are all minimal records matching that right and program.
This second step does not exclude the home facility, so it can reappear if a program also
has a grant elsewhere. Preserve this verified behavior and test it explicitly. Do not
add active-facility, active-program or support-start-date filtering that legacy does not
apply. Without a resolved home facility, legacy starts in Supervised Facility mode.

### API Map

All paths below are relative to the shared Axios API base, normally `/api`. All are GETs.
Reads require an authenticated session; broad lookup access never grants stock access.

| Step | Method And Path | Params | Fields Used | Right / Policy | Legacy Reference |
|---|---|---|---|---|---|
| Permission authority | `GET /users/{userId}/permissionStrings` | Signed-in user ID | String array; right, facility and program segments | Exact caller-required scoped grants | Cache service 166-170; permission service |
| User context | `GET /users/{userId}` | Signed-in user ID | `id`, `homeFacilityId`; shared full `UserRecord` | Current user's record | Cache service 170-180 |
| Program labels | `GET /users/{userId}/programs` | User ID; no right-specific params in legacy | Program array, `id`, `code`, `name` | Intersect with grants for this mode/right | Cache service 167-168 |
| Facility labels | `GET /facilities/minimal` | No active filter; existing lookup unwraps paged `content` | `content[]`: minimal `id`, `code`, `name` | Intersect with exact right/program facility IDs | Cache service 166, 176-180 |

Use these actual legacy reads. Do not replace them with `GET /users/{id}/facilities` or
all-programs `/programs`: available backend endpoints are not automatically option-parity
equivalents. The lookup endpoints do not provide the right-specific paging/search contract
this selector needs, so filter their results locally, as legacy does. Load them lazily on
the first selector consumer and reuse them. Do not fetch approved products or stock data
as selector warmup. Record minimal-facility payload/timing on large deployments; changing
the lookup contract is separate work if measurement warrants it.

Handle 401 through existing session retry, 403 as refusal, 404 user as missing context,
and network/5xx failures with an inline retry. Never substitute empty data for a failed
lookup: that would incorrectly tell users they have no authorized options.

### One Permission Authority

Introduce `permissionsOptions(userId)` in auth's query module, retaining `userRightsKey`
and its invalidation/session lifetime. Cache both parsed grants and derived right names.
Keep `rightsOptions(userId)` as the same canonical options with observer `select` for
the set of names. Update imperative callers such as `requireRight` and Home to read
`permissionsOptions(...).rights`: TanStack `fetchQuery` and `ensureQueryData` do not apply
observer `select`. Audit all imperative rights consumers and fixtures before changing
the cache shape. Do not put different query functions/data shapes under one key.

Neutral types/parser/matcher belong in `src/lib/permissions.ts`, with no feature imports.
Supported permission strings are `RIGHT`, `RIGHT|facility`, and
`RIGHT|facility|program`. Preserve unscoped names for existing navigation/admin checks;
they are not wildcard authority for a stock facility/program. Stock selection requires
the exact three-segment grant. Reject malformed/empty scopes for scoped authorization,
and do not invent wildcard syntax. If a future caller requires a different verified scope
policy, give it an explicit policy rather than widening Stock's matcher.

The route composes auth with the selector and supplies plain user/right/grant data.
Stock features and the selector do not import auth. Scope authorization must complete
before any stock result prefetch, including direct URLs. Refresh stale/invalidated
permissions through `fetchQuery`, following current `requireRight`, rather than trusting
an indefinitely cached result. Recheck loaded context on permission changes; hide stale
rows and disable their actions immediately when a selection loses its grant.

### Shared Queries And Invalidations

- Add `userRecordOptions(id)` in reference-data, using existing `UserRecord` from
  `src/lib/user-types.ts`, under `[...queryKeys.users.all, 'record', id]`. Do not collide
  with `users.detail(id)`, which currently holds a richer Users aggregate.
- Add `userProgramsOptions(id)` under `[...queryKeys.users.all, 'programs', id]`.
- Reuse `minimalFacilitiesOptions()` and its facility scope.
- Make ordinary Profile/Users/Home reads compose the shared user-record query where they
  currently duplicate that read. Keep deliberately fresh GETs immediately before saves
  that send the whole user unchanged. Avoid another aggregate user context cache.
- Existing `invalidateUserQueries` must invalidate canonical permissions, user record,
  user programs, Profile and Home together. User switches/sign-out continue clearing
  the query cache through existing integration. Facility/program edits invalidate their
  labels and the relevant user-program options.

### URL And Component Contract

Add `src/lib/facility-program-selection.ts` with a pure schema, option derivation and
transition functions, and `src/components/facility-program-selector/` with controlled
fields. Input is `{ mode: 'my' | 'supervised', programId?, facilityId? }`, available
options/home facility and status, plus one change callback. The caller owns Search and
its own result/filter state. No stock DTOs, routes, or registry-table internals belong
in the shared selector. Use an explicit supplied right or already filtered option data;
do not maintain mutable globally registered rights as legacy does.

Sort program and supervised facility labels by name, as the legacy template does.
Disable My mode when no home is resolved and Supervised when it has no eligible programs.
Default mode is My Facility when a home facility is resolved, otherwise Supervised;
initialize the transient caller-controlled draft accordingly. Search commits the
effective mode explicitly to the URL, so an applied selection is reloadable. My Facility
fixes the facility to home.
Program is required and is not silently defaulted to the first option. Supervised
Facility requires a selected program before offering facilities. A mode change clears
program/facility; a program change clears incompatible facility, preserving the fixed
home facility in My mode. A facility change cannot carry a program the user cannot use.
Emit one atomic draft patch; the caller commits it and resets result page on Search.
The route decides whether its text filters are retained; FM-69 retains them. Drafts are
initialized from the applied URL and restored from it after Back/Forward or external
navigation. Compute committed changes from the latest URL with the existing
search-navigation helpers. Unsubmitted drafts are transient form state, not another
persisted query authority, and reload restores the last applied selection as legacy does.

Use field-level loading/retry states behind `QueryBoundary`; the page heading and picker
frame render immediately. A complete restored context waits for option and scoped-grant
validation before stock prefetch. An incomplete URL displays the picker. A tampered
complete context is refused, not silently changed into another facility's request.
Ordinary user selection changes clear invalid dependents and show required-field hints.
Never make a user wait for reference lookups unrelated to this picker.

### Files And Reuse

Add the shared selection policy/component, shared permission parser and the two reference

### Translations And Tests

Add flat `facility-program.*` keys for mode labels, Program, Facility, Search prerequisites,
missing home/no authorized options, loading, refusal and retry. Sync all locales through
the translation skill during implementation. Validation stores keys, not translated text.

Write failing tests before the logic: exact scoped matching and malformed strings,
program-first options including home reappearance, missing home, duplicate grants,
different rights on the same pair, stale selected IDs, atomic cascading/reset behavior,
single canonical permission request for simultaneous name/scoped consumers, imperative
rights reads, user/role/home changes, user switches, and denied URLs making zero stock
requests. Test reuse via representative Stock/Requisition/CCE caller policies without
pretending fixtures replace real consumer acceptance. Browser checks include keyboard,
Arabic, phone, reload/shared URL/Back/Forward and same-user restricted UAT accounts.

## UI/UX

Port the two modes and exact authorized option behavior. Improve the presentation using
the existing form fields in one compact selector panel: mode first; Program then Facility
in Supervised mode, and the fixed home Facility then Program in My mode. My Facility is
a named fixed value, not a selectable unauthorized facility.
Use a searchable facility combobox for long lists and a short program select when suitable.
Fields stack by available content width; labels and required messages remain visible.
Use the app's radio field for the mutually exclusive modes and normal keyboard behavior.
Show explicit no-home/no-options states; failed lookups get Retry rather than empty lists.
Search belongs to the caller and cannot run with incomplete or unvalidated selections.
No capability is dropped. No new global visual style or app-shell behavior is needed.

## Build Notes

Where the build departs from the brief above:

- Home, Profile and Users keep their own `GET /users/{id}` reads. Profile reads contact details
  with it, Home's Refresh resets its own query scope and Users holds a richer aggregate, so
  composing them over `userRecordOptions` would change their refresh behavior for no gain.
- `RadioGroupField` options take `disabled`, so My Facility turns off without a home and
  Supervised Facility without supervised programs, as legacy does.
- A program save also refreshes every user's program list, so a renamed program reaches the
  picker. Role changes already refresh it through `invalidateUserQueries`.
- Supervised Facility lists every facility, as legacy does, rather than the combobox's usual
  first 50; typing still narrows it.
- The picker is one compact bar: the mode as a segmented control, then the two fields and Search,
  wrapping on a narrow page. Legacy's facility and program sit in the heading above the results.
  It starts fresh after each Search, so switching mode marks nothing missing until Search again.
- Still open: same-user restricted UAT comparison, and reuse by Requisitions and CCE.
