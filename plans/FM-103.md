## Summary

A forecast (BUQ) estimates what a facility will need next year. Preparing one is the first step:
the facility picks a forecasting period and the system fills a draft from the facility's approved
requisitions in that period. Later screens edit, submit and approve it.

Legacy shows the program as fixed text and always uses the user's home facility. The Prepare
button is always enabled, the period list is loaded by fetching every period in the system, and
the downloaded CSV opens twice with the access token in the address.

The new page keeps the same flow on one page: the facility and program as fixed text, the period
picker with Prepare (enabled once a period is chosen), and the list of prepared forecasts below,
with translated statuses, a direct CSV download and a confirmed delete. Periods that already have
a forecast in the list are marked and cannot be prepared again.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Enter | permissions, `GET /users/{id}`, `GET /users/{id}/programs`, `GET /facilities/{home}` | user id | `homeFacilityId`; program `code === 'BUQ'`; facility `name`, `supportedPrograms` | `PREPARE_BUQ` at home for BUQ | `buq.routes.js`, `buq.service.js:281-307` |
| Periods | `GET /processingSchedules`, `GET /processingPeriods` | `processingScheduleId` of code `BUQ` | `id`, `name`, `startDate` | authenticated | `useBuqCommonFunctions.jsx:33-55` |
| List | `GET /bottomUpQuantifications` | `facility`, `status=DRAFT&status=SUBMITTED&status=REJECTED`, every page | `id`, `processingPeriodId`, `targetYear`, `status` | any BUQ right | `useGetBuqsByStatus.jsx`, `usePrepareBuq.jsx` |
| Taken periods | `GET /bottomUpQuantifications` | `facility`, no status, every page | `id`, `processingPeriodId` | any BUQ right | none (legacy lists only the open statuses) |
| Prepare | `POST /bottomUpQuantifications/prepare` | `facilityId`, `programId`, `processingPeriodId` | 201 DTO | `PREPARE_BUQ` | `PrepareBuq.jsx:38-60` |
| Download | `GET /bottomUpQuantifications/{id}/download` | none | CSV blob, `buq_quantification_preparation_report.csv` | `PREPARE_BUQ` | `PrepareBuq.jsx:70-87` |
| Delete | `GET /bottomUpQuantifications/{id}`, then `DELETE /bottomUpQuantifications/{id}` | none | `status`; 204 | `PREPARE_BUQ`, home facility must match | `PrepareBuqDeleteForm.jsx` |

- Errors `{messageKey, message}`, English only: 400 `buq.error.periodAndFacilityUnique`
  ("Selected period is already prepared"), 400 facility does not support the program, 400 home
  facility mismatch on delete, 403 without the right.
- The list rejects any other param (`programId` gives 400 `buq.error.invalid.searchParams`).

### Data Flow

- Loader blocks on `requirePermissions(queryClient, RIGHTS.prepareBuq)` and the user record, the
  user programs and the home facility (needed to decide access); prefetches periods and the list
  without awaiting.
- Access (`prepareAccess` in `lib/access.ts`): no home facility, no BUQ program, or a home
  facility not supporting it shows a message with the reason in the page; no exact
  `hasProgramGrant(PREPARE_BUQ, home, buq)` throws `ForbiddenError` (the standard no-access page).
- Query keys: new `buq` scope for the list, `buq.list({ facility })`; periods under
  `[...processingPeriods.all, 'buq', scheduleId]`, read by the feature itself (a shared periods
  lookup in `reference-data` was left out: the user keeps shared code unchanged), so period saves
  in Processing Schedules refresh them. Rows sort by Forecasted Period, then period start. Prepare and delete wait
  for the `[...buq.all, 'list']` prefix to refresh (`buq.list()` ends in `undefined` and matches
  nothing), Prepare also after a refusal; both first write their result into the list and the
  taken periods, so a deleted report never stays actionable even if the refresh fails.
- The loader reads the user record, programs and home facility fresh on entry (cached on stay),
  in parallel with the permissions, so role and support changes made in this session count. It
  prefetches the schedules and, once they arrive, the BUQ periods, without awaiting; the list only
  on entry, not on hover preload.
- The picker reads the facility's forecasts in every status without suspending (only to mark
  taken periods), so a list failure shows only the list error; it stays disabled until those
  forecasts have loaded. The list reads the period names without suspending: a periods failure
  shows the Forecasted Period in their place instead of hiding the list.
- The chosen period and the delete confirmation are local state, not URL (one-shot actions, as
  legacy). List paging is local and in the URL (`page`, `size`) as Roles; a page past the end
  (after a delete) is clamped. The shared schema also accepts `sort=targetYear` and `dir`; the
  order stays Forecasted Period ascending.
- Writes through `useSessionMutation`; download as the CCE export (`fetchReport` plus
  `downloadFile`).

### Server-Side Work

- Periods: legacy fetches all 434 periods and filters by schedule code; we resolve the BUQ
  schedule and send `processingScheduleId` (2 periods, 1.4 KiB instead of 151 KiB).
- Period names: legacy calls `GET /processingPeriods/{id}` per row; we map rows to the periods
  already loaded.
- List stays fetched whole (one facility, three statuses, small) and sorted and paged locally by
  Forecasted Period, as legacy.

### Rules

- Facility is always the home facility; program is the user's program with code `BUQ` (legacy
  matches by name; demo code and name are both `BUQ`).
- Prepare only with a period; one request at a time (the period input itself is disabled while
  it runs); the picker clears after success.
- BUQ counts as supported only when the home facility's support is active and started before
  today, as the server checks; otherwise the page shows the unsupported message.
- A period with a forecast in any status is offered disabled with "Already Prepared" (the server
  refuses a second forecast per facility and period, whatever its status); a refusal still shows
  the server message in place and refreshes the list.
- Delete always confirms; Download and Delete for every listed row, as legacy. Delete rereads the
  forecast first and refuses one that has moved past Draft, Submitted and Rejected: the server
  deletes in any status. After a delete focus moves to the list.
- A prepared forecast without products gets its own toast description (the facility has no
  approved requisitions in the period).
- A period missing from the BUQ schedule shows the Forecasted Period as its name.
- Forecasted Period is `targetYear` (the period's end year); Quantification Period is the period
  name; rows sorted by Forecasted Period ascending.

### Risks And Edge Cases

- Prepare duplicates consumption of multi-version products (backend bug, vault); shown as the
  server returns it.
- Deleting a forecast that later screens show is allowed for every listed status, as legacy.
- A user whose PREPARE_BUQ grant is on another facility passes the backend's unscoped check; the
  page refuses it (exact home grant).
- No home facility, BUQ program missing or not supported: clear message instead of legacy's crash.

## Decisions

- **Program and facility fixed from the home facility** (AC 5): legacy and the backend
  (save, submit, delete) assume the home facility, and the right is granted there.
- **Periods filtered on the server** and names mapped locally, instead of legacy's full fetch and
  per-row calls.
- **Taken periods disabled** in the picker, using the facility's forecasts in every status
  (ultra review, 2026-11-12: the local instance's only free-looking period already had an
  approved forecast, so the earlier list-based rule offered a period the server always refuses).
- **Delete rereads the status** (ultra review, 2026-11-12): the server deletes in any status, so a
  stale row could delete an authorized or approved forecast.
- **Row actions as two icon buttons** (`RowActions`, master #137 changed the two-action rule).
- **Delete confirmation in local state** (user, 2026-11-06): the AC and the epic say nothing about
  it; legacy keeps the modal in component state, and row deletes elsewhere (requisitions) do the
  same. Only Service Accounts put it in the URL.
- **Statuses of this list only** (user, 2026-11-06): Draft, Submitted, Rejected; the other BUQ
  statuses come with the screens that show them.
- **Tests at the component and rule level** (user, 2026-11-06), loader in the browser checks.
- **"No Reports Available"** in Title Case, the house style for empty states; same words as legacy.
- **"Report" throughout** (user, 2026-11-06, review): Report List, Delete Report?, Report Prepared,
  Report Deleted, as legacy; "forecasting period" stays for the period.
- **Download success toast kept** (user, 2026-11-06, review): "Download Complete" with the period,
  as legacy's "Data has been downloaded successfully".
- **Heading without "Program:" label** (user, 2026-11-06, review): "facility · program", as CCE.
