# FM-47: Convert To Order

https://openlmis.atlassian.net/browse/FM-47 · Parent: [FM-39] Requisitions

## Scope

- New Convert Requisitions To Order page at `/requisitions/convert`, the live
  `nav.requisitions.convert-to-order` entry.
- Filter by Program and Facility, server paging, selection across pages, a Supplying Depot select
  per row, Convert To Order and Release Without Order on the ticked rows.
- Not in scope: offline (the route stays online-only); manual orders ([FM-49]/[FM-50]).

## Summary

After a requisition's final approval, a supply planner at the supplying warehouse turns it into
an order for that depot, or releases it without an order when it will be supplied another way. In
legacy this is a paged list of approved requisitions the planner's warehouses can supply, with a
depot dropdown per row and two buttons acting on the ticked rows.

The new page keeps all of that: same columns, the single available depot preselected, ticks kept
across pages, the same checks and confirmations. It adds the filter and page in the address, a
phone layout with one card per requisition, the server's reason when converting fails (legacy
shows "Error occurred"), and keeps the ticks after a failure so the planner can fix and retry.

### API Map

| Step | Method And Path | Params / Body | Fields Used | Right | Notes |
|---|---|---|---|---|---|

| Release / convert | `POST requisitions/batchReleases`, header `Idempotency-Key` (`randomId()`, as legacy; not checked by the server) | `{createOrder, requisitionsToRelease:[{requisitionId, supplyingDepotId}]}` | 201 `{requisitionDtos, requisitionErrors}`, ignored | ORDERS_EDIT at each depot | One `@Transactional` batch, all or nothing. 403 `{messageKey, message}` for a missing depot right or unknown id; 400 for `release.mustHaveSupplyingFacility`, `release.requisitionMustBeApproved`, `validation.cannotConvertToOrderWithoutApprovedQty`, `convertingMultipleRequisitions` (fulfillment failed) |

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.convert.tsx`; loader awaits
  `requireRight(queryClient, RIGHTS.ordersEdit)`, prefetches the list, programs, facilities and
  `deploymentTimeZoneOptions` unawaited; `pendingComponent` with the real header and skeleton.
- Search schema: a paging-only schema (`tableSearchSchema` needs sort fields; pass none or omit
  the sort keys), page and size (default 20, as the other requisition lists),
  `programId`, `facilityId` (uuids). Filter changes return to page 1. `size` is always sent (without
  it the server returns every row in one page). Rows are keyed and de-duplicated by requisition id
  (the server's join can repeat a requisition).
- Columns: View menu with hideable columns and `useCardView`, as the approval list; Program,
  Facility and Supplying Depot stay visible.
- `convertListOptions(search)` under `queryKeys.requisitions` (refreshed after actions).
- One depot map, keyed by requisition id, is the only source for both the rendered selects and
  the request body. It is seeded from each row's sole depot (the server always sends a
  one-element list, whose element can be `null`: then no depot); on refetch an id keeps its chosen
  depot only while that depot is still offered, otherwise it falls back to the fresh seed. Ticks
  store only id and label (a page-level selection map with a value type, not filter-scoped; `withoutIds` made generic); the body
  reads depots from the map, so it always sends what is shown, not a stale copy. Ticked rows on
  other pages keep their last known depot in the map.
- The depot control is a plain `Select size="sm"` (not the form `SelectField`, which needs a form)
  with an sr-only label naming the row and `aria-invalid` when a ticked row lacks a depot. In cards
  it renders through the depot cell in `TableCards` (cells may render components that use hooks,
  as `ViewRequisition` does); `RequisitionListTable` gains `isRowInvalid`/`tone` pass-through.
- Buttons: with rows on the page and nothing ticked, page-level `size="lg"` Release Without Order
  and Convert To Order buttons sit below the table (as the approval list's View Selected), so the
  "nothing ticked" message can show; once ticked, both move into `DataTableSelectionBar` with
  `SelectionBarLabel`. No buttons on an empty list, as legacy.
- Actions: `useSessionMutation`, blocked offline (`requireOnline`) and while pending (double-click
  guard); session checks after each await. On success: toast, drop the sent ids from the selection,
  invalidate `queryKeys.requisitions.all` and `queryKeys.home.all`, clamp a now-empty last page back
  to the last page with rows (replacing history, as the approval table does), and focus the list
  after rows disappear. Filter changes keep the ticks, as legacy, and close any open confirmation or
  error dialog. The selection is page state, so it ends when the user leaves the page. On a definite failure (4xx other than `convertingMultipleRequisitions`): keep the selection
  and show the server's message. On an uncertain outcome (no response, 5xx, or the 400
  `requisition.error.convertingMultipleRequisitions`, which wraps fulfillment transport failures
  after orders may already exist): never infer success from a row's absence in the paged list.
  Read each submitted requisition (`GET v2/requisitions/{id}`) for its status: RELEASED or
  RELEASED_WITHOUT_ORDER is done and leaves the selection; still APPROVED after a conversion stays
  ticked but blocked behind a warning ("Orders may already exist for these requisitions. Check
  orders before converting again.") with an explicit Convert Again choice; a read that fails or is
  refused keeps the outcome unresolved with the same warning. Release Without Order creates no
  orders, so its uncertain outcome only needs the status read.

### Rules

- Validate before confirming: nothing ticked gives the action's legacy message; any ticked row
  without a depot opens the invalid dialog ("Supplying Depot Not Selected"), tints such rows on the
  current page and focuses the first one there (cards: `revealField`). No red pager pages, since
  this list is paged by the server and ticks on other pages have no page index. Release also
  requires a depot, as the server checks it.
- Confirm with legacy's text, then send one request for all ticked rows.
- Facility cell `code - name`; District from the facility's zone; Date Approved a timestamp in the
  deployment time zone shown as a date; Emergency `FlagBadge`; empty cells blank.
- Rows keep the server's order.

### Risks And Edge Cases

- All or nothing: one bad row fails the batch; the message names the reason, ticks stay.
- Requisitions whose template hides Approved Quantity are listed but can never convert
  (`cannotConvertToOrderWithoutApprovedQty`); Release Without Order works for them. The server's
  message says so; test it.
- A depot could stop being valid between load and send; the server refuses and the list refetches.
- The whole batch, fulfillment included, runs in one transaction (`REQUIRES_NEW` on `buildOrders` is
  a self-call with no effect), so a fulfillment failure rolls requisitions back to Approved. The
  risk is the reverse: a timeout after fulfillment created orders; the uncertain-outcome refetch
  above covers it.
- Without a unique sort tie-breaker, rows can shift between pages; this is the server's order, as
  legacy.

## UI/UX

**Port**: columns, filter fields, depot preselection, page select-all, ticks across pages, both
buttons, messages and confirmations, refresh after action.

**Improve**: filters and page in the URL with filter changes back to page 1; Clear Filters; the
server's reason on failure and ticks kept; the depot sent is always the one shown (legacy can send a
stale copy); phone cards (band: tick and Program/Facility; rows: details and the depot); Emergency
as `FlagBadge`; selection bar with counts. Filters: Facility (combobox, names only, as legacy) then
Program, reusing the Valid Destinations toolbar pattern (`assignments-toolbar.tsx`).

**Drop**: legacy's `storageKey` URL param (selection is page state); sort control (none in legacy);
nothing else.

## Decisions

- **Keep the confirmation**, as legacy: release and conversion are irreversible and affect orders.
- **No sort sent**; the server's order is kept, since custom sorts can fail.
- **Page size 20**, as the other requisition lists.
- **Ticks survive filter changes as well as paging**, as legacy (user, 2026-10-30), an exception to
  AGENTS.md's rule that filter changes clear selection. The selection bar's count includes ticks
  outside the current filter, and its Clear empties them all; ticked rows that are not shown keep
  their last known depot in the depot map, so `useFilterScoped` is not keyed by the filter here.
- **Route `/requisitions/convert`**; the label stays legacy's.
