# FM-35: User Profile

https://openlmis.atlassian.net/browse/FM-35 · Parent: FM-30 General: auth, home, profile ·
Subtasks: FM-36 Basic information form, FM-37 Role assignments (4 sub-tabs), FM-38
Notification settings

## Scope

This PR adds the Profile page at `/profile`, which every signed-in user can open from
Account in the avatar menu. It also removes Settings from the avatar menu and from the
sidebar footer.

Two changes reach every page and ride along, because the page has no entry point
without them:

- Account links to the page.
- The breadcrumbs support a page outside the nav, so Profile shows Home / Profile.

The PR does not add a forgot-password flow on the login page, and it does not change
the admin Users screens. The one exception: the admin reset password dialog moves to
the shared password rules (see Decisions).

## Summary

Every user has a profile: their name, email, phone, the roles they hold, and how they
want to get notifications. In the old UI it opens by clicking the username in the
header. It has three tabs:

- **Basic Information:** the name, email and phone can be edited. Username, job title
  and home facility are read-only.
- **Role Assignments:** a read-only copy of the admin's roles screen.
- **Notification Settings:** a digest schedule for each kind of notification.

A Change Password button opens the same dialog admins use to reset someone else's
password.

It works, but it is rough:

- Role Assignments takes about 5 seconds to open.
- Mistakes are only reported after pressing save, and the server's reason is never
  shown.
- Cancel says "restored successfully" even when the reload fails.
- The password dialog is titled "Reset Password" and can email you a link, then signs
  you out anyway.
- Unsaved changes are lost without warning.
- The tables and toolbar break at phone width.

The new page keeps the same three parts and fixes the rest:

- It opens from Account in the avatar menu, and shows Home / Profile.
- Basic Information shows the read-only facts as a summary. The editable fields check
  as you type after the first save, and saving changes only what you edited.
- Changing your email explains that a verification link was sent, shows the pending
  address, and lets you send the link again.
- Role Assignments reuses the Edit User Roles tabs, read-only: rows appear as soon as
  the roles are known, and they can be searched and sorted.
- Notification Settings is a list of simple cards. The schedule reads as "Daily at
  08:00" or "Weekly on Monday at 08:00", and anything more unusual stays editable as a
  custom schedule.
- Change Password asks for the new password twice, says the rules up front, shows the
  server's reason when a password is refused, then signs you out to sign in again.
- Leaving with unsaved changes asks first.
- It works on a phone and in Arabic.

### Data flow

- **Routes.**
  - `/profile` is a layout route. It renders `ProfileWorkspace` once (header, Change
    Password, the tabs as links) around the open tab, plus the Change Password dialog,
    so a tab switch never remounts the header or loses focus.
  - `/profile/` is Basic Information, `/profile/roles` is Role Assignments, and
    `/profile/notifications` is Notification Settings. Each has
    `staticData.crumbKey: 'profile.title'`.
  - A tab that edits puts Save and Cancel in `ProfileFooter`, which portals into the
    footer slot after `Workspace`.
- **Loaders.**
  - The layout loader reads `referenceDataUserId` from the store and awaits
    `ensureQueryData(profileOptions(userId))`. The header and every tab need this record,
    and the pending component already draws the page's frame.
  - The pending verification and the home facility are prefetched, deferred.
  - The roles and notifications children prefetch their own lookups, deferred.
- **Query keys**, under `queryKeys.profile`:
  - `profile.detail(userId)`: the user plus contact details, also read by the avatar
    menu for the name.
  - `[...profile.all, 'pending-email', userId]`
  - `[...profile.all, 'subscriptions', userId]`
  - `[...profile.all, 'digest-configurations']`
  - `facilities.detail(id)`, in reference-data.
- **URL.**
  - `?dialog=password` on the layout search opens Change Password: opening pushes a
    history entry, closing steps back.
  - `/profile/roles` reuses `rolesSearchSchema` (tab, q, page, sort, rights), minus
    `dialog`; the role tabs take the narrower `RolesTableSearch`.
- **After a save, even one that failed part way**, invalidate:
  - the `profile` keys
  - `queryKeys.users.all`, so an admin's list shows the new name
  - `firstNameOptions(userId)`, so the Home greeting updates

  The Basic Information route does the last two, since it may import any feature.

### Server-side work

- **Home facility.** Legacy loads all 2,734 minimal facilities to show one name. Use
  `GET /facilities/{id}` instead.
- **Supervisory nodes.** The roles tab still needs the full `/supervisoryNodes` list for
  labels. It is cached for 10 minutes and never blocks rows, as on Edit User Roles, so
  rows show in well under a second while node names fill in.
- **Role rows.** They are filtered, sorted and paged in the browser, as on Edit User
  Roles. A user holds at most a few dozen assignments, and no endpoint pages them.
- **Save.** Save runs one call after another instead of in parallel, and skips a call
  whose part did not change. If the user is saved and the contact details fail, the
  page refetches and shows the error, so the draft never lies about what was stored.

### Rules

- First and last name are required and trimmed; the server also rejects whitespace.
  Email is optional but must be valid when given. Phone is free text.
- Username, job title, home facility and the verified flag are shown, never sent
  changed.
- Allow Notifications is enabled only when the saved email is present and verified
  (RDUI `user-profile-basic-information.html#L33`).
- Changing the email does not change it yet. The server keeps the old address, emails a
  link to the new one, and the page shows the pending address with Resend.
- **Password.** The server rules (AUTH `PasswordResetRequestDtoValidator.java#L31-L85`):
  - 8 to 72 characters, letters and digits only, at least one digit
  - no spaces
  - does not contain the username, first name or last name, case-insensitive
  - a strength check that runs only on the server; its message is shown as sent

  The confirm field must match.
- **Digest.**
  - With Use Digest on, the schedule is required and the channel must be Email, so SMS is
    disabled in the channel list rather than refused after submit.
  - With it off, the cron is not sent.
  - A configuration with no subscription defaults to Email, digest off.
- A simple schedule is `0 {m} {h} * * {*|0-6}`, with Sunday as 0. Any other valid
  expression is shown as a custom schedule and kept as typed.

### Risks and edge cases

- The page is load-bearing for every user, including ones without admin rights. Check
  it as a non-admin if the test server has one; if not, record that the check could not
  run.
- Moving `dialog-parts` and `discard-changes-dialog` out of users touches files other
  sessions may be editing. Keep those moves in their own commit, so a rebase conflict
  stays mechanical.
- `rolesSearchSchema` is owned by the users feature. The profile roles route extends it
  and drops `dialog`.
- The email change is asynchronous: the saved email stays the old one until the link is
  opened. The success toast says so.
- Opening the verification link turns Allow Notifications on server-side. The page
  shows whatever it reads next.
- A user with no contact details: the notifications tab shows a "Add an email to get
  notifications" empty state instead of a save that would 404.
- A password change that the server refuses on strength returns a zxcvbn-based English
  sentence, which is shown as sent.
- Two sessions editing the same profile: the last save wins, as in legacy.

## Decisions

- **Routes.** Profile is a page with three child routes, not a dialog: it has its own
  structure. The URL owns the tab and the open dialog.
- **Feature layout.** It is a new `features/profile`. The roles tab is composed in the
  route from the users feature's `RoleTabs`, made read-only when `onAdd` and `onRemove`
  are missing. The small shared parts (`serverMessage`, `ErrorAlert`,
  `DiscardChangesDialog`) move to `src/components/`. The alternative, profile files
  inside `features/users`, would avoid the move but put a self-service screen in the
  admin feature.
- **Save.** It sends only the parts that changed, one after another, and never
  `POST /users/auth`. This is safer than legacy's three parallel writes with a forced
  `enabled`.
- **Cancel.** It resets the draft, since the page was not opened from a list to return
  to.
- **Password rules.** The client mirrors the server's rules, and the admin reset dialog
  adopts them too. Otherwise it keeps sending passwords the server refuses ("letters and
  digits only").
- **After a password change**, the user is signed out, as in legacy, so the new password
  is proven at once.
- **Breadcrumbs.** Off-nav pages with a `crumbKey` show Home / crumb. Pages without one
  still show nothing.

- API calls that differ from legacy, on purpose, against the FM-35 AC "uses the same API
  calls as the legacy screen": no `GET /users/auth/{id}` and no `POST /users/auth` (nothing
  on the page edits the sign-in account, and legacy only sent `enabled: true` back);
  `GET /facilities/{id}` for the home facility name instead of all of
  `/facilities/minimal`; no `POST /users/auth/forgotPassword`, since the emailed reset
  option is dropped. Every other call is the legacy one.
- The ticket's "Update Profile" and "Update Subscriptions" read "Save Profile" and "Save
  Settings", and the notifications table is a card list that fits a phone.

## As Built

What changed from the plan while building it:

- Field labels and name/email validation reuse the `users.form.*` keys.
- Rebased onto FM-119 (#18), which had already moved `dialog-parts` and
  `role-rights-dialog` to `src/components/` and built the password rules with a live
  checklist. The profile uses those instead of its own copies: one set of password rules
  and one checklist serve both password dialogs, and Change Password gains the checklist
  and the "too weak" message.
- After the rebase, the 404 lookup, the verified badge, `fullName` and the user and
  contact details types (`src/lib/user-types.ts`) moved to shared code, since several
  features use them. The search updater and URL dialog open and close that five pages
  repeated became `useSearchNavigation` in `src/hooks/`, used by Users, Roles, Edit User
  Roles and both profile routes.
- The role tabs and table take a narrower `RolesTableSearch` (tab, filter, paging, sort),
  so the profile's own `dialog` param never clashes with the roles page's.
- The avatar menu loads the name only when it opens, from the profile query.
- The Notification Settings tab shows an empty state for a user with no contact details,
  since the subscriptions endpoint 404s for them.
