# FM-120: Service Accounts

https://openlmis.atlassian.net/browse/FM-120 · Parent: FM-116 Admin: Users & Access

## Scope

Administration > Service Accounts: the list of API keys, Add and Delete. A new
`service-accounts` feature, route, right and nav entry. Nothing shared changes beyond
what the page needs.

## Summary

A service account lets another system, not a person, use the OpenLMIS API: a reporting
tool, a national health information system, a nightly sync script. An administrator adds
one and OpenLMIS generates a key. That key goes into the other system's settings, and
the system sends it with every request. It never expires; deleting it is how access is
revoked, and whatever uses it stops working at once. A key belongs to no user and has no
roles; each service decides which calls accept a key at all.

In the old UI, Service Accounts is a table of keys with their creation date and a Delete
button, and an Add button. Add and Delete each ask for confirmation. It works, but:

- There is no way to copy a key except selecting the text by hand.
- Nothing says what a key is or what deleting one breaks.
- A failed delete says "key undefined", and a half-finished add or delete can leave a
  key behind that the screen can no longer remove.
- It breaks on a phone.

The new screen keeps the same actions and fixes these:

- Each key has a Copy button, and a newly added key is shown right away, ready to copy.
- The confirmations explain what happens, and Delete is clearly marked as destructive.
- Add and delete finish cleanly or undo themselves, so no stray keys are left.
- It works on a phone and in Arabic.

## Agent Brief

### API Map

| Step | Method and path | Params | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| List | `GET /apiKeys` (auth) | `page`, `size`, `sort=creationDetails.createdDate,desc` | `content[].token, createdDate`, `totalElements` | `SERVICE_ACCOUNTS_MANAGE` | `api-keys.service.js:35`, `ApiKeyController.getApiKeys` |
| Add, 1 | `POST /apiKeys` (auth) | no body | `token, createdDate` | same | `service-account.factory.js:50` |
| Add, 2 | `POST /serviceAccounts` (referencedata) | body `{token}` | | same | `service-account.service.js:35`, `ServiceAccountController.java:63` |
| Delete, 1 | `DELETE /serviceAccounts/{token}` (referencedata) | | 204 | same | `service-account.factory.js:70` |
| Delete, 2 | `DELETE /apiKeys/{token}` (auth) | | 204 | same | `ApiKeyController` |

Errors: `403 noFollowingPermission`; `400 apiKey.create.clientUserNotSupported`;
`404 serviceAccount.notFound`, `404 apiKey.notFound`, `400 token.invalid`. `page` without
`size` is a 400, so always send both.

### Data Flow

- Loader awaits `requireRight(SERVICE_ACCOUNTS_MANAGE)`, then `prefetchQuery` of the page
  from `loaderDeps`, deferred.
- URL: `page`, `size`, `sort` (only `createdDate`, default newest first), and the open
  dialog: `?add=true`, `?delete=<token>`. Opening pushes, closing replaces.
- Server does paging, sorting and the total. Nothing is done in the browser.
- Add: one dialog at `?add=true`: the confirmation, then, once created, the new key with Copy
  and Done in the same dialog, so the key is in front of the user before the list.
- Add: the two calls in `createServiceAccount()` in `api.ts`. If step 2 fails, delete the
  auth key from step 1 and rethrow, so no key is left without its account.
- Delete: `deleteServiceAccount()` runs step 1, treats its `404` as done, then step 2. That
  lets the screen remove a key a legacy half-add left behind.
- After either, `invalidateQueries(queryKeys.serviceAccounts.all)`. If a delete empties the
  last page, the table steps back a page as the Users table does.

### Rules

- Both confirmations are required before any request (`service-account-list.controller.js:76,107`).
- Create order: auth then referencedata. Delete order: referencedata then auth.
- A key is shown in full: this list is the only place to read it again.
- Delete opens on Cancel, not on the key's Copy button, since deleting cannot be undone.
- Focus stays in the dialog while a request runs, and moves to Copy once a key is added.

### Risks and Edge Cases

- Test has one key from 2018; the empty state and paging need stubbed responses.
- The Clipboard API needs a secure context; `localhost` and HTTPS both qualify. If it
  fails, the toast says so and the key stays selectable.
- A rollback that itself fails leaves the key; the dialog names that key and says to delete it
  from the list, which Delete can do.
- Show the full key, as legacy does; masking would leave no way to read it again.
- Roll back a half-finished add, and finish a half-finished delete. The screen must never
  leave a live key it cannot remove.
- Confirm dialogs are URL state like the rest of the list, so Back closes them.
- No Created By column.
