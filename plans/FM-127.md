# FM-127: Facility Types

https://openlmis.atlassian.net/browse/FM-127 · Parent: FM-124 Admin: Facilities & Supply Chain

## Scope

Administration > Facility Types: the list, and one dialog to add or edit a type. It is the
first screen of the admin round that sets up what Stock Management reads (see
[FM-62](FM-62.md), "Administration first"), so it also adds two pieces the next screens
reuse:

- a facility types lookup in `reference-data`, which Facilities, Reasons, Valid Sources and
  Destinations and approved products will pick from;
- a `NumberField` in the form kit for whole numbers, which Products, Programs and Lots need.

Out of scope: deleting a type (the API marks it "avoid using" and legacy has no delete),
the audit log, and a search box (the API has no name or code search, and deployments have a
handful of types).

## Summary

A facility type groups facilities, such as Health Center or District Store. Much of the
setup hangs off it: which products a facility may stock, and which reasons, sources and
destinations its stock screens offer.

In the old UI, Administration > Facility Types is a table of code and name, sorted by
display order, with Add Facility Type and an Edit button per row. Add and Edit open the
same window: Code, Name and Display Order (all required), and Active and Primary health
care checkboxes. Save asks "Do you want to save the facility type?" first. Code can't be
changed once a type exists. It works, but:

- Inactive types look the same as active ones, and the display order that decides the
  sorting isn't shown.
- A code or name already in use is only reported after Save, in an alert, with a second
  "Failed to save" message on top.
- Display Order drops what it doesn't accept as you type, so "1.5" silently becomes 15.
- On a phone the whole desktop page is shrunk to fit.

The new screen keeps the same data, rules and flow, and fixes those:

- The table adds Display Order and Status (Active, Inactive) columns, and can be sorted by
  code, name or display order. It opens sorted by display order, as today.
- Add and Edit open the same short dialog. Code is locked on edit, as today.
- A code or name already in use is flagged on the field before saving, and again if the
  server refuses it.
- Display Order takes whole numbers only and says so, instead of changing what was typed.
- It works on a phone and in Arabic.

## Legacy Today

Screenshots: `.screenshots/FM-127/legacy-*` (desktop and phone).

- **Route:** `/#!/administration/facilityTypes?page&size`, Administration menu between
  Facilities and Geographic Zones. The dialog is its own state:
  `/#!/administration/facilityTypes/edit/:id`, Add is the same with no id.
- **Right:** `FACILITIES_MANAGE` guards both states and hides the menu item. Without it the
  URL sends the user to Home with "You are not authorized to perform this action." Reading
  the API needs no right.
- **List:** columns Facility Type Code, Facility Type Name, Actions (Edit). Sorted on the
  server by `displayOrder,asc`, no sort UI, no search, 10 per page, "Showing 6 item(s) out
  of 6 total". Inactive types are listed with nothing to tell them apart. Empty: "No
  Facility Types found." An error cancels the navigation and shows an alert.
- **Dialog:** title "Create Facility Type", or `Edit "<code>" Facility Type`. Fields:
  Facility Type Code (locked on edit), Facility Type Name, Facility Type Display Order
  (default 1), Active (default on), Primary health care. Buttons Cancel and Create or Save.
  Escape and clicking outside do not close it; browser Back does.
- **Validation:** "This field is required" per field, plus a "This form is invalid" alert.
  Whitespace counts as empty. Display Order strips non-digits as typed (`-5` becomes 5,
  `1.5` becomes 15), accepts 0, and says "The number is too large" above 2147483647.
  No length limits. No duplicate check before the server.
- **Save:** a confirm ("Do you want to create the facility type?" / "...save..."), then the
  request, a toast "Facility type created successfully" or "...saved successfully", and the
  list reloads on the same page. A refused save shows the server message in an alert and a
  "Failed to create facility type" toast; the dialog stays open.
- **Phone:** no viewport tag; the desktop layout shrinks to fit.

## Agent Brief

### API Map

| Step | Method and path | Params and body | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| List | `GET /facilityTypes` | `page`, `size`, `sort` (`displayOrder`, `code` or `name`, `asc`/`desc`; default `displayOrder,asc`) | `content[].id, code, name, displayOrder, active`, `totalElements` | none to read | `admin-facility-type-list.routes.js:37-47` |
| Lookup | `GET /facilityTypes` | no `size` (returns all), optional `active` | `content` | none | Facility add, valid sources, reasons, FTAP routes |
| Edit, load | `GET /facilityTypes/{id}` | | all fields, incl. `description` | none | `admin-facility-type-edit.routes.js:34-39` |
| Add | `POST /facilityTypes` | `{code, name, displayOrder, active, primaryHealthCare}` | 201, the created type | `FACILITIES_MANAGE` | `facility-type-edit.controller.js:111-115` |
| Edit | `PUT /facilityTypes/{id}` | the loaded type with the edited fields, `id` and `description` kept | 200, the saved type | `FACILITIES_MANAGE` | same, `facility-type.service.js:97-101` |

Errors:
- `400 referenceData.error.facilityType.code.duplicated` / `.name.duplicated` (both unique
  ignoring case). On `PUT` it may instead come back as `409
  referenceData.error.facilityType.saving.with.id`; treat both as a save failure and map
  the two duplicate keys onto their fields.
- `404 referenceData.error.facilityType.notFound` for an unknown id.
- `403 referenceData.error.unauthorized`.
- A sort on an unknown property is a `500`, so the schema allows only the three sort fields.

`PUT` upserts and replaces every field: an unknown id creates a new type with a random id,
and a field left out is set to null. So only `PUT` a type loaded from `GET /{id}`, and send
its `description` back. No versioning: the last save wins, as in legacy. Accepted for now;
[FM-178](https://openlmis.atlassian.net/browse/FM-178) (epic FM-177 Potential BE
improvements) records it for the backend.

### Data Flow

- Loader awaits `requireRight(queryClient, RIGHTS.facilitiesManage)`, then prefetches the
  page from `loaderDeps`, deferred; when `facilityType` is an id, it also prefetches the
  detail and the lookup.
- URL: `page`, `size`, `sort` (default `displayOrder,asc`, kept out of the URL), and
  `facilityType=new|<id>` for the dialog, through `useSearchNavigation`.
- The server pages, sorts and counts. Nothing is done in the browser, except the duplicate
  check against the lookup.
- Keys: `queryKeys.facilityTypes.list(query)` for the page, `.detail(id)` for one type,
  `['facilityTypes', 'lookup', { active }]` for the lookup. A save invalidates
  `queryKeys.facilityTypes.all`, which refreshes all three.
- A page past the end (after a size change) steps back to the last page, as the Users table.

### Rules

- Code, Name and Display Order required; whitespace alone counts as empty; code and name
  are trimmed before sending (`facility-type-edit.html:11-15`, Angular `ng-trim`).
- Display Order is a whole number from 0 to 2147483647 (`positive-integer java-integer`).
- New type defaults: display order 1, active on, primary health care off
  (`facility-type-edit.controller.js:74-80`).
- Code is read-only on edit (`facility-type-edit.html:11`).
- Code and name are unique ignoring case (`unq_facility_type_code`, `unq_facility_type_name`
  on `LOWER`); the edited type does not clash with itself.

### NumberField

A text input with `inputMode="numeric"` and `dir="ltr"`, holding a string, so the form
shows exactly what was typed and the schema says what is wrong, rather than stripping
characters as legacy does. The schema turns it into a number. It follows the form kit's
registry rules (no i18next), takes the same `layout` as `TextField`, and later screens use
it for pack sizes, quantities and orders.

### Risks and Edge Cases

- Duplicate on `PUT` may be `400` or `409`: handle both.
- The lookup check runs on the full list, but another admin may add the same code in the
  meantime; the server stays the final check.
- Deep link to `?facilityType=<unknown>`: the dialog shows not found, never an Add.

## UI/UX

- **Port:** the table of types sorted by display order, one shared dialog for Add and Edit,
  its titles ("Create Facility Type", `Edit "<code>" Facility Type`) and buttons (Create,
  Save), the same fields, defaults and rules, Code locked on edit, the dialog in the URL so
  Back closes it, the list reloading on the same page after a save.
- **Improve:**
  - Display Order and Status columns, so inactive types and the sort order are visible;
    both can drop on a narrow page and come back from the View menu.
  - Sorting by code, name or display order, which the server already supports.
  - Duplicate code or name flagged on the field before and after saving, instead of an
    alert and a second failure toast.
  - Display Order explains what it accepts instead of rewriting the input.
  - Active and Primary Health Care as switches with a line of description each.
  - Row actions in a "..." menu; Add Facility Type ends the toolbar.
  - Works on a phone and in RTL.
- **Drop:** the "Do you want to create the facility type?" confirm before saving, so the
  dialog saves like Users and Roles; and the "This form is invalid" alert, since the errors
  show on the fields.
- **States:** loading skeleton; no types at all (with Add); error with Try Again; the dialog
  loading, not found and load error; saving keeps the dialog open with Save pending.
- **Accessibility:** focus goes to Code (or Name on edit, since Code is locked), then to
  the first invalid field on a refused submit.

## Decisions

- **The edit title follows legacy**, `Edit "<code>" Facility Type`, rather than the name
  the AC mentions. The AC is to be corrected to match.
- **No confirm before saving.** Create and Save send the form at once, as the Users and
  Roles dialogs do, and every CRUD dialog after this one does the same. A confirm stays only
  where a save reaches other records, as Roles asks for a role users hold.
- **`PUT` replacing every field is accepted for now**: the dialog sends the whole loaded
  record back. The backend side is FM-178.
- **Server paging, as legacy**, although deployments have few types: it keeps the screen
  the same as the other admin lists and costs nothing.
- **The duplicate check uses the unpaged lookup**, which the next screens need anyway.
- **`NumberField` holds a string** and validates it, rather than a number input, so nothing
  is rewritten under the user's fingers and "1.5" is refused, not read as 15.
- **The FM-62 epic plan ships in this branch**, as its own `docs: plan FM-62` commit. It
  is the full backlog of what has to be done before Stock Management work starts, and this
  screen is its first item.
