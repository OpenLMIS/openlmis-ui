# FM-126: Facility Edit

https://openlmis.atlassian.net/browse/FM-126 · Parent: FM-124 Admin: Facilities & Supply Chain

## Scope

The Edit Facility page: a facility's information and the programs it supports, opened from the
Facilities list. Item 4 of the admin round in [FM-62](FM-62.md). It reuses the facility page that
[FM-125](FM-125.md) builds for Add, with the record loaded and one Save, so it ships as its own
PR stacked on FM-125.

Out of scope: removing a supported program (legacy dropped it on purpose, OLMIS-8105),
deleting a facility, and the fields no legacy screen shows (location, comment, go-down date,
extra data), which a save keeps as they are.

## Summary

In the old UI, Edit opens a full page titled with the facility's name and two tabs. Facility
Information has the same fields as Add, with its own Save. Associated Programs lists the
programs the facility supports, with their start date, whether each is active and whether it is
fulfilled locally, a form to add another, and its own Save Programs. It works, but:

- Each tab saves only its own copy of the facility, so saving one tab quietly throws away
  unsaved changes made on the other.
- Leaving the page loses unsaved changes without asking.
- Facility pickers elsewhere keep showing the old name until the admin signs out and in again.
- On a phone the whole desktop page is shrunk to fit.

The new page keeps the same fields, tabs, help texts and rules, and fixes those:

- One Save at the bottom stores both tabs together, so nothing typed on either tab is lost.
- Switching tabs keeps everything; leaving with unsaved changes asks first.
- Save and Cancel go back to the list where the admin left it, with its page and filters.
- The page always loads the facility fresh from the server, and every picker sees the change
  at once.
- It works on a phone and in Arabic.

## Legacy Today

Screenshots: `.screenshots/FM-126/legacy-*`.

- **Route:** `/#!/administration/facilities/{id}`, keeping the list's query params,
  `FACILITIES_MANAGE`. Breadcrumb Home / Administration / Facilities / Edit Facility, title
  "Edit {name}" (the saved name). Reloading works.
- **Loads:** `GET /facilities/{id}`, `GET /programs`, `GET /facilityOperators`,
  `GET /facilityTypes?active=true`, `GET /geographicZones`.
- **Facility Information:** the FM-125 fields and help texts, Operational Date required here
  only (`ng-required="vm.facility.id"`), the selects clearable, Code editable. Name, Code,
  Description, Zone and Active are locked for a facility managed by another system
  (`extraData.isManagedExternally`). Save sends `PUT /facilities/{id}` with this tab's copy.
- **Associated Programs:** add row Program* (programs not yet supported) and Start Date*, Add;
  table Program, Active, Start Date (help popover), Locally Fulfilled, all editable; no remove;
  empty "No programs are associated with {name}". Save Programs sends `PUT` with this tab's copy
  (`facility-view.controller.js:123-124, 165-183`).
- **After a save:** "Facility saved successfully!" and the list, reloaded. Failure: "Failed to
  save facility!". Cancel: back to the list, no prompt.

## Agent Brief

### API Map

| Step | Method and path | Params and body | Fields used | Right | Legacy ref |
| --- | --- | --- | --- | --- | --- |
| Load | `GET /facilities/{id}` | | every field, `supportedPrograms[]` | none | `admin-facility-view.routes.js:26-64` |
| Lookups | as FM-125 | | | none | same |
| Save | `PUT /facilities/{id}` | the whole loaded record, `id` included, with the edited fields and the whole `supportedPrograms` list | 200, the facility | `FACILITIES_MANAGE` | `facility-view.controller.js:165-183` |

`PUT` replaces every scalar field: anything left out is cleared (description, dates, comment,
location, operator, `extraData`). So build the body by spreading the loaded record, as
`toFacilityTypeBody(values, saved)` does. Without `id` in the body the server tries to insert a
new facility. A non-empty `supportedPrograms` replaces the set; each item needs `id` or `code`
and both flags, since a missing flag saves as off. Errors as FM-125, plus
`404 referenceData.error.facility.notFound` on load and `400 ...facility.idMismatch`.

### Data Flow

- Route `/administration/facilities/$id` (`facilities_.$id`, no nesting): the loader awaits
  `requireRight` and a fresh read of the facility together (`fetchQuery` with `staleTime: 0`, so
  the draft never starts from a cached copy), and prefetches the lookups, deferred; each picker
  loads behind its own boundary, as on Add. A missing
  facility shows the not-found state with a link back, as Edit User Roles does.
- The detail query is `queryKeys.facilities.detail(id)`, the key `facilityOptions(id)` already
  uses in `reference-data`; that lookup's type widens to the full `Facility` rather than a second
  query for the same record.
- The draft lives in `FacilityEditor` above the tabs, as on Add; `tab=programs` is a search
  param. Opened from the list's row menu with its search in history state.
- Save: `PUT`, toast, invalidate `facilities.all` (list, minimal lookup, Profile's home
  facility), back to the list. A draft edited while saving stays, as Edit User Roles does.

### Rules

- Every FM-125 rule.
- Operational Date required on Edit, though optional on Add, as legacy
  (`ng-required="vm.facility.id"`), as the user decided.
- A facility managed by another system (`extraData.isManagedExternally` is `"true"`) locks
  Name, Code, Description, Zone and Active, as legacy and the server do.
- The current type, zone or operator stays selectable even when the lookup no longer offers it
  (an inactive type).
- Saved programs cannot be removed; rows added since the page opened can.
- Code is editable and checked by the server, as on Add.

### Tests

Written before the code they cover:
- `api.test.ts`: the `PUT` keeps every loaded field and `id`, sends the whole program list.
- `facility-form.test.ts`: values from a loaded facility (missing name, inactive type, no
  operator), the update body, locked fields when managed externally.
- `facility-editor.test.tsx`: a tab switch keeps both tabs' edits; one Save sends both; a refused
  code shows on Code; a saved program has no remove.

In the browser, writes stubbed: load, every field filled, edit both tabs then Save once, Cancel
with and without changes, an unknown id, reload on the page, `divo1`, Arabic at desktop and
phone width.

### Risks and Edge Cases

- No version check on the server: two admins saving the same facility, the last save wins, as
  in legacy (recorded for FM-177 with the other `PUT` findings).
- `PUT` regenerates right assignments on the server; slow on big data, as legacy.

## UI/UX

- **Port:** the title, both tabs and their fields, help texts and columns, the add row, no
  remove for saved programs, locked fields for externally managed facilities.
- **Improve:**
  - One Save for both tabs, in the page's footer, instead of two saves that overwrite each other.
  - A prompt before leaving with unsaved changes.
  - Back to the list with its page and filters.
  - Fresh data on every visit; pickers elsewhere updated at once.
  - Phone width and RTL.
- **Drop:** the separate Save Programs button, now part of Save.
- **States:** page skeleton, not found with a link back, load error with Try Again, Save
  pending.

## Decisions

- **One Save for both tabs**, which also fixes legacy's tabs overwriting each other; the AC asks
  that a new program saves with the facility.
- **The Add page with the record loaded**: one editor for both, built in FM-125.
- **Saved programs cannot be removed**, as legacy since OLMIS-8105.
- **Operational Date is required on Edit**, as legacy, as the user decided.
