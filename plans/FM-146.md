## Summary

Administrators organize rejection reasons into named, coded categories and can activate
or deactivate them. Legacy provides a paginated list, an Add dialog and an Edit page.
The new UI keeps those screens and fields, with a stable list order, translated titles
and breadcrumbs, inline required-field errors, and the standard responsive admin layout.
Save and Cancel return to the list with its previous settings.

## Agent Brief

### API Map

All paths are under `/api` in the requisition service, using the shared Axios client.
The UI right for every row is `USERS_MANAGE`; these controllers check no backend right.

| Step | Method And Path | Params Or Body | Fields Used | Legacy / Backend Ref |
|---|---|---|---|---|
| List and reason picker | `GET /rejectionReasonCategories` | First request without params; follow remaining pages if present | Page metadata; `id, name, code, active` | REQUI list route `:34-36`; REQ category controller `:70-82` |
| Open Edit | `GET /rejectionReasonCategories/{id}` | UUID | Whole saved record | REQUI view route `:36-38`; REQ controller `:90-101` |
| Add | `POST /rejectionReasonCategories` | `{name, code, active}` | Saved record, 201 | REQUI add controller `:73`; REQ controller `:111-128` |
| Save Edit | `POST /rejectionReasonCategories` | `{...saved, name, code, active}`, retaining `id` | Saved record, 201 even for update | REQUI view controller `:64`; REQ controller `:111-128`; domain importer copies ID |

Supported but unused: `PUT /rejectionReasonCategories/{id}` (200, upsert),
`GET /rejectionReasonCategories/search?name&code&active` (Set/array, not a paged
sortable list). No DELETE. Do not move to `/search` or invent server sort support.

### Reads, State And Saves

- Add `RejectionReasonCategory = { id: string; code: string; name: string; active: boolean }`
  in `reference-data/lib/types.ts`. Normalize nullable server Active to `false`, the
  unchecked legacy presentation; always write an explicit boolean.
- `fetchRejectionReasonCategories()` and `rejectionReasonCategoriesOptions()` live in
  `reference-data`, under exactly `queryKeys.rejectionReasonCategories.list()`.
  Start with the no-param legacy GET, which currently returns the entire collection in
  one response. Adapt the existing `fetchProcessingSchedules` loop, changing only the
  initial request and follow-up size. If `totalPages > 1`, read every remaining page
  with explicit `page` and positive `size` from the response,
  with session-scope checks before and after each await. Do not pass a huge size again
  for page 1: the backend multiplies Java integers when slicing. Publish the query only
  after all pages succeed. Never silently display a truncated collection. A `page`
  without `size` returns 400; the fallback is a stub-tested guard for a future capped
  response, not behavior observable with today's default.
- Both controllers materialize HashSets before slicing and ignore sort. Local ordering
  follows Programs/Roles: Name ascending by default; Name, Code and Active sortable,
  then Code and ID as deterministic ties. Work on the complete collection. A multi-page
  fallback has no server snapshot guarantee if another administrator changes data.
- `tableSearchSchema`, `textFilterSchema`, and `useSearchNavigation` own list state.
  URL: `page`, `size`, `sort`, `name`, and `category=new` for Add. Name is a local,
  case-insensitive substring search. No extra Active/Code filters in this parity slice.
  Search resets page 1 and replaces history; sort/page add history. Clamp out-of-range
  pages after loading/filtering. Pagination and filtering do not issue new list requests.
- Await `requireRight` before starting list reads. List loader fire-and-forgets
  `prefetchQuery`; toolbar/header remain outside `QueryBoundary`. Use a 30-second list
  freshness override as Roles does, without changing the lookup's shared cache key.
- Add dialog uses `?category=new`, `CLOSED_DIALOGS`, `useSearchNavigation` and
  `useDialogTarget`. Closing restores list state and works on a directly linked dialog.
  No detail read is needed for Add. Guard closing during mutation and show failures inline.
- Edit route has `preload: false`, blocking fresh `fetchQuery({...detail, staleTime: 0})`
  on entry and cached `ensureQueryData` on `cause: 'stay'`. Capture one draft; background
  reads must not replace user edits. Provide a form skeleton, page-level not-found and
  retry/error states. `useDiscardGuard` protects dirty drafts and pending saves.
  Run `requireRight` and the required Edit detail read together in `Promise.all`, as
  Edit Reason does. Detail keys use `queryKeys.rejectionReasonCategories.detail(id)`
  and `queryKeys.rejectionReasons.detail(id)` from the same shared scopes.
- Preserve list search in route-owned TanStack Router `HistoryState` augmentations,
  colocated with the list routes: `rejectionReasonCategoriesListSearch` and
  `rejectionReasonsListSearch`. Also pass only list params in the Edit link's search,
  validate them on Edit without the Add dialog param, and set
  `staticData.crumbParentSearch` to return them, as Stock Card does. Save/Cancel prefer
  captured history state and fall back to validated URL state, then defaults. The
  linked parent crumb uses URL state, retaining settings after reload or sharing.
  Add `crumbKey` to Edit; no shared breadcrumb changes are needed.
- Use `useSessionMutation`, `ErrorAlert` and `serverMessage(error) ?? t(fallback)`;
  preserve fields and draft after errors. A successful save invalidates
  `queryKeys.rejectionReasonCategories.all` AND `queryKeys.rejectionReasons.all` because
  reasons embed category values. Toast title plus description, then return to the list.
  Failed refresh after a successful write must not encourage a duplicate write.

### Rules And Errors

- Name and Code required on both forms; whitespace-only input is invalid. Do not introduce
  arbitrary length limits, case-insensitive uniqueness rules or a new right. Active starts
  off, matching legacy's unchecked Add checkbox; explicit false replaces legacy's possible null.
  Validate trimmed text for emptiness but send the entered text unchanged, as legacy does.
- Master schema makes both Name and Code unique in each table separately. Categories and
  reasons can share the same code (`BUQ` already does). Duplicate code/name is HTTP 400,
  not 409, with localized `message` and known `messageKey` values
  `requisition.error.rejectionReasonCategory.code.duplicated` and
  `requisition.error.rejectionReasonCategory.name.duplicated`. This is source-verified,
  not a live write result. Show the server message in `ErrorAlert`; generic translated
  fallback handles unmapped responses. Do not depend solely on messageKey recognition.
- Category PUT has no explicit mandatory check; reason PUT checks null name/code. The
  actual missing-items key on current master is `validation.missing.mandatory.items`.
  UI validation applies regardless of which write operation checks it server-side.
- Missing detail GET is 404. PUT can recreate a missing ID, and collection POST also
  merges by ID; opening Edit must first get the existing record. Concurrent changes
  have no version conflict protection on this API, as in legacy.

## UI/UX

- **Port:** Name, Code, Active, Edit, Add dialog, full Edit page, Save/Cancel, all records
  including inactive, legacy rights, read/write call chain and successful list return.
- **Improve:** translated titles/crumbs, required Code on Edit, explicit inactive default,

  standard responsive table with View and end-of-row Edit menu. Active is a labeled
  status, not an unexplained empty tick cell.
- **Drop:** FM-147's single Reason Information tab; legacy localStorage resource
  cache and duplicate/generic failure-toast behavior. TanStack Query owns these reads.
  No user field or action is dropped.

List uses standard Workspace with a one-sentence description, Name search, View, then Add.
Keep existing singular nav/list labels Rejection Reason Category and Rejection Reason;
new Add/Edit labels use those nouns consistently in translated text.
No Filters button without secondary filters. Name and action remain visible; Code and
Active are user-hideable and can yield to container width. Match table/skeleton/View
visibility, preserve table form on phones and allow horizontal scrolling. Distinguish no
records from no search matches with Clear Filters. Editors use narrow Workspace, a
two-column field grid collapsing naturally to one, and sibling sticky narrow footer
with large Cancel at start and Save at end. SwitchField replaces the checkbox.
Use logical layout, existing direction providers, translated accessible names and
keyboard focus. Existing admin design takes precedence over a new visual style.

## Decisions

- One PR and one `rejection-reasons` feature for both tickets; shared collection reads
  belong to reference-data for FM-43.
- Add remains a dialog and Edit remains a page by the user's explicit legacy-container
  instruction, even though a short editor would otherwise fit a dialog.
- Use the actual legacy collection POST for both Add and Edit. The prompt's statement
  that Edit PUTs came from the older service API, not the screen controller's call path.
- Read the unparameterized collection first, then every additional page if needed;
  current master/live default returns all rows in one request. Sort/page locally.
- Start Active off and always send a boolean. Keep inactive rows visible.
- Add a local Name search and standard View/menu actions; no new server filters.
- Carry list settings in the Edit URL as well as history so breadcrumbs, reloads and
  shared links return consistently, using the existing `crumbParentSearch` hook.
- Show duplicate code/name errors through serverMessage/ErrorAlert, without a new
  client-side uniqueness policy or a real duplicate write during planning.
- Both names and codes are unique in master migrations. Correct the earlier research
  assumption in FM-147; no confirmed duplicate-name data-loss ticket is warranted here.
