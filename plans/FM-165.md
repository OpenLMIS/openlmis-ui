## Summary

A worker signs in while connected and carries on working while the app downloads what
Adjustments needs. Once that download finishes, they can reopen the program list and editor,
even after restarting the browser without a connection. Their edits stay on that device.
Submitting offline saves the event on the device and sends it when the connection and a valid
session return. The app says "Synced" only after the server accepts it.

Legacy removes queued events before upload and clears them on sign-out or a refused token.
We will retain every event until its result is recorded, including after session expiry.
A refusal keeps the event and its explanation. After a lost answer, the user checks history
and chooses whether it was recorded or should be sent again, with a duplicate-event warning.
Signing out warns about work waiting to sync, retains it for the same user, and prevents
another user from opening it.

The spike proves that complete path on Adjustments before we size the wider offline layer.
Issue and Receive will reuse the editor, storage and sync rules in later stages. Their downloads
and offline activation remain separate work.

## Legacy Today

Legacy routes under `/#!/stockmanagement` flag Adjustments, Issue and Receive as offline-capable.
Adjustments uses `STOCK_ADJUST` for the home facility/program; reading its stock also needs
`STOCK_CARDS_VIEW`. It downloads programs, products, stock summaries, lots and reasons at login.
Its editor supports quantities, reasons, free text, occurred date, VVM and signature. Offline
Submit reads "Submit Offline", queues the event, shows the submittedOffline toast and opens
Stock on Hand for the same facility/program, without a print offer. Unsaved lines need discard
confirmation when leaving; there is no device draft that survives a restart.

The queue belongs to the signed-in user. Reconnect and post-login start oldest-first uploads.
The failure handler attempts to show a modal alert and move every failed event to sync errors,
not only server refusals. If error.data is absent, reading error.data.message throws before
the error is stored; the event was already removed from the queue and is lost. Logout and any
401 handled by the auth interceptor clear all localStorage except the locale, deleting both
the queue and sync errors. Requests marked ignoreAuthModule bypass that interceptor. The
offline logout warning only explains that login needs a connection; it does not warn of loss.
Legacy disables unsupported offline routes. Stock on Hand warns that stock may be stale.

Login awaits the promises returned by its post-login actions. Orderables for all the user's
programs and all lots are downloaded, rather than only records referenced by stock. The stock
summary runner starts per-program requests in a forEach without returning their promises, so
login does not await those summaries. Our entirely nonblocking download and referenced-only
product/lot bundle are deliberate improvements, not a claim that legacy awaits every dataset.

## Agent Brief

### Current Foundation And Gaps

- `src/integrations/local-db.ts:25-26` has version 1 and version 2 with
  `physicalInventoryDrafts: 'draftId'`. Extend this database; do not create another one.
- `src/features/auth/api/queries.ts` parses permission strings into rights and scoped grants.
  `requirePermissions` in `auth/lib/access.ts` fetches them through Query. They currently
  survive only in memory. An offline reload fails before the stock editor can open.
- `src/routes/(protected)/-stock-event-program-picker.tsx` also needs the user record,
  user programs and home facility. The editor validates the exact facility/program grant.
- Adjustments and Unpack use `EventEditor`, but their routes duplicate the page wrapper.
  `StockEventEditorPage` in `-stock-event-editor.tsx` currently accepts only printable kinds.
  Move both there first, using `config.print` to compose a printable child when needed.
  Keep hooks unconditional within their components. Preserve Unpack's reason ids, contents,
  simple confirmation and online-only policy, and both kinds' no-print flow.
- `src/features/stock-events/api/api.ts:28-60` fetches v2 summaries with `nonEmptyOnly=true`,
  deduplicates cards, then hydrates only referenced products and lots. It currently uses
  product ids and discards summary version identities. Preserve known version identities in
  the offline snapshot. The identity helper in `reference-data/api/api.ts:189-209` ends with
  latestVersions, which collapses older versions of the same id. Add a variant that retains
  every requested id/version pair; keep the latest-only behavior for its existing consumers.
- `EventEditor` already has validation, signature confirmation and `retry: false` on Submit.
  Its unknown-outcome flag is only memory state and can be reset by a new attempt or reload.
  Replace that limitation for the selected workflow with durable attempt state.
- `src/integrations/axios.ts:40-50,60-68,90-91` checks identity, waits before dispatch while
  expired, checks scope after responses, and replays on 401. Queue transport must neither wait
  nor replay, while keeping scope checks. A typed not-sent error returns a row to queued;
  a session error after dispatch, even after 201, leaves uncertainty. Query retry does not
  control these interceptor paths. Downloads also need a fail-fast expired-session policy.
- `src/features/auth/store/login-data.ts:36` persists sessions across restarts. Downloads need
  valid-session boot and reconnect triggers as well as sign-in/renewal/borrowed-session events.
- Axios has a 60-second timeout (`axios.ts:22`); `src/lib/http.ts:10-11` excludes ECONNABORTED
  from offline errors. Handle slow-download timeouts explicitly instead of assuming offline.
- Physical Inventory's local repository and generic serial autosave writer provide patterns
  for session checks, flushing and write failure. Do not change its offline action policy.
- `src/lib/online.ts`, `SidebarNotices`, `StatusAnnouncer`, `OfflineNotice`, `LoadError` and
  existing Query boundaries provide connection state, messages and fallback UI.

Read details and rights:

- Grants retain the original strings, including facility/program scopes. Reparse with
  `parsePermissions`; do not serialize a `Set`. The picker intersects user programs,
  supported programs and `STOCK_ADJUST` grants. Download stock only where the same home/program
  also has `STOCK_CARDS_VIEW`. No home or no permitted programs is a completed empty result.
- Stock query parameters are `facilityId`, `programId`, `nonEmptyOnly`, and paging if used.
  Read every page and verify completion. Keep `canFulfillForMe` stockCard id, stockOnHand,
  orderable id and lot id, plus the root summary's product version identity. Deduplicate by
  stock card id as the existing screen does. Do not invent versions for nested fulfilling ids.
  The response is a summary/card snapshot, not full stock-card transaction history.
- Resolve versioned products through a new all-requested-versions identity helper with
  `{identities: [{id, versionNumber}], page, size}`. Deduplicate by id/version, not id alone;
  verify every requested identity resolved before marking complete. Unversioned ids use GET.
  Keep product id/version, productCode, fullProductName, netContent, dispensable, identifiers
  and editor-required fields. The identity POST is a read, not a stock mutation.
- GET id lookups use at most 100 distinct ids and all returned pages, with the existing bounded
  concurrency and session checks. Empty ids send no request. Do not download all orderables.
- Lots retain id, lotCode, expirationDate and tradeItemId. Stock event quantity is in doses;
  pack conversion needs netContent. Keep date values as ISO dates and VVM as current enums.
- With `GS1_SCANNING` enabled, download id/gtin for the referenced products' trade items using
  GET id batches. Resolve scanned GTINs locally. Unknown/offline-missing GTIN is unavailable
  locally, not proof it is unregistered on the server. Manual product selection still works.
- Reasons retain hidden, program/facility-type assignment and nested reason fields including
  id, name, type/category and free-text allowance. Apply `reasonsOf(..., 'ADJUSTMENT')` as today.
  This call requires authentication. It does not need source/destination or fulfills reads.
- Download reads can return 401, 403, missing records or network/server errors. A 403 must
  never be hidden by falling back to older permissive data. Missing local data is not a 404.

Upload uses eventPayload in stock-events/lib/event-form.ts unchanged. Omit documentNumber
for online and offline Adjustments, as legacy does; the server assigns its normal number:

```text
programId, facilityId, signature, eventOrigin: "ADJUSTMENT"
lineItems[]:
  orderableId, lotId, quantity, occurredDate, reasonId, reasonFreeText
  extraData: {vvmStatus}, when applicable
```

The master controller checks home facility/program and `STOCK_ADJUST`. It returns 201 with
the created UUID. Service JSON 400/403/404 with messageKey and 401 with messageKey or OAuth
error are definitive non-commit responses. Authentication
precedes the controller and its transaction rolls back mapped processing exceptions. A service
401 permits one resend after same-user renewal. Gateway HTML or an unrecognized body does not
provide that guarantee; 502/504, timeouts and other 5xx remain uncertain.

Master has no client event id or idempotency key for this POST. `resourceId` belongs to the
Physical Inventory contract and is not a deduplication mechanism. Each accepted Adjustment
creates a new event. Do not add a header/parameter and assume the backend honors it.

Master recalculates stock from the earliest new line through later movements. Any negative
balance at or after occurredDate throws ERROR_EVENT_DEBIT_QUANTITY_EXCEED_SOH, returning 400
and rolling back the whole event. This includes backdated debits that invalidate later stock.
Classify it as a definitive "stock changed" refusal in recovery and expect it to be the most
common offline refusal, to be measured during the spike. A stale debit that remains within
stock is accepted: there is no wider snapshot/version conflict check. Keep the UI debit cap
against downloaded stock, retain refused signed payloads and never silently rebase them.

Master generates a per-facility sequential document number when documentNumber is absent.
Keep this legacy behavior for online and offline events so visible numbers stay unchanged.
History returns the assigned number with STOCK_CARDS_VIEW. There is no client correlation
value or automatic unknown-result match; the user reviews Stock Cards and Transaction History.

### Durable Data And Dexie Schema

Use `getLocalDb()` for the current session; only owner-bound queue outcome writes may reopen
the captured original database after identity changes. Its database name is `openlmis-ui:<deployment>:<userId>`; deployment
includes the server and app base. Identity change closes it and clears Query. Sign-out closes
access but never deletes the database. Explicit sign-out cannot be undone offline.

Keep versions 1 and 2 and the existing `physicalInventoryDrafts` table unchanged. Add version 3
for downloaded data, then version 4 for drafts, version 5 for submission/recovery tables and
version 6 to initialize retained sync-error history. Append versions rather than reuse numbers.

| Version | Table | Dexie Index Declaration |
|---|---|---|
| 2 | physicalInventoryDrafts | `draftId` |
| 3 | offlineAccess | `userId` |
| 3 | adjustmentDownloads | `[facilityId+programId]` |
| 4 | stockEventDrafts | `draftId, [kind+facilityId+programId+state], updatedAt` |
| 5 | stockEventQueue | `++sequence, &localEventId, draftId, [status+sequence]` |
| 5 | stockEventSyncErrors | `&localEventId, [facilityId+programId], failedAt` |
| 5 | stockEventReceipts | `[draftId+revision], &localEventId, serverEventId` |
| 6 | stockEventSyncErrors | Existing indexes; initialize `history: []` for earlier records |

Table contents:

- `offlineAccess`: owner userId, raw permission strings, user record, user programs, home
  facility, fetchedAt, generation and format version. The bootstrap coordinator is its only
  writer: fetch all parts, validate identity, then commit the complete snapshot together.
  Auth/reference query functions fetch online results or read the saved snapshot offline;
  they never write individual parts. The shared repository takes raw-reader callbacks from
  shell composition, keeping auth and reference-data within the feature import rules.
  No token/password here. Session credentials retain the existing auth store behavior.
- `adjustmentDownloads`: owner, facility/program/type ids, generation, fetchedAt, hydrated
  cards with resolved product/lot data, version identities, valid reasons and trade-item/GTIN
  mappings when scanning is enabled. An empty but complete bundle is valid. Never label a
  partial response complete. Replacing one scope does not erase another scope or any draft.
- `stockEventDrafts`: owner and scope, kind, draftId, revision, state, editable line values,
  product/lot display snapshots, signature when confirmed, savedAt/updatedAt, download
  generation and last accepted revision. Preserve typed quantity text across unit changes.
  States distinguish editing, queued, refused, uncertain and accepted, plus archived saved
  copies. Keep attempt history and user resolution choices with the original revision. Enforce
  one active editing draft per kind/facility/program in a transaction; archived copies may be many.
- `stockEventQueue`: localEventId, draftId/revision, kind/scope/owner, immutable payload,
  sequence, queuedAt, status, attemptId, attemptStartedAt, frozen POST body and last failure.
  Status is queued, sending or uncertain. Save the exact body before dispatch; a safe renewal
  resend keeps it unchanged. A user-authorized resend keeps the payload and sequence, but
  starts a new attempt and preserves the previous attempt and decision in the draft history.
- `stockEventSyncErrors`: the entire payload/revision and display snapshot, localEventId,
  failure category, HTTP status if known, messageKey/message, failedAt and resolution state.
  Unknown outcomes may have a linked entry here while their queue row remains uncertain.
- `stockEventReceipts`: exact draftId/revision/localEventId, acceptedAt, resolution source
  (server response or user confirmation), confirming user/time and optional server details.
  serverEventId is present for a verified 201 and may be absent for "It Was Recorded"; do not
  invent a UUID or label user confirmation as a server response. This preserves sent status
  on reload. Prune receipts after 30 days without changing the draft's accepted state.

Stage 3 lifecycle is intentionally narrower than the final download flow: valid boot always
attempts access refresh, and an unavailable database-scoped download lock skips the attempt
immediately (`ifAvailable`) instead of waiting and comparing batch generations. This prevents
competing writers without introducing stage 4 progress, staleness or retry machinery. Stage 4
must extend the same batch lock with generation rechecks, program bundles and status observation.
Shell-composed raw readers use `session: false` so background requests neither wait for renewal
nor replay; Axios still checks the captured session scope before dispatch and on responses.
The repository also checks scope after each read and before/after its transaction.
Keep separate bootstrap reads: route queries can fall back to device data or wait for renewal.
Ordinary query reads retain the existing authentication behavior. Device results are marked
outside their DTOs, immediately stale, and never structurally shared with server results.
Access-sensitive loaders use `fetchQuery`, since `ensureQueryData` returns cached stale data.
`homeFacilityOptions` has its own key for stock selectors/editors and the Profile home label;
`facilityOptions` stays online-only so device copies never feed whole-record facility saves.

  without a final status, allow a short tick for pending channel messages, then clear running or
  report unfinished scopes as failed with Retry.
- Boot reuses complete data younger than 30 minutes. Reconnect and own/borrowed identity or
  token changes force refresh; Retry targets failed programs, or access when its bootstrap
  failed. Programs without STOCK_CARDS_VIEW are excluded from downloads and failures; their
  list status stays Not Downloaded. Refresh requests outside eligible home programs are dropped.
  Data timestamps use deployment time on the program list.
  A fresh boot publishes no running/complete transition. Completion announcements clear after
  four seconds, like the back-online notice, before later notices can repeat them.
- Only coordinator bundle requests use fail-fast `backgroundRead`, `session: false` and their
  own abort signal. Foreground editor reads join an in-flight coordinator request for the same
  scope, restarting independently after cancellation or a background 401 to retain session
  renewal/replay. Independent foreground reads omit unused scanning mappings and coalesce
  with each other; access-classified failures fall back to device data.
  A background 401 expires only its current token and never waits or replays. Session renewal
  schedules a fresh batch. Canceling a download cannot cancel an editor's device fallback.
- Bundle-backed cards and reasons have separate scoped query keys. The editor and picker use
  the same bundle scope, so refetches keep device fallback and never replace Issue/Unpack cards
  with stripped products. Opening Adjustments before Unpack preserves kit children.
- An accepted online Adjustment requests a coordinator refresh for that facility/program,
  marks its bundle `stale: true` under the download lock, preserving its downloaded time, and
  downloads it immediately in the background.
  Navigation does not wait; failed refresh retains the old stale bundle and offers Retry.
  Stale bundles remain usable offline; the program list shows Needs Refresh with the last
  downloaded time.
  A refresh requested during a running batch is queued so older in-flight stock cannot satisfy it.
- Each timed-out read gets at most one retry. The global 60-second timeout is unchanged;
  stage 1 measurements do not justify raising it. No-response connection failures stop the
  remaining batch even if the browser still reports online. ECONNABORTED reports a timeout,
  retains prior complete data and offers Retry without changing connection state.
- This pass adds a nullable event-kind download policy for Adjustments, preserving the other
  kinds' query paths. It does not add draft persistence or sidebar/palette capability gates.
- The stage 3 reconnect generation now advances in `online.ts` before Query's reconnect work;
  rights retries after sign-out throw SessionEndedError rather than No Access.

Prefer one complete hydrated bundle per program in this spike. It matches the selected
screen's reads, avoids a general cache framework and commits readiness atomically. Measure
duplication across programs before choosing normalized shared product tables for later work.
Keep complete editor DTOs, not every server field; record the exact whitelist in implementation.

Draft autosave compares the stored revision with the editor's expected revision inside the
write transaction, then increments it. Enqueue, Clear and Discard check that revision too.
A mismatch stops writes and says "This draft was edited in another tab"; offer to load the
stored draft or keep the current edits as a separate archived copy, never overwrite silently.
Opening a saved copy for editing explicitly replaces the active draft while archiving that draft.
Local subscriptions invalidate readers but cannot replace unsaved edits. Serial autosave alone
does not prevent two-tab overwrites. Submit flushes, validates and collects signature, then
atomically stores the final revision and immutable queue entry. Show success only after commit;
disable repeat confirmation while pending and guard localEventId uniqueness.

Submitted revisions cannot be edited while queued/sending/uncertain. Further work starts a
different local draft. A refused event may be copied for correction into a new revision after
explicit review, retaining the refused original. Only a matching accepted revision can mark
that event synced; an older response cannot mark a newer draft synced.

No API calls run inside Dexie transactions. IndexedDB can commit when unrelated async work
is awaited, as described by [Dexie transactions](https://dexie.org/docs/Dexie/Dexie.transaction()).
Keep network work between short durable state transitions.

### Read And Download Flow

1. Successful sign-in establishes identity and returns immediately. A shell-level coordinator
   observes first login, same-user renewal, borrowed sessions, boot with a restored valid
   session and reconnect. It schedules work without awaiting login, route loading or navigation.
   Sign-in/renewal/borrowed-session change and reconnect refresh access and permitted bundles;
   valid-session boot refreshes missing or stale copies. Explicit Retry targets failed scopes.
2. Take a per-database offline-download Web Lock for the whole bootstrap/download batch,
   separate from the upload lock. Other tabs observe progress/completion instead of duplicating
   it. Under the lock recheck durable generations and skip work completed by another tab for
   this trigger. Only the bootstrap writer commits offlineAccess. Then download permitted home
   programs with bounded concurrency through the shared bundle helper. Foreground queries coalesce
   independently of abortable coordinator reads; neither can write a partial bundle or bypass
   download ownership.
   Start the sidebar spinner with the batch, not per route. Unsupported locks disable this
   download path with an explanation; ordinary online queries still work. The bundle helper
   still serves online reads without the lock, without persisting offline bundles.
3. Publish each program as ready only after its full bundle commits. Successful programs stay
   usable if another fails. Keep the prior complete generation during refresh; show its age.
   Finish the batch as complete or partial failure and report failed scopes with Retry.
   Stop/pause on connection loss or session expiry, with incomplete scopes explained. Do not
   leave a fetch spinner running indefinitely while a request waits for another sign-in.
4. Adjustment queries use the bundle helper online and Dexie offline. Access queries use their
   own online readers and the single coordinator-written offlineAccess snapshot offline.
   Query remains a memory cache; no individual access query persists partial bootstrap data.
   Access reads may fall back after no-response failures, ECONNABORTED timeouts or 502/503/504
   without a JSON error body. Treat parsed JSON objects conservatively as definitive service
   errors, including gateway statuses. Cancellation and service 400/401/403/404/500 never fall
   back. Local absence still means "Connect To Download This Data". Explicit 401 follows renewal;
   explicit 403 does not use an old grant or server copy.
5. Permissions queries reconstruct parsed rights/grants from `offlineAccess`; reference-data
   queries read that snapshot for user, home facility and programs. Validate owner and scope
   after every await. Empty permission strings mean no rights, not a fetch failure.
6. On offline boot, the protected identity gate and exact grant/facility/program checks can
   block briefly on local reads. Bulk stock/reason work remains deferred behind QueryBoundary.
   The header, toolbar and sidebar remain usable while data loads.
7. Missing snapshot/bundle throws a typed local-unavailable error. Extend existing offline
   failure handling to recognize it. It ends in "Connect To Download This Data", never a
   server 404, No Access caused by missing data, or endless suspense. Actual denied access
   still shows No Access. Do not use an empty array as a missing-bundle substitute.
8. Subscribe to committed local draft/queue changes and update/invalidate relevant Query keys.
   Reconstruct them from Dexie after restart. Reuse userRightsKey and existing user, program,
   facility, validReasons and eventStockCards keys; add local-event keys through key-factory.

Access snapshots and program bundles become stale 30 minutes after fetchedAt. A committed
bundle remains available offline at any age, visibly dated; staleness triggers a background
refresh when connected, not deletion or a local editing ban. Boot reuses younger complete data.
Reconnect/renewal forces refresh even for young data; accepted uploads mark that scope stale
and refresh it immediately. Offline rights describe last-known access, not current server grants.

Handle ECONNABORTED as a timed-out download, with bounded read retries, a stopped spinner and
Retry, not as proof the device is offline. Retain prior complete generations and explain missing
ones. Keep the 60-second default initially; measure every large-facility request against it.
If readings exceed it, set a measured finite timeout for these reads only and record the reason;
do not raise the global timeout or leave session waits running indefinitely.

Use `networkMode: 'always'` for local reads so Query runs them offline rather than pausing them.
This matches the app and [TanStack network modes][query-network].
Do not install a Query persister, persist paused Query mutations, or cache API responses in
the service worker. App assets, runtime config and catalogs already have their worker policy.

Page/size/keyword remain in the URL through the existing schemas. Drafts, queue entries,
credentials and record payloads stay out of it. Offline search, paging, packs/doses and
column choices operate on the complete local bundle and editor lines.

### Upload Flow, Order And Unknown Results

One app-level coordinator wakes after boot, sign-in/renewal, a committed enqueue and reconnect.
It sends only when connected and the same user's session is valid. It awaits a fresh bootstrap
snapshot before upload after reconnection/renewal; removed or empty grants leave events queued
and pause only their scope with an access-changed notice until rights return or unsent events
are removed. Only a definitive server answer creates a refusal.
Connection state is a hint, not proof of API reachability.

Use a per-database Web Lock for one uploader across tabs. Another tab observes local changes
and status without uploading. An unsupported lock implementation fails closed for automatic
sync and reports that limitation; do not use a timeout lease that lets a second POST start
while the first may still run. Validate support in the browser targets before rollout.
See [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).

For the oldest eligible sequence whose facility/program is not blocked by uncertainty:

1. Capture owner, database and session scope; check all before every request and completion.
   In a transaction change queued to sending with attempt id, start time and frozen POST body.
2. Send one POST outside the transaction with a typed queue transport policy. Its request
   interceptor rejects an expired/mismatched session before dispatch with a not-sent error;
   it never waits for renewal. Its response interceptor never replays 401. Preserve identity
   checks and expire the refused session as needed. All mutation retries remain off; never
   use session: false. A SessionEndedError alone does not establish whether dispatch happened.
3. On verified 201 with event UUID, atomically store the receipt, mark its exact revision
   accepted, and remove the queue row. Then show "Synced" and refresh stock data.
4. On definitive non-commit refusal, atomically store the full event/error, mark the draft
   refused, and remove only the queue row. Continue with later events in sequence, as legacy.
5. On service JSON/OAuth 401, atomically return the row to queued, pause and renew the same
   user. After fresh grants permit one resend with the same frozen body. A further
   refusal pauses again; no automatic retry loop. An unrecognized/gateway 401 is uncertain.
6. A typed pre-dispatch not-sent error returns the row to queued; pause for session errors.
   Session errors after dispatch, including a scope check throwing after 201, are uncertain
   unless its UUID can be safely recorded for the original owner. Timeout, lost connection,
   abort, proxy failure, 5xx or unrecognized response are uncertain. A crash with a sending
   row is uncertain on restart; without durable proof of no dispatch, never downgrade it.
7. Keep the uncertain row and explanation and stop later events for that facility/program,
   including connected Submits. Other scopes remain eligible in sequence order. One POST runs
   at a time across the database. Reconnect/restart obey the same durable scope barrier.
   Resolution uses the flow below; no unresolved event is silently bypassed within its scope.

Safe retry rules are explicit:

| Situation | Safe Action |
|---|---|
| GET lookup failed | Retry the read with bounded backoff |
| Local enqueue failed | Retry local storage; no POST was started |
| Queued or typed pre-dispatch not-sent | Send once when connection/session allow |
| Service JSON/OAuth 401 | Renew same user, check grants, resend once; no interceptor replay |
| Service JSON 400/403/404 | Definitive refusal; retain original; correct explicitly |
| Negative-stock service 400 | "Stock changed" refusal; refresh and review correction |
| Gateway HTML/unrecognized 401/4xx | Uncertain; status alone cannot prove non-commit |
| Timeout/lost answer/502/504/other 5xx | Uncertain; user resolves; no automatic resend |
| Crash sending or session error after dispatch | Uncertain unless original receipt is recorded |
| 201 recorded in Dexie | Never resend; refresh reads independently |
| 201 received but receipt commit failed | Hold attempt; retry receipt write, never POST |

Keep a received UUID in memory while retrying only its receipt transaction. A failed write
never leads to another POST. After a crash before receipt commit, the attempt stays uncertain.
A known UUID can be verified through the existing event/detail reads if rights permit.

Unknown results stay on the device until the original user resolves them in the app. There
is no automatic resend or match by quantities, stock balance or the normal document number.
An empty history search or elapsed time does not prove that the original upload failed; its
server transaction may still be running. Keep the facility/program barrier until a user choice.

The pending events page (FM-168) shows the full event details, attempted time, uncertainty and
blocked facility/program. Link to the matching Stock Card(s) for its product/lot lines and to
Transaction History for that facility/program. These are online reads, subject to current
STOCK_CARDS_VIEW. The spike may ship a minimal version of this view before FM-168 exists.
The sidebar's "Review Device Events" action opens it. The user checks history, then chooses:

- "It Was Recorded": atomically mark the exact revision as sent, store a user-confirmed
  receipt and decision audit, remove the uncertain queue row and mark any linked error resolved.
  Release the scope barrier and refresh stock reads when connected. No POST is sent.
- "Send Again": first show the duplicate-event confirmation described in UI/UX. Only explicit
  confirmation atomically returns the same immutable event and revision to queued, preserves
  its sequence and archives the uncertain attempt and decision in the draft's history. Mark
  any linked error resolved without deleting it. Release
  its scope barrier; the worker starts one new attempt when connection/session/grants allow.
  Cancel leaves it uncertain. The previous attempt is not claimed to have failed.

Both transitions check owner, exact revision and current uncertain status inside the local
transaction. Record who chose, when and which action. Repeated or stale clicks cannot enqueue
another copy. User decisions are retained with the original; they are not proof of server state.
Automatic boot/reconnect/session renewal never authorizes a resend of an uncertain attempt.

STOCK_ADJUST does not imply STOCK_CARDS_VIEW. Users without current viewing rights still get
both choices and the duplicate warning, with an explanation that they cannot check history
themselves. Do not call or bypass protected history endpoints, infer rejection from 403 or
expose another user's records. They may ask someone with access to check before choosing.

Successful upload and subsequent download are separate. A failed refresh does not turn an
accepted event back into pending. Mark its bundle stale and retry only reads. Download refresh
never overwrites a local draft. Do not optimistically rewrite authoritative stock summaries;
show pending work and stale stock distinctly until the server copy is refreshed.

### Session And Identity Rules

Persist permission strings and required identity records in Dexie, not localStorage. The
existing session store remains the source of identity and tokens. FM-166's localStorage rule
applies to offline business data, not a new redesign of existing credentials/preferences.

First sign-in requires a connection. A previously authenticated, still locally known user
may use downloaded data and save locally while offline. Cached rights are for device access,
not proof that the server will still permit an upload. Explain their age when offline.

Auth defaults to a 1800-second sliding lifetime: every valid server use extends it, offline
time does not. TOKEN_DURATION can override that value. After about 30 minutes offline, a
password before sync and "Sign In To Sync" are the normal reconnect case, not an edge case.
Keep the app's rule that an actual 401 establishes expiry; expiresAt is only an earliest bound.

Use the existing same-user renewal dialog when connected. While known offline, show "Sign In
To Sync" in the sidebar and permit local editing instead of a blocking login dialog. A failed
renewal connection offers continuation offline. Uploads stay paused; no token guessing or
offline password authentication. The expiry time is not a sign-out timer; actual 401 decides.

Observe identity changes from own login, other tabs and borrowed legacy sessions. Stop old
work, close the old database, clear memory/query data and rerun route gates. Scope checks
remain before/after asynchronous work. An already-dispatched POST might finish for the old
user; its result cannot update the new user's page/database. A result not durably recorded
in the old database remains uncertain when that owner next returns.

Before deliberate logout, flush the current draft and count unsynced drafts, queued/sending
events, uncertain outcomes and unresolved refusals. Warn even while online, combine with the
existing offline-sign-out warning, and allow staying signed in. A failed flush must be shown
before leaving. Confirmed logout ends access but retains all device records for that user.
External identity changes cannot prompt first; they still must not erase committed drafts.

This warning and pause-on-expiry retention deliberately fix legacy's destructive sign-out/401.

### Business Rules And Server-Side Work

Preserve [FM-66](FM-66.md#rules) and existing meaningful validation tests: Adjustment reasons
only, valid visible assignments, required free text, valid non-future occurred dates, whole
nonnegative quantities, pack conversion, debit cap, VVM policy and signature confirmation.
Keep validation/focus for hidden or paged lines. New lots are not an Adjustment capability.

with a branch-only shortcut. Do not download the full approved catalog or full card histories
for Adjustments. Sources, destinations and fulfills join the download for later workflows.

### Risks And Edge Cases

- Master has no idempotency. Unknown outcomes block only their facility/program until the user
  resolves them. Explicit "Send Again" may apply the Adjustment twice; warn before confirming.

  movements. Master rolls back the whole event. Stale debits still within stock are accepted,
  without broader snapshot conflict checks; offline balances alone cannot reconcile devices.
- A copied reference snapshot can have revoked rights or outdated reasons/products/lots.
  Check fresh rights before upload and preserve refusal details without losing the event.
- The existing nondismissible expiry dialog would block offline editing. Change that narrow
  interaction with identity tests rather than bypassing the session mechanism.
- A crash after acceptance before receipt commit needs user review. Empty history cannot prove
  non-application. Without viewing rights, explain that the user cannot check it themselves.
- Database upgrades, blocked tabs, quota, private mode, browser eviction and device loss can
  interrupt storage. Show errors and retain committed data; never pretend a write succeeded.
- Background downloads can be slow even with few records. Cap concurrency, allow cancellation
  on identity change, measure the 60-second timeout and retain per-program completion. Boot,
  reconnect and two-tab coordination must refresh stale copies without blocking navigation.
- Do not run automatic POST retry through HTTP interceptors, Query, a worker or a second tab.

## Decisions

1. **Adjustments is the proof screen.** It is migrated, has the simplest stock payload and
   exercises scoped access, stock/reference downloads and a real non-idempotent write.
2. **Move Adjustments and Unpack to the shared page first.** Remove both duplicate wrappers
   through print-policy composition. Preserve Unpack's existing online behavior and reason ids.
   Issue/Receive use offline behavior only after their downloads and tests exist.
3. **Dexie is the one durable store.** Query remains disposable memory. Persisting Query too
   would duplicate records, obscure completeness/age, and still need separate transactions
   for drafts, revisions, queue attempts and errors. Dexie gives those records explicit owners
   and atomic transitions. Do not add Query cache persistence or worker API caching.
4. **Download at sign-in without blocking.** Commit complete per-program snapshots and report
   failures in the sidebar. The coordinator alone writes access snapshots. Also refresh on
   valid-session boot/reconnect; stale means 30 minutes. One download Web Lock covers the batch.
5. **Preserve local work on conflicts/refusals.** Never overwrite or merge a signed local event
   with a refreshed server copy. Keep refused payloads and actual reasons; correct explicitly.
   Negative balances at or after occurredDate roll back the event with a definitive stock-changed
   400. Stale debits within stock pass; there is no wider conflict/version check.
6. **Pause on session expiry.** Preserve the known user, draft and queue; request same-user
   sign-in, normally after about 30 minutes offline. Offline expiry cannot block local editing.
   Logout warns and retains work; both rules fix legacy loss. Another user cannot resume it.
7. **No blind retry of uncertain stock uploads.** Sending state precedes dispatch, accepted
   state follows the server answer and local receipt commit. Unknown outcomes are durable
   facility/program barriers until the user resolves them. Queue transport neither waits nor
   replays; typed not-sent failures return to queued. GET and definitive refusals differ.
8. **One uploader and ordered events.** Use a database-scoped Web Lock, one event at a time.
   Definitive refusals move to errors; unknown results stop later events only in their scope.
9. **No silent stock projection.** Keep downloaded stock marked with its age and pending work
   separate. Refresh after acceptance; do not present a local guess as authoritative stock.
10. **Measure the selected bundle before sizing.** Current size is unmeasured. Essential Meds'
    roughly 10 MB full catalog is context for later Receive, not the spike's claimed footprint.
11. **Keep the three FM-167 user decisions fixed.** PI's local count behavior, background
    download status and inline typed Receive lots remain the baseline for later offline work.
12. **Merge the complete spike together.** All stages stay on this branch, independently
    reviewable but merged only when sync/recovery and online submission work. No flag is added.
13. **Compare draft revisions before writes.** Autosave/enqueue/discard cannot overwrite another
    tab's changes. Preserve both revisions with an explicit load/copy choice on conflict.
14. **Keep normal document numbers, as legacy does (2026-10-13).** Omit documentNumber online
    and offline; the server assigns its usual per-facility sequence. No client marker or unique
    number is added. This preserves legacy parity and leaves visible numbers unchanged.
15. **The user resolves unknown results in the app (2026-10-13).** FM-168 shows event details
    and Stock Card/Transaction History links. The user chooses It Was Recorded or Send Again,
    with a duplicate warning before resend. Both choices remain without STOCK_CARDS_VIEW.
    Ship a minimal view in the spike if FM-168 is not ready, so recovery is usable at release.
16. **Read-only measurement fixture (2026-10-13).** Use test.openlmis.org as administrator,
    Comfort Health Clinic, Family Planning and Essential Meds. Never submit events during
    measurement; this gives a repeatable baseline without changing stock.
17. **Browser targets (2026-10-13).** Current Chrome, Edge, Firefox and Safari support Web Locks
    and are the targets for offline download and sync. Without Web Locks, disable both with
    an explanation; the helper still serves online reads. This keeps online use available
    while avoiding competing download writers or uploaders.
18. **Retention (2026-10-13).** Keep accepted receipts 30 days, then prune them to limit growth.
    Never delete archived/refused drafts or sync errors without the user's choice. Receipt
    cleanup preserves accepted draft state; pending/uncertain work remains until resolved.
