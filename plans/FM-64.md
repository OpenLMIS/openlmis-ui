# FM-64: Issue

https://openlmis.atlassian.net/browse/FM-64 · Parent: [FM-62](https://openlmis.atlassian.net/browse/FM-62) Stock management

## Scope

The Issue screen for one program at the user's home facility, and its page on the shared stock
program picker ([FM-63](https://openlmis.atlassian.net/browse/FM-63)). It builds on Adjustments
([FM-66](https://openlmis.atlassian.net/browse/FM-66), `plans/FM-66.md`): the editor, line table,
form rules and scanning take an event kind. Receive
([FM-65](https://openlmis.atlassian.net/browse/FM-65)) can reuse the editor when its own rules are built.

Not in this PR:

- Receive's screen and its valid sources lookup (FM-65).
- Offline: legacy queues an issue submitted offline. That comes with the offline pass (FM-166,
  FM-168); FM-64 stays open until it ships.

## Summary

An issue records stock leaving the facility for another place: a health facility it supplies, or
an organisation such as community health workers. The storeroom manager picks a program, adds the
products and lots being sent, says where each goes, how much and when, optionally gives a reason,
and submits them together after signing.

It works like Adjustments, which is already in the new UI, with these differences, all as legacy:

- Each line has **Issue To**, picked from the places this facility may issue to for the program,
  and **Destination Comments** when that place allows them (organisations do, facilities do not).
- The reason is optional and lists only transfer reasons that remove stock ("Transfer Out" on test).
- Only stock that can actually be issued is offered: no lots with zero stock, no expired lots.
- After submitting, legacy offers to print the issue report; the new screen does too.

What changes for users: the page and its table show at once while the product list loads (as slow
as legacy's for a program with thousands of approved products, since it uses the same list so the
same products are offered), a quantity above stock on hand is always refused with a clear message (legacy skips that check when no reason is
picked), typed decimals, negatives and future dates get a message, and one screen works on desktop,
tablet and phone. Barcode scanning works as on Adjustments where it is turned on.

## Legacy Today

Evidence: `.screenshots/FM-64/research-a-findings.md` (browser), legacy source snapshots under
`.screenshots/FM-64/openlmis-stockmanagement-ui/`, `legacy-a-network.json`. Adjustment's live
findings in `plans/FM-66.md` apply where the template is shared.

Test data on 2026-10-09: `srmanager2` and `administrator` hold `STOCK_ADJUST` and
`STOCK_CARDS_VIEW` at Comfort Health Clinic for Essential Meds and Family Planning. Both programs
list Balaka District Hospital and CHW as destinations and Transfer Out as the only issue reason;
Essential Meds has 2 issuable cards of 6, Family Planning 3 of 4.

- **Routes:** picker `/#!/stockmanagement/issue` ("Issue for Comfort Health Clinic", Program and
  Action columns, "Make Issue"); editor `/#!/stockmanagement/issue/{programId}/create?page&size&keyword`,
  title "HC01 - Comfort Health Clinic - Essential Meds". Right `STOCK_ADJUST`. Phone routes
  `issueMobile/*` are a separate flow opened by URL.
- **Same template as Adjustments**, plus Issue To and Destination Comments after Stock On Hand.
- **Products offered:** cards with stock on hand other than zero (`!== 0`, so a negative card stays),
  then lots expiring today or later; lots with no expiry and no-lot cards stay. Issue never creates a
  lot. Kits are not unpacked on issue. The Product and Lot selects are required, so the shared
  `select-one-option` directive picks a sole option for the user.
- **Columns:** Lot Code and Expiry Date show when some offered product has lots; VVM Status when
  some offered product uses VVM; both worked out after the issuable filter.
- **Issue To:** a required (by validation, not the `required` attribute, so never auto-picked) select of `GET /validDestinations?programId&facilityId` (on test, for
  both programs: Balaka District Hospital, a facility, and CHW, an organisation). Destination
  Comments appear only when the destination allows free text, up to 255 characters, cleared when
  Issue To changes.
- **Reason:** optional; non-hidden `DEBIT` reasons of category `TRANSFER` (only Transfer Out on
  test, which allows comments). Its "Select an option" placeholder stays selectable, so a picked
  reason can be cleared. A deployment build constant, `DEFAULT_ISSUE_REASON_ID`, can preselect
  one and make it required.
- **Line defaults:** Add prepends the line and copies Issue To, Destination Comments, reason, reason
  comments and date from the most recently added line as it is **now**: legacy keeps a live reference
  (`previousAdded = vm.addedLineItems[0]`, controller `:212,218-235`), so edits made to that line
  after adding it carry over, even once it is removed. The reason falls back to the default reason
  when that line has none (`:232`), and the date to today when that line's date is empty (`:218-224`).
- **Quantity:** at least 1, at most the Java int maximum; the stock on hand check runs only when a
  debit reason is picked, so a line with no reason reaches the server unchecked.
- **Clear:** "Are you sure you want to clear? This will remove all products and quantities.", then
  removes the lines the filter shows.
- **Submit:** validates every line; the signature dialog is the confirmation; success shows "Stock
  issue event has successfully been submitted", then "Print the stock issue report?" (Print, No);
  Print opens `GET /stockEvents/{id}/print?lang` in a new tab; then Stock On Hand for the facility
  and program. Failure shows the server's message and keeps the lines.
- **Server:** accepts a zero quantity, and decides each line's type from its fields, not from
  `eventOrigin`: a line with no destination and no reason is a physical count that **sets** stock on
  hand to the quantity, and one with Transfer Out but no destination a debit adjustment
  (`StockCardLineItem.isPhysicalInventory`, `StockEventDto.isPhysicalInventory`). So Issue To being
  required protects the data, not just parity. It refuses a destination not assigned to the program
  and facility type, destination comments on a facility destination (even an empty string, the check
  is `!= null`), reason comments without a free-text reason, a reason that is not `DEBIT`/`TRANSFER`,
  and stock below zero at any point of the card's history (recalculated in date order).
- **Phone flow:** loads every product, then reasons, then destinations before showing anything; no
  expired-lot filter, no signature, no print.

### Data Flow

- **Routes:** `/stock-management/issue` (picker) and `/stock-management/issue/$programId`, search
  `page`, `size`, `keyword`, as Adjustments.
- **Loader** as Adjustments: loads `requirePermissions(RIGHTS.stockAdjust)` and the user record
  in parallel, then blocks on the home facility, the exact grant and the supported program;
  prefetches, deferred, stock cards, destinations and reasons, side by side.
- **Destinations** `validDestinationsOptions({ programId, facilityId })` in `reference-data`, every
  page of 100, keyed `[...queryKeys.validDestinations.all, 'lookup', filter]` so the Valid
  Destinations admin screen's saves refresh it and its `list` keys never collide. It duplicates the
  admin features' one-page fetchers on purpose, since a feature cannot import another.
  `fetchValidAssignments` reads valid destinations only; valid sources belong to FM-65.
- **Draft, filter, paging, submit** exactly as Adjustments, through the generalised editor. The table
  waits inside nested boundaries: reasons first, then destinations. Submit, Add and scanning
  wait for lookup data, and remain usable if a background refetch fails with cached data.
- **Stock list:** `fetchEventStockCards` moves from v1 to legacy's v2 list for every kind, Adjustments
  included, so both offer exactly legacy's products: `GET /v2/stockCardSummaries?nonEmptyOnly=true`,
  then the cards' products and lots by id, built into the same `EventStockCard` shape, so the picker,
  lines and scan code do not change. The query key stays, and the loader still prefetches it
  deferred.
- **Offered cards:** `ProductLotPicker` reads its own cards, so it takes the kind's card filter
  (`issuableCards` for Issue), and so does the scan resolver's `products`. The picker picks a sole
  product or lot option, as legacy's required selects do; that fixes the same gap on Adjustments.
  Lot Code renders only after a product with lots is picked; before a pick, only Product and Add
  appear. Products without lots keep Lot Code hidden and remain addable in both editors.
- **Columns:** Lot Code and Expiry Date show when some offered card has a lot, VVM Status when some
  offered card uses VVM, as legacy. Draft lines also keep these columns visible when refreshed
  stock no longer offers their lots or VVM products, on both Issue and Adjustments.
- **Line defaults:** taken from the current values of the most recently added line, which the editor
  keeps in `event-editor.tsx`, covered by `event-editor.test.tsx`. Two legacy fallbacks are added: the reason falls back to the default reason, and an empty
  date to today (`previousLine.occurredDate || today`); the second also fixes Adjustments, whose
  test expecting an empty date changes.
- **Adding waits for reasons and destinations**: Add and scanning stay off until both have loaded, so
  every line gets the default reason, as legacy resolves them before the screen opens.
- **After submit:** the draft counts as clean for every way of leaving (a `submitted` state fed to
  `useDiscardGuard`, not only `allowLeave`), so neither reload nor sign-out prompts while the Print
  question is open; a failed submit keeps it dirty.
- **Scan expiry mismatch:** asked once per batch (lot id, else lot code) until the page reloads, as
  legacy's `stock-scan.service.js:160-172`, kept in a module store in `src/lib/` and cleared when the
  user changes; Adjustments asks per scanned date and forgets on leaving, which this fixes too.
- **After submit:** success toast, then the Print dialog (the editor calls `onSubmitted(eventId)`, and
  the route owns `usePrintReport`, which imports auth, while the feature's dialog only renders); Print opens the PDF in the page's language
  and always in doses (`showInDoses=true`), as legacy sends no unit and the server defaults to doses;
  either answer goes to Stock On Hand.
- **Default reason:** `defaultIssueReasonId` in `config.json`, through `src/lib/runtime-config.ts`
  (`DEFAULT_ISSUE_REASON_ID` in the docker template, entrypoint and compose), as legacy's build
  variable. When it names a listed issue reason, a new line starts with it and the reason becomes
  required; unset or absent from the listed issue reasons, the reason is optional and starts empty.

### Risks And Edge Cases

- **No destinations configured** for a program: Issue To is empty and Submit cannot pass; the
  editor says no destinations are set up and to contact an administrator.
- **Slow product list:** on a program with thousands of approved products the Add Product panel waits
  as long as legacy's screen does; its skeleton retains the Product label and announces loading
  only to screen readers. Clear, Keywords and the empty table stay usable. A timeout or failure shows the cards error with retry, as now.
- **Geography:** when the first line has a destination, the server checks every line's destination
  against the same list `GET /validDestinations` returns; the UI offers only that list, so a refusal
  means it changed after loading and shows as the server's message.
- **Stock cap limits:** the per-line cap checks today's stock on hand. Two lines of one lot that
  together exceed it, or a backdated issue that dips below zero before a later receipt, pass in the
  browser and are refused by the server with its message, as in legacy.
- **Print dialog:** the discard guard is already released (the lines are submitted) while it is open;
  a user change behind it remounts the page as anywhere else.
- **Renaming Adjustment's files** touches merged code: Adjustment's tests must pass after the rename
  and before Issue is added; only the parity fixes change its tests, on purpose.

## Decisions

- **Logic follows legacy exactly**: which products and lots are offered, which reasons and
  destinations, what is required, line defaults, Clear, the payload, Print and the landing. The UI
  improves (filters, layout, messages, focus), the rules do not change. The two exceptions are below
  and were agreed on 2026-10-09. Legacy rules the shared editor missed are restored for Adjustments
  too: an empty date on the last line defaults the next to today, a sole product or lot is picked,
  lot and VVM columns follow the offered cards, and a scanned expiry mismatch is asked once per
  batch.

- **Legacy's v2 stock list, not v1**, for Issue and Adjustments, agreed on 2026-10-09: v1 lists every
  card at the facility, so it could offer stock of a product no longer approved there, which legacy
  never offers. The price is legacy's wait on large programs (17 to 22 s for Essential Meds on test),
  so the ticket's "a few seconds" holds only for smaller programs; the rest of the page never waits.
- **One editor for every event kind**, configured by kind, rather than a copy per screen: Issue
  now, Receive next, Kit Unpack later.
- **Stock on hand cap on every Issue line**, as the ticket asks, rather than legacy's reason-only
  check. The server refuses stock below zero either way; the user just sees it on the line before
  signing. Cases only the whole card's history shows stay with the server, as in legacy.
- **Invalid Submit opens an AlertDialog**, as Reverse and legacy do, with the existing invalid
  title and description. Closing it focuses the first invalid field on its page, clearing a filter
  that hides it. Lines keep their order. Every inline field hides error text, retains its red
  highlight and accessible description, and shows its error on hover or keyboard focus in a Tooltip
  without adding tab stops. Server failures use the same dialog, retaining unknown-outcome wording
  and the draft; closing them returns focus to Submit.
- **Clear removes the lines the filter shows**, as legacy and Adjustments, with the count in the
  confirmation; with no filter that is every line, which meets the ticket's intent.
- **Print after submit is ported**, though the ticket does not mention it, since legacy users rely on
  the issue report.
- **Barcode scanning in scope** behind `GS1_SCANNING`, matching only issuable stock.
- **Layout**: Issue uses the full content area and an aligned sticky footer; Adjustments keeps
  its default width. At or above 672px, lower-priority columns hide by measured fit and the
  rest scrolls inside the table. Below 672px of measured content width, lines use cards
  (user, 2026-10-19), replacing the earlier sideways-scrolling phone table. Program pickers
  also use cards, with the program and action in the band. Line bands hold the product label
  and Remove; read-only rows retain lot wording and stock values, editable rows centre their
  controls, Quantity included (`[Packs] + [Doses]` in Packs), with Total Quantity after it. Pending views use
  an empty card list. Closing invalid Submit scrolls the card into view before field focus.
- **The real submit check runs on test.openlmis.org**, one issue, as `srmanager2`.

## Final Editor Decisions

- Invalid Submit and server failures open an AlertDialog. Closing validation focuses the first
  invalid field on its page; closing a server failure returns focus to Submit. An unknown-outcome
  failure also retains an inline warning until another submission starts or the user leaves.
- Inline fields keep accessible error descriptions and show error tooltips on hover or focus,
  without adding tab stops. Quantity inputs preserve typed text through unit changes, including
  an empty Packs value on single-dose lines.
- Issue quantity inputs fill their cell. Each Packs input keeps its own translated placeholder
  minimum; only spare width is shared equally, with 0.25rem gaps around the punctuation.
  A hidden character-unit header sizer uses only translated placeholders with room for at least five
  digits. Inline-size containment prevents typed values from widening the column. Adjustments
  fills its cells while retaining the existing column minimums and visibility thresholds.
- Comment textareas, date triggers and VVM selects fill their cells with fixed minimums and
  inline-size containment. Hidden header sizers retain destination and reason column minimums.
  Issue date sizers reserve the widest formatted month with a two-digit day in the page language;
  Adjustments retains its existing date minimum.
  Comment textareas wrap. Product names are the only truncated content;
  a focused name retains its trigger until blur if a resize makes it fit.
- The fit observer follows table remounts. No-match views retain fitted visibility, while language,
  unit, fit-content and container-width changes discard obsolete measured column widths. Automatic
  visibility recalculates when matching rows return.
- Stock-card failures show an empty table or card list without a loading announcement.
  Pending editors reuse
  cached facility and program names when available.
- Existing translated quantity, validation, failure and Close keys cover all five locales.
- Compact selects and inputs keep master's font, padding and gap, so Reverse Transaction is
  unchanged. Destination and reason selects fill their column, which reserves its widest option
  through hidden, aria-hidden text; long Adjustment reasons wrap within the existing column.
- At or above 672px, Issue keeps the app's compact cell padding. Measured fit hides optional
  columns while the row overflows; English fits at 1600px in both units. Tables scroll sideways
  only once every optional column is hidden. Below 672px, measured fit gives way to cards.
