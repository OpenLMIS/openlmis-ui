## Summary

View Requisitions lets anyone allowed to see requisitions find them by facility. In legacy the
user picks a facility (only those they have rights for), presses Search, and gets a paged table of
that facility's requisitions, newest first. A Filter button narrows the list by program, status
and the date the requisition was started. Each row opens the requisition.

The new page works the same way and keeps every column, filter and message. It adds a clear
prompt before the first search, keeps the search in the address so reload and Back return to the
same results, lets Date Initiated sort both ways, and shows cards instead of a sideways-scrolling
table on phones. Opening a requisition the user may not see explains why on its own page instead
of an error popup over the list.

## Legacy Today

Route `requisitions.search`, `/#!/requisitions/view?facility&program&initiatedDateFrom&
initiatedDateTo&requisitionStatus&offline&sort&page&size`. Entry guard: a role with
`REQUISITION_VIEW` and a home facility, or a supervision role with VIEW
(`permission.service.js:331-351`). Screenshots: `.screenshots/FM-39/legacy/final-search-facility-*`,
`final-srmanager2-search-filters-*`, `verified-admin-req-search-*`, `divo1-search-*`.

- A required, searchable Facility select and Search sit on the start side. Before any search the
  table says "No requisitions found" / "Showing no items". "No facilities found" when the user has
  none.
- Facility options: facilities of the user's `REQUISITION_VIEW` permission strings first, then the
  member facilities of requisition groups whose nodes this user's VIEW nodes are partners of;
  de-duplicated by id keeping the first, sorted by name ignoring case, cached until logout.
  srmanager2 sees Comfort only, srmanager4 Kankao only, divo1 17 EPI facilities, administrator and
  psupervisor long lists. On test the only partner-node user is `chaz` (VIEW role at
  SN-CHAZ-LILONGWE-DIST-1.1, no VIEW permission strings).
- Sorted By with one choice, Date Initiated (`createdDate,desc`). The server honours both
  directions; without `sort` it returns oldest first.
- Filter popover: Program (the drafted facility's programs; "There are no programs for this
  facility. Please contact the Admin." when it has none), Status ("Select status", then Initiated,
  Rejected, Submitted, Authorized, In approval, Approved, Released, Released without order,
  Skipped; one value, no All), Offline, Date Initiated From and To, Cancel and Search.
- Columns: Program; Facility (`code - name`); Period; Start date; End date; Date initiated;
  Status; Emergency (tick when true); Offline (tick); Actions (View Requisition, Remove Offline
  Requisition). Ten rows per page.
- View Requisition loads the record twice, then opens Patients when the template has it, else Full
  Supply. Without VIEW for that record the API answers 403, a popup says "You are not authorized to
  perform this action." and the user stays on the list. srmanager2's search returns five records it
  cannot open; administrator gets 403 on the three EPI records its search returns (search matches
  any role at a node, opening needs VIEW).

Known problems: sort direction cannot be changed; a new search keeps the old page number; the
facility list ignores rights changes until logout; programs missing from the user's program list
show as blank options; period dates shift a day west of UTC; an unreadable sideways table on
phones; the 403 popup.

The partner lookups run only when the user holds a supervision role with VIEW; most users stop at
the role check. Unknown params return 400 and unknown sort keys 500, so the page sends only these.

### Rights

- New `src/features/auth/lib/requisition-access.ts`: `canViewRequisitions(permissions, user,
  roles)` is true for any `REQUISITION_VIEW` grant or a role assignment with a supervisory node
  whose role holds VIEW, as legacy's guard. `requireRequisitionView(queryClient)` awaits
  permissions, user record and roles and throws `ForbiddenError` otherwise; it returns them for
  the loaders.
- `NAV_RIGHTS` (`src/lib/nav-rights.ts`) for `/requisitions/view` keeps `REQUISITION_VIEW`.
  `canOpen` in `nav-access.ts` takes only the rights set (used by `useNavGroups` and by
  `useCanOpen`, which `AppBreadcrumbs` calls), so the rights set both hooks pass it counts
  `REQUISITION_VIEW` when the user's supervision roles hold VIEW, read from the same cached user
  record and roles. Sidebar, palette and breadcrumbs therefore agree for partner viewers.

### Data Flow

- Route `src/routes/(protected)/_protected.requisitions.view.tsx`, laid out as the Transaction
  History route. Loader awaits `requireRequisitionView` with the same user-change guard, starts
  `deploymentTimeZoneOptions()` and the picker lookups, and prefetches
  `requisitionSearchOptions(search)` from `loaderDeps` only when `facility` is in the URL, the
  date range is valid and the facility is one of the grant facilities (partner facilities are
  confirmed by the page before its request starts). `pendingComponent` as
  `TransactionHistoryPending`.
- Search params `facility`, `program`, `status`, `initiatedFrom`, `initiatedTo` plus
  `tableSearchSchema` page, size and sort (`createdDate` only, default desc). Names follow legacy's
  facility and program rather than the shared picker's `facilityId`/`programId`, since this
  picker has no program step.
- Picker as the shared one: a draft until Search writes `facility`; the sole option is picked
  automatically (srmanager2, srmanager4); a linked facility the user cannot pick leaves the
  picker blank with no request; a linked program not offered for the facility is dropped.
- Outcomes as `TransactionHistoryOutcome`: no facility shows the pick message, a linked facility
  the user cannot pick the refused message, a draft that differs from the applied facility the
  search-pending message, From after To the date-range message with Clear Dates; each a
  `DataTableEmpty` in a `DataTableCard`, under the toolbar.
- Everything else follows AGENTS.md List Pages.
- Query keys: `queryKeys.requisitions` (new): `list(params)`. Partner lookups stay under
  reference-data's `supervisoryNodes` and `requisitionGroups` keys, so node and group saves
  refresh them.

## Offline

The page is online-only, like Transaction History, and needs no offline code of its own:

- Not registered in `src/routes/-offline-pages.ts`, so `_protected.tsx` refuses direct offline
  entry with Not Available Offline, hides an already-open page behind the shell notice, and the
  nav marks the entry as needing a connection.
- No download provider, Dexie table, `deviceQuery` or `SnapshotAlert`; queries keep the default
  network mode.
- Load failures go only through `ListError`, `LoadError` and `ErrorFallback`, which already use
  `useOfflineFailure`, so reconnect retries follow the shared path.

## Decisions

- Default page size is 20, matching Transaction History's `EVENTS_PAGE_SIZE` override.
  Requests, the pager and skeletons share `REQUISITIONS_PAGE_SIZE`; legacy uses 10.
- An auto-picked or drafted facility shows the Search prompt until applied, rather than asking
  the user to choose the facility again.
- Facility-only picker in the feature, inside the selector's exported frame; the shared
  selector's program step does not fit.
- Partner facilities through `GET requisitionGroups/{id}` per partner group instead of legacy's
  unpaged 5 MB list; same data.
- VIEW access counts supervision roles too, so partner-node users such as `chaz` keep the page.
- The status filter stays single, as legacy.
- Date Initiated sorts both ways; the server supports it, legacy only lacked the control.
- Requisition screens follow the Stock Management design and reuse its components (2026-10-27);
  the row's View button follows Stock On Hand and Transaction History rather than AGENTS.md's
  "..." menu rule.
