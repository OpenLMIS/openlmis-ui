## Summary

After district approvers approve a forecast, the national level gives the final approval. From
the Consolidated Summary a national approver can approve many forecasts at once, or open one to
check it first. This ticket is that second path: one forecast, read-only, with Approve and Reject.

Legacy opens the same read-only form the district approver sees. The only differences are the
Approve call (final approval instead of district approval) and that every way out goes back to
the previous page. Approve and Reject show for any forecast opened by address, whatever its
status, even though the server would then finally approve a rejected or draft forecast. It
downloads every product in the system before showing anything, asks twice before a rejection, and
on a phone the buttons overlap.

The new page is the district approve page with the national actions: it opens only forecasts
waiting for this approver's final approval, checks again just before each decision, asks once
before approving, rejects from one dialog, shows the server's error in place and returns to the
Consolidated Summary with its search, refreshed. It works on a phone and in Arabic.

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Enter | permissions, `GET /users/{id}/programs` | user id | program `code === 'BUQ'` | `MOH_APPROVAL` or `PORALG_APPROVAL` anywhere | `buq.routes.js:184-190` |
| Zones | `GET /bottomUpQuantifications/supervisedGeographicZones` | `programId` | root zone ids | `MOH_APPROVAL` or `PORALG_APPROVAL` | `MOHSearchBuq.jsx` |
| Membership | `GET /bottomUpQuantifications/forFinalApproval` (read fresh on enter and before each decision) | `programId`, `processingPeriodId` (the forecast's), `geographicZoneId` (each root zone) | `bottomUpQuantification.id` | `MOH_APPROVAL` or `PORALG_APPROVAL` | none (legacy opens any id) |
| Forecast and lookups | as FM-105 (`GET /bottomUpQuantifications/{id}`, products by id, facility, remarks, sources, currency, periods) | | as FM-105 | any BUQ right | `useFacilityDemandForecasting.jsx:98-133` |
| Approve | `POST /bottomUpQuantifications/finalApprove` | `id=<id>` in the query, no body (legacy repeats it in a body the server ignores) | the returned forecast (list of one) | `MOH_APPROVAL` or `PORALG_APPROVAL`, unscoped | `FacilityDemandingForecasting.jsx:190-198,279-281` |
| Reasons, Reject | as FM-107 | | | `MOH_APPROVAL` or `PORALG_APPROVAL` accepted | `RejectionCommentsForm.jsx:64-103` |

`finalApprove` checks no status, node, zone or facility type and returns `List<BottomUpQuantificationDto>`
(`BottomUpQuantificationService.java:610-619`); 404 for an unknown id. `forFinalApproval` lists
only APPROVED forecasts on the user's MOH and PORALG nodes, filtered by facility type (MOH alone:
non-primary; PORALG alone: primary). Reject accepts AUTHORIZED, IN_APPROVAL or APPROVED.

### Data Flow

- Route `_protected.buq.national-approval_.$id.tsx` (no nesting), `preload: false`, reloads only
  on entry, `crumbKey`: the loader blocks on `loadNationalAccess`, then in parallel the forecast
  (`loadForecast`) and the supervised zones; then the fresh final approval list for the
  forecast's period and each root zone; a forecast in none of them throws `notFound`.
- The editor gets a `national` mode (`programId`, root zone ids): actions `finalApprove` and
  `reject` for APPROVED only, nothing editable. Approve reuses the FM-107 confirmation, mutation,
  failure dialog and leave flag with its own wording; Reject reuses the FM-107 dialog unchanged.
- Before each decision `ensureStillOpen` rereads the forecast and the final approval list as
  above, and sends nothing when it moved on or left the list (FM-107 rule).
- After a decision: toast, refresh the BUQ lists (the summary's list is under `buq.list`), return
  to `/buq/national-approval` with the summary's search from history state, read once on open.
- The summary: an Actions column with Review (`Button` in the table, `CardActions` in cards),
  passing its search (`zone`, `period`, page, size) in history state.

### Rules

- The approver changes nothing; final approval sends no body, so nothing in the forecast changes
  but its status.
- Approve and Reject only for forecasts in the user's final approval list (APPROVED at their MOH
  or PORALG nodes, of the facility types their rights allow); others are Not Found. This is the
  only guard: the server's final approval checks no status, node or facility type.
- Reread before each decision; a forecast that moved on or left the list gets the "changed"
  message and nothing is sent (FM-107).
- Approve requires complete funding, as legacy and FM-107.
- Reject: at least one BUQ reason, comments up to 4000, one dialog (FM-107).
- After a decision: toast, refresh, return to the summary with its search.

### Risks And Edge Cases

- A national approver could finally approve a rejected or draft forecast by address (backend bug);
  the list check refuses it.
- A forecast of a facility type the user's right does not cover is not in their list, so Not
  Found, matching the server's own list filter.
- The grid recalculates line costs with current prices (FM-105, as legacy), while the summary shows
  the costs stored at the last save; they can differ (seen in legacy: 1 800.00 against 200.00).
- More than one root zone (nodes in two countries): one list read per root; normally one.
- A deleted remark or source used in the forecast makes the read 500 (vault bug); shown as the
  load error.

## UI/UX

**Port**: the FM-107 grid, details, totals and funding dialog, all read-only; Approve with a
confirmation; Reject with reasons of category BUQ and General comments; Cancel back to the
summary; the toasts.

**Improve**:
- Opens only forecasts waiting for this approver's final approval; others are Not Found with a
  link back to the summary.
- Approve and Reject only for APPROVED forecasts, checked again before sending.
- One step to reject; the server's error in place.
- Back to the summary with its group, period and page, and the list refreshed, so the decided
  forecast is gone.
- The row action reads Review, as on the Approve list, distinct from the column View menu; a
  `Button` in the table, `CardActions` in cards (AGENTS.md single row action).
- Cards and a sticky footer that fit a phone.

**Drop**: Approve and Reject on forecasts not waiting for final approval; the second rejection
confirmation; downloading every product and period; the loading modal; returning by browser Back.

States: loading (real header, skeleton), not found, load error with retry, ready, approving,
rejecting, server refusal, "changed" refusal. RTL with logical classes; names in `<bdi>`.

## Decisions

- **One editor for three roles**: national mode is an action set on the FM-105 editor, as FM-107.
- **Membership from the final approval list** by the forecast's period and the root of the user's
  supervised zones: the grid's URL has no zone, and the root covers every zone below it.
- **Reread before Approve and Reject**, as FM-107: the server's final approval has no checks.
- **Approve only for APPROVED**, unlike legacy, which shows it for every status.
- **Reject without a second confirmation**, as FM-107.
- **Row action labelled Review**, as on the Approve list.
- **Return to the summary, not browser Back**: the same place in both cases from the summary, and a
  defined place when opened by address.
- **Real decisions on the local instance** only with the user's go-ahead, with setup and cleanup.
- **Branch from FM-108**, which is not merged.
