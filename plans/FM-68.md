## Scope

One PR for the whole of FM-68 and its three subtasks: the Physical Inventory program list, the
draft page with its grid, the reason, Add Product, Edit Lot and submit dialogs, autosave on this
device, Save, Delete, Submit with the print prompt, Deactivate, VVM and barcode scanning. It also
completes [FM-63](https://openlmis.atlassian.net/browse/FM-63)'s Physical Inventory row (Status
and Start or Continue).

The logic is legacy's, rule for rule (the user, 2026-10-09: "100% parity with legacy"). The new UI
changes only what fits its shell: URL-owned filters, inline errors, page layout and faster
loading. The few legacy defects fixed are named under Decisions.

Not in this PR:

- Offline. Legacy opens drafts offline from its cache; that comes with the offline pass
  (FM-166, FM-168). FM-68 stays open until then, as every stock story does.
- Issue, Receive and Kit Unpack (FM-64, FM-65, FM-67). Physical Inventory adds new files to
  `src/features/stock-events/` and changes none of the existing editor files, so it does not
  collide with the FM-64 and FM-77 threads.

## Summary

A physical inventory is a stock count. A storeroom manager counts every product on the shelf,
enters the counts, explains any difference with reasons, and submits. The counts then become the
stock on hand.

In legacy, Stock Management > Physical Inventory lists the programs at the user's home facility
with a status: Not Yet Started (Start) or Draft (Continue). Start creates a draft that everyone at
that facility shares. The draft page lists every product that has stock, grouped by category, with
lots, stock on hand, a box for the counted quantity, the reasons and the quantity still
unaccounted for. Counts are kept in the browser as the user types, so a reload keeps them; Save
sends the draft to the server for others to see. Add Product brings in products or lots that are
not listed, including a brand new lot for users allowed to manage lots. Submit asks for the date
of the count and an optional signature, records the counts, offers to print the inventory, and
opens Stock On Hand.

The new UI keeps every step, rule, dialog and message. It changes three things users will notice:
the page opens faster on large programs, because it no longer downloads every approved product up
front; filters apply as you type and live in the address, so a link reopens the same view; and
one responsive page replaces both the desktop screen and the separate phone screens.

### Data Flow

- **List route** `/stock-management/physical-inventory`: as Adjustments, loader blocks on
  `requirePermissions(RIGHTS.stockInventoriesEdit)`, defers the user record, programs and home
  facility. Each program row reads its own `physicalInventoryDraftOptions({programId, facilityId})`
  behind a small status skeleton. Start is a `useSessionMutation`: post, seed the draft query, go
  to the draft page; on `draft.exists`, refetch and go anyway.
- **Draft route** `/stock-management/physical-inventory/$programId`, search `keyword`,
  `includeInactive`, `page`, `size` (default 20), defaults out of the URL. The program in the path,
  not the draft id, so a reload or a shared link finds the facility's current draft.
  - Loader blocks on the permission, the user record and the home facility, checks the exact grant
    and that the facility supports the program (else `ForbiddenError`), then reads the draft with
    `fetchQuery(physicalInventoryDraftOptions, { staleTime: 0 })` on `cause: 'enter'` and the
    cached copy on `stay`, as product edit does, with `preload: false`. No draft shows "No draft
    for this program" with Back to the list (it was submitted or deleted elsewhere). It
    prefetches, deferred, the stock lines, the eligible products and the valid reasons.
  - `useReloadForUser`, as the Stock Card.
- **Two loads** (defect 7):
  - *Stock lines*, `v2/stockCardSummaries?nonEmptyOnly=true`, then their products and lots by id.
    Enough to show the grid: every line legacy shows is one of these, or a line in the draft or
    the local copy. Source confirms the filter drops only empty summary groups, keeping inactive
    cards and stocked fulfilling products (`StockCardSummariesV2DtoBuilder.java:66-114`).
  - *Eligible products*, legacy's own full load (`buildEligibleProducts`, a port of
    `full-stock-card-summary-repository-impl.js:70-157`): every approved product, its fulfilling
    products and all their lots, plus "no lot". Deferred behind the grid. Add Product, scanning,
    the VVM column rule and the empty-save fallback wait for it, each with its own pending state,
    and Save and Submit wait for it too, since both drop lines outside it, as legacy.
- **Lines** (`buildInventoryLines`): the stock lines, the server draft's lines and the local
  copy's, merged by line key. Once the eligible products are in, a line whose product is not
  among them is dropped, as legacy (`physical-inventory.factory.js:217-246`). Membership is
  legacy's `isAdded`: a stock card exists, a quantity (including `-1`) or reasons are in the
  draft, or the user added it. Then search, include-inactive, sort by product code, group by
  product, page by 20 groups, category bands per page.
- **Line key**: `orderableId|lotId` for a recorded lot, `orderableId|none` for no lot, and
  `orderableId|new:<clientId>` for a lot not created yet. The client id stays in the local copy
  and is swapped for the server id once the lot is created.
- **Session flags**, kept in page state and the local copy, never sent: `justAdded` (added in this
  session, so its row offers Delete, as legacy's `$justAdded`) and `newLot` (its lot can still be
  edited, `$isNewItem`). A successful Save clears `newLot` but keeps `justAdded`, as legacy
  (`draft.controller.js:459`).
- **State**: one TanStack Form holding the line drafts (count, reasons, VVM, flags), never the
  whole product list. Filter and paging change only the search.
- **Local copy** (FM-72): a Dexie table `physicalInventoryDrafts`, keyed by draft id, in the
  signed-in user's database: `{draftId, programId, facilityId, lines, modified, savedAt}`, lines
  holding only what the user changed.
  - Written on every change; the next change waits for the running write and then writes the
    latest state, so writes never overlap or arrive out of order.
  - Each write captures `getSessionScope()` and the database it opened, and is dropped if the
    user changed, so a late write never lands in another user's database.
  - On open, a `modified` local copy wins over the server draft, as legacy. Cleared after a
    successful Save, Delete and Submit; kept on any failure. A copy for a draft id the server no
    longer has is dropped.
  - Leaving: legacy needs no prompt because its write is synchronous. Ours asks only while a write
    is still running or the last one failed: `useDiscardGuard(pending || failed)`, which also
    covers a reload. Otherwise leaving is silent, as legacy.
- **Indicator**: "Saving Changes" while a write runs, "Saved On This Device" once it resolved,
  "Not Saved On This Device" if it failed, with the counts still on screen.
- **Save**: confirm (always, legacy's warning), create new lots one by one (`settleFew`,
  scope-checked), write each new id into the local copy at once so a retry never creates a lot
  twice, then `PUT` every member line (count, or `-1` when uncounted; reasons; VVM). If there is
  no member line, send the eligible products as legacy's placeholders with no quantity, since the
  server refuses an empty list (`PhysicalInventoryValidator.java:95`). Success: toast, clear
  `modified` and `newLot`, refetch the draft. Failure: error toast with the server's message; the
  local copy stays.
- **Submit**: first, any displayed inactive line with stock on hand 0 blocks with legacy's
  inactive message. Then every member line is validated, not only the filtered ones; on errors
  clear the keyword, open the page of the first error, focus it, toast the legacy message. Then
  the occurred date dialog; Confirm creates new lots, posts every member line once (an inactive
  uncounted line as 0; never resent on an unknown outcome, as FM-66), clears the local copy,
  invalidates `physicalInventories`, `stockEvents`, `stockCardSummaries` and `stockCards`, toasts,
  asks Print or No, then Stock On Hand with `mode: 'my'`, the facility and the program.
- **Print** through `usePrintReport` with `openReport`, as the Stock Card, so the token never goes
  in the URL.
- **Delete**: confirm, `DELETE`, clear the local copy, invalidate the draft query, back to the
  list, toast.
- **Dialogs** (reasons, Add Product, Edit Lot, deactivate, save, delete, occurred date, print) are
  page state, not URL state: each edits the unsaved draft on this page, like FM-66's signature
  dialog, and has nothing a link could reopen.

### Scanning

Legacy's rules (`draft.controller.js:832-911`, `stock-scan.service.js:136-197`), in a new
`physical-inventory-scan.ts`, so the shared `stock-scan.ts` is not changed:

- Look the GTIN up (`tradeItemByGtinOptions`), then match against the eligible products, not only
  the grid, so a stockless product or a lot not yet listed is found.
- An unknown lot asks to add it as a new lot (with `LOTS_MANAGE`), else it is refused.
- An expiry that differs from the scanned one asks once per scan batch.
- Each scan adds one pack in doses to the line's count (`netContent`, else 1).
- A line the filters hide is revealed: the keyword is cleared and an inactive line is reactivated
  for the draft, as legacy, and its page is opened.

### Rules

All legacy's, with the source in the research:

- Open: exact `STOCK_INVENTORIES_EDIT` at the home facility for the program; the facility
  supports the program. The stock lines also need `STOCK_CARDS_VIEW`, as legacy's load; without it
  the grid shows a message naming the right instead of a broken page.
- New lot: `LOTS_MANAGE` in any scope; code required, unique per product among listed and new
  lots, compared without case as the server does (defect 8); expiry optional, not before today.
- Count: whole number from 0 to 2147483647, packs times net content plus remainder, required on
  submit for every member line, except an inactive line, which is sent as 0 when uncounted.
- Unaccounted: count − stock on hand − Σ(credit) + Σ(debit), blank stock on hand as 0, must be 0
  on submit. Reasons: valid for program and facility type, not hidden, every category, without
  `BALANCE_ADJUSTMENT`; each quantity above 0.
- Member line (legacy `isAdded`): a stock card exists, the draft holds a quantity (including
  `-1`) or reasons, or the user added it; and its product is eligible. Only members are shown,
  saved and submitted.
- Include Inactive Items off hides inactive lines with stock on hand 0. Any such line shown, with
  the switch on, blocks submit first with legacy's inactive message, counted or not; inactive lines
  with stock go through the normal checks.
- Delete (row): only lines added in this session (`justAdded`), at once.
- VVM column: shown when any eligible product uses VVM; a VVM status only on such a product.
- Progress: product groups whose every line is counted, out of the product groups after the
  filters.
- Deactivate: active, stock on hand 0, not added this session, online.
- Occurred date: required, default today, not after today. Signature optional, at most 255.
- Save and Submit create new lots first and stop on a lot error, naming the codes.

### Risks And Edge Cases

- One shared server draft per program and facility: two people saving overwrite each other, as in
  legacy. Recorded, not solved.
- A draft submitted or deleted elsewhere while open: Save may answer an error or recreate nothing;
  show the server's message and keep the local copy.
- `PUT` sends `reason: {id}`: the server reads only the id
  (`PhysicalInventoryLineItemAdjustment.java:112`).
- Essential Meds: the eligible products take legacy's 15 to 21 s behind the grid, so Add Product,
  scanning, Save and Submit wait that long there; the grid itself should not. Measure both on test.
- `orderableFulfills` and `lots?tradeItemId` for 10,000 products go out 100 ids a request, about
  100 requests each; check the time on Essential Meds in step 1.
- The researcher's real draft on test (Family Planning, Comfort Health Clinic, id
  `d6ec47c0-71ee-47da-aa41-fad0ba628e40`, empty) is the fixture for browser checks; the final real
  submit consumes it.

## Decisions

- **Autosave as legacy (FM-72)**: on this device, on every change, the local copy wins on reopen,
  Save sends it to the server. No server autosave and no conflict prompt: legacy has neither, and
  the user asked for legacy's logic. The copy lives in the user's own Dexie database instead of a
  shared `localStorage` key, which fixes defects 4 and 5.
- **Leave prompt only while the local write is unfinished or failed**: legacy's synchronous store
  never needs one; ours is asynchronous, so this is part of fixing defect 4.
- **Load in two steps** (defect 7): the grid from `nonEmptyOnly=true`, legacy's full set behind it
  for everything that needs every product. Same calls as legacy plus one, same rules. Save sends
  member lines only, with legacy's placeholders when there are none.
- **Defects fixed**: 1 (validate hidden lines), 2 (count 0 in Add Product), 3 (keep the local copy
  on a failed submit), 4, 5, 6 (no `BALANCE_ADJUSTMENT` reasons), 8 (lot codes compared without
  case). Nothing else departs.
- **Dialogs in page state**, not the URL: they edit the unsaved draft and a link could not reopen
  them, as FM-66's signature dialog.
- **Program id in the URL**, not the draft id, so a link finds the current draft.
- **Files only added in `stock-events`**, none of its existing ones changed, to stay clear of the
  FM-64 and FM-77 threads. The picker change is additive.
- **One PR**, steps as commits, as a list whose draft cannot be submitted is not a usable screen.
- **Offline later**, with the offline pass; FM-68 stays open until then.

  stockless lines can appear before the eligible products resolve. The full eligible load drops
  ineligible products once it finishes. Its failure is retryable without replacing the grid.
