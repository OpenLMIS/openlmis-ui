# FM-90: Shipment

https://openlmis.atlassian.net/browse/FM-90 · Subtasks: FM-94 grid, FM-95 packs and doses,
FM-96 actions · Parent: FM-88 Fulfillment

## Scope

This PR adds the shipment screen at `/orders/fulfillment/<orderId>`. Fulfill Orders' Start and
Continue Fulfillment open it, instead of handing off to legacy.

It covers:

- the header, with Facility CCE Status
- the product and lot grid
- the Packs and Doses toggle
- the actions: Save Draft, Generate Pick Pack List, Delete Draft, Cancel Order, Confirm Shipment
- a read-only view of orders that already have a shipment

The branch builds on PR #133, which is not merged. Its first commit is shared groundwork that the
proof of delivery branch (FM-91 and FM-92) also builds on (Steps).

Out of scope: offline, since legacy has none here, and the proof of delivery screens.

## Summary

A warehouse fulfils an order by choosing how many packs of each lot to send.

In legacy:

- Opening an Ordered order starts a draft and marks the order Fulfilling.
- The screen lists every product ordered, with the lots the warehouse holds, their VVM and expiry,
  the ordered quantity and the stock available.
- The user types a fill quantity in packs for each lot.
- The user can save the draft, print a pick pack list for the store, and confirm the shipment.
  Confirming marks the order Shipped, issues the stock and creates the proof of delivery the
  receiving facility confirms later.
- The user can also delete the draft, which returns the order to Ordered, or cancel the order.

The new screen keeps all of that and fixes legacy's problems:

- It never crashes on orders it cannot fulfil.
- It shows actions only to users allowed to use them.
- It keeps typing after Save.
- It shows VVM for every lot.
- It loads the stock once instead of three times.
- It works on a phone.

## Legacy Today

Evidence is in `.screenshots/FM-90/`: `findings.md`, `fixtures.md`, the network logs and the
screenshots. The source is `openlmis-fulfillment-ui/src/shipment-view` and `shipment`.

### Opening

**Route.** `/#!/orders/:id/shipment`, opened from Fulfill Orders only. The route needs
`SHIPMENTS_VIEW` or `ORDERS_VIEW`.

**Reads:**

- `GET /api/orders/{id}`.
- Stock summaries for the supplier and program (`/v2/stockCardSummaries`, one `orderableId` per order
  line). These cover only products approved for the supplying facility's type, so a line can have no
  summary.
- The latest product versions and the lots.
- `GET /api/stockCards?id=…`, only to read VVM. This returns 20 cards by default, so later lots lose
  their VVM.

The summaries are read two to three times per open, about 13 requests in all.

**By status:**

- **Ordered:**
  - Builds one line per fulfilling stock card (zero stock and expired included).
  - Each line uses the **latest** product version, since summaries carry no versions.
  - Sends `POST /api/shipmentDrafts`, and the order becomes Fulfilling.
  - The header shows the re-read order, so Status reads Fulfilling.
- **Fulfilling:** `GET /api/shipmentDrafts?orderId`.
- **Shipped:** `GET /api/shipments?orderId`, read-only; only the shipped lines.
- **Other statuses:** an internal error (seen live on a cancelled order).

**Toolbar.** It shows only for Ordered and Fulfilling orders. Inputs follow status only, with no edit
right check.

### Header

- **Title.** "Fulfilling Order - <code>", with an Emergency badge.
- **Fields:**
  - Status: raw enum
  - Date Created
  - Program
  - Facility: the requesting facility
- **Facility CCE Status:**
  - "Loading" first.
  - "Unknown" without `CCE_INVENTORY_VIEW` at that facility, or on error.
  - Otherwise one of: "No CCE tracked at this facility", "All functioning", "Not fully functioning",
    "Not functioning".
  - A coloured status icon and, for active alerts, a labelled "Active Alert" badge (legacy's red
    dot alone relied on colour).
  - A popover titled "{N} Inventory Items", listing each item with its alert badge.

The breadcrumb is Home / Orders / View Shipment.

### Grid

**Columns, in order:** Product Code, Product, Lot Code, VVM Status, Expiry Date, Order Quantity,
Fill Quantity (in Packs), Available SOH, Remaining SOH.

Order Quantity, Available SOH and Remaining SOH carry "Quantities are provided in {Packs|Doses}".

**Rows** follow the order lines:

- **A product filled only by itself, with no lot:** one editable row.
- **Otherwise:**
  - A shaded product row with the ordered quantity and the summed fill, available and remaining.
  - A filling product with several lines gets a subgroup row (by product id): no order quantity, no
    lot, no expiry.
  - Then its lot rows. Lot rows leave Product Code and Product blank.
  - A filling product with one line shows as a single row with its own code and name.
- **Any row without a lot** shows "No Lot Defined".
- **Lot order:**
  1. No lot first.
  2. VVM descending; no VVM counts as Stage 1.
  3. Expiry ascending, with no expiry first.
  4. Stock ascending.

**"No stock available":**

- A full-width message after any group row (product or subgroup) whose available packs total 0,
  including stock below one pack.
- When a product row has 0, its children are hidden.
- A subgroup with 0 keeps its lot rows below the message.
- A single product row never shows the message.

**VVM** is the stock card's latest line item's `extraData.vvmStatus`. The labels are Stage 1 and
Stage 2.

### Packs and Doses

- **Default unit:** Doses, from the deployment flag. The choice is stored and shared with stock
  screens. The toggle hides when only one unit is allowed.
- **Fill is always typed in packs.** The input strips non-digits. Toggling changes display only.
- **Missing or zero pack size:** legacy has no fallback. Zero gives Infinity, missing gives NaN.

| Column | Packs | Doses |
|---|---|---|
| Order Quantity | `orderedQuantity` | `orderedQuantity × nc` |
| Fill | packs | packs |
| Available, lot | `floor(SOH / nc)` | `floor(SOH / nc) × nc` |
| Remaining, lot | `available − fill` | `(available − fill) × nc` |
| Group available | sum | sum of each child in its unit |
| Group remaining | `Σavailable − Σfill` | `(Σavailable − Σfill) × group nc` |

Example, nc 84, stock 1,000 doses, fill 1:

| Mode | Order | Available | Remaining |
|---|---|---|---|
| Packs | 1 | 11 | 10 |
| Doses | 84 | 924 | 840 |

### Validation

- **Blank:** "This field is required". Zero is valid.
- **Above available packs:** "Can't exceed available stock on hand".
- **When it shows:** a row's errors appear as soon as focus leaves the row.
- **Confirm:**
  - An invalid form stops Confirm with the alert "This form is invalid", before the confirmation
    prompt.
  - Confirm then re-checks after the prompt; a failure there shows "Failed to confirm shipment".
- **Save does not validate,** so blank or too-high fills are saved as typed.

### Actions

All actions need an Ordered or Fulfilling order.

| Action | Also needs | Confirmation (buttons) | Request | Result |
|---|---|---|---|---|
| Save Draft | nothing | none | `PUT /api/shipmentDrafts/{id}` | "Draft has been saved", then a full page reload, which also refreshes stock. "Failed to save draft" |
| Generate Pick Pack List | nothing | none | opens a tab, saves, then `/api/reports/templates/common/583ccc35-88b7-48a8-9193-6c4857d3ff60/pdf?shipmentDraftId=…` | the PDF |

## Agent Brief

### API map

| Step | Method and path | Params / body | Fields used | Right (server) |
|---|---|---|---|---|
| Order | `orderOptions` / `fetchOrder` (exists; widen `Order` type) | none | `orderCode, status, emergency, createdDate, program, requestingFacility, supplyingFacility, orderLineItems[].{orderable(id, productCode, fullProductName, netContent, dispensable.displayUnit, extraData.useVVM, meta.versionNumber), orderedQuantity}` | `canViewOrder` |
| Stock | `GET /api/v2/stockCardSummaries`: extend `fetchOrderStockOnHand`'s reader to keep `canFulfillForMe` | `programId`, `facilityId` (supplier), `orderableId` (repeated, batches of 100); no paging needed | `content[].orderable.id`, `canFulfillForMe[].{orderable.id, lot.id, stockOnHand, stockCard.id, active}`; **no versions** | `STOCK_CARDS_VIEW` for the program at the supplier |

| Lots | `lotsByIdsOptions` | lot ids | `lotCode, expirationDate` | none |

| Delete Draft | `DELETE /api/shipmentDrafts/{id}` | none | 204 | `SHIPMENTS_EDIT` |

| Pick pack list | `GET /api/reports/templates/common/583ccc35-88b7-48a8-9193-6c4857d3ff60/pdf` | `shipmentDraftId`, `lang` | PDF blob | `ORDERS_VIEW`, `SHIPMENTS_VIEW`, `STOCK_CARDS_VIEW`, each anywhere |
| CCE status | facility-wide readers added to the CCE feature: all pages of `GET /api/inventoryItems` and `GET /api/cceAlerts` (with `size`) | `facilityId`; `deviceId` | `functionalStatus, referenceName, facility.id`; active alerts | read only when `CCE_INVENTORY_VIEW` is granted at that facility; results also filtered by `facility.id` (the server ignores the filter without the grant) |

**Server facts:**

- **Draft PUT:**
  - It **creates a draft when none exists** and never checks order status.
  - It replaces `notes`, which are cleared if left out.
  - Lines match by `id`. Lines without an id are inserted; lines left out are deleted.
  - A body `id` that does not match the path gives 400 `fulfillment.error.shipmentDraft.id.mismatch`.
- **Draft create errors:**
  - `fulfillment.error.shipmentDraft.create.orderWithWrongStatus`
  - `fulfillment.error.shipmentDraft.order.duplicate` for concurrent creates
  - The rights check runs first.
- **Confirm:**
  - Each line issues `quantityShipped × netContent` doses as a stock event. Zero lines are skipped
    after the valid-destination lookup, so an all-zero shipment still needs a destination.
  - The stock event uses a service token. Its errors pass through, for example
    `stockmanagement.error.event.debit.quantity.exceed.stockOnHand`.
  - `fulfillment.error.shipment.lineItems.required` for an empty line list.
  - `fulfillment.error.stockEvent.missingSourceDestination` without a valid destination.
  - The stock event is remote and is not rolled back if a later step fails.
- **Versions.** Bodies need `orderable.versionNumber`. Confirm looks products up by exact version.
- **Pick pack list.** It answers 200 with a blank PDF for an unknown draft id.
- **Draft reads.** `GET /shipmentDrafts` with an unknown order gives 400
  `fulfillment.error.shipmentDraft.order.notFound`.

### Data flow

**Route** `src/routes/(protected)/_protected.orders.fulfillment_.$orderId.tsx`. The breadcrumb is
Home / Orders / Fulfill Orders / Shipment (`crumbKey`); the order code goes in the title.

- **Loader:**
  - Starts `requirePermissions([SHIPMENTS_VIEW, SHIPMENTS_EDIT, ORDERS_VIEW])` and a fresh order read
    (`fetchQuery`, `staleTime: 0` on `cause: 'enter'`) in parallel.
  - Then, by status:
    - **Ordered or Fulfilling:** prefetch the stock summaries and the draft, both fresh on
      `cause: 'enter'`.
    - **Any other status:** prefetch the shipment (fresh on enter), and the summaries as well. Legacy
      shows today's Available SOH on shipped orders.
  - Also prefetches the deployment time zone and the CCE status.
  - `preload: false`.
- **Stock and lookups**, as three stages:
  1. **Summaries:** `[...queryKeys.stockCardSummaries.all, 'shipment', programId, supplierId,
     orderableIds]`.
  2. **Product versions:** latest versions of the filling products, via `orderablesByIdsOptions`.
     Draft creation waits for these and nothing else.
  3. **Lots and VVM:** keyed from the summaries; they never block creation. Allocation inputs wait for their first successful read, so named lots and their VVM are identifiable.
- **Products and lots from saved lines.** Draft and shipment lines resolve their products and lots
  directly from their own references, with exact versions (`orderablesByIdentitiesOptions`) and
  `lotsByIdsOptions`. That covers read-only shipments and draft lines whose stock card has gone.
- **Read-only shipments** show Available SOH and Remaining SOH from today's stock, as legacy.
- **Draft creation:**
  - After render, for Ordered orders, when the user holds `SHIPMENTS_EDIT` at the supplier.
  - Needs only the summaries and the filling products' versions.
  - **Concurrent creates are deduplicated.** A module-level in-flight promise (keyed by session
    scope and order id) is shared across mounts until it settles. Completed promises are removed;
    a fresh entry read decides whether creation is needed, including after another tab deletes a draft.
  - **Another tab got there first:** `orderWithWrongStatus` or `order.duplicate` means the draft
    exists, so read it.
  - Then refetch the order (now Fulfilling) for the header.
- **Form:**
  - One `useAppForm` with `lines.<key>.fill` and the draft `notes`.
  - Rows subscribe with `useStore` selectors, as the Create Orders editor and Physical Inventory do.
- **Validation:**
  - **Validity** is computed continuously from each line's current value and available packs. It
    updates as the user types and whenever refreshed stock changes availability.
  - **Visibility:** a row's highlight and tooltip appear once the row has been left (blur) or Confirm
    has been tried, as legacy. Once visible, they follow the current validity.
  - **Confirm** re-validates against the latest values after the confirmation prompt, before POST.
- **Return.**
  - `order-return.ts` gains a Fulfill Orders target, which Fulfill links pass.
  - Delete, Cancel and Confirm return there; the default is Fulfill Orders (Decision 8).
- **Draft and shipment cache keys:**
  - Draft: `[...queryKeys.orders.all, 'shipment-draft', orderId]`.
  - Shipment: `[...queryKeys.orders.all, 'shipment', orderId]`.
- **What each action does to the cache:**

  | Action | Cache changes |
  |---|---|
  | Draft create, Save | Write the response into the draft key |
  | Delete Draft, Cancel Order | Remove the draft key |
  | Confirm | Remove the draft key; invalidate the shipment key |
  | Draft create, Delete, Cancel, Confirm | Invalidate `orders.list`, `orders.requesting-facilities`, `home` and the order detail |
  | Save, Confirm | Invalidate the stock summaries (`stockCardSummaries.all`) |
  | Confirm | Request a refresh of downloaded offline stock for the supplying facility and program |

  Delete, Cancel and Confirm stop automatic draft creation while the page returns, so a refetched
  Ordered status cannot recreate the deleted draft.
- **Reopening** reads the order, the draft and the shipment fresh.

### Rules

**Lines** (`shipment-lines.ts`):

- **Order lines without a summary** form an empty group with "No Stock Available".
- **Draft lines.** Built from each summary's `canFulfillForMe`, merged with draft lines by product id
  and lot id (no lot matches no lot):
  - Draft values win.
  - Cards new since the draft start at 0 (Decision 5).
  - Draft lines whose card has gone keep a row with 0 available.
- **Read-only shipments** show only shipment lines (no merge).
- **Grouping, subgroups, lot order and "No Stock Available":** as Legacy Today.
- **One exception to hiding a 0 product's children:** rows with a fill above 0 stay visible (and
  invalid) so the user can correct them (Decision 5).

**Quantities** (`shipment-quantities.ts`):

- The table in Legacy Today, exactly.
- A missing or zero pack size **displays** as if it were 1 (Decision 9). The server multiplies by the
  real pack size, so such a line with a fill above 0 is invalid: "This product has no pack size.
  Contact an administrator." That blocks Confirm.

**Validation:**

- **Fill:** required, and no more than the available packs. Messages are legacy's.
- **Input:** `NumberField` whole numbers (Java int max) with the standard message, instead of legacy's
  silent stripping (Decision 3).
- **Save and Pick Pack List** do not validate, as legacy.
- **Confirm** validates first. If invalid, it opens the invalid-submit AlertDialog and reveals the
  first field. Then the legacy confirmation, then POST.

**Who may do what** (status Ordered or Fulfilling, and grants at the supplying facility, read with
`facilityGrants`):

| Action | Needs |
|---|---|
| Inputs, Save Draft, Delete Draft (a draft exists), Confirm (at least one line) | `SHIPMENTS_EDIT` |
| Generate Pick Pack List | `SHIPMENTS_EDIT`, plus `ORDERS_VIEW`, `SHIPMENTS_VIEW` and `STOCK_CARDS_VIEW` anywhere |
| Cancel Order | `ORDERS_EDIT` |

**Other statuses:**

- **With a shipment** (Shipped, Received and later): read-only shipped lines.
- **Without one** (Cancelled, Transfer Failed and others): the header and an in-place notice, "This
  order can no longer be fulfilled". No draft requests.
- **A user who cannot read drafts or shipments** (`ORDERS_VIEW` only, a 403): an in-place "You can't
  view this shipment" notice.
- **No stock read right** (403 on summaries): an in-place error.

**Save Draft:**

1. **Check the draft still exists.** Re-read it by order (about 300 ms). If it is gone, open a
   dialog: "This draft no longer exists", with Reload.
2. **Send** the API fields only: line ids, versions, packs and the existing notes.
3. **Compare** the returned draft id with ours. A different id means the server just created a stray
   draft: show the same dialog.
4. **On success,** show the toast, refetch the stock, update the draft key, and keep typing made
   during the save dirty (submitted-snapshot merge, as the Create Orders editor).

The check narrows the stale-draft window but cannot close it. Another tab could still delete,
cancel or confirm between the read and the PUT, and only a backend conditional update would close
that gap. This residual risk is accepted and documented.

**Save speed.** Server persistence is about 670 ms (read plus PUT) against legacy's 372 ms. That is
within the 500 ms tolerance. The visible success, about 0.7 s, beats legacy's 2.2 s reload-and-toast.

**Pick Pack List:**

- `usePrintReport({ serverAuthorized: true, userId, facilityId: supplierId, programId, right:
  SHIPMENTS_EDIT })`.
- `beforeRequest` runs the save. `openReport` opens the tab in the click. The report request is
  `fetchReport` with `lang`.

**Failures:**

- Server errors open an AlertDialog with the server message, as the Create Orders editor. Typed
  values are kept.
- Unsaved fills trigger `useDiscardGuard`. Delete, Cancel and Confirm skip it after their own
  confirmation.

**CCE status:**

- The route reads `CCE_INVENTORY_VIEW` at the requesting facility. Without it, it shows "Unknown"
  and sends no request.
- It renders in its own `QueryBoundary`, so it never holds the header.

## Decisions

1. **Fill stays in packs** in both units ("Fill Quantity (In Packs)"), as legacy and the server's
   packs. Entering doses would allow quantities that are not whole packs. FM-95's wording says every
   column converts; the user confirmed legacy's behaviour.
2. **Opening an Ordered order creates the draft, as legacy,** but after render and never in a
   preload.
3. **Whole-number input with a message** replaces legacy's silent stripping (`1.5` became `15`).
4. **Save keeps the page and typing, and refreshes stock.** Legacy reloaded everything.
5. **New stock cards join a draft at 0. Vanished cards and filled rows under a no-stock product stay
   visible.** Legacy hid them or crashed.
6. **VVM is read for every VVM lot,** not just the first 20 cards.
7. **Actions follow rights and status:** `SHIPMENTS_EDIT` or `ORDERS_EDIT` at the supplier, and the
   pick pack list's report rights. Legacy showed them by status only.
8. **Return** goes to the list that opened the page, defaulting to Fulfill Orders. Legacy fell back
   to View Orders, but only Fulfill Orders opens this screen.
9. **A missing or zero pack size displays as 1 but blocks Confirm** for lines with a fill. Legacy
   showed Infinity or NaN; the server issues by the real pack size.
10. **Save re-reads the draft first and compares its id afterwards.** This narrows, but cannot
    remove, the chance of a stray draft when another tab acts at the same moment.
