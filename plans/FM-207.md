## Scope

- **In:**
  - one tour, `tours/admin-list.tour.ts`, registered for the 20 Administration pages that show a list;
  - `data-tour` attributes on existing elements of the shared list parts: search, Filters, View, the
    sortable column header, the list itself, status badges (`FlagBadge`), row actions, Select Page and

  - a `data-tour` attribute on each page's loaded Add or Create button (about 15 buttons, attribute

    - a `success` legend tone (the green status badge);
    - a `column` step looks for its header in the list holding its anchor, not the first list on the

    - an anchor inside a busy skeleton never plays, even once the load wait runs out.

  - other module changes: the runner already skips steps whose part a page lacks;

    back);
  - dialogs (Add, Edit, delete confirmations) and the Filters popover contents: opening one ends a tour,
    so the steps describe them.

## Summary

Every Administration list (Users, Facilities, Products, Roles and the rest) gets a Show Guide button.
One guide serves them all, because they share the same toolbar, table and pager. It walks through:
- the search box;
- Filters, View and the Add or Create button;
- sorting by a column heading;
- what the green and red status badges mean (Active or Inactive, Enabled or Disabled, Yes or No);
- the actions on each row, with the Actions column highlighted and a legend of the common icons;
- ticking rows for bulk actions, on the two pages that offer it;
- moving between pages.

A page shows only the steps for the parts it has: Programs, for example, has no search, so its guide
starts at View. Legacy has no guide.

Legends, as on Offline Events and Physical Inventory (`legend`):
- **Statuses:** `success` with a check, "Active": green tick, yes, active or enabled; destructive with a
  cross, "Inactive": red cross, no, inactive or disabled. Each page uses its own words; the legend says so.
  `TourLegendItem.tone` gains `success`.
- **Actions:** outline Edit (pencil), View (eye), "..." More Actions (ellipsis; the screen's ghost button
  shown as outline), destructive Delete (trash). Other icons (Copy Key, View Rights, Configure) are named
  by their tooltips.
- Legend labels get their own keys, `onboarding.admin-list.label.*`, so the tour leans on no feature's
  keys.

The actions step highlights the Actions header in tables, found by `data-table.actions` ("Actions",
matching 18 of the 20 lists in every locale). It falls back to the first row's actions, with the list
holding them spotlit, on cards, on Requisition Templates (its header says "Action") and on pt Geographic
Zones ("Acções"). The runner takes that list as `closest('[data-tour="list-table"]')` of the target, so
an empty first program table on Requisition Templates is never spotlit by mistake.

Content intent (the shipped English copy is the source of truth; names stay generic, since each page has
its own labels):
1. Type to narrow the list; the box says which fields it searches. Some pages search by code in Filters.
2. Filters holds the other filters; they apply as you pick, the badge counts active ones, Clear Filters
   resets them.
3. Pick the columns to show; Reset Columns brings the defaults back. On cards, the details and the sort
   order.
4. Adds a new record, where you may add.
5. Click a column heading to sort by it, again to reverse; on cards, sort from View. True over an empty
   table too.
6. Yes/no and active/inactive columns (rows on cards) show a badge with a tick or a cross and its word.
7. Each row's actions: icons with a tooltip, or a "..." menu when there are more; deleting asks first.
8. Tick rows, or the page; a bar under the list counts them and offers Clear and the bulk action. True
   over an empty table too.
9. Move between pages and pick Rows Per Page; the page, sort and filters stay in the address, so a link
   or reload keeps them.

### Rules

- **Registry:** `data-table/` gets plain string attributes (`data-tour="list-search"` and so on), no
  import; they are removed when the folder moves into the registry. AGENTS.md lists no such exception;
  the PR says so, since AGENTS.md stays untouched. `display/`, `shared/` and the pages import
  `TOUR_ANCHORS`, whose values match the strings; nothing types the plain strings, so the browser check
  covers each anchor.
- **No anchors on loading parts** (as FM-204): toolbar anchors only when not `disabled`, the pager anchor
  only on the real pager, Add only on the loaded button. Table skeletons draw the real header and the
  card skeleton the real list, so the runner skips any anchor inside `aria-busy="true"`; if the 30 s
  wait runs out, no placeholder is toured.
- **Popovers:** the steps never open Filters, View or a row menu.

### Risks

- **Empty or no-match list:** a table keeps its header, so sort and select remain; statuses, actions
  and pager drop out. On cards, select drops too.
- **Load error:** `ListError` replaces the list; only the toolbar steps remain.
- **`FlagBadge` elsewhere:** it also sits in editors and requisition grids; only the admin tour uses
  `list-flag`, and on a list page the first match is a list cell.
- **Users "..." menu:** tables highlight the Actions header; cards point at the "..." button.
- **Other screens:** `RowActions` and the shared toolbar parts appear on stock and requisition pages too;
  the attributes are inert there, since those tours use their own anchors.

## Decisions

1. **Anchors as plain attributes in `data-table/`** (user, 2026-11-18): meets AC 6 without importing app
   code into the registry folder. FM-200 had planned page wrappers instead.
2. **An attribute on each Add or Create button** (user, 2026-11-18): the button is page code, not a
   shared part; an attribute is not tour logic.
3. **The 20 list pages, including Requisition Templates** (user, 2026-11-18); the two CSV pages get no
   tour.
4. **One step per part, first match:** short steps, each skipped where the page lacks the part.
5. **Statuses and actions as before:** a legend in the tooltip, like Offline Events and Physical
   Inventory. The statuses step points at the first badge, since status columns have different names on
   each page; the actions step highlights the shared Actions header.
