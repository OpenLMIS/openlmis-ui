# FM-65: Receive

https://openlmis.atlassian.net/browse/FM-65 · Parent: [FM-62](https://openlmis.atlassian.net/browse/FM-62) Stock management

## Scope

The Receive screen for one program at the user's home facility, and its page on the shared stock
program picker ([FM-63](https://openlmis.atlassian.net/browse/FM-63)). It extends the shared event
editor that Adjustments ([FM-66](https://openlmis.atlassian.net/browse/FM-66)) and Issue
([FM-64](https://openlmis.atlassian.net/browse/FM-64)) already use. Receive becomes a third entry in
`EVENT_KINDS`. Where its rules differ, a new policy field is added that every kind sets. Nothing
is copied.

This PR also brings in:

- The valid sources lookup, the approved product search and the lots by trade item lookup, in
  `reference-data`. [FM-68](https://openlmis.atlassian.net/browse/FM-68) reuses the last two.
- New lots typed by hand or scanned, sent inside the stock event.
- A `defaultReceiveReasonId` runtime setting, wired through to deployment.

Not in this PR:

- **Offline.** Legacy keeps Receive's products on the device and queues receipts made offline.
  That comes with the offline pass (FM-166, FM-168), and FM-65 stays open until it ships. The
  checks are listed under Offline Acceptance (Later).
- **Kit Unpack ([FM-67](https://openlmis.atlassian.net/browse/FM-67)).** It is built in
  parallel. Its policy names are agreed below, but no option is added for it here.

Shared editor changes go in their own commits, before the Receive commits, so FM-67 and FM-68 can
rebase onto them.

## Summary

A receipt records stock arriving at the facility from a supplier: a warehouse, another facility or
an organisation such as an NGO. The storeroom manager picks a program, adds each product and lot
received, says where it came from, how much and when, optionally gives a reason, and submits after
signing. If a lot does not exist yet, a user allowed to manage lots types its code and expiry date
on the spot.

Legacy is the slowest stock screen. Before showing anything it downloads every approved product of
the program, with all its lots and stock. For Essential Meds (10,003 products) that took about
95 seconds the first time on the test server and 32 seconds after that, with the browser frozen
for long stretches. Its phone version also fills the browser's storage and fails.

The new screen opens straight away. It asks the server only for what the user is looking at: the
products matching what they type, then the lots and stock of the product they pick. Measured on
both the test server and UAT, the screen's data arrives in under a second, and picking a product
takes about a third of a second. The products and lots offered are exactly legacy's. Nothing is
stored in the browser.

Everything else works as on Issue, and as in legacy:

- **Received From:** each line takes one of the places the facility may receive from.
- **Source Comments:** shown only when that place allows them.
- **Reason:** optional; only Transfer In is set up on test.
- **Other features:** Packs/Doses, Filter, Clear, the signature step, the "Print the stock receive
  report?" question, and barcode scanning where it is turned on.

What changes for users:

- **Speed.** The screen is fast.
- **Finding products.** Typing searches the server. Legacy's list could also be searched by
  name, but only after downloading all 10,000 products.
- **Input fixes.** A typed "1.5", a negative number or a future date gets a clear message.
- **New lot checks happen before Submit.** A new lot code that matches an existing lot in any
  letter case is refused with "This lot code already exists." A new lot cannot be added for a
  product with no trade item, where legacy fails only at Submit.
- **One screen** works on desktop, tablet and phone.

Submit contract details, from backend `origin/master` `b318fcb9` (UAT runs 5.4.1, test
5.5.0-SNAPSHOT; both include OLMIS-8288 `a983d712`):

- `sourceId` is the assignment's `node.id`, never its `id` or `node.referenceId`.
- Omit `sourceFreeText`, `reasonId` and `reasonFreeText` when empty. The server refuses source free
  text when the node is a reference-data facility, even an empty string.
- **Lot fields:** send `lotId` for an existing lot. For a new lot, omit `lotId` and send `lot` with
  `lotCode` and, when set, `expirationDate`; sending both is refused.
- **What the server does with a new lot** (`StockEventLotResolutionService`, run before
  validation):
  - It reuses an existing lot of the product's trade item with the same code in any letter case,
    silently ignoring the expiry sent.
  - Otherwise it creates the lot with the service token, so it checks no `LOTS_MANAGE`. The lot
    remains if the event then fails.
  - It refuses a product with no trade item, and a code outside 1 to 20 characters of the GS1
    set.
- A line with a source and no reason is a credit. A product with no stock card gets a new card.

### Data Flow

- **Routes:** `/stock-management/receive` (picker) and `/stock-management/receive/$programId`,
  with search `page`, `size` and `keyword`, as Issue.
- **Loader:** the shared `loadStockEventEditor(queryClient, programId, 'receive')`, unchanged in
  shape:
  - It blocks on the grant, user, home facility and supported program.
  - It returns `canManageLots = permissions.rights.has(RIGHTS.lotsManage)` alongside
    `canViewStock`.
  - It prefetches, deferred and side by side: the counterparty lookup (from `counterparty`), the
    reasons, and the products by `products` policy. For Receive that is the first approved
    products page with an empty search, instead of stock cards.
  - This departs on purpose from the AGENTS.md server-search filter rule (fetch on first
    opening). Legacy's product select is usable as soon as the screen shows, and the request
    costs about 0.35 s.
  - Without `STOCK_CARDS_VIEW` the editor shows the same "no stock view" message as Issue, since
    stock on hand cannot be read (legacy cannot open either).
- **Editor with `approved-products`:**
  - It never reads `eventStockCardsOptions`, so the stock-cards parts are skipped: `cardsQuery`,
    `StockCardsReady` and the cards error branch (`event-editor.tsx:140-147, 545-559, 778-789`).
  - The table is ready once reasons and sources are.
  - The products search failing shows its own state in the picker, with Retry (new
    `stock-events.products-search-error-*` keys). It is not the stock cards error ("Could Not
    Load Products").
- **Product picker** (`ProductLotPicker`, shared):
  - It reads products by the kind's `products` policy.
  - `stock-cards` keeps today's suspense read of `eventStockCardsOptions` and the kind's
    `cardFilter`.
  - `approved-products` uses a searched `Combobox`, following the Lots page's server-search
    pattern:
    - **Search:** debounced `approvedProductsOptions({facilityId, programId, name, page: 0,
      size: 50})`, in server order.
    - **Fulfilling products:** the facility's fulfilment map
      (`facilityOrderableFulfillsOptions({facilityId, programId})`) and its fulfilling products'
      details load in the background after the screen opens, about 4 s, never blocking it. Once
      loaded, each fulfilling product is its own option: placed before an approved product it
      fulfils for on the page (legacy's order for a product without stock of its own), and also
      matched by its own name against the typed text, so a search finds it as legacy's does.
      Until then the list shows approved products only.
    - **More results:** a Show More item at the end of the list loads the next page of 50, so
      every approved product stays reachable even when many share a name.
    - **Status:** the Lots page's product search status helper, moved to
      `src/lib/product-search-status.ts`, reports how many are shown of how many match, and that
      typing finds more.
    - **Picked option:** kept while the list changes.
    - **Sole option:** a sole product is picked only when the program has exactly one approved
      product (`totalElements === 1` with no search). This is legacy's `select-one-option`.
- **On picking a product** (approved products), these load in parallel:
  `lotsByTradeItemsOptions([tradeItemId])` when the product has a trade item, and
  `eventStockOnHandOptions({facilityId, programId, orderableIds: [approvedId]})`. The approved id
  is the product itself, or the approved product it fulfils for.
  - **Lot list:** built by `receiveLotOptions` in `lib/products.ts`, in this order:
    - "Add New Lot", first, when `canManageLots` and the product has a trade item;
    - "No Lot Defined";
    - every lot by expiry ascending, expired included.
  - **Stock on hand** of each candidate is read from the summaries by
    `stockKey(orderable, lot)`. A lot or product with no card has `null` stock on hand, shown
    blank.
  - **Lot field visibility:** the Lot field shows only when there is more than No Lot Defined to
    choose from; otherwise the no-lot entry is picked as the sole option and Lot stays hidden, as
    on Issue.
  - **While loading:** Add stays disabled while lots or stock load. A failure shows an inline
    error with Retry in the panel.
- **New lot in the picker:**
  - Choosing Add New Lot reveals New Lot Code (required) and Expiry Date (optional) in the panel,
    as legacy. Expiry Date is a `DatePicker` with `earliest` = today; these fields sit outside
    the TanStack form.
  - The picker sits inside the editor's `<form>`, so Enter in New Lot Code runs Add and never
    submits the event.
  - Add validates them, then adds a line whose lot is `{lotCode, expirationDate, tradeItemId}`
    with no id and stock on hand 0.
  - The panel keeps the typed values after Add, as legacy.
- **New lot on the line:**
  - The Lot Code cell shows the code as a link-styled button opening an Edit Lot `FormDialog`
    (Lot Code, Expiry Date, Cancel, Save) with legacy's Edit Lot rules (Rules).
- **Lines:** `EventLine` changes in four ways:
  - `destination` and `destinationComments` become `counterparty` and `counterpartyComments`.
  - `stockOnHand` becomes `number | null`, along with `ScanCard.stockOnHand` and the row schema.
    The cap compares only numbers, and the keyword filter skips a `null` stock on hand.
  - `lot` becomes `LotSummary | NewLot | null`, where `NewLot = {lotCode, expirationDate,
    tradeItemId}`.
  - It gains `productHasLots`, set when the line is added. It replaces the table's
    `productsWithLots` from cards (`event-line-table.tsx:162-164, 472-475`) for every kind, so the
    no-lot cell says No Lot Defined or Product Has No Lots, as legacy.
  - The payload maps `counterparty` to `destinationId` or `sourceId`, and a new lot to `lot`.
- **Columns:**

### Risks And Edge Cases

- **Unsorted pages:** `approvedProducts` has no `ORDER BY`. Pages were consistent in 10-page and
  repeat checks, but the order is not guaranteed. Show More reads the next page of the same
  search.
- **Wildcards:** `%` and `_` in the search match every product, since the server does not escape
  them in `ILIKE`. This is accepted.
- **Fulfilling products arrive after about 4 s:** until the background map loads, only approved
  products are listed. No data on test or UAT has fulfilments today.
- **Approval changes:** approval saves on the Products page do not invalidate the
  approved-products search key. The picker sees them on its next fetch or reload, which is
  acceptable for an admin change.
- **Lot races:** a lot with the same code created elsewhere after the lots loaded is silently
  reused by the server with its own expiry, and the receipt still lands on it. A new lot created
  for an event that then fails stays in reference data, as legacy's POST-first flow leaves it.
- **No sources** for the program: Received From is empty and Submit cannot pass. The editor says
  no sources are set up.
- **No `STOCK_CARDS_VIEW`:** as Issue, stock cannot be read, so the editor explains instead of
  opening (legacy fails the same way).
- **Shared editor refactor** touches Adjustment and Issue. Shared commits come first, with both
  kinds' suites green before any Receive code.

## Decisions

- **Products come from the paged approved products search, not legacy's full download.** It offers
  the same 10,003 and 26 products and is about 100 times faster. The ticket's "same API calls as
  legacy" yields to its performance criteria here; every other call is legacy's.
- **Name search in one Product box:** legacy's select2 searches product names, so typed text is
  sent as `orderableName`.
- **Fulfilment, lots and stock on demand:**
  - fulfilling products from one facility fulfilment request in the background (about 4 s),
    instead of legacy's 256 requests by id, so they are found by their own names as in legacy;
  - lots and stock on hand per listed page of 50 products.
- **New lots go inline in the stock event,** as the backend on master allows, for both typed and
  scanned lots, rather than legacy's separate POST for typed ones.
  - The UI keeps legacy's `LOTS_MANAGE` gate on Add New Lot, since the server does not check it.
  - The duplicate check covers any letter case and the whole trade item. Both match how the server
    resolves inline lots, so a typed code can never be silently merged into another lot.
- **Lot Code and Expiry Date are always shown on Receive;** VVM Status follows the draft lines.
  Legacy derives both from the full product list, which is no longer downloaded.
- **Stock on hand is blank for a lot or product without a stock card,** in both units (empty cells
  stay blank). Legacy shows "0 ( +0 )" in Packs.
- **Layout as Issue (agreed in FM-64):** tables stay tables, optional columns hide by measured fit,
  and the rest scrolls inside the card. This is the house reading of "stacks without horizontal
  scrolling".
- **Print after submit is ported,** shared with Issue through the `print` policy.
- **Routes keep passing the default reason,** so Issue's tests are untouched; it is not a kind
  field.
- **The real submit check runs on test.openlmis.org;** UAT is read-only.

Departures from the plan and findings carried forward:

- **Rescanning a draft new lot** counts on its line without the expiry question, as legacy;
  the question is asked only for lots the server already holds.
- **Received From and Issue To can be cleared** with Select An Option, as legacy's clear button
  allows; Submit then marks the line required. The next line copying the source and reason after
  Clear is legacy's own behaviour, since legacy never resets its last added line.
- **Lots and stock on hand are preloaded** for each listed page of products, in one lots request
  and one stock on hand request per page, so picking a listed product is ready at once, as in
  legacy, without legacy's long first load. The picked product's own lots and stock start from
  its page's data and stay fresh for a minute, so a pick sends no request and keeps its lots
  across later searches. Only a pick made before its page's data arrives shows the spinner on
  Add, while a status line announces Loading Lots.
- **Every invalid line stays marked after a failed Submit,** including lines added later and
  lines on other pages, and the pager turns pages holding invalid lines red, as legacy's pager
  does. The form revalidates whenever the shown lines change, since fields that mount lose their
  stored errors. The invalid and failure dialogs carry the error icon Reverse uses.
- **Fulfilling products that fail to load** show an error with Try Again rather than silently
  leaving those products out.
- **The new lot and Edit Lot expiry fields** use a Pick A Date placeholder, so screen readers hear
  "Expiry Date" once, as legacy's labelled date input reads.
- **Receive editor tests for Received From and Source Comments, no sources and a sources error**
  were not duplicated: these run the same counterparty code as Issue's tests, keyed by side, and
  the source payload is covered in `event-form.test.ts`. The Receive editor tests read sources
  through `validSourcesOptions`, so a wrong lookup fails them.
- **The past expiry message** cannot be reached by hand, since the calendar disables past days;
  it still guards scanned lots.
- **Arabic uses two words for lot** in the lot list ("تشغيلة" from `stock-events.lot-code`,
  "دفعة" from `stock-events.no-lot-defined`), an existing inconsistency in master's catalog.
