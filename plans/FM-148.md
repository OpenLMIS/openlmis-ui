## Summary

A requisition template decides what a requisition form looks like for one program at some
facility types: which columns it shows, in what order, under what names, and how each value is
filled in (typed by the user, calculated, or read from stock cards). A facility cannot start a
requisition until a template exists for its program and facility type.

In the old UI, Administration > Requisition Templates lists templates under one heading per
program, alphabetically, with each template's name, its facility type (or "2 Facility Types",
with the names in a hover tooltip, as legacy), whether it is report only, and a cog icon to configure it. Programs
without a template say so. Add Requisition Template opens a window with a name, a program, a
report only checkbox and a table of facility types; facility types can only be picked after the
program, and types another template of that program already uses are not offered. Creating
asks for confirmation, then opens the new template's configuration.

The new screen does all of that as legacy does (the user's decision, 2026-10-14), with only the
fixes the ticket asks for and one that prevents lost data: report only reads Yes or No instead
of "false"; a template needs at least one facility type, which legacy forgot to check; the
bottom bar no longer covers rows; and facility types that were deactivated still show by name
instead of vanishing from the count.

## Legacy Today

Route `/#!/administration/templates` (`openlmis.administration.requisitionTemplates`), right
`REQUISITION_TEMPLATES_MANAGE`, from Administration > Requisition Templates. Evidence:
`.screenshots/FM-148/research-a-legacy-browser.md`, `research-b-source-api.md`,
`verify-legacy.md`, `verify-api.md`, and `legacy/list-*.png`, `legacy/add-*.png`.

- **List**: one heading per program, every program the API returns, sorted by name; templates
  sorted by name. Columns Template Name, Facility Type, Requisition Report Only, Action
  (a cog icon button). A template with several types shows "{n} Facility Types" with a hover tooltip
  of names; names come from the active facility types, so an inactive type silently drops out of
  the cell and the count. Empty programs keep the table header and say "No requisition templates
  for {program} program". Report Only prints the raw boolean. Add Requisition Template sits at
  the end of the fixed bottom toolbar.
- **Add** (`/#!/administration/templates/add`): Name and Program (API order) required,
  Requisition Report Only checkbox, then a Facility Type select sorted by name, disabled until a
  program is chosen, under the note "You need to select program first", with Add Facility Type,
  and a Facility Type Name / Actions table ("No facility types added yet"). Changing program or
  report only clears the chosen types.
- **Offered types** (`template-add.controller.js:188`): active types, minus types other
  templates of the program use. For a report only template, only other report only templates
  count; otherwise every template of the program counts.
- **Create**: an empty form shows "This field is required" and "This form is invalid". Any valid
  form opens "Do you want to create a new requisition template for the {program} program?", then
  POSTs, toasts "Requisition template created successfully" and opens the new template's Columns
  tab. Zero facility types pass: the POST carries `facilityTypes: []`, which the server stores as
  a template with no type and report only forced off. Duplicate names are refused only by the
  server. Legacy's default columns give Average Consumption the source Stock Cards, which its own
  Columns tab then refuses.
- **Rights**: srmanager2 has no menu entry and is refused the URL.

## Agent Brief

### API Map

All under `/api`, master, verified live on test.openlmis.org (GETs only).

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| List and eligibility | `GET requisitionTemplates` | none (unpaged array of templates that are not archived, about 225 kB for 7: each item carries its full `columnsMap`) | `id`, `name`, `program.id`, `facilityTypes[].id`, `requisitionReportOnly` | `REQUISITION_TEMPLATES_MANAGE` | `admin-template-list.routes.js:36` |
| Programs | `GET programs` | none | `id`, `code`, `name` | none | `:39`; already `programsOptions()` |
| Facility type names | `GET facilityTypes` | none (a page with default size `Integer.MAX_VALUE`, so every type) | `id`, `code`, `name` | none | not in legacy; `facilityTypesOptions()` |
| Facility types offered | `GET facilityTypes?active=true` | `active=true` | `id`, `code`, `name` | none | `:42`; `facilityTypesOptions({ active: true })` |
| Column catalog for Create | `GET availableRequisitionColumns` | none (a page holding all 33) | every field, copied whole | none | `admin-template-add.routes.js:34` |
| Create | `POST requisitionTemplates` | body below | `id` of the 201 response | `REQUISITION_TEMPLATES_MANAGE` | `template.js:93` |

The unfiltered facility types call is the one addition to legacy's set: legacy only reads
active types and so loses inactive ones (see Decisions).

**Create body**, built by `buildNewTemplate` from the catalog (legacy
`template-add.controller.js:222`, `template.js:153,439,449`):

```json
{
  "name": "...", "program": { "id": "..." }, "facilityTypes": [{ "id": "..." }],
  "requisitionReportOnly": false, "populateStockOnHandFromStockCards": false,
  "rejectionReasonWindowVisible": false, "patientsTabEnabled": false,
  "numberOfPeriodsToAverage": 3,
  "columnsMap": { "<name>": { "name", "label", "indicator", "definition", "displayOrder",
    "isDisplayed", "source", "option", "columnDefinition" } }
}
```

- Every catalog column, keyed by `name`. `label`, `indicator` and `definition` copied from the
  catalog; `columnDefinition` is the catalog object unchanged (the server refuses a modified one).
- Order: locked columns (`canChangeOrder: false`) first, in the order `skipped`,
  `orderable.productCode`, `orderable.fullProductName`, then any other locked column; then the
  movable columns in the order the catalog returns them (the server does not sort it).
  `displayOrder` counts from 0. Legacy's lock order constant still uses the old product column
  names; the new code uses the current names.
- `isDisplayed` true except `averageConsumption` and `calculatedOrderQuantityIsa`, as legacy.
- `source`: `USER_INPUT` when offered, otherwise the first source, as legacy. This gives
  `averageConsumption` (hidden) the source Stock Cards, which the Columns tab then flags until it
  is changed or the stock flag is turned on, as in legacy.
- `option`: the first catalog option as the whole object (`id`, `optionName`, `optionLabel`):
  the server compares all three. Omitted when the column has none.
- `program` and `facilityTypes` as `{ id }`; legacy sends whole lookup objects, the server reads
  only `id`. Legacy omits the rejection reason and patients flags; the server stores false
  either way, so sending false changes nothing.

**Server rules** that shape the dialog (requisition master):

- One template per program, facility type and report only flag
  (`20230206102658839__update_template_assignments_index.sql:35`). A clash answers 400
  `requisition.error.validation.programFacilityTypeAssignmentExists`.
- Names are unique, ignoring case (`lower(name)`), among templates that are not archived,
  across all programs; a clash answers 400
  `requisition.error.validation.templateNameDuplication`. Name is `varchar(255)`.
- Errors answer `{ messageKey, message }`; `serverMessage` reads `message` already.

### Data Flow

- Route `src/routes/(protected)/_protected.administration.requisition-templates.tsx`. Loader:
  `await requireRight(queryClient, RIGHTS.requisitionTemplatesManage)`, with a
  `pendingComponent` for that wait as Programs; then prefetch, without awaiting, templates,
  programs and the unfiltered facility types. `QueryBoundary` around the program sections; the
  header and its Add button render at once.
- Search: `{ template?: 'new' }`, with `CLOSED_DIALOGS = { template: undefined }` and
  `useSearchNavigation`, as Programs. Only Add is a dialog, so `'new'` is the only value; anything
  else is dropped by the schema.
- Keys: `queryKeys.requisitionTemplates` (`list()` here, `detail(id)` in FM-149) and
  `queryKeys.availableRequisitionColumns` for the catalog, which no save changes. Create
  invalidates `requisitionTemplates.all`.
- The dialog prefetches the catalog and the active facility types when it opens. Program and
  facility type fields each sit in a `LookupBoundary`; the facility type field also needs the
  template list for eligibility, which the page has loaded. Create `ensureQueryData`s the catalog
  first; if that fails, the dialog keeps the draft and shows `ErrorAlert` with the server's
  message, and Create retries.
- After Create, toast "Template Created" with legacy's "Requisition template created successfully.", then
  `navigate` to the configure route with the new id (FM-149), replacing the `?template=new`
  entry so Back returns to the list.

### Rules

- Program sections: every program from `GET programs`, sorted by `programName` with
  `localeCompare`; templates by name the same way.
- Facility Type cell: one type shows its name; more than one shows "{count} Facility Types" and
  shows a tooltip on hover or focus listing the names in saved order. Names come from the unfiltered lookup, so
  inactive types still count and show. An id the lookup does not know shows nothing and still
  counts.
- Offered types, legacy's rule (`eligibleForNewTemplate`): active types, sorted by name, minus
  types already in the table, minus types other templates of the chosen program use. For a report
  only template only other report only templates count; otherwise every template of the program
  counts. Changing the program or report only clears the table, as legacy.
- When no type is left: the picker says "Every facility type already has a template for this
  program." and Add stays disabled.
- Name: required, trimmed, at most 255. No client duplicate check, as legacy; the server's 400
  for a duplicate name lands on the Name field, and any other failure shows in `ErrorAlert` with
  legacy's "Failed to save the requisition template" and the server's message.
- Create first confirms, as legacy: "Do you want to create a new requisition template for the
  {program} program?" with Create and Cancel.
- Facility types: at least one ("Add at least one facility type."), shown under the table.

## UI/UX

**Port**: grouping, order, columns, empty messages, the tooltip, the Add fields, the facility
type picker and table, and its rules.

**Improve**, only where the ticket asks or data would be lost:

- Report Only reads Yes or No (No muted, as Reasons' Allow Free Text).
- At least one facility type is required.
- Inactive facility types keep their name and count.
- Add sits in the page header beside the title, instead of a fixed bottom
  toolbar that covers rows.

Everything else follows legacy, including the Create confirmation, programs in API order in the
dialog, server-only duplicate names and legacy's default
columns. The pickers are this app's searchable comboboxes, holding the same options in the same
order.

**Drop**: nothing.

**Layout**: `Workspace` with an icon, title Requisition Templates and a one-sentence
description. Each program is a section with its name as a heading and a table of Template Name,
Facility Type, Requisition Report Only and Action (Configure). The four columns stay at every width;
the table scrolls sideways on a phone. The dialog: Name, Program, Requisition Report Only, then
the facility type picker with Add and the table below.

**States**: a pending page while rights load; then three program headings with two-row table
skeletons, without pager placeholders; `ListError` with retry; an empty program shows its
message; a deployment with no programs shows one empty state. In the dialog, each lookup field
has its own loading and error state.

## Decisions

The user chose legacy's behaviour for everything (2026-10-14).

- **Add stays a dialog**: four fields and one save, as legacy and the house rule.
- **Legacy's facility type picker and table in the dialog**, with trash Remove.
- **Legacy's eligibility rule and clearing**, stricter than the server, which only refuses the
  same program, type and report only flag.
- **Legacy's confirmation before Create**, programs in API
  order, no client duplicate name check, and legacy's default columns (Average Consumption on
  Stock Cards).
- **At least one facility type**, as the AC asks, although legacy and the server accept none.
- **After Create, open the configure page**, as legacy; the list is refreshed for the way back.
- **Inactive types are named from the unfiltered lookup**, one extra cached GET, so saved
  assignments never vanish from the cell.
- **Pager opt-out on `DataTableSkeleton`**, additive and default unchanged, so grouped tables
  without a pager get a matching skeleton.
