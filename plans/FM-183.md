# FM-183: Programs: Page and Sort the List on the Server

https://openlmis.atlassian.net/browse/FM-183 · Parent: FM-177 Potential BE Improvements

## Scope

Two changes:

- **Backend** (`openlmis-referencedata`, a PR to `migration`): a paged, sorted search for
  programs.
- **Frontend** (this repo, in PR #34, FM-142 Programs): the Programs list moves from paging in
  the browser to that search.

`GET /api/programs` stays exactly as it is, a plain array of every program. Out of scope: any
other change to programs (FM-180, FM-181, FM-182).

## Summary

The Programs screen loads every program and pages and sorts them in the browser, because the
server can only return the whole list. That is fine for a handful of programs, but it is the one
admin list that works this way, and it would not scale.

Upstream tried twice in 2019 to add paging to the existing endpoint and reverted it both times:
changing what `GET /api/programs` returns broke every caller that reads it as a list, the legacy
UI and other services among them. So the list stays as it is, and a separate search returns one
page at a time, sorted, with the total count, the way facilities and orderables already work.

For users nothing changes on screen. The Programs list pages and sorts the same way, now done by
the server.

## Acceptance Criteria

| AC | How it is met | How it is checked |
| --- | --- | --- |
| `GET /api/programs?page=0&size=10&sort=name,asc` returns one sorted page with the total count | `POST /api/programs/search?page=0&size=10&sort=name,asc` returns a Spring `Page` (see Decisions: a new search, since `GET` cannot change shape) | Repository and controller integration tests; a call on the local backend |
| A request without paging params still returns every program | `GET /api/programs` is untouched; the search without `page`/`size` returns every program in one page | Existing `GET` tests unchanged; a new test for the unpaged search |
| Once it ships, the new UI's Programs list moves to server paging | The list reads the search like Facility Types; browser paging and sorting removed | Unit tests, browser |

## Agent Brief

### Backend

`POST /api/programs/search`, beside the existing `GET /api/programs/search?name=`:

| Part | Behaviour |
| --- | --- |
| Query params | `page`, `size`, `sort` (`code`, `name`, `active`, each `,asc` or `,desc`); no `size` returns every program, as other searches here do |
| Body | Optional: `{ "code": "...", "name": "..." }`, each matched as a part of the value, ignoring case, like the supervisory node and facility searches; any other key is a `400` (`referenceData.error.program.search.invalidParams`) |
| Unknown sort field | `400 referenceData.error.program.search.invalidSortingColumn` "Invalid sorting property: {0}", instead of the `500` Spring gives elsewhere |
| Response | `Page<Program>`, items shaped exactly as `GET /api/programs` returns them |
| Right | None, as `GET /api/programs` |

Files:
- `ProgramController`: the `POST /search` mapping.
- `ProgramRepositoryCustom` / `ProgramRepositoryImpl`: `search(params, pageable)` with a criteria
  query and a count query, as `SupervisoryNodeRepositoryImpl`; sorting by `code` reads the code
  inside the embedded `Code`.
- `ProgramSearchParams`: reads the body; `ProgramMessageKeys` and `messages_en.properties`: the two
  keys.
- `api-definition.yaml`: the new method; `CHANGELOG.md`: a line under the unreleased version.

Tests, written first:
- `ProgramRepositoryIntegrationTest` (real database): pages with the total count; sorts by code,
  name and active both ways; filters by code and name ignoring case; no size returns all.
- `ProgramControllerIntegrationTest`: returns the page and passes the paging on; refuses an unknown
  sort field and an unknown body key with `400`; works with no body.

Never merged without the user and the core team (backend PR rule).

### Frontend (PR #34)

- `src/features/programs/api/api.ts`: `fetchProgramsPage(query)` posts `{}` to
  `/programs/search` with `page`, `size`, `sort`; `queries.ts`: `programsListOptions(query)` on
  `queryKeys.programs.list(query)`, apart from the lookup's `list()` key.
- `lib/search.ts`: `toProgramsQuery(search)`, as Facility Types' `toFacilityTypesQuery`.
- `programs-table.tsx`: server paged like Facility Types, with `useDeferredValue` and the
  past-the-end step back from `totalPages`; `programs-list.ts` and its sort go.
- The dialog keeps the unpaged lookup for the code check on Add; a save invalidates the lists.
- `AGENTS.md`: Programs leaves the "endpoint cannot page" rule, Roles stays its example.

The Programs PR can only merge after the backend PR is on `migration` and its image is deployed,
or the list fails on servers without the search. Locally,
`../openlmis-ref-distro/use-local-referencedata.sh origin/FM-183` runs it.

## Decisions

- **A new search, not a changed `GET`**: the two upstream attempts to page `GET /api/programs`
  were reverted for breaking its callers; `POST /<resource>/search` with a `Page` is how this
  service pages other lists.
- **Code and name filters now**, though the list has no search box yet: they cost one predicate
  each and match the other searches, so a search box later needs no backend change.
- **Unknown sort fields are a `400`**, unlike other endpoints (see FM-178), since a `500` says
  nothing to the caller.
