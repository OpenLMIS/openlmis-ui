# FM-43: Requisition: Approve Mode

https://openlmis.atlassian.net/browse/FM-43 · Parent: [FM-39] Requisitions

Shipped in one PR with [FM-45] (approval list), branch `feat/fm-45-43-approve`.

## Scope

- Opens approver editing on the requisition page built in [FM-41]/[FM-44]: approval columns,
  Sync, Approve, Reject with reasons when the template asks for them, return to the approval
  list.
- Approver unskip of skipped lines when the deployment's unskip setting is on.
- Not in scope: Patients templates ([FM-42]); their approvers keep the read-only page with the
  legacy link, so `LegacyActionsNote` stays for them only. Batch approval ([FM-46]).

## Summary

After a requisition is authorized, approvers up the supervision chain review it, can change the
approved quantity and add remarks, then approve or reject it. Approving at the top of the chain
moves it on to ordering; rejecting sends it back to the facility.

Today the new UI shows these requisitions read-only with a link to the old UI. With this change
approvers work in the new page: only Approved Quantity and Remarks are editable, totals follow the
approved quantity as they type, Sync saves their changes, and Approve or Reject ask for
confirmation and then return to the approval list. When the template asks for rejection reasons,
Reject first asks for them. Errors are checked before the confirmation; legacy asks first and
checks after.

## Legacy Today

Walked as psupervisor on AUTHORIZED Family Planning (Comfort Health Clinic, Mar2017) and an
IN_APPROVAL ARV record, writes stubbed. Findings: `.screenshots/FM-43/research-a-legacy-browser.md`,
`research-b-legacy-source-api.md`; screenshots `.screenshots/FM-43/legacy-*.png`.

- Footer: Save/Sync with Server at the start, Reject and Approve at the end; Print in the header;
  no Delete, Submit or Add Product. Skip checkboxes shown, disabled.
- Editable: Approved Quantity (Packs/Doses input, whole numbers, required, at most 2147483647) and
  Remarks (250) on both tabs. Total cost updates on every change.
- Approve: "Are you sure you want to approve this R&R?", then validates ("R&R has errors, please
  correct them to proceed."), saves (`PUT v2/requisitions/{id}`, `If-Match`), `POST
  requisitions/{id}/approve` with `{}`, toast "Requisition has been approved!", back to the
  previous screen (default the approval list).
- Reject: with the template's rejection window, a Rejection Reason dialog (Category, Reason, Add,
  table with Remove, Update enabled once one is added); then "Are you sure you want to reject this
  R&R?", save, `PUT requisitions/{id}/reject` (reasons as the body, otherwise none), toast
  "Requisition has been rejected!", back.
- Sync: PUT, then reloads the record and a 5.3 MB `requisitionGroups` list; "Requisition has been
  synchronized!". Sync while invalid still saves.
- Defects not ported: confirmation before validation; duplicate and inactive reasons offered; the
  unskip setting opening every column and Add Product.

## Agent Brief

### API Map

| Step | Method And Path | Body | Right | Notes |
|---|---|---|---|---|
| Sync | `PUT v2/requisitions/{id}` with `If-Match` | whole record (existing `transform.ts`) | APPROVE at facility/program | Server keeps only `approvedQuantity`, `remarks`, `skipped` and `extraData` for approvers |
| Approve | `POST requisitions/{id}/approve` | `{}`, `Idempotency-Key` | APPROVE at the current node | 409 `approve.inProgress` or reused key; 400 validation; response status IN_APPROVAL, APPROVED, RELEASED or RELEASED_WITHOUT_ORDER |
| Reject | `PUT requisitions/{id}/reject` | `[{rejectionReason:{id,name,code,active,rejectionReasonCategory}}]` when the window is on, else none; `Idempotency-Key` | APPROVE at the current node | 400 `missingRejectionReason`, `requisitionWasSplit` |
| Reasons | `GET rejectionReasons`, `GET rejectionReasonCategories` (existing reference-data options) | | none | active only, sorted locally |
| Unskip setting | `GET requisitions/unSkipRequisition` | | none | `{ unskipRequisition: boolean }` |

### Data Flow

- Capabilities (`lib/capabilities.ts`): add approve and reject to `SHIPPED_ACTIONS`, open
  `approverEditing`, drop the TB Monthly approver extras until [FM-42], and pass
  `unskipWhenApproving` from a new `unskipSettingOptions` query through `capabilityContext` and
  `pendingPolicy`. Patients templates stay closed ([FM-42]).
- API (`api.ts`): `transition()` gains approve and reject (reject with an optional reasons body),
  each with the attempt's `Idempotency-Key`.
- Route action mutation: Approve and Reject join the existing save-then-transition flow; the
  mutation variables carry the reject reasons. Before the confirmation, Approve validates only
  `policy.editableColumns` on non-skipped lines (`validateRequisition` gains a column filter) and
  opens the existing invalid dialog on failure; it never takes the stock-count-date branch of
  `begin`. Reject needs no validation. The save before the transition always runs, as legacy;
  its 409 and 403 use FM-41's existing save-failure path.
- Uncertain outcomes (no response, 5xx, any 409): keep the attempt, its key and the saved
  baseline, and block Sync, Approve and Reject until it is reconciled. Refetch: approve is done when
  the status is APPROVED, RELEASED or RELEASED_WITHOUT_ORDER, or IN_APPROVAL at another
  `supervisoryNode`; reject is done when the status is REJECTED. Any other change (for example
  someone else rejected) is a conflict: reload the record without announcing success.
  `modifiedDate` alone proves nothing. `approve.inProgress` keeps the attempt and reconciles again
  on the next click with the same key; only a definite failure (a 4xx other than 409, or a
  refetch showing the record unchanged after an `idempotencyKey.alreadyUsed` 409) releases the
  block and takes a new key.
- Return: `requisitionReturn` widened to `/requisitions/approve` ([FM-45]). Without it the page
  returns to View Requisitions, as today, so View Requisitions users are not sent elsewhere.
- Existing invalidation of `queryKeys.requisitions.all` and `queryKeys.home.all` already covers
  the list and Home counts.

### Rules

- Editable for approvers: approved quantity and remarks only. TB Monthly's extra columns depend on
  the Patients tab on the server, so they wait for [FM-42].
- Skipped lines keep their stored value on every approver save: `lib/transform.ts` sends each
  line's stored `skipped` when the Skip column is hidden, since the server turns null into false
  during approval (`RequisitionLineItem.java:408-412`). A shown Skip column stays visible and
  disabled for approvers, as legacy, unless the unskip setting is on.
- Reject hidden on split partner copies (existing); a split original gets the server's
  `requisitionWasSplit` message.
- Reasons: active reasons of active categories, sorted by name, no duplicates; at least one when
  the template's `rejectionReasonWindowVisible` is on. The dialog lives in the URL as
  `?dialog=reject-reasons` through `useSearchNavigation`, distinct from the existing
  past-reasons `rejection` dialog.
- The gate uses APPROVE at the current node, as legacy; the server also accepts a supervising
  node's APPROVE role, which legacy does not offer either.
- Comments: the existing Add Comment works for approvers, as legacy, and saves with the record.

### Translations

Following the existing patterns: `requisitions.edit.actions.approve` and `.reject`, their
`-confirm` titles and descriptions, `requisitions.edit.success.approve`/`.reject` and
`-description`, `requisitions.reject.*` (dialog title, description, category, reason, add,

### Tests

- Capability test: approver gate open with APPROVE at the current node, closed elsewhere,
  closed on Patients templates; unskip only with the setting.
- Workflow tests (detail route harness): Approve with an invalid approved quantity opens the
  invalid dialog and sends nothing; valid Approve saves then approves with a key and navigates
  to the return target; Reject with the window on requires a reason and sends it; an uncertain approve
  that completes late is reconciled as approved without a second POST; another approver's
  rejection meanwhile is reported as a conflict; repeated clicks while reconciling send nothing;
  creator-column errors do not mark rows invalid for approvers.
- Pure: reason filtering and duplicate prevention if it lands in `lib/`.
- Browser in `review-pr`: psupervisor on the AUTHORIZED and IN_APPROVAL records with writes
  stubbed; reasons dialog with a stubbed template; Arabic; phone cards; network vs legacy.

### Risks And Edge Cases

- No test template enables rejection reasons; checks use a stubbed record. A real check needs a
  template change on test, which needs the user's approval.
- A device draft from read-only days does not exist for approvers; drafts start on first edit.

## UI/UX

**Port**: the action bar, editable columns, confirmations, toasts, reasons dialog, return.

**Improve**: validate before confirming; reasons dialog offers only active, unused reasons; no
5 MB reload after Sync; split originals explain why Reject failed; phone cards for the reasons
table.

**Drop**: the unskip setting's extra editing (only unskip is opened); Sync while invalid stays
allowed, as legacy, since it saves drafts.

## Decisions

- **Approve validates approval columns only**, matching the server; legacy validates every shown
  column, but approvers cannot fix creator columns.
- **Footer order stays FM-41's**, as Stock screens, rather than legacy's Sync at the start.
- **Skipped values are kept** on approver saves.
- **TB Monthly extra columns wait for [FM-42]**.
- **Approver records return to where they were opened**: the approval list through history
  state, otherwise View Requisitions.

## Implementation Notes

- Browser, Arabic visual and live network checks are deferred to review, as the build brief
  forbids browser use and server access. All transport in workflow tests is mocked.
- An uncertain Approve or Reject keeps its original attempt and saved baseline. Its button
  checks the outcome on the next click without resending; the other server actions and edits
  remain disabled. An unchanged read keeps the block, except for an unchanged server baseline
  after an already-used-key response. Existing Submit and Authorize retry behavior is retained.
- The return union uses a separate `approvalReturnState` helper so existing Create/Authorize
  callers keep their current signature.
