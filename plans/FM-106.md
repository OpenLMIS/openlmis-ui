## Summary

After a facility authorizes its forecast, a district approver reviews and approves it. This page
is their inbox: the forecasts waiting for them, with the facility, its district and region, the
period and the date it was sent, and a summary of how many facilities they supervise and how many
forecasts have been sent.

Legacy shows the same summary and table, but downloads every product in the system once per
row before showing anything (about 4 seconds for one row), turns any failed request into "No
reports available", and does not fit a phone.

The new page shows the same information from two requests plus facility lookups, with a
loading state, an error with Try Again, a clear empty state and cards on a phone. The View button
that opens a forecast comes with the approve grid (FM-107).

## Agent Brief

### API Map

| Step | Method And Path | Params | Fields Used | Right | Legacy Ref |
|---|---|---|---|---|---|
| Enter | permissions, `GET /users/{id}/programs` | user id | program `code === 'BUQ'` | `APPROVE_BUQ` anywhere | `buq.routes.js:129-136` |
| Summary | `GET /bottomUpQuantifications/approveFacilityForecastingStats` | `programId` | `totalFacilities`, `totalSubmitted`, `percentageSubmitted` (whole number) | `APPROVE_BUQ` | `ApproveBuq.jsx:105-123` |
| List | `GET /bottomUpQuantifications/forApproval` | `programId`, no paging (the server then returns every row) | `id`, `facilityId`, `processingPeriodId`, `statusChanges` (`status`, `occurredDate`) | `APPROVE_BUQ` | `useFacilityDemandForecasting.jsx:98-133` |
| Facilities | `GET /facilities?id=` (batched, 100 per request) | the rows' facility ids | `code`, `name`, `type.name`, `geographicZone` (name, level, parent) | authenticated | per-row `GET /facilities/{id}` |
| Periods | `GET /processingSchedules`, `GET /processingPeriods` | `processingScheduleId` of code `BUQ` | `id`, `name` | authenticated | per-row `GET /processingPeriods/{id}` |

The list holds Authorized and In Approval forecasts at the user's exact (program, node) pairs
(`BottomUpQuantificationRepositoryImpl.java:204-244`). Errors `{messageKey, message}`; 403 without
the right; 400 without `programId`.

### Data Flow

- Loader: blocks on `requireRight(queryClient, RIGHTS.approveBuq)` and the user's programs;
  `approveAccess(programs)` gives `ready` with the BUQ program or `no-program` (shown with
  `BuqUnavailable`). Then prefetches the stats, the list, the BUQ periods and the deployment time
  zone without awaiting; facilities are read by the table once the list arrives.
- Queries: `buqApproveStatsOptions(programId)` and `buqsForApprovalOptions(programId)` under
  `queryKeys.buq`, so FM-107's approve and reject (writes invalidate `[...buq.all]`) refresh both.
  `facilitiesByIdsOptions(ids)` and `buqPeriodsOptions` from the existing lookups.
- Summary and table each sit in their own `QueryBoundary`: a failed stats call keeps the table,
  and the reverse.
- Rows: one helper joins facility and period, picks the latest Authorized change by date and sorts
  by it, oldest first (who has waited longest), then facility name.
- URL: `page` and `size` (local paging) through the shared list search schema; fixed order, no
  sort UI, as legacy.

### Server-Side Work

- The list is read once without paging, as legacy: it can page but not sort by facility, period
  or date (`sort=authorizedDate` is a 500, no sort gives an unstable order), and an approver's
  inbox is small. Paged and sorted locally.
- Per-row requests drop: the list already carries every field the table needs except facility
  and period names; facilities come in one batch, periods from the BUQ schedule.

### Rules

- Program is the user's program with code `BUQ`; no facility scope on the page (the server
  scopes the list to the user's nodes).
- District Name is the facility's zone name; Region is `regionOf(zone)`, empty when no ancestor has
  level code `Region` (legacy throws).
- Submitted Date is the latest Authorized `occurredDate`, compared as dates, shown in the
  deployment time zone (legacy compares formatted text).
- Percentage Submitted is the server's whole number with a localized percent sign.
- For FM-107 (recorded from the backend): approve checks only the unscoped right and the status,
  so the grid must open only forecasts from this list.

### Risks And Edge Cases

- The summary can disagree with the table (Decisions); the description says what it counts.
- Forecasts approved at a lower node move to the parent node (In Approval) and leave this user's
  list; they appear for the parent's approver.
- A deleted remark or source of funds used in a listed forecast makes the list 500 (vault bug);
  shown as the list error.
- A user with `APPROVE_BUQ` only at a home facility (no node) passes the right check but gets an
  empty list from the server; the empty state covers it.

## UI/UX

**Port**: the summary's three values, the seven columns and their order, Submitted Date from the
Authorized change, 10 per page, "No reports available", no search form.

**Improve**:
- `Workspace` page with a one-sentence description; the summary as a row of labelled values, one
  line on desktop and stacked on a phone.
- Loading skeletons; list and summary errors with Try Again, never shown as empty.
- Rows ordered oldest Submitted Date first, so the longest waiting comes first.
- Cards below 672px, titled by the facility name.
- Localized dates and percent in the deployment time zone.

**Drop**: the loading modal and the global error modal; per-row forecast, product, remark,
facility and period requests.

States: permissions loading, no BUQ program, summary loading or error, list loading, empty, error
with retry. RTL with logical classes; facility and zone names in `<bdi>`.

## Decisions

- **No row action until FM-107**, as FM-104 with Forecast: View and the Actions column come with
  the approve grid, so the AC "each row's action opens the approve grid" moves to FM-107.
- **Summary from the server, as legacy**: the AC asks for legacy's calls, and the server counts
  every forecast of the supervised facilities (any period, any status after Submit), so the values
  need not match the rows. Computing them from the rows would match the table but differ from
  legacy and from FM-108's figures.
- **No search form**: the endpoint has no filters and UAT shows none; an inbox of a few rows per
  approver does not need one.
- **List read whole and paged locally**, oldest first (Server-Side Work).
- **Branch from FM-105**, which is not merged.
