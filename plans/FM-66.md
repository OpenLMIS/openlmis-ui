# FM-66: Adjustment

https://openlmis.atlassian.net/browse/FM-66 · Parent: [FM-62](https://openlmis.atlassian.net/browse/FM-62) Stock management

## Scope

The Adjustment screen for one program at the user's home facility, opened from the Adjustments
program picker ([FM-63](https://openlmis.atlassian.net/browse/FM-63), `plans/FM-63.md`), which
ships in the same PR. It builds the pieces Issue, Receive and Kit Unpack reuse later: the editable
line table, quantity entry in packs or doses, the signature step, the stock event submit and GS1
barcode scanning behind the `GS1_SCANNING` flag. Scanning is built as shared pieces (parser, key
capture, status indicator, resolver) with Adjustment as the first consumer; Issue, Receive and
Physical Inventory plug into them with their own lot rules.

Not in this PR:

- Offline: legacy queues an adjustment submitted offline. That comes with the offline pass
  (FM-166, FM-168); FM-66 stays open until it ships.
- Transaction History (FM-75). Until it exists, a submitted adjustment is checked on Stock On Hand
  and the Stock Card.

## Summary

An adjustment records stock that changed for a reason other than issuing or receiving it:
damaged, expired, stolen or lost stock, or stock returned to the facility. The storeroom manager
picks a program, adds the products and lots that changed, gives each a reason, a quantity and a
date, and submits them together, optionally signing.

Legacy downloads every product of the program before the screen appears: about 23 seconds on the
test server for a program of 10,000 products, of which two have stock. Its phone version takes 30.
The new screen asks the server only for the products that have stock at the facility, which takes
under a second, and shows the same table, reasons, rules and signature step.

It also fixes legacy's input defects: "1.5" no longer becomes 15, "-1" no longer becomes 1, a date
typed in the future is refused, and the table no longer needs sideways scrolling on a tablet or
phone. One screen replaces both the desktop and the phone versions.

Where a deployment turns barcode scanning on, a "Ready to scan" indicator shows in the toolbar. A
hand scanner reads a product's GS1 barcode (product code, lot, expiry) anywhere on the page: the
first scan adds the line, and each further scan of the same product and lot adds one pack to it.

## Legacy Today

Screenshots: `.screenshots/FM-66/` (desktop, tablet and phone, empty, line, validation, filter,
clear, signature, after submit) and `.screenshots/FM-62/desktop-adjustment-*.png`. Evidence:
`.screenshots/FM-66/research-report.md`, `research-b.md`, `network-requests.json`.

- **Route:** `/#!/stockmanagement/adjustment/{programId}/create?page=0&size=10&keyword=`, title
  "HC01 - Comfort Health Clinic - Essential Meds", breadcrumb Home / Stock Management /
  Adjustments / that title. Right `STOCK_ADJUST` for the home facility and program.
- **Toolbar:** Filter (a "Keywords" popover, kept in the URL), Product and Lot Code selects with
  Add, and the Packs/Doses toggle when the deployment allows both. A fixed footer has Clear and
  Submit, both disabled until a line exists. Empty table: "Add a product to make an adjustment.
  You have not added any products yet."
- **Products offered:** every product with a stock card at the facility for the program, also at
  zero stock and with expired lots. The lot select lists "No lot defined" for a card without a
  lot, then lots by expiry; a product without lots shows "Product has no lots". The same product
  and lot can be added more than once.
- **Line defaults:** the first line's date is today; each later line copies the previous line's
  date, reason and comments.
- **Reasons:** for Essential Meds on test: Facility return (credit); Damage, Expired, Stolen,
  Lost, Passed open-vial time limit, Cold chain failure (debit). Comments appear only for a reason
  that allows free text (Lost), up to 255 characters; changing the reason clears them.
- **Quantity:** at least 1, at most the Java int maximum; for a debit reason, at most the card's
  stock on hand, checked line by line. In Packs, the entry is packs plus remaining doses and a
  Total Quantity column shows the doses; the event always carries doses.
- **Date:** required, today or earlier through the calendar, but a typed future date passes the
  client (the server refuses it).
- **VVM Status:** a column when any added product has `extraData.useVVM = "true"`; Stage 1 or
  Stage 2, optional.
- **Lines** page 10 at a time in the browser.
- **Clear** asks "Are you sure you want to clear? This will remove all products and quantities."
  and removes the lines the filter shows.
- **Submit** validates every line. On errors: inline messages and an alert, "Adjustments have
  invalid fields". Otherwise the "Choose signature" dialog (Signature, optional; "Submitted by
  administrator"; Cancel, Confirm) is the confirmation. Success: "Adjustments has successfully
  been submitted", then Stock On Hand for that facility and program. Failure: the server's
  message, lines kept.
- **Defects:** "1.5" becomes 15 and "-1" becomes 1 without a message; a typed future date passes;
  a filter with no matches repeats the "no products added" text; the table and toolbar clip at
  768 and 390 px. The phone version lists programs without checking rights, accepts zero, has no
  Packs/Doses or comments, and loads valid destinations it never uses.
- **Scanning** (flag on): a "Ready to scan" dot in the toolbar, no input field; the page listens
  for fast key bursts ending in Enter or Tab. GS1 element strings with GTIN (01), lot (10), expiry
  (17) and serial (21) are parsed; the GTIN is looked up with `GET /tradeItems?gtin=`, matched to
  a loaded product by `identifiers.tradeItem`, then to its lot by code (case-insensitive) or its
  no-lot card. The first scan adds a line with the usual defaults; each scan adds one pack, in
  doses, to the first matching line. A lot not on the screen is refused (Adjustment never creates
  lots); a recorded expiry that differs from the barcode asks to continue with the recorded date.
  Status: "Checking scan...", "Scan accepted", or the reason it failed, for 2.5 s. Full rules and
  messages: `.screenshots/FM-66/research-gs1.md`.
- **Speed:** `GET /v2/stockCardSummaries` (10,003 rows, 13 to 21 s) then 256
  `GET /orderables?id=` (up to 9 s each): 23.4 s on test to offer two products.

### Data Flow

- **Route** `/stock-management/adjustments/$programId`, search `page`, `size`, `keyword`, as legacy.
- **Loader** blocks on `requirePermissions(RIGHTS.stockAdjust)`, the user record and the home
  facility, then checks the exact grant and that the facility supports the program; otherwise
  `ForbiddenError`. It prefetches, deferred, the stock cards and the valid reasons.
- **Stock cards** `stockCardsForEventOptions(programId, facilityId)`: every page of v1, one cache
  entry, keyed under a new `stockEvents` scope that Stock On Hand's and Stock Card's keys also
  invalidate on submit. Not read when the user lacks `STOCK_CARDS_VIEW` there; a message
  explains instead.
- **Draft** is one TanStack Form array in the page, in memory, behind `useDiscardGuard`. Filter
  and paging change only the search, so the draft survives them.
- **Submit** runs the schema on every line. If anything fails: clear the filter, go to the page
  of the first error, focus it, and show an error toast. Otherwise open the signature dialog;
  Confirm posts once (the button stays pending, and a second click does nothing).

### Scanning

Shared, so Issue, Receive and Physical Inventory reuse it:

- `src/lib/gs1/parse-gs1.ts`: pure `parseGs1(raw, { currentYear })`, legacy's parser: AIs 01, 10,
  17, 21; symbology prefixes `]d2`, `]C1`, `]e0`, `]Q3` optional; GS as `\u001D`; known fixed
  lengths for skipped AIs; GTIN-14 check digit; expiry `YYMMDD` with `DD=00` as the month's last
  day and a 49 years back, 50 ahead century window; lot and serial 1 to 20 characters of the GS1
  set (the regex `lot-form.ts` already uses). Returns `{ ok, gtin, lotCode, expiry (yyyy-MM-dd),
  serial, warnings }` or `{ ok: false, error }`.
- `src/lib/gs1/scan-capture.ts`: pure reducer over key events and timeouts (40 ms gap, at least 8
  characters, suppression from the third character, Enter or Tab suffix, 300 ms idle, 150 ms late
  suffix window, GS from `\u001D` or Ctrl+]). It returns effects: suppress, restore the focused
  field's value, replay a short burst as typing, emit a payload.
- `src/hooks/use-barcode-scan.ts`: runs the reducer on `document` keydown and keyup in the capture
  phase, applies its effects, and calls the screen's handler one scan at a time (a queue, so two
  quick scans never race). Off while a dialog is open, when the flag is off, and after unmount.
- `src/components/scan-status.tsx`: the dot and its `role="status"` text (Ready to scan, Checking
  scan..., Scan accepted, or the error), back to Ready after 2.5 s.
- `src/lib/stock-scan.ts`: pure `resolveScan(scan, tradeItemId, products, lines, policy)` returning
  refuse (with a reason), count an existing line, add a new line, or confirm an expiry mismatch
  first. The policy carries each screen's lot rules (Adjustment: no new lots).
- `reference-data`: `tradeItemByGtinOptions(gtin)`.
- `stock-events/lib/apply-scan.ts`: add one pack in doses (`netContent`, else 1) to the line, or
  add a line with the same defaults as Add.

Adjustment's handler: parse, look up the trade item, resolve, confirm the expiry mismatch when
needed (remembered for this draft only), apply, then show the line (clear a filter hiding it,
turn to its page) without moving keyboard focus.

### Risks And Edge Cases

- **A submit with an unknown outcome** (connection lost after sending) is never resent: the
  lines stay, and the page says to check the stock card before submitting again.
- **Two debit lines on one card** each pass on their own, as in legacy; the server refuses the
  event if together they go below zero, and its message is shown.
- **Stock that changed since the page loaded**: the server's check decides, as in legacy.
- **A scanner set up without the GS separator** can make a lot swallow the expiry; legacy has the
  same limit. The message tells the user to report it to an administrator.
- **Scan while typing** in a cell: the first two characters reach the field and are put back once
  the burst is a scan, as legacy.
- **The signed-in user changes** while the page is open: the cache clears and the loader's grant
  check runs again.

## Decisions

- **Paged v1 summaries instead of legacy's unpaged v2**: 0.8 s against 14 s for even the paged
  v2 on the test server, same right, product and lot already resolved. The difference in which
  cards appear is noted under Server-Side Work.
- **Rights as legacy**: `STOCK_ADJUST` opens the screen; loading products needs
  `STOCK_CARDS_VIEW`, exactly as legacy's call does. The new UI explains the missing right.
- **Desktop legacy's behaviour wherever the phone version differs**: rights-checked programs,
  zero refused, comments and Packs/Doses available, signature step.
- **Clear removes the lines the filter shows**, as legacy, and the confirmation says how many.
- **Debit check per line**, as legacy; the server catches combined lines.
- **In-memory draft with a discard guard**, as legacy desktop. Keeping drafts across a reload or
  offline belongs to the offline pass.
- **Feature `stock-events`** hosts every event screen, so Issue and Receive reuse the table
  without importing another feature.
- **Barcode scanning in this PR**, behind `GS1_SCANNING` (the user's call), built as shared pieces
  for the later event screens. Adjustment never creates lots, as legacy.
- **The real submit check runs on test.openlmis.org** (the user's call): one adjustment, then its
  effect on Stock On Hand and the Stock Card. Routine browser checks stay read-only with the submit
  stubbed.
- **One PR with FM-63**, picker commits first (see `plans/FM-63.md`).
