## Summary

Administrators use Geographic Zones to inspect the geographic hierarchy and maintain
catchment populations. Legacy offers a paged list, four filters, a details modal and a
population modal listing a zone's direct children.

The new screen preserves those capabilities and the deployment's population-editing rule.
With automatic calculation off, every zone's population can be edited. With it on, only
zones at the lowest configured level can be edited; other zones open read-only. The server
recalculates ancestor populations when automatic calculation is on.

Filters stay in the address, Parent becomes searchable, levels show their names, and invalid
population text is rejected before saving. Population visualization keeps the stored total
and lists every direct child. Saves show useful server errors and refresh shared zone data.

### API Map

manage right on the server. The UI still applies the legacy manage gate before fetching.
Backend master `9f258aa4` was compared with remote master on 2026-10-15.

Search `{}` returns all zones; a nonempty body containing only empty values returns 400
`search.lacksParameters`. Trim and omit blank text, absent parent and absent level. Preserve
numeric level 0 if a deployment uses it. Validate URL numbers as finite Java integers before
requesting; invalid UUIDs/numbers fall back to no filter. Unknown but well-formed parent or
level values return 400: retain the URL, show the server message when available and keep
the toolbar's Filters/Clear Filters reachable above the list error. Retry stays in the
existing error view, but correcting/clearing the stale selection is the useful recovery.

Master defaults an omitted page size to `Integer.MAX_VALUE`
(`BE/main/java/org/openlmis/referencedata/CustomWebMvcConfigurerAdapter.java:57`,
`BE/main/resources/application.properties:83`). Thus legacy's unpaged child search returns
all children, not just ten or twenty. Do not introduce a first-page-only child request.
List queries always send both page and size. Name order is explicit because the repository
does not supply a default. No nested Level/Parent sorting is offered.

### Data Flow And Cache

- The loader awaits `requireRight` only, then starts list/levels/parent-option prefetches
  without awaiting them. No detail prefetch. Keep header and toolbar outside the list
  `QueryBoundary`; suspend the table on page data and levels together so actions are correct
  on their first render. Existing rows stay dimmed during deferred list requests. Derive
  the boundary's `resetKey` from the list query so changing filters clears a previous error;
  keep Clear Filters in the toolbar rather than extending the shared error component.
- `geographicLevelsOptions` already sorts by `levelNumber`; take the maximum from the full
  configured list, including levels with no zones. Do not compute it from a filtered page
  or zone lookup. Failed level reads show Retry rather than permissive edit controls. With
  no usable levels, withhold policy-dependent actions and explain the configuration issue.
- The deployment flag is loaded before first render by runtime-config. Read it using
  `useFlag` in the route and pass policy data into the feature. Never read it from
  `import.meta.env`, admin settings or arbitrary query parameters.
- URL owns `page`, `size`, the four filters, `zone=<uuid>` for details and
  `population=<uuid>` for visualization. Fixed name order is the sole supported sort;
  normalize other sort input and leave the default out of the URL. `openDialog` clears the
  other dialog key; if both arrive in a hand-edited URL, prefer `zone`. Use
  `useSearchNavigation` for opening/closing and list state updates. Closing restores the
  originating filters/page; directly linked dialogs replace just their dialog parameters.
- Each dialog mounts a keyed content subtree with `useOpening`; full-detail keys extend
  `queryKeys.geographicZones.detail(id)` with that opening number. Fetch full detail for
  View as well as Edit; do not use a paged/search/lookup row as a save body. The fresh detail
  and configured levels decide the title and whether Save exists, including direct links.
- Reuse the existing geographicZones/geographicLevels scopes. Paged lists use
  `queryKeys.geographicZones.list(query)` with explicit page/size/sort, distinct from the
  array lookup's `list()` key. Children use a distinct tagged list key including parent id
  and opening; never collide with a paged result or the lookup.
- Save uses `useSessionMutation`. On success, invalidate every non-detail query in
  `queryKeys.geographicZones.all` using a `queryKey[1] !== 'detail'` predicate, including all
  paged lists, child results and the existing shared lookup. Mark cached detail queries
  stale without refetching the current draft;
  later dialogs always get new per-opening keys. Auto-calc may change every ancestor, so
  invalidating only the edited id is insufficient. Close and toast only for the same session.
- Pending save disables submission and closing through `useDialogTarget` and its mutation
  key. On failure retain the typed value and show `serverMessage(error)` with a translated
  fallback. Missing details use `DialogNotFound`; other load failures use
  `DialogLoadError`; forbidden/offline states follow existing components.

### Business Rules And Validation

| Setting / Level | Detail Action | Editable Fields | Visualize Population |
|---|---|---|---|
| Auto-calc off, lowest level | Edit | Population only | Hidden |
| Auto-calc off, other levels | Edit | Population only | Available |
| Auto-calc on, lowest level | Edit | Population only | Hidden |
| Auto-calc on, other levels | View | None, no Save | Available |

Lowest means the maximum configured `levelNumber`, regardless of child count. Derive the
same policy for list actions, fresh detail rendering and submission. A direct dialog link
must not bypass it. A missing/unusable level number never grants editing in auto mode.

Population is optional, accepts 0, and ranges from 0 to 2,147,483,647. Use
`wholeNumberText` with optional mode and `toOptionalWholeNumber`, accepting Arabic/Persian
digits and converting blank to explicit `null`. Do not duplicate the shared digit parser.
Negative, fractional, exponent and nonnumeric input is invalid. Preserve an existing
invalid legacy population visibly; Save requires a valid value. Never silently clamp it.

`BE/main/java/org/openlmis/referencedata/domain/GeographicZone.java:77` stores an Integer;
`updateFrom:123` replaces other fields, including nullable coordinates, boundary and
extraData. Preserve nested level/parent ids and all other saved fields. PUT enforces the
manage right but does not enforce the lowest-level restriction, which is a UI policy.
Keep the body's `id` unchanged too. Externally managed zones have additional invariants
for name, code, parent and coordinates (`validate/FhirLocationValidator.java:69` and
`GeographicZoneValidator.java:56`); those checks are conditional on external management,
not a general prohibition on backend edits. Population remains editable under our policy.

`BE/main/resources/application.properties:99` binds auto-calc to
`CATCHMENT_POPULATION_CALC_AUTO`, default false.
`BE/main/java/org/openlmis/referencedata/aspect/CatchmentPopulationAspect.java:71` sums
direct-child populations and saves ancestors recursively. Null children are skipped; an
all-null sum stays null. Do not reproduce this calculation in the browser.

### Risks And Edge Cases

- UI and referencedata containers must receive the same auto-calc setting. No backend
  endpoint exposes it, so a deployment mismatch cannot be detected automatically.
- Whole-record PUT has no demonstrated conditional-update contract. Fresh-per-opening
  reads prevent hover/lookup-cache overwrites; another administrator can still change a
  record while the dialog is open. Do not claim conflict protection.
- Null fields are commonly omitted by the server, and 0 is meaningful. Keep missing table
  values blank; use existing missing-value presentation only outside the table.
- A configured lowest level may have no zones. Do not enable editing at the next level.
- Stale parent/level links can fail server validation. Offer clear recovery without
  silently changing a well-formed selected filter.
- Ancestor sums also return Java integers. Valid child values can still exceed that total
  range when combined; keep the server-error recovery path rather than computing limits
  or ancestor totals in the browser.
- Parent lookup and unpaged visualization can grow. Preserve the agreed complete lookup
  and all-child behavior; do not add new backend contracts or drop rows.

## Decisions

1. Preserve the exact flag-driven Edit/View rule and hide Visualize only on the lowest
   configured level. It is a global level rule, not a leaf-zone rule.
2. `CATCHMENT_POPULATION_CALC_AUTO` is boolean, `deploymentOnly`, default off, matching
   legacy and backend. Admin flag values cannot override it; deployment docs require both
   containers to use the same setting. Local development uses `public/config.json`.
3. Use configured levels for both Level options and the maximum-level policy. Reuse the
   existing sorted zones lookup and `toZoneOption` for Parent.
4. Use URL dialogs and fresh full records per opening. Keep all seven fields; Edit changes
   only optional nonnegative integer population. View is fully read-only.
5. Save immediately without a second confirmation, per the explicit user decision;
   explain ancestor recalculation in the edit description when enabled.
6. Visualization remains a child table, not a chart. The header is the stored population,
   and the unpaged search must include all direct children.
7. Share the existing zone type and cache scope so saves refresh pickers on Facilities,
   Supervisory Nodes and Requisition Groups, plus ancestor data after auto-calculation.
8. Jira's actual parent is FM-124. FM-39 is the shared planning umbrella; no Jira hierarchy
   is changed. Research uses saved evidence, current source and the new read-only legacy
   browser run described above. Save behavior is source-verified and will be checked with
   stubs after approval. Test's observed Edit on District rows is consistent with auto-calc
   off; UAT's ticket observations are consistent with it on, so verify each deployment.
