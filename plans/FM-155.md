# FM-155: System Notifications

https://openlmis.atlassian.net/browse/FM-155 · Parent: [FM-154](https://openlmis.atlassian.net/browse/FM-154) Admin: system & integrations

## Scope

Add the administration page for system notifications: a server-paged list with filters, and one
dialog that adds and edits a notification. Saves refresh the top-bar bell shipped in
[FM-2](FM-2.md).

Not in scope:

- The top-bar bell itself (FM-2, on master). It only gains a refresh after admin saves.
- Deleting notifications: legacy offers no delete, and the ticket does not ask for one.
- The notification audit log, which no legacy screen shows.

## Summary

Administrators post short messages, such as planned downtime, that every user sees in the
notifications bell while the message is active and inside its date window.

In legacy, Administration → System Notifications lists the notifications with Title, Author,
Created Date, Active, Is Displayed and Message, ten per page. A Filter popover narrows the list
by author and to displayed notifications only. Add opens a form with the author prefilled and
Active ticked; Edit opens the same form on its own page with the saved values. Start and expiry
are a date and a time. Legacy downloads every user in the system to fill the author filter, so
an administrator who may manage notifications but not users cannot open the page at all.

The new page keeps the same list, filters and fields. Add and Edit both open in a dialog over
the list. The author filter lists every user, as legacy, and appears for administrators who may
also manage users; the rest of the page works for every notification administrator. Times are
entered and shown in the deployment's time zone, which the form names. On phones the list
becomes cards. Saving updates the list and the bell at once.

## Legacy Today

Researched on test.openlmis.org and in `openlmis-referencedata-ui`; screenshots in
`.screenshots/FM-155/legacy-*`.

- **Route**: Administration → System Notifications, `#!/administration/systemNotifications?page=0&size=10`,
  guarded by `SYSTEM_NOTIFICATIONS_MANAGE` (menu and route). Add is the `/new` modal; Edit is the
  `/{id}` full page. Both keep the list's filter and paging params.
- **List**: columns Title, Author (full name), Created Date (date only), Active and Is Displayed
  (check or blank), Message (full text, wrapped, line breaks kept, shown literally), Actions
  (Edit only). No sorting; server order is Active, then Expiry Date, both descending. Ten per
  page, no size selector. Empty: "No system notifications found."
- **Filter popover**: searchable Author dropdown and an Only Displayed checkbox (unchecked means
  any status), Search and Cancel; applied filters counted on the button.
- **Form**, in this order: Author (disabled; signed-in user on Add, original author on Edit),
  Created Date (Edit only, disabled, with seconds), Message (required textarea), Start Date and
  Expiry Date (optional date and time pickers, each bounding the other; opening an empty picker
  fills in the current date and time), Title (optional, 255 characters with a characters-left
  counter), Active (checked on Add). Buttons: Cancel and Add System Notification / Update
  System Notification. Errors show under the fields and in a "This form is invalid" alert.
- **Feedback**: "System Notification has been created successfully" / "... updated
  successfully"; failures "Failed to create System Notification" / "Failed to update System
  Notification" plus the server message. Saves return to the list and clear the bell cache.
- **Known problems**:
  - Every list transition downloads all users (1,209 on test) for the author filter and name map.
    `GET /api/users` needs `USERS_MANAGE`, so a notification-only administrator cannot load the page.
  - The pickers mean to use the deployment time zone but convert through the browser's: a Warsaw
    browser showed 9:20 and sent 08:20Z while the deployment is UTC. No zone is shown.
  - Typing a date instead of picking one throws `viewValue.toISOString is not a function` and
    nothing saves.
  - The server's unfiltered `isDisplayed` flag can be wrong (below); Arabic paging shows literal
    `{0}` and `{1}`; at 390 px the table scrolls sideways past Message and Actions.
- **Timings**: menu to table 1.1-1.6 s; save to row 1.25 s.

## Agent Brief

### API map

All served by `openlmis-referencedata` (identical on master and v15.7.1).

| Step | Method and path | Params / body | Fields used | Right | Legacy ref |
|---|---|---|---|---|---|
| List | `GET /api/systemNotifications` | `page` (0-based) with `size`, `expand=author` (new; legacy joined names from `/api/users`), optional `authorId`, `isDisplayed=true` | `content[]`: `id`, `title`, `message`, `createdDate`, `startDate`, `expiryDate`, `active`, `author{id,firstName,lastName}`; `totalElements` | any signed-in user (route needs the manage right) | `admin-system-notification-list.routes.js:26-48` |
| Author options | `GET /api/users` (existing `allUsersOptions`, 5 min fresh) | `sort=username,asc`, unpaged, as legacy | `id`, `firstName`, `lastName`, `username` | `USERS_MANAGE` | `admin-system-notification-list.routes.js:40-48` |
| Prefill author name | `GET /api/users/{id}` (existing `userRecordOptions`) | signed-in user's id | `firstName`, `lastName` | self | `current-user.service.js:53-74` |
| Edit read | `GET /api/systemNotifications/{id}` | none (no `expand` support) | all fields; `author{id}` only | `SYSTEM_NOTIFICATIONS_MANAGE` | `admin-system-notification-edit.routes.js:39-55` (legacy reads it only when the row is not on the current page; we always read fresh, Decision 10) |
| Edit author name, cache miss | `GET /api/systemNotifications` | `authorId=<author.id>`, `expand=author`, `page=0`, `size=1` | `content[0].author{firstName,lastName}` | as List | replaces legacy's `GET /api/users/{id}` fallback, which needs `USERS_MANAGE` for other users |
| Create | `POST /api/systemNotifications` | `{author:{id}, message, active, title?, startDate?, expiryDate?}`; no `id`, no `createdDate` | response DTO | `SYSTEM_NOTIFICATIONS_MANAGE` | `admin-system-notification-edit.controller.js:106-116` |
| Update | `PUT /api/systemNotifications/{id}` | full record: body `id` equal to the path id, original `author.id`, original `createdDate` string as received | response DTO | `SYSTEM_NOTIFICATIONS_MANAGE` | same |

- Only `authorId`, `isDisplayed`, `expand`, `page`, `size`, `sort` are accepted; anything else is
  `400 invalidParams`, so the URL's `displayed` must map to `isDisplayed` and never pass through.
  `page` without `size` is `400`.
- Dates are ISO 8601 instants; send `Z` strings and `null` for cleared dates.
- Errors carry `{messageKey, message}` under `referenceData.error.systemNotification.`: `400`
  `message.required`, `author.required`, `createdDate.required`, `startDate.after.expiryDate`,
  `id.provided`, `idMismatch`, and `referenceData.error.validation.isInvariant` for a changed
  author or created date; `403` without the right; `404` for an unknown id on `GET`. Map field
  refusals with `fieldErrorFor` (`message.required` to Message, `startDate.after.expiryDate` to
  Expiry Date); show other failures in the dialog with `apiErrorText`.

### Data flow

- Route `src/routes/(protected)/_protected.administration.system-notifications.tsx`: await
  `requireRouteRights`, then fire-and-forget `prefetchQuery` for the page (from `loaderDeps`) and
  `deploymentTimeZoneOptions`. Toolbar outside `QueryBoundary`; rows read `useDeferredValue(search)`.
- Search, modelled on Lots (`src/features/lots/lib/search.ts`): `tableSearchSchema([...]).omit({ sort: true, dir: true })`,
  `usePagedTableSearch` with `defaultSort: NO_SORT`, columns with `enableSorting: false`;
  `authorId` (uuid, optional), `displayed` (`true` or absent), `notification` (`'new'` or uuid).
  UUIDs from links are normalized to lowercase.
  Filter changes return to page 1 and replace history; paging adds entries. Default size 10.
- Keys, all under `queryKeys.systemNotifications`: `.list({ displayed: true })` (the bell,
  unchanged), `.list({ admin: { page, size, authorId, displayed } })`, `.all + ['author', authorId]`,
  and `[...detail(id), opening]` for the dialog read.
- Author filter: shown only when the user also has `USERS_MANAGE` (from the resolved rights set),
  since `GET /api/users` refuses everyone else. The route composes `allUsersOptions` from the
  Users feature and passes the options to the toolbar (features never import each other). The
  query runs on first opening of the Author filter **and** whenever `authorId` is in the URL, so a
  reloaded or shared link shows the author's name (AGENTS.md linked selections). Searching is
  local over the loaded list, as legacy; options show the full name with the username as the
  muted `description`, so equal names stay distinguishable. Results are limited to 50 at a time
  with a hint to narrow by name or username. Reopening the filter retries a failed user read.
  A linked `authorId` without the right
  still filters the list and the filter count, with Clear Filters to remove it.
- Dialog: `useSearchNavigation<PageSearch>(CLOSED_DIALOGS)` with `?notification=`, `useDialogTarget`
  as Programs; edit detail read keyed by `useOpening()`, never prefetched; `DialogNotFound` for
  `404`, `DialogLoadError` otherwise. The Edit Author row loads independently of the form. Its
  query checks cached admin list pages for the author before making the targeted one-row read
  in the API map, which works without `USERS_MANAGE`. Loading and failure stay in the Author row.
- Time zone in the dialog: on open, `fetchQuery(deploymentTimeZoneOptions())` and keep the body in
  its loading state until it settles. Use the zone when `read` is true, or use a stored zone
  confirmed by a previous server read. An older stored UTC default needs confirmation because
  offline preparation can write it after a failed read. With neither, show `DialogLoadError` with Try Again. The zone is
  captured when the dialog opens and used for display, validation and save.
- Save with `useSessionMutation` and disable editable controls while the write is pending.
  On success, cancel pending list reads, invalidate the list key prefix (admin table and bell),
  close, focus Add System Notification, and show a success toast. The list keeps its filters and
  clamps a page past the end to the last page, as Lots.
- The loaded table reads `useDeploymentTimeZone`; the skeleton builds its columns with a fixed
  zone, as AGENTS.md requires.

### Server-side work

- Filtering by author and Only Displayed, and paging, stay on the server, as legacy.
- **Only Displayed rows show Is Displayed as true.** The server guarantees that each row
  matches at the time of the read, so differences between the client and server clocks do not
  affect those badges. Without that filter, compute Is Displayed locally from `active`,
  `startDate` and `expiryDate` at render (inclusive window, missing bounds open). The unfiltered
  server flag comes from a separately paged query that drops the author filter
  (`SystemNotificationController.java:255-262, 299-318`). An idle page updates on the next
  refetch (focus, paging, filters).
- **Not Displayed is not offered** as a filter value: `isDisplayed=false` adds active undated rows
  and, with an author, other authors' rows (`SystemNotificationRepositoryImpl.java:126-141`).
  Legacy offers only Only Displayed too.
- Author options: every user, as legacy (`GET /api/users`, about 1,200 rows on test), loaded once
  when needed and kept fresh for five minutes instead of on every list change. Search runs
  locally across all users, with up to 50 options shown at a time.
  Row author names come from `expand=author` on the list instead of joining that user list.

### Rules

- Message required: trimmed text must not be empty (the server only rejects empty strings).
- Title at most 255 characters, enforced in the browser: the server does not check it and a
  longer title fails as a database error. A characters-left counter, as legacy.
- Active defaults on for Add.
- Start and Expiry optional, each a date plus a time. These bounds opt in to civil-date input
  parsing and validation before converting in the deployment time zone. Picking or typing a
  date with an empty time fills 00:00 for Start
  and 23:59 for Expiry. With a date, the time is required; clearing the date clears its time and
  sends `null`.
- A new or changed Expiry includes its whole minute: H:MM is sent as H:MM:59.999.
- On Edit, a bound whose date **and** time are both unchanged sends its saved string back
  unchanged; changing either rebuilds it from the form. Validation compares the instants that
  will actually be sent: Expiry earlier than Start is refused, equal is allowed.
- `createdDate` is always echoed exactly as received (the server compares instants; never
  round-trip it through `Date`).
- Times are read and written in the deployment time zone captured when the dialog opened.
- Author is never editable: the signed-in user on Add, the original author on Edit. Created Date
  is shown read-only on Edit.
- Always send the body `id` on `PUT`: without it, or for a record deleted meanwhile, the server
  silently creates a record.
- Title and message wrap in the table and cards. Message shows the raw text with line breaks
  kept, as legacy (React escapes it).
- Untitled notices: the card band and the Edit button's accessible name fall back to the start of
  the message.

### Risks and edge cases

- Daylight-saving changes in the deployment zone; covered by `zoned-time` tests.
- A slow author read shows a loading state in the Author filter or Edit Author row.
- A deactivated notice saved under Only Displayed, or one by another author under an Author
  filter, leaves the current view, as in legacy; the success toast confirms the save.
- Default server order has no tie-breaker; rows with equal Active and Expiry may move between
  pages. Legacy has the same order; not changed.

## UI/UX

- **Port**: the columns and their order, the full message text, Edit as the only row action, the
  Filters popover with Author and Only Displayed (a checkbox), the form fields in legacy order and
  their defaults, read-only Author and Created Date, the 255-character Title counter, legacy's
  button and toast wording, ten rows per page by default.
- **Improve**:
  - Edit opens in the same dialog as Add, over the list, instead of a separate page; closing
    returns to the same page and filters. Six fields and one save fit the app's dialog rule.
  - The page opens for administrators without the Users right (legacy fails to load for them);
    only the Author filter needs that right, and its options show usernames to tell equal names
    apart. The user list loads once when needed, not on every list change.
  - Start and Expiry use the app's date field plus a native time input in the deployment time zone,
    with a hint naming the zone. This is what legacy intended; its picker converts through the
    browser's zone. Typed dates work. A picked date starts at 00:00 or ends at 23:59 instead of
    legacy's "now", which suits whole-day notices. The browser controls the native time input's
    hour cycle and day-period labels.
  - Active and Is Displayed use `FlagBadge` (check or cross with a label). Only Displayed
    uses the server's filtered result, and other views compute the badge from the dates.
  - Phone cards: Title (or the start of the message) as the band with the Edit button, other
    columns as rows.
  - Mapped refusals show beneath the corresponding field. Other save failures show once in an
    inline alert.
  - Filters apply live, as every other Filters popover; legacy's Search and Cancel buttons go.
  - View menu for hiding columns and a page size selector, as on every other list; every column
    is visible by default.
  - Toolbar: Filters at the start; View, then Add System Notification at the end.
- **Drop**: nothing a user relies on.
- **States**: loading skeleton matching the table and cards; empty ("No system notifications
  found."); no matches with Clear Filters; error with Try Again; dialog loading, not found and
  load error. Arabic: logical classes, popovers and calendars mirrored.

## Decisions

1. **Dialog for Add and Edit**, URL `?notification=new|<id>` (AGENTS.md "Choose the container").
2. **Author filter lists every user, as legacy** (user, 2026-11-26), through `GET /api/users`.
   It needs `USERS_MANAGE`, so the filter appears only for administrators with that right; the
   rest of the page, including row author names (`expand=author`), works without it.
3. **Is Displayed follows the server under Only Displayed**. Other views compute it in the
   browser from Active and the dates because the unfiltered server flag can be wrong.
4. **Only Displayed stays the only status filter**, as legacy; no Not Displayed option because the
   server's `isDisplayed=false` returns wrong rows.
5. **Times use the deployment time zone**, named in the form: legacy's intent, with its browser
   conversion fixed.
6. **No delete**, as legacy; deactivating or expiring a notice hides it.
7. **No sorting controls**, as legacy; the server's default order is kept.
8. **`@date-fns/tz` for zone conversion**, promoted from a transitive to a direct dependency, with
   the explicit skipped and repeated time rules above: nothing in the app turns a wall time in a
   zone into an instant yet, and DST makes a hand-rolled version error-prone.
9. **After a save the list keeps its page and filters**, as legacy; it does not jump to the saved
   notice. A notice that no longer matches the filters leaves the view; the toast confirms it.
10. **Edit always reads the record fresh** when the dialog opens. This narrows the time in which
    another administrator's change can be overwritten. The server accepts a whole-record update
    without a version check, so concurrent edits can still overwrite one another.

11. **Start and Expiry are a date and a time**, as legacy (user, 2026-11-26).
