# FM-166: Offline Stock Views

[FM-166](https://openlmis.atlassian.net/browse/FM-166)

## Team Summary

Stock On Hand opens offline for downloaded home-facility programs. It reads balances from the
complete home-stock download, filters by product name/code and lot, and pages locally. Queued
events never change those balances. The freshness line and pending-event note explain that limit.

Stock Card opens from the downloaded summary. A summary without history explicitly asks the
user to connect to view history. Viewing a card online saves the full server response, including
all lines and display fields, in the owner's database for supported home programs with
STOCK_CARDS_VIEW. Histories are kept without a cap until replaced by a newer view, scoped per
user and home only. Offline visits prefer saved history and check home scope and exact grants.
Legacy also caches histories on online view rather than downloading every card's history.

## API And UI Decisions

- Reuse the home-stock provider and coordinator for supported home programs with STOCK_CARDS_VIEW,
  including view-only programs and mixed adjustment/view-only access. Offline Adjustments still
  requires STOCK_ADJUST for its own facility/program scope.
- Keep `GET /api/v2/stockCardSummaries` and product/lot lookups online; offline reads use complete
  device generations. Preserve summary groups and substitute relationships rather than rebuilding
  totals from flattened cards. A lot filter recomputes the total from matching lots.
- Keep `GET /api/stockCards/{id}` for full online history. Save after session checks; storage
  failures do not prevent online viewing. No stock mutation or history-download endpoint is added.
- `stockPickerFacilitiesOptions` reads all minimal facilities online and only the home facility
  offline, in a separate cache. Reconnect reuses the server cache without blanking the picker.
  The picker keeps its selection visible and shows the not-downloaded notice when local data
  cannot serve it.
- Reconnect refreshes the open Stock Card from the server, including a previously cached card.
- Shared shell policy permits both stock routes offline. Dataset availability remains a reader
  check and raises `LocalDataUnavailableError`, using the shared Not Available Offline state.
- Show download times in the deployment time zone. Disable server printing for device data.
  Preserve desktop tables, phone cards, quantity units and Arabic direction.
- Every Adjustments submission now lands on scoped Stock On Hand, queued or accepted. FM-165
  returned queued events to the program list because Stock On Hand was online-only.

## Storage And Compatibility

Dexie version 11 adds `stockCardHistory` after version 10 removed it. Versions 9 and 10 remain
unchanged. Existing access, home stock, inventory/event drafts, queues, refusals and receipts stay
intact. Removed v9 histories are not restored.

Home-stock format 5 adds whitelisted original summary groups and hydrated product snapshots to
format 4. The coordinator refreshes older formats. Adjustments and summary-only Stock Card can
still read complete format 4 bundles; Stock On Hand requires a format 5 download. No partial
foreground response is published as a home-stock generation. History has its own format version.

## Validation And Limits

Focused tests cover filtering/paging, exact scope, local absence, history retention, identity
changes and upgrades from released databases. Headless offline browser tests cover restart,
viewed-history reuse, missing downloads and the shared navigation policy. Fixture stock POSTs
remain blocked or stubbed, with guarded preview denial as a second barrier.

Supervised facilities and keeping already-open stock pages readable offline remain deferred.
Real large-history sizing and supported-device capacity checks remain rollout work. Device
storage can be evicted or cleared; the existing retention and recovery guidance still applies.

## Shared Offline Building Blocks

- `stock-programs.ts` owns `homeStockScopes`, `isHomeStockScope` and `homeStockPrograms`.
  Download scopes require home facility, supported program and STOCK_CARDS_VIEW. Event pickers
  list home programs with event grants in both modes and disable unavailable downloads offline.
  `rights.ts` supplies the shared right constants.
- `local-records.ts` validates owner, format and optional acceptance on reads, with session and
  owner checks inside write transactions. `local-db.ts` owns typed table names and accessors.
- `deviceQuery` takes connection state explicitly and selects server or device cache keys.
  Device products/lots have independent namespaces. `useReloadOnConnectivityChange` invalidates
  both Stock Card keys on reconnect and reloads on either connection change.
- `DeviceSnapshot` identifies device results; `usePrintReport` owns their print restriction.
  `ListError` handles missing downloads and reconnect retry for every list.
- Providers expose a scope read with caller acceptance; `useDownloadedScopes` observes requested
  scopes only offline for picker readiness. Adjustments accepts formats 4 and 5; Stock On Hand
  requires format 5 with summaries and products. `PendingDeviceWork` takes a predicate and
  connection-specific messages.
- The root provider supplies the owner-scoped sign-out counter eagerly, independently of lazy
  background services. Read device work only on sign-out; do not require a new chunk while offline.
- Editors read through the complete home-stock bundle to preserve dataset consistency.
  Read-only views use server-or-device queries, composed by routes. Receive needs its own
  approved-products/lot dataset; the home-stock bundle is insufficient for its picker.
- Pure `projectStockSummaries`, `summaryStockCard` and `pageLocally` own projection and paging.
  A saved history wins if at least as new as the bundle. Otherwise the bundle supplies the balance,
  with no older history lines, even when balance and active state agree. Each uses its own timestamp.
- A verified foreground access read can save viewed home history before the first access
  generation is published. It never publishes a partial access or home-stock generation.
- Drop home-stock format 4 compatibility after old bundles expire. Format 5 is required for
  Stock On Hand. Histories have no count cap and are replaced by subsequent views.

Known limitation: Stock Card clears the open page on disconnect and reloads from device data.
Keeping open pages readable offline is deferred with the broader open-page retention work.

## Issue And Receive Offline

Part of FM-166 under [FM-164](https://openlmis.atlassian.net/browse/FM-164) Offline support,
and of the screen tickets [FM-64](https://openlmis.atlassian.net/browse/FM-64) Issue and
[FM-65](https://openlmis.atlassian.net/browse/FM-65) Receive. No separate ticket. Legacy runs
Issue and Receive offline; this brings both to the level of Adjustments.

### Scope

- Issue and Receive edit, autosave and submit offline for downloaded home-facility programs,
  queued through the existing device drafts, queue, uploader and Offline Events.
- Two PRs, each merged before the next starts: Issue first (with the shared download changes),
  then Receive.
- Not in scope: Unpack and Transaction History stay online-only, as legacy; Physical Inventory
  offline counting is a later FM-166 PR; supervised facilities stay online-only.

### Summary

Legacy downloads everything Issue and Receive need right after sign-in: where stock can go to
or come from, reasons, the facility's stock, products, lots and kit contents. Offline, Submit
reads Submit Offline, the event waits on the device and goes out in order when the connection
returns. Legacy then opens Stock On Hand and offers no print.

The new UI already does this for Adjustments. Issue needs one more downloaded list, the valid
destinations, and then uses the same download, draft, queue and recovery.

Receive offers every product the facility is approved for, not only products in stock, and can
add new lots. For Essential Meds that is 10,003 products, so Receive gets its own background
download that keeps only the fields the screen uses and, as legacy, is refreshed at each
sign-in rather than every 30 minutes. New lots typed offline go inside the queued event, as scanned lots
already do; the server creates them when the event arrives. Legacy cannot submit typed new lots
offline at all.

Both kinds skip the print offer when the event is only queued, and land on Stock On Hand for
that facility and program, as Adjustments does. As legacy, quantities are checked against the
downloaded balance only; events still waiting to sync do not reduce it.

### Acceptance Criteria

Drawn from FM-164 and the FM-166 criteria, applied to Issue and Receive.

| AC | How it is met | How it is checked |
|---|---|---|
| After one online visit, Issue and Receive open and work with the network off, also after a browser restart | Kind policy enables device drafts and datasets; counterparties and the Receive catalog download at sign-in | Browser: Issue restart then submit; Receive typed new lot queued |
| Never-downloaded data says so | Offline, picker rows stay disabled while the device is read, then show Not Downloaded with the reason (no stock-card right, older download, not downloaded) or Ready, per program and kind | Unit: picker readiness per kind; Issue's assertion in `issue.spec.ts`, Receive's in `downloads.spec.ts` |
| Saved On This Device, Synced only after acceptance | Shared draft store and submission | Existing coverage; the Issue browser submit |
| Reconnect sends queued events in order; refusals become sync errors | Shared uploader and recovery, kind-blind | Existing sync and retry specs |
| Expiry pauses sync; logout warns; no offline data in localStorage | Shared | Existing |
| Receiving many products does not fail with a storage error (FM-65) | Slim catalog in IndexedDB | Measurement on test, Essential Meds, recorded here |

### Legacy Today

Observed on test.openlmis.org as administrator, Comfort Health Clinic, Family Planning
(screenshots in `.screenshots/FM-166/`, gitignored).

- Sign-in downloads everything: products for all programs (about 10 MB), all lots, reasons, valid
  destinations and sources, fulfil mappings and unpaged stock summaries per home program
  (2.6 MB for Essential Meds). Opening the program list offline makes no calls.
- Offline, Issue and Receive lists and editors open with every control enabled; Unpack and
  Transaction History are greyed out. Submit reads Submit Offline.
- Confirmation is the usual signature dialog. After Confirm it opens Stock On Hand for that

- The queue is localStorage `openlmis.stockEvents` per user, holding the exact body without a

- A typed new lot on Receive fails offline: legacy first sends `POST /api/lots`, then shows

No new endpoints. Departure: destinations and sources keep the shared `fetchValidAssignments`
reader, 100 per page with dedupe by id, rather than legacy's single `size=2147483647` request.
The server rebuilds the whole list for each page and pages are unsorted; acceptable at real
sizes.

If the summaries plus orderables route proves slower or larger on test than
`approvedProducts`, the fallback is one unpaged `approvedProducts` request (18.6 MB) with a
longer timeout for this download only; its pages have no stable order, so it is never paged.

#### Data and storage

- **Home stock, format 6:** adds the scope's valid destinations and sources (one record, one
  generation). The provider writes 6 and its freshness requires 6, so stored 5s refresh.
  `readHomeStockBundle` and Adjustments accept 4, 5 and 6; Stock On Hand accepts complete 5 and 6
  (format 4 has no summaries); Issue and Receive require 6. A device with only format 5 shows Issue and Receive as needing a download
  until it reconnects. No Dexie version in the Issue PR (no new index).
- **Receive catalog:** provider `receive-catalog`, Dexie version 12 table
  `receiveCatalogDownloads` keyed `[facilityId+programId]`, an owned record with `userId` and
  `formatVersion` through `local-records.ts`. Holds the approved ids with their versions, slim
  product snapshots, the fulfil mapping, slim lots and, with scanning, `{id, gtin}`.
  Products cover the approved set plus every product in their `canFulfillForMe`, with those
  products' lots and GTINs, as the online picker offers. Complete generation or nothing: refuse
  when any approved product is missing.
  Scopes: `homeStockScopes` intersected with the Receive grant, with its own refresh key
  `receive-catalog:<facility>:<program>`. Registered in `-device-work-provider.tsx` with label
  key `offline.download.receive-catalog`.
- **Freshness:** home stock keeps 30 minutes. The catalog refreshes at sign-in only, as legacy:
  a complete catalog is reused on normal reload regardless of age. Providers declare their
  refresh triggers, and the catalog skips periodic checks, reconnect and
  token-only session resume (`force`) while it has a complete record for the current access.
  Expired-session password sign-in uses `sign-in` and downloads the catalog again, as legacy does. Accepted events
  never request the catalog: it has its own refresh key, `refreshAfterStockEventAccepted` keeps
  sending only the home-stock key.
- Receive stock on hand comes from the home-stock bundle; a catalog product with no summary
  shows blank stock as online does. This departs from legacy's zero for catalog-only products.
  A product in stock but missing from an older catalog is still offered, taken from the bundle.
- Reference-data fetchers used by downloads (`fetchValidAssignments`, `fetchFacilityOrderableFulfills`,
  `fetchLotsByTradeItems`, the summaries and orderables readers) take an optional request config so
  background downloads pass `signal`, `session: false` and the session scope.

#### Code changes

- `event-kinds.ts`: Issue and Receive set `drafts: 'device'`; `download` becomes a list of
  datasets with acceptance (`home-stock` with a minimum format, `receive-catalog`).
- Program picker: read the kind's datasets through `useDownloadedScopes`, a fixed number of hook
  calls gated by `enabled`; replace the hardcoded provider and `acceptsAdjustmentBundle`.
  Offline, rows stay disabled without a reason while the device is read, then show Not
  Downloaded (with reason) or Ready. Legacy shows no per-program state and alerts on entry when
  offline resources are missing. We improve this by showing the reason before entry as visible
  text, not only a tooltip. No Downloading state: going offline stops the download, so it could
  never show offline, and legacy has no per-program indicator.
  The picker still calls the home-stock provider directly, one gated call per known dataset;
  Receive adds the catalog call.
- Sign-in has its own `'sign-in'` trigger with top priority, including password sign-in after
  expiry. Reconnect and token-only session resume keep `'force'`.
- Counterparties: bundle-backed read only for kinds with a download, as reasons do, keeping the
  server key online so admin saves still refresh; `eventPayload` maps counterparties to nodes
  from the same list. Departure: device reads keep the server query key with offline-access
  freshness (refetch on reconnect) rather than `deviceQuery`'s separate key, so admin saves
  still invalidate the same entry.
- Receive picker and scanning (`ApprovedProductLotPicker`, `approvedScanProduct`): a device path
  that searches the catalog by name locally and pages it with the same Show More. The editor's
  first GTIN lookup goes through the catalog for Receive (home stock keeps it for Adjustments and
  Issue), and offline scans resolve within the catalog and the facility fulfil mapping only.
- `useDeviceDrafts` readiness and `refreshStockEventLines`: policy for approved-product kinds;
  keep typed and scanned new lots instead of replacing them with a missing card's lot.
- `useStockEventPrint`: skip the print dialog for an unsynced event; land on scoped Stock On Hand.
- Typed new lots offline: shown only with `LOTS_MANAGE` from saved access, hidden otherwise, as
  online. Downloaded lot codes refuse any match, ignoring case, so the existing lot is selected.
  Queued new lots refuse the same code with a different expiry, ignoring case; the same code
  and expiry is allowed because the server reuses the lot by code.

#### Rules

- Quantity caps are unchanged: Issue always (`stockOnHandCap: 'always'`), Adjustments with a
  debit reason, both against the downloaded balance without subtracting queued events, as legacy.
  Overdrafts the device cannot see reach Offline Events as sync errors.
- Destination or source required; free text only where the assignment allows it.
- No `documentNumber` sent; the server generates one.
- Server lot creation needs a source and no destination; codes up to 20 GS1 characters
  (`lot-code.ts` already matches); expiry optional, `yyyy-MM-dd`.

#### Risks

- The server matches a queued new lot by code only, ignoring expiry: if someone creates the same
  code after the download, the event uses the existing lot and its expiry without refusal.
- A lot created for an event the server then refuses stays created; resending reuses it.
- Catalog size on slow links at each sign-in; mitigated by background download that never
  blocks sign-in, and slim storage. Lot requests grow with trade items (one per 100).
- Product versions: queue the exact version shown; a newer catalog keeps existing draft lines on
  their version, and server refusals surface as sync errors.
- A destination removed on the server before sync is refused; Copy For Correction offers only
  current counterparties.

### UI/UX

- **Port:** Submit Offline, signature confirmation, no print offer offline, landing on Stock On
  Hand, offline notices, pending-work note, scanned new lots queued inside the event.
- **Improve:** typed new lots work offline (legacy fails); downloads never block sign-in; the
  picker says which programs are not downloaded, and why; Receive searches the full catalog instantly instead of a 30+ second load.
- **Drop:** none.
- Picker offline: disabled rows while the device is read, then Not Downloaded with reason, or
  Ready. Phone cards and Arabic follow the online editors; the Not Downloaded reason is a card
  row.
- Device-data notice: Stock On Hand, Stock Card and the stock event editors show the download
  time whenever their data came from the device. A shown notice keeps its message while a
  refetch is in flight and after a reconnect until new data arrives: server data removes it,
  device data switches it to the online copy. Offline it reads "You're offline."; when the app counts as online but
  the server cannot be reached (gateway errors) it reads "Can't reach the server.", in the
  deployment time zone. On Stock On Hand, pending device events join that note as one sentence;
  live data shows the pending-event note alone.
- Editor layout matches across kinds: the pending view uses the same measured column fit as the
  loaded table, the toolbar status takes no space when empty, and the empty-table message stays
  centred on the visible card while the table scrolls sideways.
- Adding lines never moves the page: the editor routes reload their loader only on entry or
  invalidation, so a line's URL update sends no stock request. Labelled pickers keep the Lot Code
  field in place, disabled with Product Has No Lots for products without lots, as legacy's mobile
  add page. On wide screens Receive with lot rights reserves slots for New Lot Code and Expiry
  Date in the same row, as legacy's inline form. Where the editor shows cards (below 672px),
  Add New Lot opens a small Add New Lot dialog instead, as legacy's mobile flow sends users to
  its Add Lot Code page (user decision, 2026-10-23). The dialog applies the inline validation

  typed lot and the line's Add then adds it, as legacy returns to the add page with the lot
  filled. Picking Add New Lot again reopens it with the typed values. Cancel keeps the previous
  lot and focus returns to Lot Code. The dialog state stays local, not in the URL: it is a
  transient step of the picker, whose product and search are not in the URL either.
- Lot labels follow the lots offered for the kind, as legacy: a product whose only lots are
  expired shows Product Has No Lots on Issue both when added and after a reload.
- Offline Events: as legacy's pending list, a Details column (a row on phone cards) shows each
  line's product, lot, destination, source or reason, and quantity, so events of one program can
  be told apart without opening them. An item-count button opens them in a scrolling popover
  table (cards on phones), so events with hundreds of lines keep the list short.
  Event types reuse the Transaction History labels (Adjustment, Issue, Receive); Unpack keeps
  its own label.
- Only offline failures (`isOfflineError` or a chunk failure that occurred offline) show the
  offline error page. Render bugs, service failures and storage errors use the normal error page
  and Try Again reruns the route even offline. When a rerun fails again, focus moves to the

- Try Again on a missing chunk reloads through the leave guard when our worker is active,
  including offline and after a hard reload without worker control. This normal reload has no

  Browser coverage for uncontrolled hard reload recovery uses Chromium CDP only: sign in using

  the controller-null assertion held and recovery passed. Stock event POSTs stay blocked.

### Decisions

- Destinations and sources ride in home stock format 6; the catalog is a separate provider so its

- The catalog follows legacy's sources (summaries without `nonEmptyOnly`, orderables by program)
  rather than unstable paging of `approvedProducts`.
- Typed new lots queue inside the event (FM-167 decision, 2026-10-13).

### Receive Catalog Stage 1

The catalog download and storage are registered through
`src/features/stock-events/lib/download-providers.ts`.
A complete catalog is reused on normal reload regardless of age. Legacy registers product,
lot and fulfil downloads as post-login actions (`openlmis-login/login.service.js:56-74,192`,
`referencedata-orderable/orderable.run.js:28-43`, `referencedata-lot/lot.run.js:28-30`,
`referencedata-orderable-fulfills/orderable-fulfills.run.js:28-51`). The only login caller is
`openlmis-login/login-controller.js:53-57`; a reload with a stored token does not call login.
Online, Receive still reads the server, as legacy does
(`openlmis-cached-repository/openlmis-cached-resource.js:204,215,262-263`).
Expired-session password sign-in downloads again, following legacy's modal login
(`openlmis-login/login-modal.service.js:59-61`, `login-modal.interceptor.js:36,49`).
The coordinator now distinguishes expiry renewal from token-only resume for that trigger.
Lots use the existing `LotSummary` fields without `active`; scan mappings use `TradeItem`
with `id` and `gtin`, matching the current application types.

### Receive Implementation Departures

1. Catalog-only products show blank stock online and offline, preserving the current UI.
   Legacy shows zero (`orderable-group.service.js:214,242`).
2. Slim lots omit the planned `active` field because `LotSummary` has no such field and no
   reader uses it. Scan mappings keep the existing `TradeItem` shape `{id, gtin}` rather
   than the planned `{tradeItemId, gtin}`.
3. Queued new-lot codes are checked ignoring case: the same code with a different expiry is
   refused; the same code and expiry is allowed because the server reuses the lot by code.
   Downloaded codes still refuse any match and require selecting the existing lot. This
   clarifies the original plan; legacy cannot create typed lots offline.
4. The browser specs drive the Issue and Receive editors directly, so the shared `enqueue`
   test helper keeps its existing signature without a kind argument.
5. The print hook always lands on scoped Stock On Hand. Its old offline branch for a kind
   without home stock and its test were removed: Receive now has home stock and Unpack has
   no print policy. The unused print-hook kind parameter is removed too.

Expired-session password sign-in re-downloads the catalog, following legacy rather than a
new departure. The modal uses `LoginController` (`openlmis-login/login-modal.service.js:59-61`,
opened by `openlmis-login/login-modal.interceptor.js:36,49`), so it runs the same post-login
cache actions. Token-only resume keeps `force` and reuses a complete catalog. Missing or
incomplete catalogs, changed format or newly enabled scanning still require a download.

| Stored record (JSON length) | 3,175,566 | 8,531 |

- Requests for Essential Meds: one unpaged `v2/stockCardSummaries?nonEmptyOnly=false` (19 to 24 s,
  2.6 MB decoded, 282 KB transferred); 11 `orderables?program` pages of 1000 (21 to 24 s, 10 MB
  decoded, 718 KB transferred); one `orderableFulfills`; one `lots`; no backfill.
- Both catalogs take about 1.1 MB on disk. Sign-in reaches Home in about 1 s; navigation stays
  responsive during the download (Receive opens in 0.15 s); no long task over 200 ms.
- Page size stays 1000: 2000 saves only 2 to 4 s on the product list while the summaries request
  runs as long; smaller pages are much slower (100 per page takes 83 to 107 s).
- The summaries request is the bottleneck for any further speed-up, not the page size.

### Receive Review Fixes

- Edit Lot checks queued lot expiry even when only the expiry changes. Scans check the same
  device lots before adding or counting a new lot. A scan without expiry uses the matching
  draft lot's expiry for that check. Downloaded lot codes first ask users to select the existing
  lot. Queued conflicts name the accepted expiry or explain that the queued lot has no expiry.
- Device Receive queries include facility and program in their keys, preserving each
  catalog's product version when moving between programs, including fallback reads while
  the app still reports an online connection.
- An unavailable catalog timestamp leaves the editor and draft lines visible, using the
  stock download time until the catalog can be read.
- A failed sign-in catalog refresh remains visible through periodic checks and retries on
  reconnect, even when an older complete catalog remains on the device.
- Queued and online events land on scoped Stock On Hand. Printing an accepted event keeps
  that landing; queued events skip the print offer.

## Physical Inventory Offline

Part of FM-166 under [FM-164](https://openlmis.atlassian.net/browse/FM-164) Offline support, and
of the screen ticket [FM-68](https://openlmis.atlassian.net/browse/FM-68) Physical inventory
draft. No separate ticket. Scope decided on 2026-10-13 in [FM-167](FM-167.md#decisions-2026-10-13).

### Scope

- A Physical Inventory draft opened online on this device can be opened and counted offline,
  also after a browser restart: quantities, reasons and unaccounted quantity, VVM, Add Products
  (including typed new lots with LOTS_MANAGE), Edit Lot and Remove on added rows, keyword and
  include-inactive filters, paging, quantity unit and progress.
- Offline, the program list shows only home-facility programs whose draft is on the device.
- Save, Delete, Deactivate, Print, Start and barcode scanning are unavailable offline. Submit
  offline runs the same count check as online, as legacy, then explains it needs a connection.
  Nothing is queued: offline counts reach the server only through a manual Save or Submit once
  connected.
- One PR. Not in scope: offline submit or new drafts (legacy phone only), supervised facilities,
  background download of drafts at sign-in.

### Summary

Legacy saves a draft on the device each time it is opened online and after every change. Offline,
its program list shows only those drafts, and the draft can be counted with the stock on hand,
products, lots and reasons as they were when it was opened. Save, Delete and Submit look
available offline but fail after their confirmation dialog with "This action can't be completed
while offline." Legacy keeps these copies in localStorage: on test, administrator's Essential
Meds draft (10,009 lines) was too big to save at all, so offline counting stopped at the next
reload. Signing out deletes every copy.

The new UI keeps the device copy only after the user edits, and Save removes it, so today an
opened draft is not available offline. This change saves a full copy of the draft whenever it is
opened online and keeps it after Save, as legacy does. Alongside it, the device keeps the
products, lots and reasons that draft needs, so no other download is needed. Everything lives in
the user's own device database, so size is not a problem and sign-out keeps it.

Offline, Save and Delete are visibly disabled with "Connect to use this action." instead of
failing after a dialog. Submit still checks the counts offline, as legacy, and marks what is
missing; a complete count is told it needs a connection rather than failing after the date and
signature dialog. The page says when its data was taken. When the connection comes back the page
stays as it is and the actions work again, as legacy; stock on hand refreshes the next time the
draft is opened.

### Key Question: Is The Device Copy Enough?

Not today. `InventoryLocalCopy` holds full lines (product snapshot, lot, stock on hand, stock
card, counts, reasons, VVM, new lots), but:

| Need offline | Today | Plan |
|---|---|---|
| Draft identity and lines | Only after an edit; cleared on Save, Delete, Submit | Written on every online open and after Save; cleared on Delete and Submit |
| Untouched member lines (baseline) | Rebuilt from the server draft | Stored as `baselineKeys` |
| Add Products products and lots (approved set, fulfils, trade-item lots) | Server only (`eligibleInventoryProductsOptions`) | Reference record |
| Reasons | Server only (`validReasonsOptions`) | Reference record |
| VVM column | Decided from eligible products | Follows from the stored eligible products |
| Permissions, user, home facility, programs | Access snapshot | Reused unchanged |
| Barcode GTINs | Server only | Not stored; scanning disabled offline, as legacy in practice |

Home stock is not used: it lacks products without stock cards, which Add Products offers, and
its formats change in the Issue PR. The Receive catalog is scoped to STOCK_ADJUST and not yet
merged. The stored eligible set matches what legacy's offline Add Products offers: every
summary, its fulfilling products, their lots and a no-lot entry each
(`full-stock-card-summary-repository-impl.js:44-117`).

Backend (stockmanagement `origin/master`):

  supported by the home facility (`HomeFacilityPermissionService.java:45-58`), and
  STOCK_CARDS_VIEW to show stock, as the editor today. POST `/api/lots` needs LOTS_MANAGE.

  submitted draft return 400 `isSubmitted` (`PhysicalInventoryValidator.java:70-73`,

#### Storage

- One new Dexie version, the next free number (13 if Receive's 12 merges first); rebase before
  merge. It adds table `physicalInventoryReference` keyed `draftId` and the index
  `[facilityId+programId]` on `physicalInventoryDrafts`, so listing by scope never loads every
  large copy. Existing copies stay.
- `InventoryLocalCopy` gains `formatVersion`, `baselineKeys` and `fetchedAt`/`generation`
  (a `DeviceSnapshot`). A copy without them is an older format: used online as today, unavailable
  offline.
- `physicalInventoryReference` is an owned record (`userId`, `formatVersion`, via
  `local-records.ts`): `{draftId, facilityId, programId, fetchedAt, generation, eligible, reasons}`,
  whitelisted fields only. Separate so autosave never rewrites the large product list.
- This is draft-owned data captured on an online open, like viewed Stock Card history, not a
  dataset generation; record the exception in AGENTS.md (Offline, "Data, session and identity").

#### Writes

- On online open, once stock lines, eligible products and reasons resolve, the editor sends the
  snapshot through its existing serial writer (`autosave.write`), built from the current form
  state with `modified = modified || isDirty`, so the revision chain never conflicts. An
  unmodified snapshot write shows no Saving state and does not arm the discard guard. The
  reference record is written in the same revision-checked transaction (`saveRevisionedDraft`'s
  `tables` option), carrying the copy's `generation`; reads accept a reference only when its
  draft id, scope and generation match the copy, so an interrupted open or a late write after
  Delete never yields a mismatched pair.
- If an unmodified snapshot write meets a newer revision (another tab), it adopts the stored
  revision silently: no user edit is at stake. A conflict with unsaved edits shows a conflict
  alert with Load Latest (remount from the stored copy) and Keep My Counts (write this tab's
  state over the newer revision), both revision-checked, as AGENTS.md requires.
- The writer reports failed commits: `flush()` returns or throws when persistence fails, and the
  editor treats that as not saved (Not Saved On This Device, guard armed, server actions blocked
  until a write succeeds).
- `inventoryLocalCopy` takes `modified`; Save writes the saved state with `modified: false` and the
  new baseline through the writer instead of clearing. Delete and Submit clear both rows in one
  `saveRevisionedDraft` transaction (`tables` option).
- Offline autosave keeps the stored `baselineKeys`; `removedKeys` is computed against them.
- Online, when the server draft for a scope has a different id from a device copy (or there is
  none), an unmodified copy and its reference are removed. A modified one is marked `orphaned`
  (revision-checked) and the editor or its no-draft state shows an alert that counts from an
  earlier draft are on this device, with Discard (revision-checked). It is never saved to the
  server under its old id, never offered offline, and keeps counting in the sign-out warning
  until discarded. There is no automatic pruning of PI copies.

#### Reads

- `physicalInventoryDraftOptions` gets a `deviceQuery` path: offline it returns the draft identity
  from the scope's current-format, non-orphaned copy (newest `fetchedAt` if several), or none. The list's own `ProgramsTable` then works
  unchanged: offline, rows without a copy are hidden and Start never shows; empty state "No
  Drafts On This Device".
- Editor route loader: offline, skip the staleTime 0 draft fetch and every server prefetch; read
  the copy; throw `LocalDataUnavailableError` when absent. Add an `errorComponent` through
  `ErrorFallback` so absence shows the shared Not Available Offline state, never a 404.
- The editor pins its data source when it mounts. A device open uses device-only query options
  (their own keys, no `onlineOrDevice`, no reconnect or focus refetch) for as long as it is
  mounted; an online open uses the server options as today. A draft opened online that then goes offline keeps its
  in-memory data and writes the device copy as usual.
- Offline, `InventoryRows` always uses the copy's lines, and the baseline comes from
  `baselineKeys`.
- Reconnect, as legacy (the draft controller has no connectivity listener; only the list reloads,
  `physical-inventory-list.controller.js:144-162`): the editor stays mounted with its data and
  Save, Delete and Submit work again at once. Stock on hand refreshes the next time the draft is
  opened online, when the modified copy wins over fresh balances. The offline notice remains
  until then, saying when the stock was taken.
- Server actions recheck session and connectivity before each request,
  including each lot creation, and stop with committed local counts intact when any fails.
