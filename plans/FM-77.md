# FM-77: Reverse Transaction

https://openlmis.atlassian.net/browse/FM-77 · Parent: [FM-71 Transaction History](https://openlmis.atlassian.net/browse/FM-71)

## Scope

The Reverse Transaction page, opened from the event detail page built in [FM-71](FM-71.md), and
the Reverse button on that detail page. With this, FM-71 has every legacy action.

Not in scope:

- Offline. Reverse needs the server, as in legacy; the app's offline notice covers the page.
- Backend changes. `POST /api/stockEvents/{id}/cancel` and the four cancellation reasons shipped in
  stockmanagement v5.4.0 and are unchanged in v5.4.1; the UI half shipped in stockmanagement-ui
  v2.2.0.

## Summary

Reversing undoes some or all lines of an issue, a receipt or an adjustment that was recorded by
mistake. The server records a new adjustment event that puts the stock back, dated the same day as
the original, and the original lines show which event reversed them.

In legacy, a user allowed to cancel stock events opens an event and presses Reverse. A table lists
the event's lines with the current stock on hand. The user ticks the lines to undo, picks a
cancellation reason for each (there is always exactly one that fits), may add a comment, and sees
the stock on hand each line would leave. Submit runs three pop-ups in a row: a review of the lines,
an optional signature, and a summary after saving. Mistakes, such as no line ticked or a missing
reason, are reported after pressing Submit, in a pop-up alert and on the row. Opening the page
takes 7 to 10 seconds the first time.

The new page keeps legacy's flow as it is: the same table, rules, reasons, Packs or Doses and
server checks, the reason picked by the user from "Select an option", and the same three pop-ups
(Confirm Reversal, Choose Signature, Reversal Summary) before the toast and the event. Mistakes are
shown above the table with the legacy message as the alert title, and on the row. Ticking,
unticking or changing a reason dismisses the validation alert; server failures keep their title
and description until the next Submit. Leaving with lines ticked asks first, and
Cancel and Submit keep the list's filters and page, as every page here does. Who may open the page
and which lines can be ticked follow legacy's rules exactly.

### Rules

- **Tickable** (`canReverseLine`), exactly legacy's rule (`factory.js:147-168`): no
  `cancellationEventId`, and a source or destination, or a reason in category ADJUSTMENT with
  neither `cancelMovement` nor `cancelAdjustment` tag. The event's `reversible` is not checked. A
  line without `stockEventLineItemId` stays tickable, as legacy; the server refuses it with its
  message.
- **Reasons** (`cancellationReasons(line, reasons)`): category ADJUSTMENT, tag `cancelMovement`
  for a line with a source or destination else `cancelAdjustment`, type CREDIT for an issue, DEBIT
  for a receipt, CREDIT for a DEBIT adjustment reason and DEBIT for any other reason type;
  undefined without a movement or reason. The select lists the matches
  and starts on "Select an option", never auto-picked; with none it stays empty and Submit reports
  the missing reason. Changing the reason clears the row's errors and drops comments it does not
  allow.
- **New stock on hand** (`newStockOnHand(lines, ticked, current)`): current for the product and
  lot when it is a number, else that line's own `stockOnHand`; apply each earlier ticked line
  of the same product and lot in order, then the line itself, using `reversalReasonType` (by the
  line, not the picked reason). CREDIT adds quantity and DEBIT subtracts it; blank on unticked
  rows and rows with an undefined reversal type.
- **Schema**, checked on Submit as legacy: nothing ticked gives `stock-event-reverse.none-selected`
  above the table and nothing else; otherwise every ticked row gets both marks it earns, reason
  missing (`stock-events.required` on the cell) and new stock on hand below zero
  (`stock-event-reverse.negative-stock` on the New Stock On Hand cell), and the message above the
  table is `stock-event-reverse.reason-required` if any reason is missing, else
  `stock-event-reverse.negative-stock`. Comments max 255 (`stock-events.comments-too-long`, required: the database
  column is `VARCHAR(255)` and an overlong value comes back with a wrong message). Pages holding an
  invalid row are marked in the pager; Submit opens the first one and focuses its field.
- **Server errors**: `lineErrors` go on each row's Reverse cell (by `stockEventLineItemId`) with
  `stock-event-reverse.line-errors` above the table. The server sends
  `stockmanagement.error.event.cancellation.reason.required` and `.reason.invalid` with a raw `{0}`
  (legacy shows it as is), so those two `messageKey`s map to our text: a named defect fix.
  Everything else (negative stock as `event.debit.quantity.exceed.stockOnHand`,
  `cancellation.concurrentModification`, a missing line id, the normal stock event validators such
  as a product no longer approved) is a plain `{messageKey, message}`: shown as the server's
  message, else `stock-event-reverse.failed-description`. No response at all shows the failed
  message too. `lineErrorMessage` returns `{key}` for translated messages or `{message}` for
  server text. Ticks stay and Submit works again, as legacy; a resend is safe, since the server
  refuses a line already reversed.
- **Signature**: the existing `SignatureDialog` keeps its 255 limit, a named defect fix: legacy has
  none, but the column is `VARCHAR(255)` and a longer one fails on the server.

## Decisions

- A confirm stays, as the AC asks and legacy does: a reversal writes a new event and changes stock
  cards, which AGENTS.md treats as reaching other records.
- All lines in one request, paged in the browser, as legacy: the running balance and the selection
  span pages.
- Current stock on hand from legacy's own v2 call by product, so the products it leaves out fall
  back exactly as legacy; only the orderables and lots lookups legacy adds on top are skipped, as
  the page needs just ids and balances.
- Cancellation reasons from all reasons, filtered as legacy filters, not from valid reasons: the
  server does not check reason assignments for a cancellation.
